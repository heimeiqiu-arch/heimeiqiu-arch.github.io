Stripe Payment Links 可以让商户用一个可分享的页面收款。面对定制商品、活动报名或需要额外订单备注的业务，商户可能还想在付款过程中询问顾客尺码、预约选项、内部编号或商品配置。Payment Links 的自定义字段可以收集有限的附加信息，但它并不是可以随意搭建复杂订单表单的通用数据库，也不应被用来收集完整支付凭据或高度敏感资料。

设计字段之前，先分清哪些信息是支付所需、哪些是履约所需、哪些应由商户网站在结账前收集。本文梳理 Stripe Payment Links 自定义字段的类型和用途、字段结果如何映射到订单、如何保持数据质量、隐私与安全边界，以及顾客付款后没有看到字段值时的排查顺序。Stripe 对字段数量、长度和选项的限制可能会随产品更新，配置前请检查当前 Dashboard 和 API 文档。

## 自定义字段能解决什么问题

自定义字段适用于少量、简短、与当前购买直接相关的信息。例如商户需要知道顾客希望刻印的简短文字、活动场次、选定的商品版本，或某个非敏感的业务参考号。用户在付款流程里输入或选择后，商户可以把字段结果与 Checkout Session 和订单记录关联起来，减少顾客付款后另发邮件补充资料的情况。

字段的价值在于填补订单数据缺口，而不是把商户的整个业务流程迁进支付页面。若需要多步配置、上传文件、复杂库存校验、实时资格验证、动态定价、预约时段锁定或顾客注册，应该在自己的业务页面或专门表单中完成，再由服务端创建支付链接或 Checkout Session。Payment Links 的字段本身不会帮商户判断内容是否有效、商品是否有货或服务能否履行。

每个字段都应有一个明确的业务问题和数据使用目的。若没有团队会读取该字段，也没有系统需要据此履约，就不应让顾客填写。字段越多，顾客完成付款的阻力越高，也越容易出现错误和隐私负担。

## 文本、数字和下拉选项

Payment Links 支持文本、数字和下拉列表等类型。文本可用于短备注或名称；数字字段适合确实只由数字组成的编号；下拉字段适用于商户能提前枚举且选项数量有限的情况。字段标签应说明顾客需要填写什么，尽量避免“其他信息”这类不清楚的问题。

下拉选项能减少拼写差异，适合颜色、时段或明确的产品变体选择。但若选项会影响库存或价格，应确保 Payment Link 对应的价格、商品和可售库存也与选择保持一致。仅仅让顾客在字段里选择“加大号”，不代表 Stripe 自动把订单行项目改成加大号或扣减对应库存；这部分逻辑仍由商户系统负责。

字段可以配置为必填或选填。将字段设为必填之前，确认该资料确实是完成订单不可缺少的条件，并且顾客有合理方式提供。不要为分析、营销画像或方便以后联系而把非必要字段设为强制，以免增加弃单和数据合规风险。

## 字段数量和长度如何规划

自定义字段有数量、字符长度和下拉选项数等限制。商户应将其视为少量补充信息，而不是可以无限扩展的问卷。规划时先列出真正决定履约的字段，合并重复问题，并将可选信息与必填信息分开。超过平台限制时，不要试图通过创建一堆近似链接或把多个问题塞进一个字段来规避限制。

字段标签应简洁、具体，并使用顾客所选择语言。文本长度可以限制为合理范围，避免用户粘贴整段不相关内容，也避免物流或履约后台被超长字段拖慢。若确实需要长描述，应使用商户自己的受保护表单，并在订单中只关联安全的记录编号。

下拉字段的 value 值应稳定、可识别并且适合程序处理；用户看到的 label 可以是本地化文案。不要把完整的内部数据库结构或个人资料编码进选项值。字段键应在链接配置和后台解析中保持唯一，避免不同字段在系统里都映射到同一个属性。

## 必填字段的业务与体验取舍

必填字段可以防止订单缺少某个必要选择，但同时也会阻止顾客在不知道答案或不愿提供资料时完成付款。设置前应问：没有这项信息能否接受订单？能否在付款后再确认？该信息是否已经在网站账户中获得？如果有其他安全、易用的方式拿到，就不一定要把它作为付款前提。

若产品确实需要定制参数才能履约，应在商品详情页提前说明，并在支付页面使用顾客能理解的标签。顾客应该知道为什么需要提供信息，以及付款后是否还能修改。如果字段填写错误会造成不可逆的定制，应在付款前让顾客检查最终选择。

选填字段也要解释用途。顾客可能误以为可选字段没有填写会导致订单无效，因此确认页和订单邮件应根据实际字段值展示结果。若后续需要客服补充信息，应通过验证身份后的订单入口联系顾客，不要通过普通邮件索要银行卡安全信息。

## 付款后从哪里读取字段值

Payment Links 的自定义字段属于结账过程中收集的订单信息，商户可以在 Stripe Dashboard 的付款或 Session 详情中查看，并通过对应的 Checkout Session 数据和事件处理结果写入自己的订单系统。不同集成、API 版本和事件对象的可见字段可能不同，开发时应以实际测试事件与 API 对象为准。

通常应监听 checkout.session.completed 等与付款完成相关的事件，验证 Webhook 签名后读取 Session ID、客户、line items、付款状态和 custom_fields，再按内部订单引用关联。若使用延迟付款方式，还要处理异步成功和失败事件。不要仅依赖顾客返回的成功页面，因为顾客可能关闭页面，服务器端仍需要可靠地完成数据同步。

事件处理程序要使用 event.id 去重，并确保同一 Session 重放时不会重复创建定制任务或重复扣减库存。自定义字段值写入订单之前，先校验字段键是否属于当前链接预期列表，再限制长度和允许字符。若字段缺失或为空，应按字段是否必填来决定暂停履约或采用默认处理，而不是静默填入错误值。

## 和 Payment Link、商品及订单的关联

一个 Payment Link 可以被多位顾客重复打开，因此链接本身通常代表一个固定销售配置，不一定对应唯一商户订单。每次付款会产生自己的 Checkout Session 和订单记录。商户应利用每次 Session 的 ID、付款对象 ID以及自有订单或客户引用区分不同购买者，不能只用 Payment Link ID 把所有顾客信息合并在同一个订单里。

如果 Payment Link 销售固定商品，字段只补充定制信息即可。如果每位顾客的商品、金额或数量都不同，考虑由商户服务器为每笔订单创建 Checkout Session，确保价格和商品来源可信。不要让顾客通过文本字段填写一个“价格”或“折扣金额”，也不要从浏览器提交的字段值推导应收金额。

在订单数据库中保存字段原值、字段标签版本、链接或 Session ID、收到时间和处理状态。若字段表示商品规格，最好在履约开始前把它转成结构化、可校验的内部属性，并保存转换来源。这样以后链接配置调整、标签翻译变化时，历史订单仍能理解顾客当时选择了什么。

## 避免把敏感信息放入自定义字段

自定义字段不适合收集卡号、CVC、银行卡密码、一次性验证码、政府证件号码、健康资料或其他高度敏感信息。支付凭据应通过 Stripe 的安全支付组件收集；需要身份核验时应采用相应的合规产品和受保护的流程，而不是增加一个文本字段。

也不应把字段用于收集法律限制或业务无需的信息。姓名、地址和电话等常见个人资料应优先使用 Checkout 对应的标准收集功能，因为标准字段可能有更明确的格式和处理方式。自定义字段中重复收集这些信息，会造成多个来源不一致，也增加隐私管理复杂度。

字段数据会出现在支付管理和事件处理中，访问权限、日志、导出和保留期限都应纳入商户数据治理。不要把完整字段 payload 无差别写入公共应用日志、第三方分析事件或无权限的客服系统。对履约人员只提供完成任务所必需的信息。

## 多语言与可读性

Payment Link 的字段标签是商户主动提供的内容，不能仅凭 Checkout 页面界面语言切换就假设标签会自动翻译。面向多语言顾客时，可以按目标市场维护对应的 Payment Link 或通过商户系统创建相应 Session。所有语言版本的字段键和业务语义应保持一致，便于后台以统一字段映射处理。

如果选项 label 被本地化，内部 value 可保持稳定代码，例如系统识别的标准枚举。这样顾客看到本地语言，后台依旧能正确识别选项。切勿因翻译调整 value，导致旧订单和新订单无法在报表中合并比较。

检查移动端的字段长度、标签换行和错误提示。顾客应该一眼能明白是填写姓名、订单备注还是编号；如果字段有字符限制、仅允许数字或需要特定格式，应在输入前说明，而不是提交失败后才显示不可理解的错误。

## 与税务、配送和客户信息收集的边界

如果需要配送地址，应使用 Checkout 的 shipping address collection，而不是用多个自定义文本字段拼接街道、城市和国家。标准地址收集更适合支付和履约使用，也更容易与 Session 中的配送信息关联。税务识别号、企业名称和电话等信息应优先使用 Stripe 提供的相应收集能力，再按当地税务要求处理。

自定义字段不是自动税务工具，也不会自动验证顾客是否有资格购买某类商品。税额、币种、配送费和优惠都应由可信业务规则和 Stripe 对应配置计算。字段数据可以补充订单说明，但不应覆盖价格计算结果或改变顾客已经确认的交易金额。

如果一个字段会决定商品变体或配送区域，服务器端还需验证它是否与实际库存、配送政策和订单状态兼容。顾客能在支付表单中输入某个地区，不代表商户能向那里发货；填写一个税务 ID，也不代表系统自动核验其有效性。

## 常见故障排查

如果顾客在结账页看不到字段，检查 Payment Link 当前是否启用了自定义字段、字段是否已保存并处于该链接实际版本、链接是否仍有效，以及顾客访问的是不是更新前复制的旧链接。用新的无痕测试会话复现，区分配置问题和浏览器页面缓存。

如果字段显示但订单数据库里为空，检查 Webhook 是否收到并验证、应用是否读取了正确 Session、事件处理是否把 custom_fields 和内部订单正确关联，以及字段键是否匹配。查看 Stripe Dashboard 中同一 Session 的字段值，与应用日志中的 Session ID 对比。不要为补齐数据而要求顾客再次付款。

如果顾客填写了字段但收到的内容格式不对，检查字段类型、长度限制、可选状态和输入清洗逻辑。文本内容应按普通不可信用户输入处理，避免将其直接放进 HTML、SQL 查询、文件路径或 shell 命令。需要结构化值时优先改用下拉选项或商户端的受控输入流程。

如果字段增加后转化率下降，分析是否字段过多、标签不清楚、要求信息不必要或移动端填写困难。移除不能直接服务付款或履约的字段，再观察变化。转化率波动要结合访问量和用户来源判断，不应因一个小样本变化就立刻认定某个字段一定是问题。

## 测试和运营清单

- 每个字段都有明确的履约或订单用途。
- 字段标签说明具体需要顾客提供什么。
- 必填字段确实是完成订单所必需的。
- 字段类型、长度和下拉选项符合当前 Stripe 限制。
- 对订单价格、折扣或税费没有依赖顾客自填值。
- Dashboard 中能看到测试订单提交的字段。
- Webhook 对签名进行验证，并对重复事件去重。
- 事件对象与内部订单通过稳定 ID 关联。
- 字段缺失、超长或非法输入有安全处理规则。
- 定制履约和库存处理不会因重复事件执行两次。
- 隐私声明和系统保留周期覆盖这些附加数据。
- 不收集完整卡号、CVC、验证码和其他高敏感信息。
- 移动端、不同语言和过期链接场景均完成测试。

## 数据维护与长期复核

字段配置也需要像商品价格一样纳入变更管理。新增、改名或删除字段前，应确认旧订单的处理程序仍能读取历史字段键，更新后的链接是否会影响正在结账的顾客，以及报表是否依赖某个选项值。为每次配置保留变更日期和负责人，遇到顾客付款后数据映射异常时，就能判断问题从哪个版本开始发生。对已经完成的订单，不要因为链接改版而覆盖顾客当时的原始选择；如确需修正，应保留修改前后的值和原因。

## 总结

Stripe Payment Links 的自定义字段适合收集少量、简短且与当前订单直接相关的补充信息，例如可选规格或简短备注。它不能替代复杂表单、库存系统或安全的数据收集流程，也不会自动更新商品价格、税费、运费和履约规则。

上线前应明确字段用途、必填条件和数据保留方式；付款完成后通过经过验证的 Webhook 将字段与 Checkout Session 和内部订单关联，并做好校验、去重和访问控制。只收集真正需要的信息，不要把敏感支付资料放进自定义字段，才能让顾客体验、商户运营和数据安全保持平衡。
