如果线上商店突然出现大量陌生客户、低金额付款尝试、卡片授权失败或一连串拒付，可能有人正在利用你的支付表单测试被盗银行卡资料。银行卡测试（card testing，也常被称作 carding）通常会通过自动化请求尝试判断卡片是否可用，商户可能因此看到失败交易激增、可疑小额成功付款、账户风控信号变化，或真实客户结账受影响。

出现异常后要先区分攻击流量和正常促销高峰，保护客户与支付账户，同时避免在仓促处理时把真实订单全部拦截。Stripe 对 Checkout、Payment Element 和 Radar 提供相应的防护，但商户仍需监控自己的集成、API端点和账户凭证。Stripe 对应功能会随集成和账户不同而变化；请以官方卡片测试防护文档和 Dashboard 为准。本文是技术排查说明，不保证某项规则可以拦截所有攻击。

## 一、银行卡测试攻击是什么

银行卡测试是攻击者尝试验证一组支付卡资料是否有效的过程。有些攻击会通过小金额授权或付款判断卡片状态，有些则不断变换金额、IP、邮箱、设备或用户资料，以逃避简单的单一过滤条件。攻击目的可能是建立可用卡片清单，随后对其他商户进行消费。商户网站若允许无需登录即可频繁创建付款或保存卡片，就可能成为自动化请求的目标。

攻击不一定只产生成功收费。大量失败付款、拒绝码、卡片验证尝试和临时客户记录也会消耗系统资源、干扰运营，并可能让发卡行或支付网络对商户流量产生疑虑。成功的小额交易同样要认真核对，因为攻击者可能在确认卡片可用后继续尝试更高金额。先记录异常开始时间、相关端点、交易数量和主要错误类型，再判断影响范围。

## 二、如何识别异常流量

常见信号包括短时间内失败或被拦截支付突然增多、HTTP 402 错误数量异常、同一产品出现大量极低金额尝试、随机生成的姓名和邮箱、相似地址或用户代理、同一 IP 或设备反复创建新客户。也可能出现多个 IP 分散发起请求、每个 IP 只做少数尝试，因此不能只依赖一个特征。

把实时数据与正常业务基线比较：当前交易总量、成功率、失败原因分布、新客户数量、每个账户的卡片添加次数、订单金额区间和国家分布。Stripe Dashboard 中的支付列表、开发者日志、Radar 提示和 Webhook 记录可以提供线索。商户自建的应用日志和边缘安全日志也很重要。攻击流量可能伪装成正常广告点击或促销活动，所以在实施大范围拦截前要核对活动、部署和流量来源。

## 三、先保全信息并确认影响范围

发现异常后，记下首个异常时间、峰值时间、涉及的 Stripe 账户、PaymentIntent 或 SetupIntent ID、受影响的支付端点、成功与失败数量、是否已有客户投诉和是否产生真实损失。保留必要的日志、告警和 Dashboard 查询结果，但应遵循数据最小化原则，避免把完整卡片信息、密码、API secret 或不必要的个人资料复制到工单。

确认攻击目标可能是“创建付款”“保存卡片”或购物车流程中的某个接口。检查每个端点的请求频率、认证状态、客户 ID创建、PaymentIntent创建和确认步骤。只看 Dashboard 的成功付款不够，因为大量验证尝试可能停在接口层或失败日志里。为团队指定一名事件负责人，协调支付、开发、客服和风险团队，避免多人分别更改生产规则而互相冲突。

## 四、不要只用 IP 封锁解决

按 IP 地址封锁有时有帮助，但攻击者可能使用代理、轮换地址或被攻陷的设备。共享网络、校园、企业 VPN 和移动运营商也会让多个正常客户共用相似 IP。Stripe 官方建议不要只依靠单一 IP 启发式作为防护。基于一次攻击中看到的地址做永久广泛封锁，可能拦截真实客户却没挡住新的攻击来源。

更可靠的做法是多层控制：使用 Stripe 推荐的 Checkout 或 Payment Element 集成；对创建付款、保存卡片和创建客户的服务端接口设置合理频率限制；给高风险或重复行为增加 CAPTCHA 或登录要求；使用 Radar 和风险监控；监测新账户、卡片、产品和付款尝试之间的关系。每层都要测量对正常转化的影响，必要时为已登录的老客户和新访问者采取不同但公平的规则。

## 五、检查是否使用了推荐的支付集成

Stripe 的某些托管结账或 Payment Element 集成包含针对卡片测试的多种自动或手动缓解措施，例如流量限制、模型检测或 CAPTCHA 触发等，具体适用范围依当前产品版本而异。若商户使用自建表单或较旧的集成，可能没有同样的保护信号或流程。先检查官方集成建议，并确认网站实际加载的 Stripe.js、Checkout 或 Elements 版本与文档一致。

不要因为代码里调用了某个 Stripe API，就假设所有防护自动生效。检查请求是否从预期的前端和服务器发出，客户资料是否正确关联，是否允许外部脚本直接调用创建接口。对于使用插件或电商平台的商户，联系插件维护者或建站服务商确认当前版本的防护能力，并查看官方安全更新。更换集成前在测试环境验证付款、3DS、退款、订阅和 Webhook，避免防护升级导致正常结账中断。

## 六、给付款接口添加速率限制

如果自己管理支付接口，可从创建新客户、添加支付方式、初始化付款、确认付款、重试付款和创建 Checkout Session 等敏感操作开始设计速率限制。限制条件可以结合 IP、账户、设备、会话、卡片标识、订单和时间窗口，但要避免把单一字段作为最终判断依据。速率阈值应依据正常用户行为和业务量设置，而不是照抄一个固定数字。

限流应在服务端或可信的边缘层执行，不能只在浏览器按钮上禁用提交。每个重复请求都应有适当的幂等与去重设计，防止用户多次点击或网络重试造成重复订单。对被限制的正常客户，给出可理解的提示和安全恢复路径；不要暴露具体阈值或详细风控规则。上线后监控被拦请求和正常完成率，若真实用户误伤增加，及时复核策略。

## 七、在适当环节使用 CAPTCHA

CAPTCHA 可以提高自动化脚本批量提交的成本，尤其适用于新用户、异常频率或高风险路径。但它不能完全替代服务端校验、Stripe 风险控制和请求限流。确保 CAPTCHA 的验证结果由服务端验证，且每一次需要保护的付款或卡片验证请求都必须满足规则；只在前端显示一个组件而服务器从不检查结果，无法形成有效保护。

可以考虑风险触发或逐步升级方案：正常流量保持简洁，对重复请求或新客户异常行为要求额外验证。测试 CAPTCHA 在移动端、辅助功能、不同浏览器和代理情况下的可用性，提供不会把残障客户排除在外的合规方案。若使用评分式 CAPTCHA，调整阈值前先观察真实流量分布。记录挑战通过率和放弃率，以避免把安全措施变成客户无法完成的付款障碍。

## 八、限制创建客户和保存卡片的滥用

攻击者可能不立即付款，而是反复创建客户、附加支付方式或执行验证。因此要检查保存卡片和 SetupIntent 的端点、客户对象创建方式、账户注册流程和匿名访客结账。要求账户登录或已验证会话可以减少部分滥用，但也可能影响转化。权衡时根据实际攻击路径选择控制，而不是对所有用户全面强制同一流程。

对每个客户、账户、设备和时间窗口统计卡片新增次数和付款尝试次数。高频行为可触发临时限速、额外身份验证或人工审查；处理结果需留痕。不要把任何客户的卡片信息自行记录在应用日志中，卡片数据应由 Stripe 的安全组件处理。API 密钥不得暴露在前端；Publishable Key 是公开使用的密钥类型，但其公开并不意味着可以允许未受保护的服务端业务接口被滥用。

## 九、检查 Stripe Dashboard 和 Radar

查看 Stripe Dashboard 中失败、被阻止、风险评估和相关事件的变化，确认异常交易是否被 Stripe 标记、拦截或创建了对象。若账户使用 Radar，检查规则触发情况和当前策略，不要在攻击期间为了追求付款成功而随意关闭保护。Radar 规则调整应由具备权限的人员依据账户数据进行，记录变更、范围和回滚办法。

Stripe 的默认防护可能动态选择不同干预措施，但不能保证完全阻止攻击。若自己的集成信号不足或表单实现不符合建议，系统可能更难识别异常。检查是否有重复付款失败告警、早期欺诈警告或争议，并比较正常时期的数据。Dashboard 搜索和报告结果有环境、时间与账户范围；在调查时确认当前是测试还是正式账户，以及是否查看关联账户。

## 十、攻击期间如何处理成功的小额交易

攻击可能产生少量成功付款。不要仅因金额低就忽略，也不要不核实就批量退款所有低金额订单。确认每笔付款是否有真实订单、客户信息是否合理、产品是否已履约、交易是否被客户认可。若有合理依据认为交易是未经授权的测试付款，按 Stripe 官方建议和商户退款政策及时处理，并记录退款对象和对应支付 ID，以减少后续争议风险。

批量操作前先测试查询范围和筛选条件，避免把合法低价商品或促销订单纳入。检查退款是否确实对应原交易，不要重复发起；观察退款是否成功或仍在处理。若存在争议、账户限制或疑似更大规模的泄露，联系 Stripe 官方支持和内部风险负责人。客户沟通应使用安全的官方渠道，不要在公开场合告知其银行卡测试细节或索要安全凭据。

## 十一、保护密钥和服务器端凭证

卡片测试与 API 密钥泄露不是同一种问题，但密钥暴露可能让攻击者直接创建对象或滥用支付接口。检查服务器密钥是否仅存在于受控后端、环境变量或秘密管理服务中，有没有提交到公开仓库、日志、前端代码、构建产物或工单。如果怀疑 secret key 已泄露，按 Stripe 官方密钥轮换流程处理，并确认旧密钥停用、服务部署和审计记录完成。

API secret、Webhook signing secret、数据库凭证、客户卡片数据和一次性验证码不得发送给陌生支持人员或放在公开聊天中。对密钥设置最小必要权限，并定期检查权限、访问日志和服务账号。若开发者误把密钥推送到仓库，即使随后删除文件，也应视为可能已暴露，不能只依赖删除提交。先安全轮换，再排查与该密钥相关的异常 API 请求。

## 十二、正常客户被误拦时怎么办

防护措施可能误拦真实用户，特别是在促销、新地区上线、共享网络或客户频繁重试时。监控误拦率、支付成功率、客服投诉和挑战失败率，并按新老客户、设备、付款方式和地区分析。遇到被拦用户，提供安全的替代方式，例如稍后重试、联系官方客服或使用合规支持的其他付款方式；不要要求客户通过非安全渠道发送卡片资料。

规则设计要避免基于受保护或敏感个人特征作出不当判断。对于需要人工复核的个案，核对订单和 Stripe 对象状态，而不是直接让客户不断重复提交。恢复策略应与风控相连：临时解除限制需要有身份和订单核验、权限审批和审计记录。事件结束后回看哪些规则过度阻挡正常客户，调整阈值或改进集成。

## 十三、事件期间的沟通与业务连续性

给客服团队一份简洁的事件说明：目前观察到的症状、哪些支付方式仍可用、客户应如何查询订单、哪些信息不能索取、遇到未授权投诉如何升级。不要把技术推测当成已确认事实，也不要公开攻击者正在利用的端点、具体阈值或账户安全配置。

业务负责人需要评估是否暂时暂停某个受攻击的付款流程、启用额外验证或限制访客结账。任何临时控制都要记录开始时间、范围、负责人、客户影响和恢复条件。不要为了继续营业而关闭所有风控或把支付接口直接暴露。若攻击涉及个人数据、密钥、账户访问或实际未经授权的交易，按公司的安全事件流程处理，并评估是否需要通知适当的内部或外部团队。

## 十四、处理步骤清单

1. 确认异常发生时间、规模、受影响账户和支付端点。
2. 对比失败付款、HTTP 402、低金额交易、新客户和卡片验证活动。
3. 检查 Dashboard、Radar、开发者日志和应用服务器日志。
4. 确认使用的 Checkout/Payment Element 集成和版本。
5. 对创建付款、保存卡片和创建客户接口加入服务端限制。
6. 评估 CAPTCHA、会话登录和异常流量挑战的组合方式。
7. 核查 API secret、Webhook secret 和服务器访问权限是否泄露。
8. 审查成功小额交易，确认真实性与履约，再决定是否退款。
9. 监控误拦率、客户投诉和攻击流量变化。
10. 事件结束后复盘根因、改进措施和负责人。

处理时分清攻击流量与正常客户，保存必要证据并避免复制敏感资料。所有生产规则变更都应有人负责和可回滚。

## 十五、常见问题

### 失败付款很多，是否一定遭到攻击？

不一定。促销活动、支付集成变更、发卡行故障、真实用户输入错误或自动重试也可能造成失败增加。结合时间、来源、金额、客户资料、错误码和正常业务基线判断，并检查近期部署与营销活动。

### 只屏蔽一个 IP 地址够不够？

通常不够。攻击流量可能使用多个来源，而共享网络上的正常客户也可能共用同一地址。将 IP 作为信号之一，并结合账户、会话、设备和请求行为建立多层限制。

### Stripe 会不会自动挡住所有卡片测试？

不应假设可以完全自动拦截。Stripe 提供的能力取决于所用集成、账户和当前产品，商户仍需检查自己的支付表单、服务器端接口和流量监控。

### 是否应该把金额改高来阻止小额测试？

随意改变价格会伤害真实客户，也不能从根本上解决接口滥用。先定位可被攻击的创建或验证流程，采用有针对性的控制，并根据业务和 Stripe 官方说明处理已产生的交易。

### 是否该重试所有失败付款？

不要在攻击期间对全部失败付款自动重试。过多重试可能增加噪声或干扰正常处理。按失败原因和支付对象状态决定是否重试，确保真实客户付款不会被错误重复提交。

### 需要退款所有可疑成功付款吗？

先核对对象、订单和履约记录。Stripe 官方防护建议在有可疑欺诈成功付款时评估退款以减少争议，但范围和操作仍需根据实际交易与账户流程确认。避免盲目批量退款。

## 十六、事件结束后的复盘

攻击流量下降后，统计攻击持续时间、请求来源、受影响账户、失败和成功交易、采取过的控制措施、误拦客户、退款与争议结果。确认临时规则已由负责人评估，保留有效措施，撤除已经无用或影响正常客户的临时限制。检查是否还存在被滥用的其他入口，例如保存卡片、注册账户或未登录的付款 API。

将复盘转成工程任务：迁移到推荐集成、增加服务端限流、完善幂等控制、增加 CAPTCHA 条件、保护密钥、补充报警、完善客服话术和建立响应负责人。用测试流量验证新措施不会在正常流程中阻断合法支付。定期演练异常流量告警和资金安全升级流程，而不是等下一次攻击才临时找人处理。

## 总结

Stripe 卡片测试攻击常伴随支付失败、HTTP 402 增多、低金额尝试和随机客户资料，但应结合业务基线和对象记录确认。仅按 IP 封锁或提高价格通常不是完整方案。优先使用 Stripe 建议的 Checkout 或 Payment Element 集成，保护服务端付款和保存卡片接口，结合限流、CAPTCHA、Radar、监控和幂等处理。排查成功小额交易和密钥安全，并同时监控误拦客户，才能兼顾支付安全与正常转化。

参考：[Stripe 官方银行卡测试防护指南](https://docs.stripe.com/disputes/prevention/card-testing)、[Stripe 自动化测试文档](https://docs.stripe.com/automated-testing) 和 [Stripe 卡片拒付说明](https://docs.stripe.com/declines/card)。不同集成具有不同的自动防护能力，请对照当前账户和官方文档落实。
