在线支付风控不能只靠一条“拒绝可疑订单”的规则。规则过松可能让欺诈交易通过，规则过严又会误伤真实客户，降低支付成功率并增加客服成本。Stripe Radar 会评估交易风险，并提供内置风控规则；符合账户计划和功能条件时，商家还可以创建自定义规则，对交易请求额外验证、拒绝或送交人工审核。

配置规则前，需要先确定每种动作意味着什么。拒绝会让支付无法按当前尝试继续；人工审核会让团队在付款结果或履约前检查交易；3D Secure 要求客户完成额外身份验证。它们对转化、风险和运营负担的影响各不相同。本文介绍 Radar 规则的基本思路、规则动作的选择、上线实验、误拦截处理和持续监控。规则能力及具体语法可能随 Stripe 计划和 Dashboard 更新变化，实际操作以当前官方文档为准。[Stripe Radar 规则指南](https://docs.stripe.com/radar/rules) [Radar 工作原理](https://docs.stripe.com/radar/how-radar-works)

## 先理解内置规则与自定义规则

Stripe 文档说明，Radar 会使用内置规则筛查支持的支付方式；符合计划条件时，商家还可以在 Dashboard 中建立自定义规则，例如对新客户请求 3D Secure、允许特定可信来源、拦截某类交易或审核高金额订单。[Radar 规则指南](https://docs.stripe.com/radar/rules) 不应假设所有账户都能使用相同的自定义功能，也不应把其他公司的规则直接复制到自己的账户。

内置规则基于 Stripe 的风险模型和账户设置，通常可作为默认保护层。自定义规则则适合表达商家自己掌握的业务事实，例如服务区域、订单金额阈值、账户年龄或内部风险信号。规则应补充业务上下文，不要为了让规则看起来复杂而重复实现平台已经处理的风险判断。

Radar 规则表达式引用的属性和语法需要按官方文档核对。一个字段名称相似，不表示它能用于所有支付对象或规则动作。配置前先在 Dashboard 中查看支持条件、动作及适用支付流程，再用测试数据确认规则是否在预期的交易上触发。

## 拒绝、审核和 3D Secure 有何区别

### 拒绝交易

Block 或拒绝规则适用于商家已经有充分依据，不希望这类交易继续尝试收款的情形。它会直接影响客户完成购买的机会，因此条件应清晰、可解释，并有误伤监测。基于某个单一信号一刀切拒绝，例如仅按国家、邮编或一次验证失败拦截，可能挡住合法客户，尤其是跨境、数字钱包或发卡行不支持某项校验的交易。

Stripe Radar 的规则文档特别提示，发卡行即使收到 CVC 或地址校验失败的信号，也可能基于其他风险因素批准付款。某些验证失败规则不会阻止没有提供 CVC 或发卡行不支持验证的交易；新旧规则的适用方式也可能不同。[Radar 规则指南](https://docs.stripe.com/radar/rules) 因此要确认具体信号的含义和缺失值行为，而不是假设“没有通过校验”等于欺诈。

### 人工审核

Review 适合交易价值较高或需要结合业务上下文判断的场景。审核队列可以让运营人员检查订单、客户历史、履约风险和其他信号，再决定是否履约、联系客户或采取进一步措施。它不等同于自动拒绝，也不保证最终不会发生拒付。

审核流程需要有责任人、处理时限和操作记录。若订单审核期间仍自动发货，审核就失去意义；如果所有审核都无限期等待，合法客户也会失去购买体验。建议按金额和业务风险设定优先级，准备可直接查看的订单和支付上下文，并在超时后采取明确动作。

### 请求 3D Secure

3D Secure 会要求客户完成额外身份验证。它适合希望通过认证降低某些欺诈风险，或根据规则将交易导向验证流程的情况，但会增加结账步骤。Stripe 提供自己的 SCA Engine，根据风险与认证要求自动处理相关身份验证，并建议通常依赖自动判断；手工请求 3DS 属于需要慎重设计的风控策略。[Radar 规则指南](https://docs.stripe.com/radar/rules) [SetupIntent API 对象](https://docs.stripe.com/api/setup_intents/object)

3DS 不是“欺诈退款保险”，也不能保证所有交易都成功。发卡行决定认证结果和用户体验，部分支付方式可能不支持此流程。配置后应观察认证完成率、支付成功率和争议率的变化，同时确保用户在手机、跳转页面和返回页面中都能顺利完成结账。

## 规则条件应来自业务证据

建立规则前，分析一段时间的真实交易结果，识别与欺诈、拒付或滥用有关系的信号。可以按支付金额、客户历史、订单品类、发货速度、账户创建时间或已验证信息分析，但要避免把相关性误认为因果关系。某个地区的交易风险较高，不代表该地区每个客户都不可信；某种设备被多人共享，也不意味着所有此类支付都是欺诈。

规则条件要可解释和可测试。先写自然语言版本，例如“超过某金额且客户没有历史成功付款时进入审核”，再映射到 Stripe 支持的属性。检查条件组合在缺字段时如何处理、是否只匹配信用卡还是也匹配其他支付方式，以及规则是否与其他规则冲突。

不要把客户个人敏感属性或受法律保护的特征作为不当拒绝依据。地域规则也可能涉及消费者保护或跨境交易限制。Stripe 文档明确提醒，欧盟企业可能受到 Geo-blocking Regulation 的影响，不能仅因客户来自其他欧盟成员国就阻止支付。[Radar 规则指南](https://docs.stripe.com/radar/rules) 涉及地区限制、合规和公平对待的规则应由法律或合规负责人审查。

## 从小范围测试到正式启用

规则上线前，使用测试模式或 Radar 提供的测试能力验证触发与未触发情形。准备一组代表性案例：正常历史客户、新客户、不同金额、不同币种、钱包支付、缺少验证信息、地址不匹配、浏览器重试和人工审核队列。逐条记录预期动作，再检查 Dashboard 中的实际结果和支付对象状态。

如果账户支持规则模拟或测试工具，先了解模拟范围和限制。测试结果不一定等价于真实发卡行授权、用户认证或风控模型结果。准备从仅观察、人工审核逐渐过渡到部分自动拦截的策略，尤其当规则会拒绝大量交易时，不要未经评估直接全量启用。

为每次规则变更记录版本、作者、业务理由、预计影响、启用时间和回滚方案。调整一条规则后，观察一段完整交易周期，而不是只看几笔付款。若多条规则同时变化，出现转化下降时难以定位原因；可以分阶段调整并对比相似群体的结果。


## 规则优先级与多条规则的组合

一个账户往往同时存在默认规则和自定义规则。配置前应理解 Dashboard 显示的执行顺序、匹配后采用的动作以及规则之间是否可能冲突。同一笔付款若同时符合审核条件和拒绝条件，最终结果取决于 Stripe 当前规则系统的处理逻辑，不能依靠团队对“哪条更严格”的直觉。逐条模拟代表性交易，确认客户最终经历的是拒绝、认证还是人工审核。

规则名称应描述业务目的，例如“高金额新客户进入审核”，不要只写“Rule 1”或“临时规则”。命名清楚有助于轮值人员理解触发原因，也能在多条规则影响同一笔付款时快速定位。条件改变后更新说明和变更记录，不要让规则名称与实际表达式逐渐失去对应关系。

上线采用小步变更：一次只修改一类条件，记录变更前后的交易量与结果，再决定是否继续扩大。若付款成功率、审核积压或客户投诉突然恶化，应能快速恢复到上一个已记录版本。回滚本身也要验证，并安排负责人在变更后观察告警和 Dashboard 事件。

## 监控风控效果与误伤

不要只用欺诈率或争议率判断规则是否有效。还要观察授权成功率、支付完成率、3DS 发起率和完成率、人工审核积压、审核放行比例、退款率和客户投诉。不同业务的基线不同，关注趋势和人群差异比盯着单个数字更有意义。

被规则拒绝的客户未必都是欺诈者。提供合理的替代路径，例如换用其他支付方式、联系客服或重新核对账单资料；但不要向潜在欺诈者暴露详细风控逻辑，以免对方据此绕过规则。客服工具应显示足够的风险上下文和支付结果，让工作人员能解释处理状态而不泄露模型内部信号。

误伤排查要关联 PaymentIntent、Charge、Customer、订单和 Radar 评估结果。确认规则究竟是阻止创建、要求认证、进入审核还是仅标注风险。保存时间、规则 ID、匹配条件和后续处理结果，可以让风控团队识别哪些规则对合法客户影响过大。

## 与人工审核和履约系统衔接

Review 队列必须与仓储、数字服务开通和订单状态打通。支付成功并不意味着订单适合立刻履约；如果 Radar 将交易放入审核，业务应决定是暂缓发货、限制高风险功能还是先提供低风险体验。相反，一笔交易如果已经由审核人员批准，内部状态要及时同步，避免订单仍卡在待审中。

审核人员需要标准操作流程：检查哪些材料、如何联系客户、多久内给结论、什么情况下批准、拒绝或升级给主管。决定要记录理由和证据来源。不要让审核结论只存在于聊天记录中，否则轮班人员无法了解交易当前状态。

如果平台使用 Connect，还要区分平台交易风险、连接账户风险和资金转出限制。Radar 对付款交易的规则不必然等同于对连接账户或提现的处理。平台应检查交易对象、商户责任和资金流向，避免把某一层的审核结果误认为另一层已经通过。

## 常见配置问题

**规则没有触发。**检查测试模式与正式模式、规则是否启用、属性是否适用于支付对象、实际字段是否缺失，以及是否命中更高优先级的其他规则。查看 Dashboard 记录而不是只根据代码猜测。

**真实付款被过多拒绝。**分析拒绝交易的规则与合法客户样本，确认条件是否过宽、信号是否具有偏差，必要时先调整为人工审核或 3DS 验证。不要简单删除所有规则后停止监控。

**审核队列一直积压。**检查触发比例、处理时限、人员容量、订单上下文是否齐全以及是否有自动提醒。若队列无法在业务承诺时间内处理，应调整规则阈值或增加自动化分流。

**启用 3DS 后转化下降。**按设备、支付方式、国家、认证结果和失败状态拆分，确认用户是否成功返回、按钮是否重复触发，以及被要求认证的人群是否过宽。不要仅凭总成功率判断是 Stripe 认证本身还是页面集成问题。


## 校验信号的局限

CVC、邮编或账单地址校验结果只是风险评估的一部分。发卡行可能批准校验未通过的交易，也可能不支持某项验证；数字钱包结账时客户未必直接输入卡片安全码。Stripe 文档区分了新的基于风险的 CVC/邮编规则和旧版规则，并说明有些缺少验证资料的交易不会被这些规则拦截。[Radar 规则指南](https://docs.stripe.com/radar/rules)

因此，先看清规则条件对“失败”“未提供”和“不支持”的不同处理，再评估它对业务支付方式结构的影响。若客户大量使用钱包或某些地区常见的支付方式，过度依赖单一卡片校验会造成不必要的拒绝。把校验信号与订单金额、客户历史及履约方式结合，通常更利于区分风险。

## 上线检查清单

1. 区分自动拒绝、人工审核和 3DS 验证的目标。
2. 检查 Radar 计划、规则功能与适用支付方式。
3. 使用可解释的业务信号，避免不当地区或群体限制。
4. 测试字段缺失、钱包支付和验证不可用等边界。
5. 设计审核责任人、时限、订单暂缓与升级流程。
6. 记录规则变更版本、影响假设和回滚办法。
7. 同时监控欺诈、授权成功、转化、审核积压和客户投诉。
8. 为误拦截客户提供安全的替代支付或客服路径。
9. 将支付对象、规则结果、订单和履约状态关联起来。
10. 变更后分阶段观察，并定期复核规则是否仍符合业务。

风控复盘应定期检查规则触发率及其业务影响，并在价格、销售国家、履约模式或支付方式变化后重新评估原有阈值。

不要让已过时的条件长期自动拦截新业务。

如有监管或消费者保护疑问，应先由合规负责人审阅，再进行生产规则调整。

同时保存调整前后的指标快照，便于判断实际效果。

并留存复核结论和下一次检查日期。

避免重复误伤客户。

并持续观察。

安排后续检查。

及时更新配置。

## 总结

Radar 规则的目标是在欺诈风险与真实客户支付体验之间取得可监控的平衡。自动拒绝适合有充分依据的交易，人工审核适合需要业务判断的情况，3D Secure 则增加客户认证步骤。配置前要理解条件与动作的具体语义，测试缺失数据和支付方式边界，上线后同时跟踪争议、转化和误拦截，再根据证据调整规则。

进一步实施时，请参阅 [Stripe Radar 规则指南](https://docs.stripe.com/radar/rules)、[Radar 工作原理](https://docs.stripe.com/radar/how-radar-works) 和 [Radar Review 事件说明](https://docs.stripe.com/api/events/types#event_types-review)，并在测试模式验证规则在完整支付流程中的表现。
