商户开始面向海外客户收款后，常会看到客户支付币种、Stripe 交易币种、余额币种和银行入账币种不完全相同。客户以欧元付款，Stripe Dashboard 中可能显示另一种余额；银行最终收到的结算金额又可能受到转换、费用、退款、提现安排和发卡行处理影响。把所有金额都当成同一币种或只看一个 payout 数字，容易造成对账差异，甚至误以为资金少到账。

Stripe 官方将客户付款时的币种称为 presentment currency，将商户银行账户接受的币种称为 settlement currency。客户使用的卡或银行账户还可能有自己的账户币种。三者可能相同，也可能不同。本文解释多币种金额的核对方法、常见差额来源、Dashboard 排查步骤和商户侧的对账管理。支持币种、转换方式、费用和最低金额可能因账户所在国家、支付方式、账户设置及产品变更而变化；请以当前 Dashboard、Stripe 定价页和官方文档为准。

## 一、先区分三种币种

核对跨境交易时，至少要记下三种币种。第一是客户付款方式的币种，例如持卡人信用卡账单使用的本币；第二是交易的 presentment currency，也就是商户向客户收取金额时的币种；第三是 settlement currency，也就是资金结算到商户外部银行账户时采用的币种。客户卡币种与交易币种不同，发卡行可能向客户收取外币手续费或按自己的汇率换算。

交易币种与结算币种不同，Stripe 可能根据账户设置把款项转换成结算币种。支持多币种结算的账户在符合条件时可能保留更多币种余额，但需要查看账户和银行账户设置。不要把客户账单上的本币金额直接与 Stripe 余额里的另一个币种数值相减；先统一币种和时间，再比较金额。对每笔交易保留原币金额、结算币金额和转换信息，便于日后追溯。

## 二、先用一笔具体交易建立时间线

遇到金额不符，先选择一笔付款，而不是直接拿某一周的总收入估算。记录 Stripe 付款对象 ID、客户支付金额和币种、创建日期、退款或争议状态、关联 Balance Transaction、所属 payout 以及最终结算币种。若是订阅账单，还需记录 Invoice 和支付对象之间的关联；若是平台业务，还要确认款项来自平台还是某个 Connect 关联账户。

时间线能够解释为什么“扣款日期”和“银行入账日期”不在同一天。付款成功、余额变为可用、payout 创建、payout 到达银行和银行交易显示，各自可能发生在不同阶段。使用 Dashboard 中的对象关联和报告逐项追踪，避免把某笔退款或其他订单的金额混到一起。若平台采用自动 payout，按 payout ID 回到包含该笔 Balance Transaction 的批次，再核对批次汇总。

## 三、客户看到的金额为什么可能不同

客户银行卡账单以卡片或银行账户的显示方式为准。如果商户以非客户本币收费，发卡行可能按自己的汇率转换并收取外币手续费；银行还可能在授权与正式入账时显示不同金额。客户银行卡的交易描述和换算金额不能直接代表 Stripe 给商户的结算金额。

面向客户的价格页面应清楚显示收取的币种和金额。若商户使用本地化定价，应确认客户最终提交付款时看到的具体币种，而不是只看网站首页上的默认价格。退款时也要向客户说明退款金额及币种，避免把商户收到的净结算金额当作客户退款金额。遇到客户认为金额不正确时，核对订单页面、支付对象中的交易币种、收据和银行卡记录，再解释可能的银行换汇差异；不要保证客户银行一定使用某个特定汇率。

## 四、Stripe 转换如何影响商户余额

当交易币种和默认结算币种不同时，转换会影响商户最终在余额中看到的结算金额。核对时需要看交易的原始币种、Balance Transaction 使用的币种和金额、相关转换记录、Stripe 费用以及 payout 资金来源。某些账户可能支持额外币种余额和相应银行账户配置，具体可用情况取决于国家和账户条件。

不要仅用付款日的公开汇率乘原金额来估算结算金额。实际转换时点、适用费率、账户选项以及调整项都可能使结果不同。应查该笔交易对应的 Stripe 记录和官方费用信息。若汇率或费用看起来异常，先确认选取的是同一笔 Balance Transaction、同一币种和正确日期，再联系 Stripe 支持提供对象 ID。将估算值与实际结算值分开记账，避免团队把财务预测当成精确结算结果。

## 五、Balance Transaction 与 payout 的差异

支付对象显示的金额通常描述交易层面金额；Balance Transaction 可能呈现该笔交易对 Stripe 余额的影响，包括费用、转换和净额；payout 则是从 Stripe 余额向外部账户发送的一笔资金批次。它可能包含多笔付款、退款、争议、调整和费用，所以 payout 金额通常不等于某一笔客户付款的原始金额。

对账时先打开具体付款的 Balance Transaction，检查 gross、fee、net、币种和可用日期等字段，再确认该 Balance Transaction 属于哪个 payout 或余额币种。随后查看 payout 对象的金额、币种、到达日期、状态和目的地银行账户。若一个 payout 汇总多笔交易，构建明细清单，把每笔交易净额、退款、争议及其他余额变化汇总到对应 payout，而不要把一个总额硬匹配成一笔订单。

## 六、退款会带来额外的币种差异

退款涉及原交易币种、退款币种、客户付款方式和商户余额等多个环节。退款对象记录的是退给客户的金额和状态，商户余额变动则可能受转换和退款处理影响。原支付发生转换后，退款时的汇率或资金路径可能不同，因此商户成本和客户账单的本币金额未必完全重合。

核对退款时，打开原付款和 Refund 对象，比较金额、币种、创建时间、状态以及 Balance Transaction。部分退款、多个退款、退款失败或退款正在处理，都要分别记录。客户询问金额时，优先说明商户提交的退款金额和币种，并建议其向发卡行核对入账或换算信息；商户不要把自己账户的净额当成客户必然看到的同一金额。退款未完成时，也不要重复发起新的退款，先确认原 Refund 对象最终状态。

## 七、订阅和多币种价格的对账

订阅可以按一定周期向客户收取费用，若计划面向多个国家销售，商户需要确认每个价格对应的币种、账单频率、税费、优惠、试用期和客户看到的价格信息。Dashboard 中的订阅价格、每期 Invoice、支付对象和余额交易是不同记录。价格切换或订阅升级时，可能产生按比例计算的项目或新的发票金额，不能仅用固定月费对账。

为每个订阅保存 Customer ID、Subscription ID、Price ID、Invoice ID、PaymentIntent ID和内部订单号之间的映射。检查发票上的币种与实际支付对象是否一致，确认已付款发票、未付款发票和失败重试发票没有重复计入收入。对多币种收入做报告时，选定统一的管理报表币种和转换日期规则，并将原始币种金额一并保留。会计确认的汇率政策应与 Stripe 余额的实际结算记录相协调。

## 八、Connect 平台的多币种核对

Stripe Connect 平台可能涉及平台账户、关联账户、收费方式、转账和 payout。不同账户对交易金额、费用、余额归属、结算币种和转换的处理可能不同。首先确认交易是在哪个账户上下文创建、哪一个账户持有余额，以及平台是否另有 Application Fee 或转账记录。不要把平台收入与商户关联账户收入当作一条简单的客户付款。

针对每一笔交易，记录 platform account、connected account、Charge、Transfer、Application Fee、Balance Transaction 和 payout 的关联 ID。跨账户查看时确认 Dashboard 当前账户视图；在 API 集成中，检查是否在正确账户上下文请求对象。若平台和关联账户使用不同结算币种，转换责任与账务呈现可能更加复杂，建议财务团队建立账户级对账规则，并依据 Stripe Connect 多币种说明和业务合同确定记录方式。

## 九、币种小数位和 API 金额格式

API 中的 amount 通常以币种的最小单位表示，但并非所有币种都按两位小数处理。零小数币种与部分特殊币种存在不同规则，某些货币在收款和 payout 时的金额精度也可能不同。若开发代码一律把金额乘以 100 或除以 100，可能出现错误金额、验证失败或无法完整 payout。

维护币种元数据映射，并从 Stripe 支持币种文档确认当前 API 参数格式、最小和最大金额以及特殊限制。创建付款或退款前，在服务端验证币种代码、最小单位、精度和范围。测试覆盖常见的两位小数币种、零小数币种及业务实际支持的特殊币种。前端展示与存储单位要明确区分：数据库可以保存 API 最小单位整数，但给用户显示时应按币种格式化，避免浮点运算带来的舍入误差。

## 十、Payout 金额和银行入账不同

Stripe 显示 payout 已创建或已支付，不代表银行界面已经以完全相同格式显示。需查看 payout 币种、目标银行账户、预计到达日期、当前状态和关联余额交易。银行可能需要额外处理时间，也可能以本地格式显示文本。若 payout 状态为失败、被退回或已更新，应依据对象中的具体状态和失败信息处理，不要只看待转余额减少。

若收款银行账户币种与 payout 币种不一致，银行端可能进行额外换算或处理。确认 Dashboard 中添加的外部账户适用于该币种和账户国家，核对银行名称、账户后四位或其他可安全查看的识别信息。不要在公开工单中发完整银行账号。超出预计到账时间时，先查 payout 对象和银行流水，再使用 payout ID、日期与金额联系 Stripe 或银行。

## 十一、对账表建议字段

多币种对账不应只放一列“金额”。建议保留内部订单号、客户所见金额与币种、Stripe 交易对象 ID、原始交易金额与币种、相关费用、转换前后币种金额、余额变动、退款/争议状态、Balance Transaction ID、payout ID、结算金额与币种、银行入账日期以及差异备注。字段不适用时可以留空或标注原因，避免不小心把未发生的转换记成实际数据。

批次对账时，将同一 payout 的余额交易按币种分组，分别汇总原付款净额、退款、争议、费用和调整，再与 payout 对象对应。银行账单上一个入账可能对应批次，而不是一笔订单；也可能银行收款日与 Stripe 标记的预计日期不同。保持原始记录不可覆盖，修正时追加调整行和说明。这样可以追溯每一次换汇、退款或手动操作，而不是月末才面对一笔无法解释的净差额。

## 十二、Dashboard 中的排查步骤

先通过 Dashboard 搜索交易 ID、订单关联字段或其他可靠标识，确认匹配的 PaymentIntent、Charge、Invoice 或 Refund。打开余额交易，记录币种、gross、fee、net 和可用时间，再找到对应 payout。查看 payout 的状态、账户目标和金额。如果使用多个账户，在当前视图中确认所选账户名称和 ID。

若 Dashboard 搜索结果过多，使用账户支持的过滤方式缩小日期、金额、币种和状态。不要把测试模式数据与生产模式报告混在一起。对账报告可导出，但需注意授权范围和个人信息保护。比较报告时确认时间区间和时区一致；Stripe 对象的创建时间、余额可用时间、payout 创建时间和银行到账时间不一定采用相同日期定义。查到差异后，记录每个对象 ID和当前状态，再调查原因。

## 十三、常见金额差异及处理方法

### 原币金额正确，结算币金额更少

检查 Balance Transaction 中的 Stripe 费用、汇率转换和净额，再核对 payout 是否还包含其他余额变化。不要直接把差额都归因于手续费。

### 客户银行扣款比商户收取金额高

确认商户向客户收取的币种，并询问客户是否银行卡按自身货币换算或收取了发卡行费用。商户没有收到的银行侧费用不应误记为 Stripe 商户手续费。

### Stripe 余额有多种币种

检查账户是否启用额外结算币种、外部银行账户设置和各币种余额的可用与待处理状态。分币种对账，避免把不同币种的数值直接求和。

### payout 与单笔付款金额不一致

Payout 通常可能包含多笔余额交易和其他调整。由 payout ID 回溯组成交易，逐笔汇总净额与币种。

### 退款的本币金额不同于原扣款

核对原交易币种、退款金额和发卡行账单转换，不要只用付款日的汇率反算退款。客户账单由发卡行展示时，及时向其说明商户侧提交的退款数据。

### Dashboard 和财务系统的小数位对不上

检查货币最小单位、零小数规则、舍入方式和导入字段类型。避免使用二进制浮点数进行财务精算，应采用适合货币的整数或定点表示。

### 转换费用看起来重复

先逐条找出收费记录的对象、币种、账户和适用场景，再比对 Stripe 定价和账户设置。不要用某个地区或旧费率网页推断当前账户收费。

### payout 到了银行但账上仍显示未入账

核对银行流水的交易日期、入账日期、金额、币种和描述，同时确认 payout ID对应的银行账户。必要时由财务更新匹配状态并保留对账证据。

## 十四、给客户显示多币种价格的做法

结账页应在客户确认付款前明确显示实际收取的金额和币种，避免只写一个本地数字却未说明结算货币。若商户使用自动本地化或手动多币种价格，确认每个地区展示和支付请求传入的货币一致。不要在交易完成后才通过邮件解释原来收取了另一种币种。

价格政策还应说明订阅的续费金额和周期、退款金额及币种、可能的发卡行外汇费用，以及商户客服联系方式。把客户视角的价格、Stripe 对象、财务报表和银行 payout 放在各自正确的币种上下文里。不同银行可能使用不同换算方式，商户不应承诺消费者最终银行账单金额与本地化页面完全一样，除非其支付产品和规则确实支持这样的承诺。

## 十五、开发和财务的协作流程

多币种问题通常横跨支付集成、前端价格展示、会计和银行结算。开发团队提供对象 ID、原始请求币种、余额交易与 API 版本信息；财务团队确认记账币种、汇率政策、手续费科目和 payout 匹配；客服团队提供客户看到的金额、收据和银行账单反馈。每个团队都应使用同一订单 ID和交易时间线。

上线新币种、银行账户或 Connect 流程前，先在测试环境验证金额单位、退款和账户余额行为，再用合规的真实交易小额验证银行侧实际到账和报告。记录上线时间、配置和结果。若出现系统性差异，暂停相关变更或新流程，先确定影响范围；不要在账务数据上直接批量覆盖或补差。修复后挑选几笔代表性交易复核完整流程。

## 十六、查询前准备清单

- PaymentIntent、Charge、Invoice 或 Refund 对象 ID
- 客户支付的原始金额和 presentment currency
- Balance Transaction 的 gross、fee、net 和币种
- 交易或余额转换发生的记录与汇率信息
- payout ID、币种、状态和目标账户识别信息
- 银行实际入账日期、金额和币种
- 同一报告采用的时间范围、时区和账户上下文
- 是否存在退款、争议、费用、转账或 Connect 平台分账
- API金额格式和币种小数位校验结果

联系 Stripe 或银行时提供必要的对象编号、日期和脱敏信息，不要发送 API 密钥、网银密码、短信验证码或完整银行卡号。保留差异计算过程，让对方能看清你比较的是原始交易、余额净额还是 payout 入账。

## 总结

多币种收款至少涉及客户付款方式币种、交易的 presentment currency 和商户结算的 settlement currency。Stripe 转换、支付费用、退款、争议、多个交易合并的 payout，以及银行侧换汇都可能造成金额和日期差异。对账时从具体付款对象开始，追踪 Balance Transaction 和 payout，再以同一币种和时间口径比较。多币种业务应保留原始币种数据，使用明确的金额精度规则，并让客户在付款前看清实际收取的币种。
