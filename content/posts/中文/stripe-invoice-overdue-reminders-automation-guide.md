Stripe Invoice 已发给客户，但付款期限临近或已经逾期时，商户需要用准确、适度的方式提醒客户。若完全依赖人工，忙碌时容易漏掉；若 Stripe 自动提醒和商户自建邮件同时运行，客户可能一天内收到多封相同消息。更复杂的是，发票可能已付款但 Webhook 尚未同步，或顾客通过银行转账付款而资金仍在处理中，此时继续发送催款会造成不必要的困扰。

本文说明如何规划发票发送、到期提醒、逾期通知和付款状态同步，并区分 Stripe 的自动账单流程与商户自己的消息系统。提醒频率、付款期限和停止服务规则应符合合同、当地法律和顾客沟通政策。Stripe Dashboard 与 Billing 功能可能更新，配置前应检查账户当前支持的自动化选项和 Invoice 对象状态。

## 先区分要提醒的发票类型

Invoice 可能使用 charge_automatically 自动扣款，也可能使用 send_invoice 将账单和付款指引发给客户。两者的提醒逻辑不同。自动扣款发票通常由 Stripe 尝试使用默认付款方式收款，客户需要的可能是付款失败通知或更新卡片入口；send_invoice 则要求顾客在到期日前主动打开账单付款，适合提醒应收账款和到期日期。

不要因为 Invoice status 是 open 就立即发送逾期提醒。自动扣款发票可能在 Stripe 发起付款尝试前处于待处理状态，Invoice 的 attempted、next_payment_attempt、due_date 和 collection_method 能提供更准确的上下文。特别是自动扣款模式下，due_date 可能为空，不能把 null 当成“今天到期”。

也要区分 draft、open、paid、void 和 uncollectible。草稿尚未成为正式账单，不应按已发送账单催收；paid 不应继续提醒；void 已取消，不应继续收款；uncollectible 表示商户已按特定政策标记不可收取，是否继续联系客户要按财务和法律规则决定。先检查当前对象状态再决定通知。

## Stripe 自动邮件和商户自建提醒

Stripe Invoice 可以按配置向客户发送发票及付款指引，Billing 还可能在自动账单流程中处理付款重试、提醒和自动对账。商户需要确认 Dashboard 中的邮件设置、订阅配置和发票 collection method，了解哪些邮件由 Stripe 发送，哪些由自建 CRM、客服系统或营销平台发送。

自建提醒适合需要按合同、客户分组、语言和业务状态定制消息的商户，但前提是系统能可靠读取 Stripe 当前 Invoice 状态。不能只设置一个固定时间触发邮件，不检查客户是否已经付款、发票是否作废或金额是否变化。每次发送前重新读取发票状态，并记录通知 ID 和时间。

建议把 Stripe 邮件与自建提醒的职责写清楚。例如 Stripe 负责正式 Invoice 和 hosted invoice page，商户系统只发送到期前提示和客服跟进通知。若两边都发送正式付款指引，客户可能获得两个不同链接或过时金额。遇到状态冲突时，以 Stripe 对象和实际付款记录为准，再更新商户数据库。

## 付款期限和提醒时间表

send_invoice 发票应使用与合同一致的付款期限和到期日。到期前可设置一封礼貌提醒，说明发票编号、金额、币种、截止日期和安全付款入口；逾期后再发送后续提醒并提供联系财务或申请付款安排的方式。具体提前几天提醒、逾期多久升级，要结合企业付款流程、账期长度和当地规则制定。

短账期和长期合同不应使用完全相同的时间表。账单付款周期只有数天时，一周前提醒没有意义；Net 30 企业账款可能需要提前一周告知采购部门。商户可以按客户群体和发票金额设计不同策略，但要控制总频率，避免多个自动化分别计算提醒时间造成轰炸。

每封邮件应避免夸大后果。若合同尚未允许停服或罚金，不要在提醒中写“立即付款，否则服务将终止”。付款争议、已付款但未入账、银行转账处理中和发票资料错误应进入人工处理路径，而不是继续发送同一条标准催款。

## 发票付款链接和安全性

正式发票通常可能提供 hosted invoice page 或付款指引。提醒邮件应引导客户使用官方、有效的发票入口，不要让客户把银行卡号、CVC、网银密码或验证码回复到邮件中。核对发票编号、客户、金额和币种后再发送，避免把一个客户的链接发给另一个客户。

外发邮件中的付款链接应安全生成，避免在可公开访问的页面暴露客户姓名、税号或完整发票资料。顾客点击链接时，页面应显示与 Invoice 对象一致的状态和金额。若发票已付、作废或更正，链接应反映最新状态，不应再引导客户重复付款。

如果邮件服务商重试发送或自动化多次触发，使用 invoice ID 加提醒类型和时间窗口做去重。一次提醒发送请求可能在网络超时后重试，数据库应先查询发送记录；不能因为没有收到邮件 API 的即时响应就无限重发。

## 监测付款和停止提醒

提醒任务必须在发送前查询 Stripe Invoice 的当前状态。收到 invoice.paid 或对应付款事件后，取消所有待发催收任务；收到 void 或 uncollectible 后，根据商户政策停止常规提醒；收到付款失败或需要客户操作事件后，发送与该状态相符的付款方式更新或认证指引。

Webhook 需要验证签名、持久化 event.id 并对重复投递幂等处理。事件处理可能延迟，邮件任务运行时若本地数据库仍显示 open，应直接回查 Stripe 对象以防顾客刚刚完成付款。对于银行转账等延迟方式，PaymentIntent 或 Invoice 可能处于处理中，应告知顾客正在核对，不要让顾客重复汇款。

为每张发票保存已发送提醒的时间、渠道、模板版本和结果。若客户明确提出争议、地址错误或已付款凭证，暂停自动催收并创建人工任务。处理完成后重新核对 Stripe 状态，再决定是否恢复提醒。

## 处理付款失败和需要认证的通知

自动扣款发票失败时，邮件应说明付款尝试未成功，并提供安全的更新付款方式或完成验证入口。不要在邮件中断言是余额不足，除非 Stripe 明确提供该原因。某些失败需要顾客完成 3D Secure 或主动重新付款，普通到期提醒并不能解决问题。

若 Invoice 关联 PaymentIntent 处于需要额外操作状态，确保顾客在登录账户或 hosted invoice page 中可以继续认证。系统应根据实际状态决定是否暂停服务、重试或等待。重复请求扣款不应作为认证失败的替代方案。

对于订阅，Stripe Billing 的付款失败恢复可能涉及 Smart Retries、自动重试和订阅状态变化。商户需要避免自建定时任务和 Stripe 自动重试对同一张发票并行尝试。将付款结果、通知和客户门户中的更新付款方式流程统一起来，减少客户重复操作。

## 多语言和客户沟通

国际客户可能需要按其网站语言或账户语言收到提醒。模板要准确显示发票编号、金额、币种、税费和到期日期，并让顾客明白如何联系商户。自动邮件的账单条款和语言配置不一定跟随商户网站自动变化，应分别测试 Stripe 模板和自建 CRM 模板。

提醒应使用客户熟悉的商户名称和稳定的付款入口，避免像钓鱼邮件。不要通过陌生域名发送附件或要求顾客登录不明页面。发票邮件若采用 Stripe hosted invoice page，应让顾客能从商户网站或客户门户确认链接真实性。

联系频率也要遵循合同和适用的催收规定。避免在不合适时间连续发送提醒，提供客服联系方式和争议处理入口。顾客回复付款已经完成时，先查询 Stripe 和银行对账状态，再决定下一条消息。

## 自动化规则和幂等设计

自建提醒任务可使用 Invoice ID、提醒阶段、应发送时间和模板版本构成唯一业务键。任务执行前读当前状态，锁定该 Invoice 的发送动作，成功后记录提供商 message ID。失败时区分可重试的网络故障、永久无效地址和对象状态变化，并限制重试次数。

用户可能更新客户邮箱、修改付款期限或更正发票。提醒系统应在发送时使用适当的当前邮箱和发票版本，并在变更后重算后续时间表。若客户有多个发票，不要只按邮箱去重，可能误把一张账单的提醒取消掉；需要以 Invoice ID 精确管理。

批量催收前生成预览列表，过滤 paid、void、uncollectible、draft 和仍在付款处理中发票。较大金额或特殊客户可以加入审批。发完后监控退信、投诉和付款转化，但不能只以顾客是否付款作为判断邮件是否合规和清晰的唯一指标。

## 常见问题排查

如果客户没有收到发票或提醒，检查 Invoice 的 Customer email、状态、collection_method、Stripe 邮件设置、Webhook 事件和邮件送达日志。invoice.sent 等事件可帮助确认是否由 Stripe 发送过发票邮件；如果是自建邮件则检查自己的消息服务记录。

如果客户收到重复邮件，查 Stripe 自动邮件、自建提醒、CRM 工作流、队列重试和同一发票的历史通知记录。为每个通道明确负责人，暂停重复触发的规则，并使用幂等键去重。

如果已经付款却仍然收到催款，检查 Stripe 对象是否已 paid、付款事件是否延迟或失败、本地状态是否未同步、银行转账是否仍处理中，以及提醒任务有没有发送前回查。给客户一个不需要再次付款的状态确认方式，并停止后续邮件。

如果发票逾期却没有提醒，检查它是 send_invoice 还是自动扣款、due_date 是否设置、auto_advance 是否关闭、客户邮箱是否有效以及提醒规则是否启用。对于自动扣款发票，应关注付款失败事件和 next_payment_attempt，而不是依赖不存在的到期日。

## 上线清单

- 按 charge_automatically 与 send_invoice 区分提醒策略。
- 检查发票状态、到期日、付款尝试和付款中状态。
- Stripe 自动邮件与商户自建提醒的职责明确。
- 每封提醒包含正确的 Invoice ID、币种、金额和安全链接。
- 使用 webhook 验签、事件去重和发送前状态回查。
- 客户付款、作废或争议后停止对应催收任务。
- 避免自建任务与 Stripe Billing 重试并行扣款。
- 记录每次提醒的时间、模板、渠道和结果。
- 对特殊客户、高金额和批量催收设定审批规则。
- 提供争议、已付款凭证和联系方式修改入口。
- 测试多语言、邮件退信、重复任务和延迟付款方式。
- 不在邮件或日志中收集卡号、CVC、密码或验证码。

## 客户分层与账户负责人协作

企业客户可能由采购、财务和实际使用者分别负责，提醒对象应与发票账单联系人和合同约定相符。若 Invoice 邮箱是通用应付账款地址，商户可以在销售系统中记录客户经理，但不要未经授权把付款细节发送给无关联系人。若客户主动要求将发票抄送多人，应验证收件人并限制邮件中的敏感数据。

高价值客户可以设置人工跟进任务，在自动提醒前由账户负责人确认服务是否仍在提供、发票是否有争议、采购系统是否已登记。这样可避免自动催收破坏仍在处理的商务沟通。人工跟进完成后，负责人要在系统中登记结果和下一步日期，而不是让发票永久停留在“等待回应”。

对小额或标准化消费者账单，可使用较自动的提醒策略，但要设置清晰的停止条件和退信告警。顾客多次收到退信时，商户应提供账户页面更新邮箱的安全流程，不能继续向旧地址反复发送包含订单信息的邮件。对于企业发票地址变更，保留变更来源和顾客确认时间。

## 测量提醒是否有效

跟踪各提醒阶段的送达率、打开或访问率、付款完成时间、退信和客服反馈，但遵守隐私和数据保护要求。衡量时按唯一 Invoice 统计，并区分自动扣款与客户主动付款，避免一张发票多次提醒被计作多个客户。观察付款速度的改善同时关注投诉和退订情况，不要为了提高催收率无限增加邮件频率。

使用分组比较模板、语言或发送时间时，确保顾客只接收一套相互一致的账单通知。测试结果应由小样本开始，并为已付款、争议或已作废的发票保留排除逻辑。若某个模板降低了投诉但付款延迟变长，也要考虑账户团队的跟进成本，不能只看单一转化指标。

## 发送频率的最后检查

发送前根据时区和客户本地工作日检查时间，避免系统将同一提醒同时推送到邮件和短信。允许顾客联系商户或提出账单异议，并暂停相应自动化，直到争议有结论。用清楚的发件人名称和主题，确保顾客可以识别这是他们最近的真实发票。

## 发送频率的最后检查

发送前根据时区和客户本地工作日检查时间，避免系统将同一提醒同时推送到邮件和短信。允许顾客联系商户或提出账单异议，并暂停相应自动化，直到争议有结论。用清楚的发件人名称和主题，确保顾客可以识别这是他们最近的真实发票。定期复核模板内容。

## 总结

Stripe 发票提醒应围绕 Invoice 的真实状态和付款方式设计。send_invoice 需要关注到期日和客户主动付款；charge_automatically 则要监控自动扣款、付款失败和需要认证的状态。邮件设置、Webhook、商户 CRM 和支付页面如果职责不清，就容易重复催款或遗漏真正需要客户采取的动作。

通过发送前查询 Stripe 当前对象、为通知任务做幂等、在付款后停止催收，并为争议和延迟付款保留人工流程，可以减少顾客困扰和财务错误。上线前逐一测试付款成功、失败、作废、逾期、银行转账处理中以及重复 Webhook 场景。
