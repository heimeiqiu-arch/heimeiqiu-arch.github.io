# Stripe Webhook 重复通知怎么处理？事件去重、重试与乱序排查

接入 Stripe Webhook 后，开发者常会看到同一条支付通知被调用多次，或者先收到“处理中”，后收到“支付成功”，而日志时间和业务预期不一致。若处理器每收到一次请求就直接发货、发邮件或给用户加一次额度，重复投递就可能变成重复履约。若程序只记住“支付成功”便忽略后续事件，又可能漏掉退款、争议或订阅状态变化。

Webhook 是服务端接收异步事件的机制。它不是浏览器跳转，也不是只发送一次的队列消息。Stripe 官方文档说明，事件投递可能因未及时得到成功响应而重试；同一事件可重复投递，不同事件也可能涉及同一个对象。事件之间也不应假设严格按业务先后顺序到达。因此，可靠实现需要同时处理验签、事件去重、状态核对、快速响应、异步任务和对账恢复。

本文面向正在接入 Stripe 的开发者和运营技术团队，重点讲如何设计不因重复通知而重复操作的流程。不同语言框架的具体 API 写法会变化，下面用通用结构解释要点。Stripe 的事件类型、API 版本和 Dashboard 界面也可能更新，部署前应查看当前官方文档，并在测试环境验证。

## 为什么会收到重复 Webhook

网络请求可能在发送方或接收方遇到临时错误。例如，Stripe 已经将请求发出，但你的服务器在处理过程中超时；或者处理完成后，响应在网络中丢失。发送方无法确认接收端是否真正完成工作，就可能按投递规则再次发送。服务器返回非成功状态、响应时间过长、实例重启或临时网络故障，也可能导致重试。

因此，“端点收到两次请求”不等于“Stripe 对客户收了两次钱”。Webhook 代表事件通知，实际支付状态仍需看 PaymentIntent、Checkout Session、Invoice 等对应对象及其状态。开发者应先核对事件 ID、对象 ID、事件类型、创建时间和 Stripe Dashboard 中的交易，再判断是重复通知、重复付款还是业务系统重复创建了订单。

还有一种情况看起来像重复事件，实则是不同类型的事件描述了同一笔交易的不同阶段。例如，支付流程先发生一个状态更新，之后又有支付成功事件；订阅续费可能产生发票相关事件和支付相关事件。单纯按“某个 PaymentIntent 只处理一次”可能会把有意义的后续状态也丢掉。去重粒度必须和事件语义匹配，而不是把同一对象的所有后续更新统统当成重复。

## 先区分事件 ID 和业务对象 ID

Stripe Event 有自己的唯一 ID，常见形式以 evt_ 开头。事件中的 data.object 又有对象 ID，例如 PaymentIntent、Checkout Session、Invoice 或 Subscription 的 ID。两类 ID 解决不同问题：Event ID 用于识别相同事件的重复投递；对象 ID 用于把多个相关事件关联到订单、客户或订阅。

一个常见的实现错误是仅用对象 ID 去重。例如第一次收到 PaymentIntent 成功事件后，数据库记下该 PaymentIntent；几秒后退款或争议相关事件使用同一笔支付对象，如果程序因为对象 ID 已存在就忽略，就会漏掉退款处理。另一个错误是没有记录事件 ID，只依赖“订单已发货”布尔字段；一旦有多个事件类型、并发请求或数据库重试，就很难判断此前处理到了哪一步。

建议在 webhook_events 表或等价存储中保存 Stripe 账户范围、事件 ID、事件类型、对象 ID、接收时间、处理状态、尝试次数和错误摘要。event_id 通常应有唯一约束，防止并发处理时两个请求同时判断“还没处理”并都执行副作用。若采用 Connect 等多账户场景，还要把所属 Stripe 账户或上下文纳入业务关联，避免不同账户中的事件被错误混合。

## Webhook 接收端的基本处理顺序

稳妥的处理器可以拆成接收和业务执行两段：

1. 接收原始请求体和 Stripe-Signature 请求头。
2. 使用正确端点的签名密钥验证请求，验证失败就拒绝处理。
3. 解析事件，提取 Event ID、type、data.object.id 和关联账户。
4. 在数据库事务中登记事件；若唯一键表明同一 Event ID 已登记，则不重复执行。
5. 把事件或可恢复的事件 ID 放入内部任务队列。
6. 尽快向 Stripe 返回成功响应，避免把长时间业务逻辑放在 HTTP 请求内。
7. 后台工作进程加载事件，读取当前对象状态并执行业务逻辑。
8. 保存处理结果和错误信息；失败时按内部重试策略或人工补偿继续。

这只是常见设计模式，团队可以按规模和框架调整。关键是先完成签名校验和可持久化登记，再返回成功；不能先返回 200、随后把事件放进一个可能丢失的内存任务里。进程若在二者之间退出，Stripe 已认为投递成功，你的系统却没有可恢复记录。

如果业务很简单，也可以在请求线程内直接处理，但应设置合理超时、数据库幂等约束和可重试设计，并保证处理失败时返回适当非成功状态。支付后立即调用多个外部服务、生成大文件或等待人工系统，通常不适合阻塞 Webhook 请求。用可靠队列解耦处理，可以缩短响应时间，也能让失败任务可查看、可重放。

## 验签要使用原始请求体

Webhook 签名验证用于确认请求确实来自 Stripe，且请求内容未被中间环节改写。多数 Stripe SDK 的验签方法需要原始请求体、Stripe-Signature 请求头和该端点的 signing secret。若框架先把 JSON 解析后重新序列化，空格、字符编码或字段顺序可能变化，签名校验会失败。应按所用语言 SDK 的说明，在 JSON body parser 改写内容之前保留原始字节。

每个端点、环境和账户应使用对应的签名密钥。测试环境与实时环境的密钥不同；轮换密钥时要遵循 Stripe 当前机制，在过渡期安全配置新旧密钥。不要把 whsec_ 开头的签名密钥写进浏览器代码、公开仓库、日志或工单截图。环境变量和秘密管理工具应限制访问权限，并在泄露后及时轮换。

不要通过关闭验签来“解决”签名错误。先确认请求发到了正确环境的端点，代理层是否截断或重写了请求体，签名头是否完整，以及应用是否使用了与端点匹配的 secret。开发测试时，使用 Stripe CLI 或 Dashboard 提供的安全测试流程，避免手工构造一个没有真实签名的 HTTP 请求后误以为线上逻辑已经验证。

## 正确实现按 Event ID 去重

理想情况下，收到请求后在数据库中原子地登记 event_id。如果数据库已存在相同 event_id，说明很可能是同一事件再次投递；可以返回成功响应而不重复加入业务队列。登记记录应有数据库唯一索引，而不是仅依赖先查询、再插入的两步逻辑。两个并发请求可能同时通过查询，唯一约束才能成为最终保护。

伪代码可以表达为：

```text
verify_signature(raw_body, signature, endpoint_secret)
begin transaction
  inserted = insert webhook_event(event_id, type, object_id, status="received")
             on conflict(event_id) do nothing
  if inserted:
      enqueue durable job(event_id)
commit
return HTTP 200
```

实际系统的事务与队列未必能放在同一个数据库事务里。若先登记数据库、再推消息，进程可能在中间崩溃，形成“登记了但没有排队”的记录。可采用 transactional outbox（事务发件箱）模式：在同一数据库事务里写事件登记和待发送任务，由单独的发布器重试送进队列；也可以周期扫描尚未排队的 received 记录并补发。选择哪种方式取决于业务重要性和基础设施，但必须能从持久化记录恢复。

处理状态不要只用一个布尔值。至少区分 received、queued、processing、succeeded 和 failed，或者设计等价状态。进程异常退出时，应允许过期的 processing 记录重新领取；成功后才标记完成。记录错误摘要、执行版本和最后尝试时间，有助于定位长期失败。对重试次数和失败告警设定边界，避免任务无限静默重试。

## 用业务幂等防止重复副作用

Event ID 去重只解决同一事件再次发送的问题。业务副作用还应使用自己的幂等键。例如，“订单首次支付成功”可以用内部 order_id 加履约动作类型作为唯一业务动作键；“发放一次月度权益”可以由 subscription_id、invoice_id 和权益周期组成键。队列可能重复投递，工作进程可能在外部调用成功后崩溃，因此仅有事件表仍不一定能保证只执行一次。

发货前，在数据库里用事务将订单状态从 awaiting_payment 原子地改为 paid_pending_fulfillment；只有成功完成状态迁移的工作进程才创建履约任务。履约服务也应接受内部唯一订单号或幂等键。发送邮件时，不一定能控制邮件服务绝对只发送一次，但可记录发送尝试并使用供应商支持的幂等能力；若供应商没有这种能力，就应设计重复发送的容忍机制和客服补救流程。

对 Stripe API 发起的写操作，按当前官方 API 文档为可重试请求使用适当幂等键。不要每次重试都生成一个全新键，否则相当于告诉 API 这是新的操作。客户端请求的幂等键和 Webhook 的 Event ID 是不同层次：前者帮助避免重复创建支付等 API 操作，后者帮助识别重复投递的通知。两者可能同时需要。

不要把状态标记和副作用顺序随意颠倒。先发货、后写数据库状态，如果写入失败，重试时可能再发一次货。先写成已发货、后调用仓库接口，如果调用失败又不重试，也会造成漏发。更可靠的做法是用事务状态机和可重试的履约任务，明确区分“准备发货”“已发送请求”“仓库确认”“失败待处理”等阶段。

## 处理事件乱序与当前对象状态

Webhook 可能并不按创建时间或业务顺序到达。一个典型问题是先收到较新的状态，后收到较旧事件；若处理代码每次都把事件快照中的 status 直接覆盖本地状态，就可能让订单从 paid 倒退回 pending。为此，应避免假设事件到达顺序等于对象状态变化顺序。

可根据业务关键事件执行两类处理。第一类是事件驱动的单次动作，例如针对某个 invoice 首次支付成功安排权益发放；用 invoice ID 和周期键幂等即可。第二类是同步某个对象的当前状态，例如维护订阅状态；在必要时使用 Stripe API 按对象 ID 获取最新对象，再根据最新状态更新本地视图。重新读取当前状态会多一次 API 调用，应结合频率、权限、限流和缓存策略使用。

即使拉取当前对象，也需要业务规则定义状态转换。例如，已履约订单不能被一条旧的付款失败事件自动回滚；退款事件应进入退款工作流，而非简单覆盖 paid 字段；争议事件应标记为待审核，而不是删除订单。把交易状态、履约状态、退款状态和争议状态分开建模，通常比用单一 status 字段承载所有含义更容易维护。

对每个事件类型维护明确处理表：哪些事件触发发货、哪些只刷新状态、哪些需要通知、哪些应忽略但记录。Stripe 可能增加事件类型或字段，处理器应对未知类型安全记录并返回成功（前提是已可靠保存），而非因无法识别所有事件而无限失败。关键事件缺少字段时，应记录诊断信息并触发告警，不要静默假定付款完成。

## 如何排查 Stripe Dashboard 显示成功但网站没更新

先从 Stripe Dashboard 找到对应 PaymentIntent、Checkout Session 或 Invoice，记录其对象 ID 和关联事件。然后在开发者 Webhooks 页面找到对应端点的投递尝试，检查事件类型、响应状态、响应时间和错误信息。比较请求时间、内部接收日志、队列消息与订单记录，确认问题发生在“Stripe 未投递”“端点未接收”“验签失败”“没有入队”“后台处理失败”还是“业务状态未更新”哪一段。

如果端点回应 2xx，但订单未更新，重点检查响应前是否已经把事件持久化。若记录存在但任务不存在，查看入队和 outbox 发布日志；若任务失败，检查数据库约束、对象关联、事件 API 版本及外部服务错误。若完全没有记录，确认 Live/Test 模式、端点 URL、选择订阅的事件类型和网络访问。不要只看某条应用日志中的“收到 webhook”，还要核对事件 ID 和最终处理状态。

使用 Dashboard 的重发功能或 CLI 重放事件前，先确认处理逻辑已有幂等保护。否则，人工重放可能再发货、再发权益或重复触发外部通知。推荐先在测试环境使用测试事件，再针对一个已知事件在生产进行受控恢复，并监控订单变化。对账工具和补偿脚本也应按业务对象及唯一键工作，不能简单地对每个失败事件盲目执行整个流程。

## 队列重试、死信和人工补偿

任务队列应对瞬时错误进行有上限的退避重试，例如数据库短暂不可用、下游超时或限流。对永久错误，例如订单不存在、币种不支持或关联数据损坏，应进入可观测的失败队列，而不是每几秒重复相同请求。具体退避参数由业务量和服务限制决定，不应照抄别的项目数字。

失败队列必须有人负责。给支付成功但未完成履约、退款状态未同步、争议通知未记录等关键场景配置告警。告警内容包括事件 ID、对象 ID、内部订单号和失败阶段，但不要包含 secret、完整银行卡数据或不必要的个人信息。设置处理负责人、升级路径和操作记录，避免失败任务长期堆积无人发现。

人工重试前先查看事件处理历史和当前业务状态。若仓库已发货，只是订单页面未更新，正确操作可能是修复状态映射，而不是重新创建发货单。若支付成功但还未发货，则可重新运行安全的履约步骤。补偿动作也要有自己的审核和幂等标识，记录谁在何时执行、影响哪些订单，以及如何回滚或联系客户。

## 权限、隐私和日志留存

Webhook 请求体可能包含客户邮箱、地址、付款对象和业务 metadata。日志只保留排查所需字段，并遵循公司的隐私和数据留存政策。不要把整份请求体长期写到无访问控制的普通日志。事件表应限制读写权限，对敏感字段加密或避免存储，依据实际业务和法规要求设定留存周期。

签名密钥和 API secret 不应写入代码仓库。生产与测试密钥分开管理，员工权限按职责配置。上线前检查反向代理、API Gateway 和 WAF 对请求体大小、方法、路径和请求头的设置，确保不破坏签名验证。对公网端点增加限流和监控，但不要只依赖来源 IP 白名单作为真实性验证；应按 Stripe 官方方式验签。

保存错误信息时，避免在日志里打印完整 secret 或个人资料。创建开发者调试面板时，只展示最小必要信息，并支持按 Event ID、对象 ID 和内部订单号检索。对密钥访问、重放事件和人工补偿操作保留审计日志。

## 上线前的检查单

- 使用 Stripe SDK 按官方要求验证签名，并保留原始请求体。
- 为 Event ID 建立唯一约束，处理同一事件的重复投递。
- 将订单、发票、订阅等对象 ID 与内部业务记录关联。
- 把登记事件与后台任务设计成可恢复流程，避免消息丢失。
- 为发货、权益发放、退款等副作用建立业务幂等键。
- 对事件乱序采用状态机，避免旧数据覆盖新状态。
- 处理器快速返回成功，耗时逻辑放入可持久化队列。
- 为失败任务设置重试上限、死信记录、告警和负责人。
- 在测试环境验证超时、重复投递、签名错误和后台失败场景。
- 重放生产事件前检查当前订单状态和补偿结果。
- 对密钥、客户资料和日志访问实行最小权限。

## 常见问题

### 收到两次相同 Webhook，是 Stripe 扣了两次款吗？

不一定。相同 Event ID 的重复投递通常表示通知重试，不代表产生了两笔付款。核对 Stripe Dashboard 的 PaymentIntent、Charge 或 Invoice，以及内部交易记录。只有出现不同的实际支付对象或银行入账记录时，才进一步调查是否重复收费。

### 只按 Event ID 去重够不够？

不够。Event ID 能识别同一事件的重复投递，但不同事件可能要求对同一业务对象执行不同动作。还需要按订单、发票或订阅周期设计业务幂等，并正确处理状态变化。

### Webhook 接口是不是只要返回 200 就行？

返回成功状态可以告诉 Stripe 该次投递已被接收，但前提是你的系统已经可靠保存事件或可恢复任务。如果先响应再把消息放在内存里，服务器崩溃时会丢掉事件。应优先保证持久化，再尽快响应。

### 是否要为每个事件都重新请求 Stripe API？

不一定。对需要准确当前状态的同步流程，重新读取对象有助于应对乱序；但 API 调用需要考虑限流和性能。对于不可重复的业务动作，事件类型和对象数据可能已经足够。根据具体用例选择并进行测试。

### 事件重放会不会重复发货？

如果没有幂等保护，可能会。重放前确认业务动作键、订单状态和履约系统的幂等能力。先在测试环境演练，再对生产个案进行可审计的恢复。

## 总结

Stripe Webhook 的可靠处理，核心是把通知投递和业务操作分开设计。先验证签名，以 Event ID 唯一登记并持久化，再尽快响应；耗时动作交给可恢复的后台队列。针对发货、退款、订阅权益等建立业务幂等，不要把同一对象的所有后续事件一概忽略。用状态机应对乱序，通过 Dashboard、事件表和队列日志定位失败阶段，并在重放前核实当前业务状态。结合 Stripe 官方 Webhook 文档、所用 SDK 和项目的支付流程做测试，才能减少重复操作与漏处理。
