商家希望客户下一次结账不用重复输入卡片，订阅业务则需要在未来周期自动扣款。Stripe 可以通过 SetupIntent 或带有未来使用设置的 PaymentIntent，保存并准备付款方式后续使用。但“把卡片保存起来”不是单纯在数据库中保留一个 PaymentMethod ID：还涉及客户是否同意、未来是否会在客户不在线时扣款、是否需要银行授权或额外身份验证，以及付款失败后如何让客户完成认证。

本文解释保存付款方式的两种常见集成方式、on_session 与 off_session 的用途差异、客户同意信息和支付方式验证、后续扣款失败处理以及上线测试要点。不同支付方式和地区的授权要求可能不同，Stripe 的 API 能力也会更新，实施时应以当前官方文档和适用规则为准。[Stripe 保存与复用付款方式](https://docs.stripe.com/payments/save-and-reuse) [SetupIntent API](https://docs.stripe.com/api/setup_intents)

## 先确认未来怎样使用付款方式

保存付款方式前，先说明未来付款的场景。客户是否会在结账页面在线并确认每一笔付款？商家是否会在客户离开网站后自动扣款？扣款是订阅周期固定发生，还是使用量达到阈值后触发？付款金额是否固定，还是会因税费、数量或用量而变化？这些答案决定应以何种方式设置付款方式及其后续使用范围。

Stripe SetupIntent 的 `usage` 用于说明付款方式未来使用意图。官方 API 对象指出，如果只在客户仍处于结账流程中时使用，可选 on_session；如果未来客户可能不在结账流程中，则使用 off_session。未提供时文档给出的默认值为 off_session，但工程实现不应依赖默认值猜测业务意图，最好明确设置并测试。[SetupIntent 对象参考](https://docs.stripe.com/api/setup_intents/object)

“客户已在线保存卡片”不自动等于“客户授权商家未来任意时间、任意金额扣款”。产品应向客户说明保存目的、后续扣款类型、频率或触发条件、取消方式，并获得适当同意。订阅合同、结账确认和付款方式保存选项应使用一致的说明，不要把笼统的“记住我的卡”当作无限范围的未来收费授权。

## SetupIntent 适用于单独设置付款方式

SetupIntent 用于设置和验证付款方式，但本身不收取一笔购买金额。它适合客户在账户设置页先添加卡片、订阅开始前准备付款方式，或商家需要在收费之前完成支付方式认证的场景。SetupIntent 经由客户端确认时，可能需要客户完成额外步骤，例如银行跳转或强客户认证；应用应根据 Intent 状态继续引导，不能只看请求是否创建成功。

SetupIntent 应关联到正确的 Stripe Customer，使完成的 PaymentMethod 附加到相应客户。服务端根据登录用户查找内部 Customer 映射，不要接受浏览器随意传入其他客户 ID。确认完成后，读取 SetupIntent 的状态和 PaymentMethod，确保设置成功；如果状态是 requires_action 或 requires_payment_method，说明用户还没有完成设置或需要补充方法。

如果客户只是希望保存卡片用于后续在线结账，设置用途应与该意图一致；如果未来要自动扣款，则应按 off-session 场景建立流程，并确保相应授权和支付方式规则满足要求。银行账户、钱包和本地支付方式的可复用条件可能与卡片不同，不能把卡片方案无差别应用到所有支付方式。

## PaymentIntent 收款时同时准备未来复用

如果客户当前正在付款，商家可以在 PaymentIntent 上配置未来使用行为，使本次付款与后续复用衔接。Payment Element 也可展示保存付款方式的复选项；Stripe Customer Session 的相关配置会影响保存选项以及未来使用设置。用户勾选与否应由实际交互决定，服务端不要假定每位客户都同意保存。[Customer Session 对象](https://docs.stripe.com/api/customer_sessions/object)

这种流程的优点是客户完成一次真实付款时即可完成付款方式设置，减少独立添加步骤。但若当前付款失败、客户取消认证或不勾选保存选项，后续不能仍然按“已准备好自动扣款”来处理。应用应读取 PaymentIntent 与 PaymentMethod 的实际状态，并保存用户选择和授权记录。

另一个关键点是“设置成功”与“本次付款成功”是不同状态。PaymentIntent 可能需要验证、处于处理中或失败；SetupIntent 也可能成功设置付款方式但没有收取任何金额。数据库中应分别保存付款交易状态和付款方式设置状态，客服和重试逻辑才不会把两者混为一谈。

## 用户同意和授权记录

在结账或账户设置页面，说明保存行为和未来收费方式。对于订阅，可以明确展示每期金额、周期、首次收费日期、后续自动续费以及如何取消；对于不固定金额的后续扣款，应说明金额计算依据和触发条件。不同地区与支付方式的授权要求并不完全相同，商家需结合合同条款与专业意见设计文案。

保存同意记录应足以重建当时的用户选择，例如用户 ID、Customer ID、同意发生时间、使用目的、页面文案版本、所选付款方式和授权类型。不要保存敏感卡号或安全码来证明同意；这些支付数据应由 Stripe 安全处理。记录的目标是证明用户对业务条款的选择，而不是复制付款凭证。

如果用户取消订阅或删除付款方式，应用也要更新后续自动扣款策略。移除付款方式后，已有订阅可能无法按原计划收款；应提醒客户提供替代方式或选择其他处理方式。不要因为一个 PaymentMethod ID 仍留在本地数据库，就认为它仍有效、仍被授权或可以继续使用。

## Off-session 后续扣款与认证

Off-session 表示客户不在当前支付页面或应用交互中。商家尝试自动扣款时，Stripe 可能成功，也可能因余额不足、卡片失效、风险拦截或要求认证而失败。正确设置未来用途可以帮助支付网络识别付款方式的预期用法，但不保证之后每次都成功，也不免除客户在某些情形下重新认证的需要。

处理后续扣款时，基于 PaymentIntent 或发票支付结果创建明确的状态机。成功后更新账单；失败后区分可重试、需要客户操作和永久拒绝等情况。若需要客户完成 3DS 或其他验证，应提供安全的回到应用路径，让客户在在线状态下完成，而不是后台无限重复尝试。订阅的发票重试规则与邮件通知也应与产品宽限期一致。

不要把每种失败都立刻触发“换卡”提示。有些失败是暂时性网络错误，有些需要银行认证，还有些可能是客户账户余额不足或支付方式不支持该使用场景。根据 Stripe 返回的状态和错误类型提供具体下一步，避免暴露不必要的风控信息。真实收款状态应以 Stripe 的支付对象与发票为准。

## 数据模型和多付款方式

一个 Customer 可能关联多个 PaymentMethod，订阅也可能有自己的默认付款方式。客户在设置页更新默认卡后，不能假设所有既有订阅都会使用新卡。系统应明确客户级默认方式与订阅级默认方式的优先关系，并在创建或更新订阅时设定预期的付款方式。

建议内部保存 Stripe Customer ID、PaymentMethod ID、设置来源、设置状态、使用意图、授权记录索引和最后确认时间。不要将卡号、CVC 或银行登录凭据保存到自己的系统。展示时仅使用 Stripe 返回的安全摘要字段，例如品牌和末四位，并在必要时标记“即将过期”或“需要更新”。

用户可能删除或替换某个付款方式。Webhook 同步付款方式附加、更新和删除事件，定期核对本地默认方式是否仍可用。若一个 Customer 由多个产品或订阅共享，更新默认方式的影响范围要向用户解释清楚，避免某个业务的付款配置意外改变另一个业务的扣款。

## 常见问题排查

**付款方式已显示在账户里，订阅还是扣款失败。**检查 PaymentMethod 是否附加到正确 Customer，订阅是否指定了另一个默认方式，是否需要在线认证，以及实际发票的付款结果。不能从“卡片已保存”推断它一定可用于这张订阅发票。

**用户没有勾选保存，后台却尝试后续扣款。**检查前端复选项与服务端请求参数是否一致，是否在创建 PaymentIntent 时默认设置未来用途，以及本地是否错误地把用户默认选择记为同意。修正后应审查受影响的授权记录。

**SetupIntent 创建成功但卡片没有保存。**确认 SetupIntent 已成功确认、PaymentMethod 有效并附加到预期 Customer。对象创建成功并不等于设置流程已完成。

**后续付款需要客户验证。**检查支付对象的状态和下一步动作，引导客户在线完成认证。不要重复创建新付款对象来绕过已有认证流程。

**客户删除卡片后仍收到续费失败通知。**核对订阅的默认付款方式、Customer 默认方式和账单重试规则，确保客服能区分卡片删除与扣款拒绝。

## 上线检查清单

1. 说明保存方式的用途及未来扣款规则。
2. 区分 SetupIntent 设置和 PaymentIntent 收款。
3. 根据在线或离线使用场景明确 on_session 或 off_session。
4. 服务端验证用户与 Stripe Customer 的映射。
5. 明确记录用户授权和付款方式选择，不保存敏感卡数据。
6. 处理 requires_action、processing、失败和成功等状态。
7. 验证客户级与订阅级付款方式的优先顺序。
8. 设计自动扣款失败、再次认证和更新卡片的流程。
9. 同步付款方式变更和删除事件。
10. 在测试模式覆盖不同支付方式、浏览器返回和 Webhook 重试。


## 付款方式类型和授权差异

不要假设所有 PaymentMethod 都支持相同的未来使用模式。信用卡、借记卡、银行账户和本地支付方式在授权、结算时间、验证方式和客户可撤回授权方面可能不同。某种支付方式能够在结账页完成一次付款，并不代表它适合自动续费或可在客户不在线时再次使用。上线前应按目标国家、币种和支付方式建立支持矩阵，确认其可用于当前产品的收费场景。

银行账户可能需要微额存款验证或金融连接认证，完成输入不等于账户所有权已经验证。客户应能看到验证进度和预计耗时，后台则要基于 SetupIntent 或相关对象的最终状态决定是否启用付款方式。若验证失败，提示用户更换方式或重新进行验证，并避免以未验证账户执行不适当的收款尝试。

对于付款方式设置和首笔付款共用一个页面的场景，明确区分当前订单金额与未来扣款承诺。用户可能只想完成本次购买，并不希望保存付款方式；若保存为默认勾选，应确保授权文案足够清楚，并让用户能够作出真实选择。保存后的确认信息可以说明付款方式已添加、将用于哪个订阅以及如何管理，减少客户对后续扣款来源的疑问。

## 订阅和发票收款的衔接

如果订阅通过自动收款方式计费，创建或更新订阅时需要核对默认付款方式、收款设置和发票行为。发票失败后，应用应提供更新付款方式的入口，并在支付方式更换后按合理规则重试或由客户主动支付。不要在一次失败后不断创建新的订阅或 Invoice，以免重复收费或留下多个未付款对象。

若发票采用发送账单而不是自动扣款，保存付款方式可能仍用于客户在 Hosted Invoice 页面主动完成付款，但这不等于发票会离线自动扣取。客服和界面应根据 Invoice 的 collection_method 与实际付款对象解释下一步。区分“已设置未来可用方式”“当前发票等待客户支付”和“自动扣款已成功”，能够避免许多账单争议。

订阅升级可能触发即时发票或按比例调整。客户此前同意某种周期性收费，不代表任何临时费用都无需解释。变更价格或数量前，展示预计金额并在必要时重新取得客户确认；随后以真实发票明细记录最终收费。数据库保存订阅 ID、付款方式 ID 和每笔发票 ID 的关联，方便退款和对账。

## 迁移、更新与删除流程

当客户替换付款方式时，应先确认新方式验证成功，再决定是否设为默认。若替换过程中发生失败，旧方式是否继续保留应由产品策略决定，但要清楚显示哪张方式会被用于下次续费。对于将过期的卡片，可以提前通知客户更新，不要等续费失败后才让客户发现账户失效。

客户删除付款方式时，检查它是否仍是活动订阅或未付发票的唯一可用方式。界面可以阻止删除并要求先添加替代方式，也可以允许删除但明确说明自动续费可能失败。无论选择哪种方案，都要让用户完成明确动作并记录结果。删除卡片不能等同于取消订阅，取消订阅也不一定会删除已保存付款方式，两者应提供独立且清楚的操作入口。

如果客户在多个设备或标签页并行管理付款方式，后端要应对状态竞争。使用更新后的 Customer 和 Subscription 对象判断默认方式，避免较旧页面把新方式覆盖回去。更新成功后刷新前端摘要并保存变更事件，以便用户看到一致的卡片末四位和下次账单状态。
## 总结

Stripe 保存付款方式既可以通过 SetupIntent 单独设置，也可以在 PaymentIntent 收款过程中准备未来复用。选择方式之前，应先明确付款发生时客户是否在线、未来收费的频率和条件，再配置相应使用意图并清楚取得客户授权。付款方式设置成功不代表后续扣款保证成功；自动扣款仍需处理认证、失败重试、客户更新卡片和订阅级默认方式。

接入时可查阅 [保存和复用付款方式指南](https://docs.stripe.com/payments/save-and-reuse)、[SetupIntent API](https://docs.stripe.com/api/setup_intents) 和 [Customer Session API 对象](https://docs.stripe.com/api/customer_sessions/object)，并用测试模式验证设置、复用、认证及失败恢复的完整流程。
