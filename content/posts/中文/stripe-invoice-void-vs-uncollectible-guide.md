Stripe Invoice 长期未付款或不再需要时，商户可能会看到 void 和 uncollectible 两种处理选项。它们都能结束某些发票的正常收款流程，但业务含义不同：void 通常用于取消一张不再应向顾客收取的发票；mark uncollectible 则通常用于记录一笔仍未收回、但商户决定按坏账或不可收款处理的应收款。选择错误会影响财务报表、客户欠款记录、订阅状态和顾客收到的说明。

本文通过典型场景比较两种状态，说明在操作前应查看发票状态、付款记录、合同依据和订阅关系，并梳理 Webhook、余额、税务及后续恢复流程。具体会计处理因地区和企业政策不同而异，Stripe 的状态字段不会代替商户作出坏账核销或税务判断。不要仅为了消除 Dashboard 的未付款提醒，就随意将发票作废或标记为坏账。

## 先看 Invoice 当前状态

Stripe Invoice 常见状态包括 draft、open、paid、uncollectible 和 void。操作前先通过 Dashboard 或 API 读取当前对象、应付金额、已付金额、剩余金额、订阅关联和最后一次付款尝试。若发票仍是 draft，可能可以修正或删除草稿；若已 paid，void 或 uncollectible 不能替代退款或贷项通知；若 open，则需要进一步判断债务是否仍然有效。

也要检查是否有部分付款、Customer Balance 抵扣、Credit Note、Refund 或还在处理的 PaymentIntent。发票页面上显示未结余额，不一定代表顾客完全没有付款。若存在外部银行转账或线下收款，先由财务核实资金到账，再选择相应的对账方式，避免把已收款发票错误标为坏账。

一旦 Invoice 转为正式状态，某些操作不能像改草稿一样随意编辑。保留 Invoice ID、Customer ID、Subscription ID、金额、币种、到期日和付款历史，后续状态更新应使用 Stripe 支持的对象操作，并通过 Webhook 同步。

## 何时考虑 void

void 适合发票不应继续向顾客收取的情形，例如商户误开了重复发票、订单被取消且合同约定取消账单、发票内容需要按业务规则撤销，或双方已经确认该交易不再继续。它表示这张发票不再作为一笔待收应收款继续处理。具体能否对当前状态 void，应按 Invoice API 和 Dashboard 支持范围核实。

在作废前确认客户没有已经支付或仍在处理中。若钱已经收取，不能只 void 发票来代替退款；应检查 Charge、PaymentIntent 和 Refund，并通过适当流程处理已收资金。若只是部分收款，需先确定未付余额和已收款如何分别处理。

作废也不能代替发票更正或贷项通知。如果交易实际发生但原发票金额有错误，商户可能需要修订、重新开票或创建 Credit Note，而不是把真实交易当作从未存在。保留作废原因、内部订单和客户沟通，便于财务解释为何该发票被关闭。

## 何时考虑 mark uncollectible

mark uncollectible 常用于应收款确实存在、商户经过催收后认为不太可能收回，并根据财务政策记录为不可收取或坏账的情况。发票仍有其原始金额和历史，只是被标记为无法收回。该状态不等同于顾客已经支付，也不应向客户描述为“债务自动免除”，除非商户的法律和业务政策另有规定。

财务通常需要确定催收步骤、逾期天数、客户争议、合同责任和坏账审批后，才将发票标记为 uncollectible。是否核销、何时核销及是否仍可追偿是商户会计和法律政策，不应仅根据 Stripe 的 API 选项作决定。高金额或争议中的发票可要求主管审批。

标记后应同步内部应收账款、坏账准备和订阅服务状态。不要因为发票被标记为 uncollectible，就忽略顾客仍可能付款或提出争议的事实。若顾客后来付款，按 Stripe 当前支持流程和财务政策处理，不要假设所有未收款状态都可以直接恢复成原来流程。

## Void 和 uncollectible 的区别概览

Void 的核心是取消这张不应继续收款的发票；uncollectible 的核心是保留这笔未收应收款并记录其无法收回。Void 更像是“停止这张错误或取消的账单”，uncollectible 更像是“该账款仍存在历史，但目前按不可收取处理”。它们均不是 Refund，也不是 Credit Note 的同义词。

对客户沟通也不同。Void 后可以说明该发票已取消，不需要付款；uncollectible 则可能代表商户已经按坏账流程关闭常规收款，但债务处理仍受合同和法律约束。客服不得擅自承诺“欠款已免除”，财务也不应把 uncollectible 误当成收入已到账。

数据报表应分别统计两种结果。Void 发票通常从当前应收中移除；Uncollectible 发票用于记录坏账相关状态。具体收入确认和坏账核销必须依企业会计政策和当地规则决定。Stripe 状态给出的是账单运营状态，不是完整的总账科目结论。

## 订阅、续费和服务权益影响

如果发票来自订阅，标记或作废某一张 Invoice 不一定自动取消 Subscription。订阅可能继续生成后续发票，或根据支付失败和取消策略转为 past_due、unpaid、paused 或其他状态。操作前读取 Subscription 当前状态、collection method、重试规则和下一个账期。

若商户决定顾客不再使用服务，应分别处理订阅取消和相关发票。只 void 旧 Invoice 但保留订阅，可能下期又产生一张新账单；只取消订阅也不一定自动处理已经产生的未付款发票。两项操作应有清晰业务顺序和顾客通知。

如果发票金额错误但订阅仍有效，确认价格、数量、Proration 和下次账单设置。需要调整未来续费时更新 Subscription Price 或取消安排，不能靠作废当前发票永久修复错误价格。通过测试客户验证更改后的下期 Invoice。

## Customer Balance、Credit Note 和退款关联

Customer Balance 可能抵扣后续 Invoice，Credit Note 可能减少某张已最终化发票的应付金额，Refund 则返还实际收取的资金。void 或 uncollectible 不能替代这几种操作。选择动作前，确认发票是否有贷项、实际收款和客户余额交易，并在账务系统记录它们之间的关联。

若重复发票尚未收款，作废多余的那张可能合适；若重复扣款已经发生，则需要同时查退款，不能只把发票状态变成 void。若顾客因服务质量收到补偿，商户要决定使用 Credit Note、Customer Balance 还是现金 Refund，并按照对应流程处理发票和资金。

对税务发票而言，取消、修订和贷项可能有法定文件要求。不要通过手工修改 Invoice PDF 或删除发票记录来消除错误。保存原始文件、调整文件、顾客沟通及财务审批，确保税务报告和客户账户能够解释最终金额。

## 操作前的审批和审计

建立清晰的授权矩阵：谁可以 void 草稿或正式发票，谁可以标记 uncollectible，哪些金额需要经理审批，客户异议和退款应由谁处理。后台应显示发票是否已收款、是否有部分付款、是否关联订阅或 Credit Note，减少客服凭名称或旧邮件误操作。

每次操作都保存操作人员、时间、原因代码、原 Invoice ID、内部订单号和审批记录。原因应具体说明是重复账单、订单取消、错误金额还是坏账核销，避免所有操作都写“其他”。若顾客提出争议，附上工单或合同信息，让后续财务能追溯决策依据。

对批量处理设定上限和预览报告，操作前列出将受影响的 Invoice ID、Customer、余额、订阅和状态。小心循环中把多个 Customer 的发票都一并处理。批量 API 操作应分批执行并监控 Webhook，发现异常就停止后续批次。

## Webhook 和本地状态同步

可以根据集成需要监听 invoice.voided、invoice.marked_uncollectible、invoice.paid、invoice.payment_failed 等事件。具体事件名称以 Stripe 当前文档为准。Webhook 验证签名并使用 event.id 去重；处理事件时还要读取 Invoice 当前状态，防止旧的付款失败事件覆盖了后续已作废或已付款的结果。

本地数据库要把 void 和 uncollectible 作为不同状态，不要都映射成 cancelled 或 closed。保留原始发票金额、已收金额、剩余金额、收款方式和状态变化时间。若财务调整与 Stripe 对象状态暂时不同步，使用重试队列和定期对账，不要直接手工改数据库掩盖事件失败。

订阅权益应按商户规则和 Subscription 的当前状态判断。发票标记坏账时，是否暂停账户是业务政策；作废发票时，是否恢复服务也取决于是否存在其他待付款账单。把发票状态和服务权限分开存储，能避免一个状态误更新导致顾客突然被停服或继续免费使用。

## 常见问题排查

如果 void 按钮不可用，查看 Invoice 当前状态、是否已经付款、是否有部分付款或是否已作废。若发票已经收款，改查 Refund 或 Credit Note；若草稿尚未最终化，可以先核对是否需要修正或删除草稿。

如果标记为 uncollectible 后顾客仍收到付款提醒，检查催收规则、Invoice 当前状态、订阅自动化和异步任务。确认提醒任务读取了最新 Invoice 状态，且 Webhook 消费成功。停止重复提醒前要核实客户是否仍有其他开放发票。

如果订阅仍继续收费，检查 Subscription 是否取消、是否有计划更新、下期 Invoice 是否已创建以及是否存在多条 Subscription。作废一张历史账单并不会自动阻止所有未来账期。停止未来收费时按订阅生命周期流程操作。

若无法决定 void 还是 uncollectible，回到业务事实：这张发票是否真实应收？顾客是否已付款？商户是否仍计划追收？合同是否取消？财务是否批准坏账？根据答案选择正确账务操作，必要时由会计或法律顾问确认。

- 订阅 Invoice 作废后下一期是否仍会产生账单。
- 坏账状态下客户提醒和服务权限变化。
- Credit Note、Refund、Customer Balance 和状态操作的组合。
- invoice.voided、invoice.marked_uncollectible 等 Webhook 重复与乱序。
- 审批权限、批量操作预览和操作原因留存。
- 报表分别统计取消发票、坏账和已退款金额。
- 测试环境和实时环境的对象与密钥隔离。
- 顾客邮件与 hosted invoice page 状态符合后台记录。

## 逾期前的催收和坏账审批流程

将发票标记为 uncollectible 之前，商户通常应依据自己的应收政策完成必要的催收步骤：确认发票已正确送达，联系客户核对金额和付款方式，处理对方提出的账单异议，检查是否已通过银行或其他方式付款，并记录最后一次跟进时间。客户暂时没有回复不一定意味着该应收款可立即核销，尤其是合同仍有效、争议尚在处理中或付款正在清算时。

财务可以根据账龄报告区分刚逾期、持续逾期和已批准坏账的账单。为不同账龄设定提醒和升级流程，但每次催收都要查询发票当前状态，避免在付款成功、作废或贷项完成后继续催款。对于企业合同，可按照付款期限和争议处理条款安排沟通；对消费者订单，则遵循顾客条款、当地消费者保护规则和企业的收款政策。

核销审批中应附上原始 Invoice、交付或服务证据、客户往来、最后付款尝试、贷项和退款记录。批准人确认该笔债务是否仍有追收价值、坏账会如何进入会计报表，以及是否需要关闭订阅或服务。Stripe 把状态改为 uncollectible 不会自动替商户完成总账核销、税务冲销或法律债权豁免，这些步骤要由财务流程另行决定。

## 取消订单与作废发票

订单取消并不总意味着发票应 void。如果顾客已经收到商品或服务，商户可能仍有部分应收款；如果只取消未来履约，原本已完成部分可能仍应开票。先拆分已履约和未履约金额，查合同中的取消政策，再判断发票是否全额作废、部分通过 Credit Note 调整，或保留应收金额。取消订阅也要分别处理已产生发票和未来续费。

订单系统应保留取消原因、发生时间、批准人和受影响的 Invoice ID。若顾客的请求仅是停止下期续费，不能把已提供服务的当期账单一并 void；若商户误开了新发票，也不要取消正确的那张。建立订单与 Invoice 的一对多关联，可避免只按顾客或金额误操作。

## 自动化和重试边界

自动催收任务需要读取最新 Invoice 状态后再发送提醒或重试付款。即使某个队列任务已经排队，财务人员也可能刚刚 void 或标记为 uncollectible；消费者在任务运行前可能已付款。使用幂等操作和状态条件更新，确保不会对已经关闭的发票继续收费或催款。

对 uncollectible 发票若商户后续批准继续追收，应检查 Stripe 当前支持的重新打开、修订或新开发票流程。不要假设把状态字段改回 open 就能恢复原对象。需要创建新发票时，关联原账单和剩余应收款，并确保不会重复计算同一服务期。

## 月末报表的核对

月末分别核对应收余额、已付款发票、作废金额和不可收款金额。将 Stripe Invoice 状态与会计系统分类对照，并抽查大额和长期逾期记录。若发票处于 uncollectible，仍需按企业政策确认是否纳入坏账准备或正式核销，不能仅从 API 状态直接推导总账处理。

## 月末报表的核对

月末分别核对应收余额、已付款发票、作废金额和不可收款金额。将 Stripe Invoice 状态与会计系统分类对照，并抽查大额和长期逾期记录。若发票处于 uncollectible，仍需按企业政策确认是否纳入坏账准备或正式核销，不能仅从 API 状态直接推导总账处理。保存差异清单和复核负责人。

## 总结

void 和 uncollectible 都会改变未付款 Invoice 的后续处理，但业务意义不同。Void 常用于不再应向顾客收取的发票；uncollectible 则记录一笔仍未收回、按坏账或不可收款处理的应收款。两者都不能代替退款、Credit Note 或订阅取消。

操作前先核实 Invoice 状态、付款与贷项、订单和订阅关系，再按财务政策审批并记录原因。同步 Webhook、本地账务和顾客通知时保留这些状态的区别，避免重复催款、错误核销或仍在续费的订阅继续产生账单。
