商户在 Stripe Dashboard 启用了 Apple Pay 或 Google Pay，却发现顾客打开 Checkout 页面时没有看到对应按钮，常会以为集成代码没有生效。实际上，数字钱包按钮通常受到账户和地区支持、顾客设备、浏览器、钱包是否已经配置、交易币种以及集成模式等多项条件影响。商户后台显示“已启用”，并不意味着每个访问者、每台设备和每笔付款都一定展示该选项。

排查时应先复现具体顾客的设备、浏览器、地区和订单设置，再检查 Stripe 账户和实际 Session，而不是在生产环境反复切换付款设置。本文按从外到内的顺序，说明 Apple Pay、Google Pay 在 Stripe Checkout 中可能不显示的原因、如何使用测试环境验证，以及如何向顾客提供稳定的备选付款方式。钱包功能的支持条件可能随产品和浏览器变化，实施时请核对 Stripe 与钱包提供方的最新官方说明。

## 钱包按钮为何不是固定展示

Checkout 会根据已启用的付款方式以及当前交易条件呈现可用选项。Apple Pay 和 Google Pay 需要顾客的设备、浏览器或钱包环境能够使用该方式。若顾客在不支持的设备上访问，钱包未添加有效银行卡，浏览器环境无法访问钱包，页面可能只显示银行卡表单或其他支持的付款方式。

商户不能把“我自己的手机看得到”推断为“所有顾客都能看到”。一个顾客使用支持的钱包和浏览器，另一个顾客从社交软件的内置浏览器或桌面环境打开链接，看到的支付选项可能不同。测试前应记录完整环境，而不只记录操作系统名称。

动态付款方式也意味着 Stripe 可能根据交易和顾客环境自动展示相关方式。若 Session 创建时显式限定了 payment_method_types，商户配置可能缩小可选范围；若使用动态付款方式，Dashboard 设置仍需要正确，但界面最终展示也可能因顾客端条件而不同。

## 从顾客设备和浏览器开始

Apple Pay 通常需要受支持的 Apple 设备和浏览器环境，并且顾客已在钱包中设置可用的付款卡。Google Pay 也需要兼容的设备或浏览器、有效的 Google Pay 钱包状态和可用卡片。具体可用范围由钱包提供方和 Stripe 集成方式决定，不能将某一国家或设备的测试结果视为全球结论。

请记录顾客访问页面的设备类型、操作系统、浏览器和打开方式。特别留意应用内置 WebView、隐私浏览模式、浏览器扩展、严格的跟踪保护以及企业设备策略，这些都可能影响钱包脚本或钱包状态。若顾客从应用内点击付款链接，建议用系统浏览器重新打开作对照，而不要先要求他们删除钱包或重装支付应用。

检查顾客是否已在相应钱包中添加有效付款方式，国家或地区是否可用，设备日期时间是否正常。商户客服不要索取顾客的完整卡号、钱包密码或短信验证码来协助测试。可以指导顾客通过操作系统或钱包的官方界面自行查看卡片设置。

## 检查 Stripe Dashboard 付款方式设置

在 Stripe Dashboard 中确认 Apple Pay 和 Google Pay 已在当前账户的付款方式设置中启用，并核对账户所在国家、业务类别和测试或实时模式。不同模式使用不同数据和密钥；在测试环境启用某项方式，不等于实时环境也已可用，反之亦然。

检查设置变更是否已经保存，并确认正在测试的是同一个 Stripe 账户、正确的账户上下文和正确环境。若使用 Connect，付款可能发生在平台账户或 connected account 下，付款方式配置和域名注册也要对应实际处理交易的账户。只在错误账户中打开开关，顾客页面不会因此自动显示选项。

若 Dashboard 提示需要补充资料或完成设置，先处理该账户要求。支付方式是否能启用，可能受账户国家、业务、产品和监管条件限制。不要通过伪造商户资料、使用他人账户或绕过账户审查来使按钮出现。

## 域名和钱包配置

部分钱包流程要求商户验证网站域名或完成钱包专属设置。对 Apple Pay 等方式，检查 Stripe Dashboard 中域名注册状态和所用主机名是否完全一致。若网站同时存在根域名、www 子域名、支付子域名和测试域名，需要按实际接入要求确认哪些域名分别需要注册。一个子域名已验证，不应假设其他所有域名都会自动通过。

如果最近更换了主机名、CDN、网站平台或 Checkout 集成模式，回看域名验证文件、DNS 和账户设置是否仍有效。验证文件必须放在提供方要求的位置并可公开访问；服务器重定向、访问控制、缓存规则或大小写路径错误都可能使验证检查失败。检查过程不要把密钥或内部配置文件开放到公共网站。

Stripe 托管 Checkout、Payment Element 和自定义域名设置的具体要求可能并不相同。照着旧版教程配置自定义 Checkout 域名后，应重新核对当下产品文档和 Dashboard 状态。不要将一个钱包的域名验证步骤套用到另一种钱包或另一种集成模式。

## 核对实际 Checkout Session 配置

从服务端创建 Session 时，确认使用的 mode、currency、line_items、payment_method_types 和 dynamic payment methods 设置符合预期。如果代码明确只允许 card 或某个特定付款方式组合，钱包选项可能不会按商户期望出现。不要直接复制一段早期的固定付款方式数组，而忽略当前 Dashboard 的动态配置。

读取实际创建的 Session 对象，确认配置已经应用到该次交易。只检查开发分支里的代码或后台开关并不够，因为生产服务器可能运行了旧版本、使用不同环境变量或请求发送到另一 Stripe 账户。可将 Session ID、订单号、环境和创建时间写入安全日志，便于追踪。

如果顾客打开的是 Payment Link，设置来源是 Payment Link 对象；如果由服务器创建 Checkout Session，则设置来源可能在每次 Session 请求中。确认实际 URL 是最近生成的链接，旧链接可能仍使用旧配置。不要为测试不断生成真实付款请求，使用 Stripe 测试模式并记录测试对象。

## 币种、国家和付款方式条件

交易币种、商户账户国家、顾客所在地区和支付卡支持情况可能影响付款方式是否可用。先确认 Stripe 当前支持的币种和钱包组合，再用同一币种、同一商品和同一测试环境比较不同设备。测试中变更多项条件时，一次只改变一个变量，才能知道是什么因素导致显示差异。

不要假设只要消费者使用美元或欧元，钱包选项就一定可见。钱包提供方和 Stripe 对支付方式资格有各自规则，还可能根据设备、浏览器和账户状态过滤选项。对于跨境销售，应分别测试目标市场，不要把单一国家的验证结果作为整体上线证明。

若某个顾客看不到钱包，可以让其使用银行卡或其他已启用的付款方式继续支付。提供备选方式比阻止顾客结账更稳妥。商户不要为了让钱包显示而随意更改订单币种，因为这会影响顾客最终扣款货币、换汇成本、退款金额和财务对账。

## 测试环境与实时环境的区别

测试模式适合验证集成逻辑和事件处理，但钱包测试能力、界面展示和真实设备钱包可能不完全等同。先按照 Stripe 官方自动化测试文档完成可自动化的状态用例；真实设备钱包检查则应使用受支持的账户和设备，并遵守对应测试方法。不要用测试卡号输入到真实钱包，也不要在真实交易中用一笔收费来试验按钮是否出现。

测试时应为每个场景记录期望与实际结果，例如“iPhone Safari、测试模式、某币种、Checkout Session ID”。检查 Dashboard 中账户模式、支付方式状态和对象详情。只凭截屏很难判断问题发生在账户资格、Session 参数、浏览器环境还是钱包配置。

上线前需要在实时模式确认账户和支付方式正式具备处理资格，但不要为了测试而向自己或顾客发起未经说明的真实收费。可按 Stripe 支持的验证方式、真实业务沙箱和内部订单流程进行检查；若确实需要小额真实交易，应先遵守公司财务审批和退款流程。

## Checkout、Payment Element 与不同界面模式

Stripe Checkout 是托管结账体验，Payment Element 则嵌入在商户页面或应用中；Express Checkout Element 还提供特定钱包的快速按钮。不同界面组件有各自的显示条件、初始化步骤和域名要求。排查时先确认实际使用的是哪种产品，不要把 Checkout 的配置说明用到 Elements 上。

如果使用 Payment Element，检查组件是否在页面加载时正确初始化、是否传入当前 PaymentIntent 或 SetupIntent 对应的 client secret、支付方式动态配置是否允许钱包方式。若使用快速结账元素，核对元素是否挂载到正确容器、事件监听是否工作、页面是否在安全的 HTTPS 环境下运行。此类前端故障有时会让钱包按钮消失，但不能由“按钮没有出现”单一现象直接判断。

组件升级、Content Security Policy、脚本加载顺序和站点 CSP 也可能影响钱包脚本。检查浏览器控制台和网络面板的具体错误，同时避免把顾客 client secret 或其他敏感值贴到公共论坛。需要与 Stripe 支持沟通时提供对象 ID、环境、浏览器版本和脱敏错误信息即可。

## Apple Pay 与 Google Pay 的保存和再次使用

首次通过钱包完成一次交易，不代表以后付款页面会始终把它显示为已保存卡片。钱包支付方式有自己的交互和重复使用限制。Stripe 对已有客户 Checkout 页面中的已保存支付方式也有相关规则，Apple Pay 和 Google Pay 不一定会作为可复用的已保存卡片出现在后续会话列表里。

若想在后续交易中复用支付方式，应采用 Stripe 支持的 Customer、PaymentMethod、SetupIntent 或 Checkout 保存流程，并取得顾客对该用途的授权。顾客同意保存付款方式的范围应符合当地法律和卡组织规则；商户不能仅因顾客使用钱包付款就推断其同意未来免操作扣款。

对周期性或非现场付款，要单独核对顾客授权、setup_future_usage、付款方式和后续认证要求。不要将 Apple Pay 或 Google Pay 的一次性授权误认为订阅未来扣款已经配置完毕。给顾客提供账户管理入口和更新付款方式的安全路径。

## 常见问题的逐步排查

第一步，复现顾客环境并记录设备、浏览器、打开方式和地区；第二步，确认 Dashboard 中对应账户和模式已启用目标钱包；第三步，检查域名验证和账户资料；第四步，读取本次 Session 或 PaymentIntent，核对币种、付款方式列表及相关配置；第五步，在另一个受支持设备上用同一配置做对照。

若只有某一个浏览器不显示，优先检查浏览器和钱包状态；若任何设备都不显示，检查账户配置、Session 参数、域名或当前集成方式；若测试环境正常而实时环境不行，检查两边 Dashboard 配置、账户资格与密钥。这个判断只是排查方向，最终要以实际对象状态和错误信息确认。

如果按钮以前存在而最近消失，回顾近期发布、Dashboard 设置变更、域名迁移、API 版本升级和前端 CSP 改动。建立变更时间线后，可以缩小故障范围。不要同时修改多个生产设置，否则即使恢复了也无法知道真正原因，后续问题可能继续出现。

## 给顾客的提示和支付失败兜底

支付页面应让顾客知道钱包方式会根据其设备与浏览器而变化。若钱包按钮未显示，仍提供银行卡或其他受支持的支付方式。错误文案应表达事实，例如“此设备暂时无法使用该快捷支付方式，请选择银行卡或其他方式”，而不是断言顾客的账户、手机或卡片有问题。

如顾客更换设备或浏览器，确保订单上下文安全保留，并再次核验订单尚未支付。超时后不要创建多笔同时有效的支付请求；先查询原 Session 和 PaymentIntent 状态。用户切换付款方式时，如果之前的钱包尝试已进入处理中，应等待最终结果或按支付状态机处理，而非立即重复收费。

客服应了解钱包选项依赖顾客端条件，不要要求顾客发送钱包截图中包含的银行卡资料或手机验证码。可以让顾客告知设备型号、浏览器版本和钱包是否已完成设置，并引导使用银行卡继续支付。记录问题时只保存排查所必需的非敏感环境信息。

## 上线前检查清单

- Stripe Dashboard 中的付款方式设置属于正确账户和正确模式。
- 账户已满足钱包方式要求，没有待补资料或资格提示。
- 使用的 Checkout、Payment Element 或快速结账组件已明确。
- Session 或 PaymentIntent 实际配置没有意外限制钱包方式。
- 测试环境和实时环境分别验证，测试对象与真实交易不混淆。
- 使用的域名已按集成方式验证，子域名和自定义域名分别检查。
- 目标市场、币种、设备和浏览器覆盖主要顾客场景。
- 未显示钱包时仍有清晰可用的备选支付方式。
- 重试流程先查询原支付状态，不会重复创建或扣款。
- 顾客保存支付方式时明确取得相应授权。
- 客服流程不收集完整卡号、密码或验证码。
- 浏览器日志和支持工单不泄露密钥、client secret 或支付资料。

## 总结

Stripe Checkout 中的 Apple Pay 或 Google Pay 不一定对每个顾客都显示，因为展示受到商户账户、交易配置、地区、浏览器、设备和钱包状态等条件影响。先复现顾客端环境，再核对 Dashboard、实际 Session、付款方式设置与域名验证，可以比反复改代码更快定位问题。

商户还应提供银行卡等备选方式，确认重复使用钱包付款时符合顾客授权和 Stripe 产品规则，并在付款状态未知时避免重复创建订单。上线前按不同设备、币种、国家和集成模式逐一测试，让快捷支付成为可靠选项，同时确保不影响顾客完成购买。
