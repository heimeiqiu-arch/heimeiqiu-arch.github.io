免费试用能降低用户开始使用产品的门槛，但试用期结束时，如果客户没有添加可用付款方式，系统必须知道下一步如何处理。商家可能希望自动取消订阅，避免产生欠款；也可能希望暂停服务，等待客户补卡后再恢复；或者仍然创建一张账单，交由客服和客户线下处理。若没有提前设计，试用到期后客户可能突然失去访问权限，也可能收到一张无法支付的发票，甚至误以为自己已经被扣费。

Stripe Subscription 的 trial settings 提供了试用期结束行为配置，针对缺少付款方式的情形，可以选择取消、创建发票或暂停订阅。它们会导致不同的订阅状态和后续操作，因此不能只把设置当作接口细节。本文介绍三种选择的适用场景、试用期提醒、客户权限、账单处理和异常测试。Stripe 的字段和具体状态可能随 API 版本及产品配置变化，实施时应核对当前官方文档。[Stripe Subscription API](https://docs.stripe.com/api/subscriptions/create) [试用期指南](https://docs.stripe.com/billing/subscriptions/trials)

## 先定义“缺少付款方式”的业务含义

试用开始时不收款，并不代表试用结束时一定能自动收费。客户可能从未添加卡片；也可能添加了卡片但后来删除、过期或无法扣款；还有些付款方式需要客户在未来付款时完成认证。商家要分别考虑“没有可用付款方式”和“有付款方式但支付失败”两类问题。trial end behavior 的 missing payment method 设置主要用于试用结束时没有付款方式的情形，不应被当作所有付款失败问题的通用策略。

试用结束通常会触发订阅从免费阶段进入收费阶段。此时的服务开通规则要写清楚：用户是否立刻失去功能，是否进入宽限期，是否可以只读导出数据，客服是否可人工恢复。Stripe 的订阅状态与本地产品权限不一定自动一一对应，因此应用需要根据真实订阅和付款事件维护权限状态，而不是等一个定时任务结束后盲目执行“封号”或“继续开放”。

正式选择策略前，回答三个产品问题：试用期结束时是否允许无付款方式的订阅继续存在？是否需要生成应收款记录？用户在补充付款方式之前能否继续使用服务？如果团队、合同和产品页面对这三项没有明确答案，API 参数选得再正确也可能造成糟糕体验。

## 选项一：取消订阅

设置为 cancel 时，如果试用结束而客户没有附加付款方式，Stripe 会取消订阅。这个选择适合试用结束后必须先提供支付信息、商家不希望形成未结账单或持续占用订阅资源的场景。自动取消也能降低无人看管的免费账户长期留存成本。

取消行为应与试用开始时的客户预期一致。如果页面写着“试用结束后自动续费”，客户通常需要知道续费金额和取消方式；如果没有要求先添加付款方式，结束时突然取消可能让用户以为服务会按预期自动转为付费。相反，如果页面明确说明未添加付款方式就无法继续使用，自动取消便更容易理解。用户确认页面、试用到期提醒和账户设置要使用一致的说明。

订阅取消后，应用应基于 Stripe 的最新对象和相关事件更新权益，避免仅凭本地试用计时器判断。为误操作或用户想继续使用的情况提供重新订阅路径，同时防止恢复时意外重复创建订阅。保存原 Subscription ID、试用结束日期、取消原因和新的订阅 ID 映射，有助于客服解释账户历史。

## 选项二：创建发票

create_invoice 行为会在试用结束时创建发票，即使客户没有设置付款方式。它适合需要保留应收账款记录、通过邮件或客服跟进付款，或者客户会以银行转账等方式完成付款的业务。Stripe 文档描述该选项会在缺少付款方式时创建发票。[Stripe Subscription API 的试用设置](https://docs.stripe.com/api/subscriptions/create)

需要注意，创建发票不等于成功收款，也不等于客户一定会继续使用产品。发票可能处于未付状态，客户需要通过 Hosted Invoice 页面付款或以其他方式完成结算。产品应决定此时服务是继续、进入宽限期还是限制使用；财务系统则应按真实发票状态跟踪，而不是把生成发票当成现金到账。

商家还需测试发票的收款方式、到期日、邮件发送、失败处理和催款规则。如果客户无付款方式且没有收到清楚的付款指引，自动创建发票只会制造欠款记录。向客户展示应付金额、币种、付款期限与服务状态时，要避免把“发票已创建”说成“已扣款”。对于不适合信用赊账的自助产品，应该慎重选择此策略。

## 选项三：暂停订阅

pause 行为用于在试用结束时缺少付款方式的情况下暂停订阅。Stripe 的订阅状态会进入 paused，而不是继续按普通收费订阅运行。适合希望保留订阅关系、等待客户补充付款方式，并在之后允许恢复服务的产品。相较直接取消，它能保留更多订阅上下文；相较创建待付款发票，它可以避免立即形成预期外的欠款。

暂停后的服务权限仍需由应用决定。Stripe 不会替 SaaS 自动关闭登录、停止后台任务或保存用户数据。产品可以按策略冻结付费功能，保留只读访问，或让客户进入更新付款方式的专用页面。重新启用时要核对价格、席位数、客户同意和账期规则，不能因为对象还存在就无条件恢复原有扣款。

暂停也不等于客户已付款或承诺稍后一定续费。应向用户发送清楚的提醒，说明订阅暂停的原因、如何添加付款方式、数据会保留多久以及恢复后会收取什么价格。若企业希望设置恢复截止日期，还需配套清理或取消策略，并在账户页面显示该日期。

## 付款方式何时收集

让客户在试用开始时就添加付款方式，可以减少到期时的中断，但可能降低试用转化；允许用户先体验、结束前再收集付款方式，会增加提醒与支付设置流程。选择哪种方式取决于产品承诺、客户类型和销售周期。B2B 业务可能通过合同或账单处理付款，面向消费者的自助产品则可能依赖卡片自动扣款，两者不能套用同一套默认流程。

如果计划在试用结束时自动收费，应在试用开始前明确告知金额、币种、计费周期和收费日期。用户在试用期内更换计划时，更新下一期价格并确保页面和后端保持一致。不要只在邮件中告知费用，却在账户页面仍显示旧价格；也不要在未取得适当授权的情况下突然发起扣款。

提醒节奏可以根据试用长度设置，例如到期前几天和到期当天分别通知。邮件应包含当前试用结束时间、即将开始的收费金额、付款方式状态和管理订阅的入口。发送提醒并不保证用户已经阅读，因此后台还要监控付款方式是否添加成功、邮件是否退信，以及试用结束时最终发生了什么。

## 用 Webhook 和订阅对象同步状态

试用结束时的状态变化、发票创建和付款结果是不同的事实。应用应监听与订阅、发票和支付相关的实际事件，使用事件 ID 做幂等去重，并读取最新 Subscription、Invoice 对象核对当前状态。不要仅依赖试用结束时间的定时任务直接设置“已付费”权限，也不要只根据创建发票的事件认定收款成功。

本地数据库可以分别保存试用开始时间、结束时间、缺少付款方式时的策略、Stripe Subscription ID、发票 ID、支付状态和应用权益状态。这样客服能区分用户仍在试用、已取消、已暂停、已有待付发票或已成功转为付费。Webhook 延迟或重复送达时，状态同步逻辑也能依据对象的当前状态恢复一致性。

定时任务仍有价值，可用于提前提醒、扫描遗漏和发出运营告警，但最终账务状态应以 Stripe 对象为准。若某客户试用结束后没有产生预期行为，任务可以触发重新查询和人工告警，而不是擅自重试创建订阅或发票。涉及补偿操作时使用业务幂等键，并记录触发条件。

## 常见问题排查

**客户没有付款方式，订阅却仍显示 active。**检查 missing payment method 的配置是否被设置在正确的 Subscription 创建或更新请求上，确认试用是否真正结束、对象是否为测试模式，以及查看的是同一个 Customer 和 Subscription。不要把“前端显示试用结束”当作 Stripe 已完成状态迁移的证据。

**试用结束后创建了发票，但客户说没有被扣款。**先确认所选策略是否为 create_invoice，再检查发票状态、收款方式和支付对象。发票存在只说明账单记录被创建，不能证明付款成功。向客户提供明确付款入口和截止日期。

**客户补充卡片后订阅仍未恢复。**添加付款方式与恢复订阅可能是两个独立动作。重新读取 Subscription 状态，并根据产品策略执行恢复或重新订阅；检查是否产生恢复发票、是否需要客户认证以及下一次账期是什么。

**客户仍可使用已暂停的服务。**检查应用权限同步是否依赖 Stripe Webhook，是否有处理失败或本地状态缓存未刷新。Stripe 订阅状态变化不会自动修改应用自己的授权数据库。

**收到多张类似发票。**排查是否重试了订阅创建或手动补建发票，检查幂等键和事件处理是否重复。依据 Invoice ID、Subscription ID、创建时间和发票状态判断，而不要只看客户姓名与金额。

## 测试矩阵与上线清单

在测试环境覆盖至少以下用例：试用结束时从未添加付款方式；到期前添加有效卡；到期前移除已有卡；创建发票后通过 Hosted Invoice 支付；暂停后补充付款方式并恢复；取消后重新订阅；试用期间切换价格；付款方式需要额外验证；Webhook 重复发送或延迟送达。每种场景都检查 Stripe Dashboard、API 对象、应用功能权限、邮件内容和财务记录是否一致。

上线前可以逐项确认：

1. 选择 cancel、create_invoice 或 pause，并记录业务理由。
2. 在产品页明确试用结束时间、收费金额和无付款方式时的结果。
3. 配置试用提醒与付款方式更新入口。
4. 将订阅状态、发票状态和应用权益分开保存。
5. 对取消、暂停、待付款和成功付款设计不同的用户体验。
6. 使用真实 Subscription 和 Invoice 状态更新权限。
7. Webhook 处理具有幂等、重试和状态对账机制。
8. 验证发票通知、付款期限与失败提示。
9. 对多价格和试用中途变更进行测试。
10. 记录人工干预、恢复和重新订阅的审计信息。


## 试用转付费的指标和客服观察

配置上线后，不要只看“试用结束后有多少订阅仍为 active”。还可以分别观察付款方式添加率、试用到期时取消或暂停的比例、首张发票成功付款率、到期提醒送达率以及客户主动联系的原因。按注册渠道、产品版本和试用长度分组，能帮助判断是提醒时机不合适，还是用户对收费规则理解不清。指标用于改善沟通和产品流程，不应用来掩盖未经授权的收费或把失败付款简单归为客户问题。

客服团队需要一个统一的账户视图，同时展示试用结束时间、选定的到期策略、当前付款方式状态、最近发票和服务权限。这样用户询问“试用结束后会怎样”时，工作人员不必在几个系统里猜测。若人工决定延长试用或提前结束，操作入口应同步更新 Stripe 对象和内部记录，并留下原因与操作人，避免后台仍按照旧日期触发收费或停权。


对于使用多个 Stripe 账户或 Connect 的平台，还要确认试用订阅属于哪个账户上下文，Webhook 事件由哪个 endpoint 接收，付款方式更新发生在哪个客户对象上。测试环境和正式环境应使用不同配置并在日志中标出模式，避免把测试订阅的状态同步到真实用户权益。迁移账户、合并客户或更换价格目录时，也要逐一验证已有试用订阅的到期策略仍然有效。
试用策略也应在版本发布后持续抽查，特别关注到期当天是否出现异常发票、意外扣款或权益不同步；发现偏差时先冻结自动化扩散并核对对象，再修复单个客户记录。

还要为试用规则设置负责人，避免营销页面、应用配置和 Stripe 参数分别由不同团队长期维护却无人核对。

每次变更都应在测试模式走一遍从注册到首次付费或取消的完整路径。

## 总结

试用期结束缺少付款方式时，Stripe 可以按配置取消订阅、创建发票或暂停订阅。取消适合阻止未授权的自动续费并清理免费试用；创建发票适合需要形成应收账款并允许客户后续结算的业务；暂停适合保留订阅关系、等待用户补充支付方式的流程。它们都不会自动替代应用的服务权限、客户通知和对账逻辑。

选择策略时，应让用户在试用开始前知道未来收费安排，并在到期前提醒补充付款方式。试用结束后以 Stripe 的真实订阅、发票和付款对象同步状态，再依据明确的产品规则开放或限制服务。可进一步查阅 [Stripe 试用期指南](https://docs.stripe.com/billing/subscriptions/trials) 与 [Subscription API](https://docs.stripe.com/api/subscriptions/create)，并在测试模式中验证完整生命周期。
