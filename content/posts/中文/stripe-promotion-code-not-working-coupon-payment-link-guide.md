商户在 Stripe 中创建了优惠活动，客户却在 Payment Link 或 Checkout 页面看到优惠码无效、折扣金额不符合预期，或者首次付款减价后订阅续费仍按原价收取。排查时要先分清 Coupon、Promotion Code、Discount 和 Payment Link 之间的关系。优惠券描述折扣规则，Promotion Code 是客户结账时输入的代码，Discount 则是优惠实际应用到具体对象后的记录；入口、适用范围和限制条件都可能影响最终结果。

本文按客户输入代码、Stripe 进行资格判断、折扣应用到付款或订阅、发票展示和后续续费的顺序检查。Dashboard 界面和 API 字段会变化，具体能力取决于产品、账户及支付流程，请以 Stripe 当前官方文档为准。对外公布优惠前，建议在测试环境检查不同客户、购物金额、币种和订阅周期，避免促销文案与系统规则不一致。

## 一、先弄清楚优惠对象之间的区别

Coupon 定义折扣本身，例如固定金额、百分比、持续时间或适用产品等规则。Promotion Code 指向一个 Coupon，并给客户一个便于输入的代码，还可以设定客户、有效期、可使用次数和最低金额等限制。Discount 代表优惠已实际应用到某个客户、订阅、发票或 Checkout Session 等对象。Payment Link 则是客户进入付款流程的链接；链接是否允许输入代码是独立设置。

因此，“我在 Dashboard 看到了 Coupon”不等于客户结账时自动获得了折扣；“客户输入了代码”也不等于资格判断通过并已应用优惠。排查时从代码查到其对应 Coupon，再确认相关 Discount 是否已创建、落在哪个对象、适用的行项目和周期是什么。用 ID 和状态串联这些对象，比只看促销名称或营销邮件更可靠。

## 二、先确定客户在哪个入口付款

询问客户使用的是 Stripe Payment Link、Checkout、商户自建表单、发票、订阅管理门户还是其他支付入口。不同入口的优惠码字段和支持范围可能不同。Payment Link 需要允许 promotion codes；API 创建 Checkout Session 时也要有相应配置；订阅 Customer Portal 中是否可以添加代码，则取决于门户配置。某个页面可以输入代码，不代表另一个页面也启用了同一功能。

确认客户使用的是正确链接、正确产品和正确环境。如果营销邮件里链接指向旧版 Payment Link，当前后台配置变化不会自动说明旧链接的行为。复制链接时也要避免测试链接和正式链接混用。记录入口 URL、创建时间、链接 ID或 Checkout Session ID，以及客户操作时间，方便定位究竟是入口未开启、代码资格不符，还是已成功应用但页面展示与预期不同。

## 三、检查 Promotion Code 是否有效

打开 Promotion Code 对象，核对 active 状态、关联的 Coupon、代码文字、创建时间、过期时间、最大使用次数和已兑换次数。代码可能已停用或过期，也可能达到兑换次数上限。API 对代码大小写、唯一性和字符格式等有规定；不要仅凭宣传页拼写判断系统对象中的实际代码。

同时查看是否绑定了特定客户或设置了首笔交易限制。若代码只允许指定客户使用，其他用户输入即使拼写正确也可能不符合资格。把代码在邮件、网页和社交媒体上的大小写与空格逐字符比较，并检查复制时有没有带入标点、全角空格或隐藏字符。若因安全原因使用了多个类似代码，清楚记录每个代码关联的 Coupon 和适用人群，避免客服把旧活动的优惠码告诉新用户。

## 四、检查 Coupon 的折扣规则

Coupon 可能提供百分比减免、固定金额减免或特定持续时长。要核对 Coupon 的有效状态、折扣值、币种（适用于固定金额折扣时）、持续时间以及适用产品。固定金额折扣受币种和订单金额影响；百分比折扣则依据对应金额计算。不要把“减免 20”误解成“减免 20%”，也不要忽略营销文案是否明确了币种和周期。

如果 Coupon 只适用于部分产品，购物车或订阅中没有对应产品时，折扣可能不会应用于预期项目。多个商品、税额、运费和折扣的计算顺序也可能影响最终总额。检查折扣作用于整笔订阅、客户、发票还是特定行项目，确认与当前付款入口兼容。营销团队发布活动前，确保促销页面说的规则与 Coupon 的实际配置逐项对应。

## 五、检查最低金额和首次交易限制

Promotion Code 可能要求订单达到最低金额，或限制为首次交易/首次订阅使用。客户的小计不足、折扣前后金额计算口径不符合预期、客户历史上已有成功交易，都可能让代码不能用。确认限制使用了哪个金额字段和币种，尤其在多币种商品、税费另计、运费或折扣同时存在时。

首笔交易限制也可能与 Stripe 识别客户的方式有关。使用新的邮箱但复用既有 Customer 对象、不同账户体系映射到同一个 Customer、或者创建了新的临时客户记录，都可能影响资格判断。不要为绕过限制而随意给客户另建账户，需检查实际代码对 Customer 和订单历史的关系。若业务希望只限一个具体活动或一段时间，应在 Promotion Code 和营销条款中设置一致的边界。

## 六、Payment Link 没有优惠码输入框

若客户使用 Payment Link，检查对应链接的 allow_promotion_codes 设置是否开启。Payment Link 可能在创建时没有启用促销代码入口；后来创建的另一个链接可能配置不同。确认客户实际打开的不是旧链接、错误产品链接或测试链接，并查看该 Payment Link 对象的具体配置。

启用优惠代码前先评估该链接的其他规则：商品和数量、订阅或一次性模式、税费、客户地址收集、客户创建、试用和跳转设置。复制已有链接再改配置时，也要确认变更应用于正确对象并完成发布。若当前 Payment Link 不支持你期望的动态规则，查看 Stripe 官方产品能力，必要时采用可支持的 Checkout 集成。不要在网页上单独放一个“输入优惠码”文本框，却没有将代码传给真正的支付创建流程。

## 七、Checkout Session 的 API 配置排查

自定义集成中，检查服务端创建 Checkout Session 的请求参数是否启用了促销代码。确认请求使用的 Stripe 账户、模式、API 版本和创建路径正确，且最新代码已经部署到线上。前端显示的输入框不应代替服务器端的资格判断和 Stripe 对象配置。

从特定 Checkout Session ID 回查其 line items、discounts、promotion code 和最终发票或付款对象，确定优惠是否实际应用。如果 Session 创建时没有允许代码，客户可能在页面上看不到入口；如果允许代码但输入后不生效，则进一步检查 Promotion Code 资格条件和 Coupon 适用范围。日志中保存必要的 Session ID、请求时间和状态，不应记录任何 secret key。测试时为每种业务模式创建专门的测试 Session，验证正常、过期、不满足限制和达到次数上限的情况。

## 八、订阅为什么只首期打折

Coupon 的持续时间可能是只应用一次、在一定时间内重复应用，或在符合规则时持续适用。客户看到首期减价但后续发票恢复原价，可能正是折扣定义的预期行为，也可能是订阅未正确关联折扣。检查 Subscription 的 Discount、Coupon duration、开始与结束日期、相关 Invoice 和实际价格，不要只看第一次付款收据。

若促销文案写“前三个月优惠”，确认 Coupon 持续期和发票周期之间的关系；若文案写“终身折扣”，确认实际优惠不是一次性折扣，也要说明适用的产品和其他限制。订阅升级、降级、数量变化、按比例收费和切换价格可能改变发票总额，需查看具体 Invoice 行项目。Customer Portal 是否允许客户应用或移除 Promotion Code，取决于门户配置，不能假定它会自动继承 Checkout 中的代码输入功能。

## 九、多个折扣和应用顺序

同一客户、订阅或发票可能关联不同折扣，实际适用对象和计算方式由 Stripe 支持的产品和当前配置决定。不要假设优惠码能叠加，也不要假设系统会按营销人员想象的顺序计算。检查具体 Invoice 和 Discount 对象中的 Coupon、应用范围和金额，确认是否存在客户级折扣、订阅折扣、行项目折扣或发票级优惠。

营销规则应明确是否允许叠加、哪些商品排除、先应用哪个折扣以及是否可与试用期并用。若系统不支持需要的叠加方式，不要通过隐藏的手工折扣掩盖，而应调整活动条款或实现适合的方案。对存在多个有效代码的情况，给每个优惠设置清楚的适用范围和结束时间，并由财务确认折扣如何进入收入和税费报表。

## 十、测试优惠码时覆盖边界情况

优惠码测试不能只验证“一个代码成功”。至少要测试：有效代码、拼写错误、过期代码、停用代码、用户受限代码、首笔交易限制、最低金额未达到、达到最大兑换数、只适用特定产品的代码、不同币种和订阅续费。确认前端提示可理解，错误时不会错误地向客户承诺优惠已应用。

每次测试记录测试模式、Payment Link/Session ID、Promotion Code ID、Coupon ID、订单商品和预期总额。对一次性商品、订阅和发票分别测试，因为它们的折扣对象可能不同。验证发票 PDF、收据邮件、客户门户、Webhook 和商户数据库都记录一致的折扣信息。营销上线前让非开发人员按真实客户路径走一遍，检查代码如何复制、输入、确认和显示。

## 十一、金额与客户预期不一致

当客户认为折扣金额不正确，先查活动条款、Coupon 类型和订单构成。固定金额折扣可能只适用于某币种或部分商品；百分比折扣可能只作用于符合条件的项目；税费和运费可能在优惠之外计算。订单存在多个项目时，优惠在各项目间的分配方式也可能影响显示的折扣行。

向客户解释时说明原价、符合条件的商品、折扣金额、税费、总额和订阅后续收费。不要只回复“代码正确”或“系统算的”，应给出可核对的构成。若确实是配置错误，按商户政策决定修正订单、退款差额或为客户创建替代方案，并记录原因。不要手动改数据库金额来掩盖 Stripe 对象与订单系统的差异。

## 十二、折扣使用统计与兑换记录

活动结束后，比较 Promotion Code 的兑换次数、Coupon 使用记录、实际订阅或发票以及内部营销统计。单看一个计数可能不够，因为部分付款失败、取消或退款也会影响业务结果。按代码、活动、客户群、产品、折扣成本和续费表现整理报告，确认活动是否按预期使用。

对异常兑换、共享代码泄露或大量自动注册，检查客户、对象、时间和请求来源，遵守隐私规定。若达到最大兑换次数，应确认系统状态和活动页面的提示是否同步。下线代码时通过正式配置禁用或调整，不要仅删除网页文案，因为已经发送的邮件或社交帖子可能仍被客户访问。保留活动开始结束时间、审批人、规则版本和实际使用结果，方便复盘。

## 十三、客服处理优惠码投诉的流程

客服先询问客户使用的付款入口、代码文本、产品、订单号、结账时间和页面提示。不要索取支付密码、完整卡号或验证码。在 Stripe Dashboard 中查找实际 Session 或订阅，确认 Promotion Code 是否被提交、资格条件是否通过、Discount 是否生成、最终 Invoice 是否含有折扣。

如果代码过期或不符合条件，引用活动条款说明具体原因，并提供当前可行的购买或客服步骤；若页面入口缺失或系统配置错误，则升级到支付或工程团队。涉及金额差异时提供订单明细，说明折扣仅作用于哪些商品和周期。不要为安抚客户而未经授权承诺所有未来账单都永久享受折扣，也不要让客户重复付款来重试代码。

## 十四、变更和停用优惠的安全做法

优惠活动变更会影响共享 Coupon、Promotion Code、Payment Link 和订阅。开始前确认哪些链接或订阅引用该对象、现有客户是否仍受其影响、停用后客户如何看到错误信息。先在测试环境验证，再按活动安排变更，保留旧规则和变更时间。对已付款的订单不要假设修改 Coupon 会追溯重算。

若代码意外公开或被滥用，暂停代码前评估正在结账的客户和现有订阅，明确后续客服口径。统计影响订单，避免对所有客户批量删除折扣造成账单变化。操作要有审批和审计记录，特别是修改折扣金额、时限或适用客户群。与 Stripe API 交互的后台代码需避免在异常重试时重复创建优惠对象，可以按业务需要维护内部映射和幂等控制。

## 十五、常见问题

### Coupon 已创建，为什么客户不能输入？

Coupon 定义折扣规则，但客户可输入的入口通常由 Promotion Code 和 Checkout/Payment Link/门户配置共同决定。确认已创建客户可用的代码，并启用了当前付款入口的代码输入功能。

### Promotion Code 显示有效，为什么订单不打折？

有效状态不代表当前客户和订单符合所有限制。检查过期时间、最大使用次数、特定客户、首次交易、最低金额、产品范围、币种和当前 Session 实际应用的 Discount。

### 客户结账成功了，发票没有折扣？

确认是否输入并应用 Promotion Code、Session 或 Subscription 是否创建了 Discount、该 Invoice 是否在折扣有效期内生成。不同折扣持续时间可能只覆盖部分账单周期。

### 代码可以大小写混输吗？

Stripe Promotion Code 对代码的唯一性等处理有明确规则，输入体验和有效代码应以具体对象及官方 API 文档为准。客服应让客户复制官方提供的代码，并检查空格和标点，而不是假定任意改写都可用。

### 能否对已完成订单补用优惠码？

不要假设事后修改 Promotion Code 会自动更改已付款订单。检查具体 Stripe 对象是否支持所需变更，并按业务政策与会计流程处理退款或调整。必要时让财务审批。

### 客户门户里没有优惠码框怎么办？

Customer Portal 是否支持应用促销码取决于 Portal Configuration。检查订阅更新功能和门户设置；若未开放，客户需要通过支持的结账或订阅流程操作。

## 十六、发布促销前检查清单

- Coupon 的折扣类型、金额、币种和持续时间正确
- Promotion Code 处于可用状态，限制条件与活动文案一致
- Payment Link 或 Checkout 明确允许客户输入代码
- 产品、客户、最低金额和兑换次数限制已验证
- 订阅折扣持续期和续费价格清楚说明
- 测试过有效、过期、受限和不同币种的边界场景
- 收据、Invoice、Customer Portal 和订单系统显示一致
- 活动下线与客户已开始结账的处理方式明确
- 客服知道如何查 Coupon、Promotion Code、Discount 和对象 ID
- 折扣数据和活动结果可审计、可对账

活动正式发布后，监控使用量、支付成功率、退款和客户投诉。规则或链接发生变化时，更新文案并告知客服团队，不要让旧促销链接在不知情的情况下继续传播。

## 总结

Stripe 优惠码问题通常由优惠对象、资格限制或付款入口配置不匹配造成。先确认客户实际使用的链接或 Checkout，再检查 Promotion Code 对应的 Coupon、有效状态、期限、客户限制、金额门槛和适用产品，最后从具体 Session、Subscription、Discount 和 Invoice 核实折扣是否真正应用。促销文案应准确说明折扣值、持续期和限制，并在上线前覆盖不同客户与订单场景。

参考：[Stripe 优惠与折扣官方指南](https://docs.stripe.com/billing/subscriptions/coupons)、[Stripe Promotion Code API](https://docs.stripe.com/api/promotion_codes) 和 [Stripe Payment Link 对象](https://docs.stripe.com/api/payment-link/object)。不同结账流程和订阅配置的能力可能不同，请以账户中的设置和官方文档为准。
