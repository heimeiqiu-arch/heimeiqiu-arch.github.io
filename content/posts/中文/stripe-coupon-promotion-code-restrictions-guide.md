Stripe 的折扣能力通常由 Coupon 和 Promotion Code 两类对象组成。Coupon 定义折扣本身，例如减免固定金额或按比例打折、持续一次还是持续若干计费周期；Promotion Code 则提供客户可以输入或使用的促销代码，并可附加指定客户、有效期、使用次数或最低金额等限制。二者相互关联，但承担不同职责。若把优惠百分比、公开代码和客户限制都混在一个概念里，活动容易出现不符合预期的折扣、重复核销或客服无法解释的问题。

本文从促销活动的业务设计出发，说明何时创建 Coupon、何时创建 Promotion Code、如何设置折扣期限和限制，怎样在订阅与一次性付款中核对优惠结果，以及上线后如何监测使用情况。Stripe 对象字段、Dashboard 能力和结账方式可能因 API 版本或账户配置而不同，实际实施前请对照官方文档。[Stripe 优惠券指南](https://docs.stripe.com/billing/subscriptions/coupons) [Promotion Code API](https://docs.stripe.com/api/promotion_codes)

## Coupon 定义折扣，Promotion Code 面向客户

Coupon 是优惠规则的核心对象。它可以定义百分比折扣或金额折扣，并设置折扣持续时间，例如只应用一次、持续多个周期或在适用范围内永久持续。具体能否作用于哪些商品、订阅或客户，取决于优惠对象及其配置。促销码通常指向 Coupon，客户看到并输入的短字符串只是让折扣进入结账流程的入口。

可以用“规则模板”和“兑换凭证”来理解二者：一个 Coupon 可以承载折扣政策，而一个或多个 Promotion Code 分别服务于不同渠道、活动或受众。例如同一套 20% 折扣规则，可以有一个面向邮件订阅者的代码和另一个仅供活动现场使用的代码；也可以为每个合作伙伴单独创建可追踪的代码，但让它们都关联到同一 Coupon。这样既复用折扣规则，又能分别观察各渠道核销情况。

Stripe Promotion Code 对象包含其客户可见 code、关联 Coupon、active 状态、有效期、最大核销次数、已核销次数和 restrictions 等信息。代码在大小写不敏感情况下需要满足对应范围内的唯一性，且可限制给特定客户。[Promotion Code 对象参考](https://docs.stripe.com/api/promotion_codes/object) 因此，优惠码本身并不是安全秘密；一旦公开传播，应假设任何看到代码的人都可能尝试使用。

## 先把促销规则写成业务要求

创建对象之前，先回答折扣给谁、作用于什么、持续多久、能否叠加、到什么时候截止、最多多少人使用，以及退订后是否仍保留优惠。运营活动文案、结账页面和实际 Stripe 配置必须完全一致。若广告写“首月七折”，但 Coupon 实际作用于前三个周期，用户可能会被多收或商家损失收入。

应分别考虑新客和老客、一次性购买和订阅续费、特定商品和全目录、特定币种和跨币种使用。折扣金额是否含税、是否影响已创建的发票、优惠是否对订阅未来周期持续，都需要在测试环境逐项确认。不要仅凭 Coupon 名称或 metadata 推断它的实际折扣行为，最终要读取对象字段并检查真实结账结果。

活动还应有明确负责人和结束办法。营销团队生成代码后，谁负责停用？客户申请退款时折扣如何处理？活动预算超出预期时是否能暂停后续核销？如果没有清晰的边界，优惠码很可能在活动结束后仍然被传播和使用。

## 固定金额与百分比折扣

百分比折扣适合想按商品金额比例减价的活动，例如首期 15% 优惠。金额折扣适合固定减免，例如账单减免 10 元，但金额折扣通常需要考虑币种。若商家支持多个币种，必须确认固定金额优惠适用于哪些币种以及金额单位；不能把一种币种的绝对金额直接当成另一种币种的同等价值。

订阅优惠还要区分优惠影响哪些账期。Coupon 的 duration 和持续周期会决定是只影响一次收费、影响指定数量的续费周期，还是持续适用。客户从月付切换年付、升级方案或暂停后恢复时，优惠剩余周期如何计算，必须通过实际场景验证。不要把“前三个月优惠”翻译成“前 90 天”而不确认计费周期和日期边界。

金额展示应清楚区分原价、折扣和最终应付金额。若有税务计算，折扣对税前价格和税额的影响要在发票明细中检查。页面只显示“省 20%”可能不足以解释首期、续费和含税金额之间的区别。对于长期订阅，客户应能看到优惠结束后将恢复的价格，降低续费账单争议。

## Promotion Code 的客户和使用限制

Promotion Code 可以附加客户限制和核销限制。例如将代码绑定到一个特定 Customer，设置最大核销次数、过期时间或最低金额条件。官方对象字段还显示 restrictions 中可能包含 first_time_transaction 与 minimum_amount 等限制。[Promotion Code 对象参考](https://docs.stripe.com/api/promotion_codes/object)

“仅限新客户”需要理解 Stripe 与商家自己的客户身份定义是否一致。用户可能换邮箱重新注册，但实际上是同一家公司或同一付款方；也可能有多个 Stripe Customer 对象对应同一个真实客户。若促销资格涉及商业关系，不能只依赖输入邮箱判断，应在服务端结合自有账户系统做资格校验，并将客户映射维护正确。

最大核销数与优惠券自身的使用次数也可能是不同层次的限制。测试时分别验证代码是否达到限制、Coupon 是否已经过期或无效、客户是否符合条件以及最低金额是否满足。促销失败时要在界面给出准确且不过度泄露内部规则的提示，避免用户以为付款系统故障。

公开代码、员工专属码和客户定向码应分开管理。员工折扣不宜使用可被全网传播的通用字符串；定向客户代码应绑定具体 Stripe Customer，并在 API 创建代码时检查绑定值。对于高价值促销，考虑在服务端生成代码和校验资格，不要让浏览器直接决定折扣金额。

## 在 Checkout、订阅和账单中应用优惠

Promotion Code 可以用于适用的 Checkout 流程或 Billing 场景，但具体支持位置和参数要查看所使用的 API 或产品配置。结账页面是否允许用户输入代码、代码是否可以自动应用、是否要限制到指定 Price，都需要在商家端控制。不要把促销验证完全放到前端，客户端能修改的字段不应决定最终折扣。

创建订阅时，确认折扣关联到了正确的客户、订阅或发票上下文，并验证未来续费是否仍然适用。现有订阅的折扣更新可能影响后续发票，但不会自动重写已经定稿的历史账单。若客户在结账后使用客服补发代码，需要记录人工操作原因并确保不会重复应用。

优惠码校验失败时，确保订单或订阅没有带着部分不完整状态被创建。通过幂等请求、明确的错误处理和真实对象读取，防止网络超时导致用户重试后创建两个带折扣的订单。营销系统也不能用“用户曾输入代码”代替 Stripe 的实际折扣对象状态。

## 活动监测与财务核对

活动开始后，应观察 Promotion Code 的 active 状态、核销数量、有效期、客户范围和收入表现。核销次数上升并不一定代表活动成功，还要对比退款、取消、续费留存和折扣成本。按渠道创建不同代码或建立元数据标签，有助于识别活动来源，但不要把会变的营销文案直接当作唯一财务标识。

财务对账时检查真实发票行项目、折扣金额、税额和最终收款，不要单靠活动后台的点击数估算让利金额。对于一次性支付和订阅续费，应分别汇总首次优惠成本与后续周期的折扣影响。报表中区分 Coupon、Promotion Code、客户、订阅和 Invoice ID，避免将同一客户的多次核销误当成多个新客户。

当活动到期或预算达到上限时，可停用相关 Promotion Code，检查是否还有已创建但未完成付款的 Checkout Session。代码失效后，用户可能仍在旧结账页面；因此还要测试过期代码在提交时的实际错误提示和订单状态。停用代码、终止优惠或修改 Coupon 应有审计记录，并让客服了解生效时间。

## 常见错误与排查思路

**代码输入正确却提示无效。**核对 Promotion Code 的 active 状态、过期日期、核销上限、客户绑定、最低金额及适用产品。再确认结账流程是否支持输入这种代码以及传入了正确的 Customer 和 Price。

**折扣比预期多持续了几期。**检查关联 Coupon 的 duration 与 duration_in_months，而不是只看营销文案。读取订阅或客户当前折扣状态，并对照发票周期验证未来账单。

**优惠作用于错误客户。**检查 Customer ID 映射、代码是否有客户限制、是否存在重复客户记录。不要把名称和邮箱相同视为相同的 Stripe 对象。

**活动结束后仍有人使用代码。**确认 Promotion Code 是否仍 active，是否还有旧结账会话，或其他同规则代码仍有效。对于需要立刻停止的活动，列出所有相关代码并逐个检查，而不是只停用一个主 Coupon。

**用户说有折扣但发票全价。**确认优惠是在订单创建前应用，还是只保存在应用数据库；检查实际 Invoice 的折扣明细、订阅当前配置和发票定稿时间。已定稿的历史发票通常需要按正式账务方式更正，不能只改变后台标签。

## 上线检查清单

1. 清楚区分 Coupon 折扣规则和 Promotion Code 客户入口。
2. 确认百分比或固定金额、币种和优惠持续时间。
3. 明确适用客户、商品、订阅周期、最低金额和使用上限。
4. 在服务器验证客户资格，客户端只负责传递代码。
5. 测试新客户、老客户、多个 Customer 记录和不合格价格。
6. 检查 Checkout、订阅更新和发票中的实际折扣明细。
7. 验证退款、取消、折扣到期和代码停用的后续行为。
8. 为不同活动或渠道建立可追踪但不含隐私信息的标识。
9. 保存创建、修改和停用时间及操作人。
10. 对折扣成本、退款、留存与核销率持续复核。


## 多张优惠和折扣叠加

当商家同时提供新客优惠、合作伙伴代码和人工补偿时，需要明确同一笔订单是否允许叠加多个折扣。不要只在营销规则表里写“通常不可叠加”，还要检查实际 Checkout、Subscription 和 Invoice 配置是否会接受多个折扣对象。系统应在服务端决定可用组合，并在用户确认前展示合并后的金额。

若确实允许叠加，需要定义顺序与范围。例如先应用固定金额减免，再对剩余金额计算百分比，和先打折再减固定金额，最终金额可能不同。Stripe 支持的折扣组合方式及边界要依据当前 API 文档与产品能力实测。对账时保留每个优惠来源，方便财务把促销支出归属到正确的预算科目。

人工补偿也应与营销优惠区分。客服为了处理服务故障赠送的折扣，可能需要限定到特定客户、指定开始时间或特定账期；不要复用面向公众的通用代码。操作记录注明补偿原因、批准人、受影响账单和终止时间，防止一次性的善意处理意外变成永久低价。

## 客户端输入和服务端校验流程

用户提交促销码后，应用可以先做格式规范化并向服务端请求校验，但不能仅在浏览器中维护一个“有效”标志。服务端需要结合当前 Customer、产品价格、币种、订单金额和活动状态确认资格，再在实际创建 Checkout Session 或订阅时传递正确的优惠对象。校验与创建之间可能有时间差，因此最终创建请求仍必须由 Stripe 验证，不能把前一次预览当成锁定名额。

对错误信息分层处理：格式不正确可以提示检查输入；代码过期可以提示活动已结束；客户或金额不符合条件时给出适当说明；服务端暂时不可用则提示重试且不要创建无优惠订单。避免为了提高转化率而静默移除代码继续按全价收费，这会让用户在最后付款页面才发现价格变化。

高并发活动还要考虑最后一个名额被其他用户同时使用的情况。前端预先显示有效并不保证付款完成时额度仍在。创建会话和完成付款之间，代码可能达到核销上限；最终以 Stripe 对对象和支付流程的实际处理结果为准，并在失败时让用户选择是否继续以原价购买。

## 变更和撤销活动的影响

活动中途更改 Coupon 或停用 Promotion Code 前，先列出已经创建的 Checkout Session、待支付发票、现有订阅和已经确认优惠的订单。不同对象可能处于不同生命周期阶段，停用新核销入口不必然意味着所有已应用的折扣立即从既有订阅中移除。变更计划应说明哪些用户继续享受已承诺的优惠、哪些新交易停止接受代码，以及何时开始生效。

若发现折扣配置错误，先评估实际受影响客户和账单，再制定修正或补偿方案。不要通过改名、删除报表标签或覆盖数据库字段来掩盖已产生的交易。保留旧配置快照、变更时间、受影响对象 ID 和客户通知记录，才能在财务审查或客户投诉时复现问题。

营销活动结束后也要做复盘：核对各代码核销量与净收入，检查异常退款和重复客户，记录优惠结束后续费留存，并删除或停用不再使用的测试代码。活动数据中避免保留不必要的个人信息，渠道分析可使用代码或匿名化业务标识完成。
## 总结

Stripe Coupon 负责描述折扣金额与持续规则，Promotion Code 为客户提供可输入、可限制和可追踪的兑换入口。把两者分开设计，可以复用优惠政策，同时区分不同营销渠道与客户范围。促销上线时，应确认资格限制、使用上限、过期方式、账单金额和后续续费，之后通过真实 Invoice 与支付记录核对最终结果。

开始配置前，可查阅 [Stripe Coupons 指南](https://docs.stripe.com/billing/subscriptions/coupons)、[Promotion Code API](https://docs.stripe.com/api/promotion_codes) 和 [Promotion Code 对象参考](https://docs.stripe.com/api/promotion_codes/object)，再用测试模式覆盖有效、过期、超额和客户受限等情形。
