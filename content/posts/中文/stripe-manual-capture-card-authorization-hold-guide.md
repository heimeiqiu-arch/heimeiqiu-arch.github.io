电商、酒店、租车和分批履约业务有时需要先确认银行卡可用，再决定最终收取多少或何时收取。Stripe PaymentIntent 支持将授权与捕获分开：客户完成支付授权后，商家暂时保留授权额度，等订单可以履约或最终金额确定后再捕获款项。这种流程常被称为手动捕获或预授权。

“授权通过”不等于商家已经收到款项；银行卡上出现待处理金额也不等于最终扣款已完成。授权会有有效期限，最终可捕获金额受原授权、支付方式和网络规则限制。若业务没有明确需要等待履约或核算金额，默认自动捕获通常更简单。本文说明手动捕获的状态流转、适用场景、部分捕获与取消授权、库存和超时设计，以及测试核对方法。实际可用行为和授权时限依支付方式、卡组织、地区与交易类型而变化，应以 Stripe 当前 API 文档和 Dashboard 数据为准。[创建 PaymentIntent API](https://docs.stripe.com/api/payment_intents/create) [捕获 PaymentIntent API](https://docs.stripe.com/api/payment_intents/capture)

## 授权与捕获是两个步骤

授权阶段由发卡行判断是否批准本次交易，并暂时预留相应额度；捕获阶段由商家请求完成收款。使用自动捕获时，系统通常在授权通过后继续完成捕获；使用手动捕获时，PaymentIntent 可能进入 `requires_capture` 状态，商家需要在允许期限内主动捕获或取消。[捕获 PaymentIntent API](https://docs.stripe.com/api/payment_intents/capture)

对客户而言，手动捕获可能表现为银行卡账户上出现一笔待处理金额。页面和邮件应明确说明这是授权预留，最终金额可能根据发货、服务或账单调整。若只说“已经扣款”却尚未捕获，会导致客户困惑；如果最终金额低于预授权，也应说明银行何时释放未使用部分取决于支付处理和发卡行。

要先确认业务真的需要这种分离。例如订单需要人工确认库存、酒店离店后才知道杂费、租车归还后结算额外费用、分批发货需按实际发货金额收费，手动捕获可能有价值。若只是希望“之后再扣”但没有授权期限内的捕获计划，或希望在未来任意时间随意变更金额，就不应将预授权当作通用延期收费方案。

## PaymentIntent 的手动捕获设置

在创建 PaymentIntent 时，使用适用的 capture_method 配置来请求手动捕获；成功授权后读取 PaymentIntent 的当前状态和 amount_capturable，再根据业务节点执行 capture。创建参数、支持的支付方式及状态行为以 API 文档为准。[创建 PaymentIntent API](https://docs.stripe.com/api/payment_intents/create)

流程中至少要保存 PaymentIntent ID、本地订单 ID、原授权金额、当前可捕获金额、授权时间、预计履约时间和状态。授权成功后，订单应进入“已授权、待履约或待结算”，而不是“已收款”。仓库确认发货、客服确认服务完成或最终账单计算结束后，后端再依据可信的订单数据捕获金额。

前端不应自行决定捕获多少，也不应把客户端传来的金额直接用于 capture。服务端需检查订单状态、已发货数量、退款或取消记录、授权剩余金额以及是否已存在捕获操作，再提交请求。对捕获请求实现幂等控制，避免工作人员双击按钮、后台任务重试或多个服务并发操作造成重复处理。

## 授权有效期和过期风险

未捕获的 PaymentIntent 会在一段时间后失效；Stripe Capture API 说明，未捕获的 PaymentIntent 会在设定天数后取消，默认通常为 7 天，但实际可用期限会受到交易类型和支付方式的影响。[Capture PaymentIntent API](https://docs.stripe.com/api/payment_intents/capture) 不要把这个默认值当作所有银行卡、地区、行业和账户的固定授权期限。读取当前对象、账户设置和适用支付方式的具体期限，并在业务流程中为失败留出缓冲。

如果订单履约周期可能超过授权期限，例如预售商品数周后才发货，第一次授权可能在发货前过期。过期后不能假设原授权仍可捕获；商家可能需要重新向客户发起支付授权，而新的授权也可能被发卡行拒绝。产品应在客户购买前说明收费时间，后台应跟踪即将到期的授权并尽早决定继续、重新授权或取消订单。

为每笔授权设置内部截止时间提醒。不要等到授权临近失效时才开始联系仓库或客户。对无法在期限内履约的商品，可考虑在接近发货时再收款、采用支持的预订单流程，或选用其他符合合同和支付规则的方案。所有自动提醒都应关联 PaymentIntent 与订单，避免重复通知。

## 捕获全额、部分金额与多次捕获

默认情况下，捕获可用授权金额通常意味着对本次交易完成收款。若最终金额低于预授权，商家可按 API 支持方式指定较低的捕获金额，剩余未使用授权将按支付网络和发卡行规则释放。客户看到的待处理额度何时消失并非商家能完全控制，客服应避免承诺精确的银行入账时间。

多次或部分捕获不是所有支付场景都能用。Stripe Capture API 提供 final_capture 参数；将其设置为 false 会通知 Stripe 不立即释放尚未捕获的资金，以便后续捕获，但仅在 PaymentIntent 支持 multicapture 时适用。[Capture PaymentIntent API](https://docs.stripe.com/api/payment_intents/capture) 不要把所有卡支付都假设为支持分批捕获，也不要因需要分批发货就直接重复调用 capture。

分批履约时，应将每次捕获与具体发货批次或服务阶段关联，累计捕获金额不得超过可捕获金额和相应交易限制。每次请求成功后重新读取 PaymentIntent，检查 amount_capturable、amount_received 和状态，再更新订单。若业务需要额外收取超过原授权的金额，通常需要获得新的客户授权，而不是把原授权当作无限额度。

分批发货还要明确客户账单显示方式。不同发卡行可能以不同形式展示授权和捕获，客户可能看到待处理金额与已入账金额并存。订单详情页应列出实际已捕获的部分及尚未捕获的金额，客服也要能按 PaymentIntent 和捕获记录解释每笔数额。

## 取消订单和释放授权

在捕获之前取消订单时，通常应按适用流程取消或撤销 PaymentIntent 授权，使未使用额度尽快释放。不要仅仅把本地订单标记为取消，却留下未捕获授权直到自然过期。取消后读取 PaymentIntent 状态并保留操作记录，告知客户银行释放待处理金额所需时间可能因发卡行而异。

若订单部分履约后取消，先对照已捕获金额、剩余授权和已发货价值。对已经捕获的金额，需要依退款流程处理；未捕获部分则按授权取消逻辑释放。退款和撤销授权是不同操作，不能把它们混为一谈，也不要对未捕获金额创建退款记录。

若捕获请求失败，先查询 PaymentIntent 当前状态、授权期限和可捕获余额，再决定是否重试。超时意味着结果可能不明确，不能立刻创建一笔新 PaymentIntent 并再次扣款；应先通过 Stripe 对象和事件确认原请求是否已成功。所有人工补偿要记录原因和操作者。


## 授权金额与最终金额的沟通

预授权金额应尽量符合客户对最终账单的合理预期。若商家需要为押金、额外服务或可能发生的损坏预留金额，购买页面应说明授权用途、预估范围以及最终按什么依据结算。不能以客户同意某个预授权金额为由，任意收取未向客户说明的金额。

最终金额低于预授权时，商家只应捕获实际应付且有业务依据的金额；高于预授权时，先判断是否需要再次授权及是否获得客户同意。酒店、租赁、餐饮等场景可能有行业惯例或网络规则，但仍需依据具体支付方式和合同处理。客户对银行卡待处理记录的理解也很重要，订单页面要能区分“银行暂时预留”和“商家已经入账”。

发票和收据应使用最终捕获金额，而非初始预授权额。若系统提前发送订单确认邮件，文案需明确哪些金额只是估算或授权额度；捕获完成后再发送最终账单信息。对客户的退款请求，也先判断资金是已经捕获还是仅有授权，避免误把授权撤销说成退款已到账。

## 订单、库存和授权状态同步

授权流程应与库存预留和履约系统一起设计。付款授权成功但库存后来售罄时，需要迅速取消授权并通知客户；库存确认后才捕获，则要保证预留库存不会在等待期间被其他订单占用。订单和支付对象需要保存彼此的稳定 ID，后台可根据授权成功、捕获成功、取消或失败状态更新业务进度。

Webhook 用于可靠同步 PaymentIntent 状态。验证签名、实现事件幂等，并在处理关键事件时读取最新 PaymentIntent。事件可能重试或延迟到达，不能让旧事件覆盖本地最新状态。定时任务可以扫描即将过期的 `requires_capture` 对象，提醒工作人员处理，但最终动作应先核实 Stripe 侧当前状态。

客服后台应能区分授权金额、捕获金额、剩余额度、退款金额和待释放额度。报表也应把“授权成功”与“收入已捕获”分开，避免将预留金额错误计入已收款。月末对账时，以 Stripe 的实际捕获交易和余额记录为依据，不要仅按订单的“支付成功”标签汇总。


## 测试环境中的完整验证

不要只测试一笔授权成功的标准卡支付。至少准备授权被拒、需要客户认证、客户关闭页面、订单库存不足、全额捕获、低于授权金额捕获、撤销未捕获授权、授权接近到期以及重复提交捕获请求等案例。每个案例都要观察 PaymentIntent 状态、客户银行端可能看到的提示、Webhook 事件、本地订单状态和发货系统任务。

若业务需要多次捕获，额外验证支付方式和账户是否支持 multicapture，并测试每次捕获后剩余额度、最后一次捕获参数和未使用部分的释放行为。不要在生产环境用真实客户订单试探捕获边界。测试结果写入操作说明，客服和财务都要知道怎样解释待处理授权与实际入账的差异。

对于超时和网络中断，模拟服务端已发送 capture 请求但客户端没有收到响应的情形。恢复任务先查询 PaymentIntent，确认是否已捕获，再决定后续动作。用唯一业务请求 ID 记录每一次捕获意图，可以避免工程重试与人工点击同时发起新的收款。

## 常见问题排查

**PaymentIntent 显示需要捕获，客户说已经被扣款。**解释银行可能显示待处理授权，核对 amount_capturable 和 captured 状态，再告诉客户当前还未完成捕获或正在等待处理。

**捕获时提示授权已失效。**检查授权时间、交易类型和支付方式的具体有效期限，确认是否需要重新向客户授权。不要重复使用已取消或过期的 PaymentIntent。

**捕获金额超过可捕获余额。**重新读取 PaymentIntent 的 amount_capturable，核对本地订单调整、已完成的部分捕获和并发请求。后端应以 Stripe 返回值为准，不让前端金额覆盖可用额度。

**订单取消但待处理额度还在。**确认 PaymentIntent 是否已成功取消以及事件是否同步，说明银行释放授权可能需要处理时间。保留取消时间和对象状态，必要时向客户解释下一步。

**分批发货重复收款。**检查 final_capture 和 multicapture 支持条件、每次捕获记录、幂等键及工作人员重试日志。保证每个发货批次只产生预期的一笔捕获。


## 适用与不适用的场景

手动捕获适合商家需要在授权后核对货物、服务或最终账单的流程，例如确认库存后才发货，或客户退房时结算已发生的额外消费。若订单金额购买时已完全确定、商品立即交付且不需要人工检查，自动捕获通常更直接，也减少授权过期、客户等待和支持工单。

评估时把“需要延迟多久”“最终金额可能变化多少”“订单能否取消”“授权过期后怎样补救”写成具体流程。如果答案是数周以后才确定，普通授权窗口可能不适合；如果只是数分钟等待库存系统返回结果，可以设计较短的自动化捕获步骤。不要仅为了让后台多一个审核开关而延迟收款。

定期统计待捕获订单的平均处理时间和过期比例，评估流程是否仍值得采用。

并复核授权时长假设。

及时调整提醒与履约安排。

## 上线检查清单

1. 确认手动捕获确实解决了库存、发货或最终金额确定问题。
2. 验证目标支付方式、交易类型和账户支持手动捕获。
3. 在服务端创建 PaymentIntent 并保存订单映射。
4. 授权通过后标记“已授权”，不要直接计入已收款。
5. 监控授权期限和即将过期的待捕获订单。
6. 根据实际履约金额决定全额或部分捕获。
7. 只有支持 multicapture 时才设计多次捕获流程。
8. 取消订单时及时处理未捕获授权。
9. 对捕获、取消和 Webhook 处理实现幂等。
10. 分开记录授权、捕获、退款、余额和履约状态。

## 总结

Stripe 手动捕获适用于需要先授权、稍后确认履约或最终金额的业务。它会在客户银行卡上形成临时授权，而不是立即完成收款；授权有期限，未捕获对象会被取消，部分或多次捕获也受支付方式和配置约束。平台应将授权、捕获、取消、退款和履约分别建模，并以真实 PaymentIntent 状态同步订单。

实现前请查看 [创建 PaymentIntent API](https://docs.stripe.com/api/payment_intents/create) 和 [捕获 PaymentIntent API](https://docs.stripe.com/api/payment_intents/capture)，在测试环境覆盖授权、全额捕获、部分捕获、取消和过期处理，并根据账户与支付方式核验实际期限。
