Stripe Dashboard 出现 dispute（争议或拒付）时，商户需要在限定时间内决定如何处理并准备相应材料。收到争议并不自动说明客户恶意，也不代表商户只要上传大量截图就能赢。争议原因、订单类型、客户沟通、退款处理和交付记录都会影响证据该如何组织。准备材料的目标是让审查者能快速理解交易发生了什么、客户提出了什么问题，以及现有记录如何支持商户的说明。

本文适用于 Stripe 商户和负责客服、财务、运营的团队。争议流程、可提交字段和时限会因支付方式、卡组织、国家或账户而异，实际应以 Dashboard 中该笔争议的说明为准。本文不是法律意见，也不保证争议结果。

## 先读争议原因和截止时间

收到 Stripe dispute（争议）后，先在 Dashboard 打开该争议，核对争议编号、原始付款、金额、币种、持卡人提出的原因类别、回复截止时间和当前状态。不同原因需要的证据不同，例如“未收到商品”“订阅已取消”“不认识这笔付款”和“商品与描述不符”，不能用同一段通用说明应付所有类别。截止时间以 Dashboard 显示为准，内部应预留审核与提交时间。

## 先查交易是否已经退款

找到原始 Charge 或 PaymentIntent，核实此前是否全额或部分退款、是否有其他争议、是否存在重复订单。若款项已退款，整理退款时间、金额和 Stripe 记录；不要再声称款项尚未退还。若仅承诺退款但实际还未执行，说明不能当成退款已完成的证据。对同一交易的事实要在证据、邮件和后台记录中保持一致。

## 按争议类别选择证据

Stripe 提供的字段和卡组织审查方向会因争议类别变化。数字商品可整理访问或下载日志、交付记录和账户活动；实体商品可整理承运商、运单、发货地址和签收信息；订阅可整理购买时展示的续费与取消条款、客户确认记录、取消时间和取消后的使用记录。只提交与争议相关、能够支持主张的材料。

## 建立清楚的时间线

用简洁时间线把下单、付款确认、发货或服务开始、客服沟通、取消申请、退款和争议提交串起来。每个关键节点标注日期、时区和对应凭证。时间线能帮助审核方理解材料之间的关系，也能暴露内部记录是否互相矛盾。不要把猜测当作事实；缺少某项记录时，应如实说明，而不是用推断填补。

## 证据应能独立核验

保存订单详情、客户当时看到的条款、付款收据、发货或服务记录、客户沟通原文和平台事件。证据应能与 Stripe 原交易关联，例如有订单号、交易 ID、客户标识和日期。对于网页条款，尽可能保存当时版本、展示位置和客户确认信息；仅提供今天网站上的政策页面，未必能证明购买时客户看过相同内容。

## 不要夸大或伪造证据

只提交真实、相关、可解释的资料。不要修改截图日期、拼接不存在的签收信息、伪造客服对话、把 IP 地址描述成身份验证，或把授权状态说成客户明确同意所有条款。材料不实会损害申诉可信度，并可能造成额外账户风险。必要时让财务或法务复核陈述，确认每句话都有记录支持。

## 把长材料压缩成审核友好摘要

先用几句话说明交易内容、客户主张、商户核查结果和关键证据，再按问题类别附上支持文件。截图需完整显示相关日期、订单号和上下文，避免只截取对自己有利的一小块。对敏感个人信息做最少化处理，但不要遮掉证明交易关联所必需的字段。文件名可用日期与证据类别，不要在文件名放完整卡号或个人敏感信息。

## 在提交前做一致性复核

核对金额、币种、日期、时区、客户名称、地址和退款状态是否在所有材料中一致。确认所有附件都指向同一个交易，截图没有测试数据或其他客户记录。检查叙述有没有前后矛盾，比如一处说已退款、一处又说拒绝退款。提交前让不熟悉本案的同事只读证据包，判断其能否快速说清发生了什么。

## 理解提交后的状态

Stripe Dashboard 会显示争议状态和证据提交情况。提交后保存提交时间、证据摘要和内部工单编号，跟踪后续更新。证据已经送交后，不要在外部网页继续公开客户资料。争议结果由发卡行或卡组织按其流程决定，提交完整材料不等于保证胜诉。收到结果后记录原因，以便改进付款描述、客服处理或退款流程。

## 联系客户的边界

如适合联系客户，保持专业并尝试理解其问题，确认是否为家庭成员购买、账单描述不熟悉、订阅续费或退款未到账。若商户能及时退款或解决履约问题，可按平台支持的流程处理并保存实际完成的记录。不要施压客户撤回争议，不要以删账户或停止服务威胁客户，也不要承诺平台一定会判商户胜诉。

## 保护账号与个人资料

证据中可能包含邮箱、地址、访问记录和通信内容。只向有处理职责的人员开放，避免公开贴到社区或把完整文件发给不相关第三方。上传前确认材料和收件对象，清除与本争议无关的个人信息。遵循商户自己的隐私、数据保留和访问权限规则。

## 形成可复用的案件档案

为每一宗争议建立独立文件夹或工单，保存原始导出、最终提交版本、时间线、审核人和结果。原始文件应保持不变，编辑或裁切版本另存并注明处理方式。这样在后续出现同类理由、支付服务商要求复核或内部审计时，团队能复现提交过程，而不用依靠某位同事的记忆。

## 按案件类型组织材料

### 数字商品未收到

整理购买确认邮件、账户登录或下载记录、商品交付时间、客户实际使用活动和客服沟通。只展示与争议订单相关的访问证据，标明记录时区与系统含义。若仅有账户创建记录却没有交付或访问证据，不要把创建账户说成客户已经使用商品；可以补充实际发送与客户收件情况。

### 实体商品未收到

提供订单所填送货地址、承运商名称、发货时间、追踪编号、运输状态和签收信息。将物流页面与原订单对应起来，确保不是同一客户的另一笔订单。若承运商显示投递但没有签收，可如实提供投递记录与查询结果，不应自行推定由客户本人收取。

### 订阅取消争议

准备购买时展示的自动续费周期、价格、取消方式和退款政策，以及客户接受条款的记录。补充取消请求的接收时间、账户操作日志、后续通知和服务使用情况。关键是说明客户在购买时看到什么、何时提交取消、商户何时处理，避免只引用当前网站上的一般政策。

### 商品与描述不符

提供购买页面当时的商品描述、规格、图片或服务范围，连同实际交付内容、质量检查结果和与客户沟通记录。针对客户提出的具体差异逐点回应。不要只重复“商品符合描述”，要说明对应哪条规格、哪张记录，无法确认的部分应坦诚说明。

### 不认识的扣款

整理付款收据、订单确认、客户账户和商户名称/账单描述之间的关系，以及购买后的通知。如果账单名称与网站品牌不同，提供交易时页面如何说明商户身份的证据。地址、邮箱或设备相似可以作为辅助背景，但不能把这些线索说成绝对证明持卡人本人操作。

### 重复收费

逐笔列出付款时间、金额、币种、交易 ID、对应订单和退款状态。若其中一笔确为重复并已退款，附退款记录及退款时间，并解释另一笔对应的商品或服务。避免只提交一个订单页面而不说明另一笔交易，审核者需要看出为何保留或退回每笔金额。

### 退款未处理

提供原付款、退款发起日期、退款金额和 Stripe Dashboard 中的实际退款状态。客户的银行何时显示款项可能受发卡行处理影响，不要承诺固定到账日期。若退款还没发起，应按真实情况说明并考虑先处理退款，而不是提交一份把未来计划描述为已完成的材料。

### 客户已经取消但又被续费

对照取消请求时间、订阅的计费时间、系统实际处理时间和客户看到的确认邮件。说明是否在下一次续费前收到请求，以及系统记录何时更新。若商户取消流程有延迟或通知失败，应提供准确记录并按政策处理，不要将客户操作时间改写成后台完成时间。

### 服务质量不满意

呈现购买页面说明的服务范围、交付日期、服务成果、沟通过程和客户具体反馈。围绕客户不满意的事项回应，而不是只提供合同首页。若存在可改进或补救方案，保留提出方案和客户回应的记录；不要把客户没有回复理解成对服务质量满意。

### 价格或金额不符

核对商品页面标价、折扣条件、税费、账单币种和交易确认页。把计算方式解释清楚，说明客户在购买前能看到的总额。若折扣没有应用或价格发生配置错误，应调查并如实处理；不要仅凭后台现价证明过去付款金额正确。

### 客户沟通证据

提供完整且相关的邮件或客服消息上下文，包含日期、发送方和问题解决过程。避免只截取一句对自己有利的话，或删掉客户提出异议的前后文。需要翻译时保留原文，并标注译文；不要改写成客户没有表达过的承认或确认。

### IP 与设备资料

访问日志可辅助说明数字商品是否被访问，但共享网络、VPN、代理、动态地址和家庭设备都会影响解释。说明日志字段含义、记录来源与时区，不要将 IP 地址等同于真实姓名或身份证明。使用此类资料时只提交相关交易期间的数据，并避免过度采集。

## 提交前核对清单

- 原始付款、争议编号、币种和金额是否一致？
- 已确认 Dashboard 显示的原因类别和提交截止时间？
- 每份文件是否对应这一位客户和这一笔交易？
- 时间线是否说明购买、交付、沟通、退款和争议节点？
- 是否保存客户购买当时能看到的政策和价格？
- 退款状态是否准确，未完成的退款有没有被误写成已完成？
- 截图上下文完整、日期与时区清楚，且没有其他客户数据？
- 事实陈述是否克制、可验证，没有把推测说成事实？
- 是否有同事复核附件与说明之间的一致性？
- 是否保存最终提交版本、提交时间和后续处理人？

## 常见准备错误

### 只上传很多文件，没有说明关联
文件数量多不等于证据充分。应写一段简洁说明解释每个附件证明什么，并让编号、日期、金额和客户能对应到争议交易。缺少关联说明会让审查者自行猜测截图的来源。

### 只展示有利片段
删去不利的客服对话或把截图裁得看不出时间和上下文，可能让整个材料显得不可靠。应提供必要的完整上下文，解释事实而不是隐藏矛盾。若商户犯了操作错误，准确说明并按政策处理。

### 用当前页面代替历史页面
现行退款与取消条款未必与客户购买时的版本相同。保留历史版本、确认记录、邮件或结账页版本更有帮助。不能证明当时显示过某条政策时，不要声称客户已经明确看到。

### 把授权说成最终付款
银行授权、支付成功、发货和退款是不同节点。提交前确认每个状态的准确含义。客户账户中暂时看到一笔扣款，不能证明商户已成功收款；退款已创建也不一定证明银行已经入账。

## 结果跟踪与流程改进

证据提交后保存 Dashboard 中的提交记录，注明谁复核、提交日期和采用的材料版本。按平台状态跟踪后续决定，不要重复提交互相矛盾的说明。若争议失败，记录原因类别、缺少的证据、条款展示方式和服务履约情况，从中改进账单描述、退款入口、取消流程、交付通知或客服响应。

定期抽查案件档案是否能让未参与本案的人重建完整时间线。将争议原因与业务流程连接起来，例如客户不认识账单描述时检查商户名称展示；订阅取消争议时检查取消确认邮件；商品未收到时检查物流通知。目标是减少可预防的误解和服务问题，而不是只在争议发生后堆材料。

## 总结

收到 Stripe 争议后，先核对原因类别、原始交易和截止时间，再按订单类型整理能核验的材料。把证据和交易关联，建立客观时间线，核对退款、政策与交付记录，并在提交前复核陈述和附件的一致性。只提供真实、相关的材料；争议结果由相应支付网络流程决定，准备充分也不能保证胜诉。
