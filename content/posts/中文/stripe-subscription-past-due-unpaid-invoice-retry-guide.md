# Stripe 订阅显示 past_due 或 unpaid 怎么办？发票重试与服务权限核对

使用 Stripe Billing 收取周期费用时，商家可能在 Dashboard 看到订阅状态为 past_due（逾期）或 unpaid（未付款），客户则收到付款失败邮件，仍然可以访问服务或突然被停用。理解这两个状态需要同时查看订阅、关联 Invoice（发票）、付款尝试和商家的重试设置，而不是只盯着一个标签。

Stripe Billing 的订阅状态会随着发票付款和重试规则变化。Stripe 官方资料说明，订阅发票付款失败后，系统可能继续尝试付款；所有重试仍失败后，订阅可以按商家的设置变为取消或 unpaid。past_due、unpaid 与发票显示的 Open、Retrying 等提示是不同层级的状态。某些 Dashboard 徽标只是对发票当前情况的描述，不是独立的 Invoice status。

本文提供商家与客户的排查方法，帮助确认欠款对应哪个账期、是否还会自动重试、是否需要客户进行身份验证，以及服务何时暂停。Stripe Billing 的重试策略、状态和菜单会更新，并受商家账户配置影响，应以当前 Dashboard 和官方文档为准。

## past_due 和 unpaid 有什么区别

past_due 通常表示订阅的付款存在问题或关联发票尚未成功付款，商家可按配置继续重试、通知客户或要求其更新付款资料。past_due 并不意味着一定已经取消订阅，也不代表当前发票永远无法支付。需要检查该订阅的最新 Invoice、PaymentIntent 状态以及下一次重试时间。

unpaid 通常表示商家的最终重试动作将订阅标记为未付款。此时与 active 或 past_due 时的服务权限、后续发票处理和客户沟通可能不同。某些计费设置可在重试结束后取消订阅，另一些设置则将其标记为 unpaid。具体行为取决于 Stripe Billing 配置和商家实施，不能只凭状态名称推断所有账户都相同。

订阅状态也不同于 Invoice 状态。Invoice 可能显示 draft、open、paid、uncollectible 或 void；Dashboard 还可能在 open 发票旁显示 Past Due 或 Retrying 的辅助标记。看到一张发票 open 不等于订阅一定 unpaid；反之，订阅状态变化也不能证明所有历史发票都已解决。

## 第一步：找到具体订阅和发票

商家在 Dashboard 中先打开对应 Customer 和 Subscription，记录订阅 ID、当前状态、套餐、账单周期、创建时间、取消或试用设置。然后查看最新的关联发票和 PaymentIntent，确认应付金额、币种、付款方式、最近一次失败代码、重试次数和计划中的下一次动作。

一个客户可能有多个订阅或多个 Stripe Customer 对象。确保查看的是当前服务对应的订阅，不要只根据邮箱搜索结果判断。如果订单系统使用自己的客户 ID，应核对内部客户记录与 Stripe Customer ID、Subscription ID、Invoice ID 的关联，避免将另一项服务的欠款误认为当前订阅。

还要分清一次性付款失败和订阅续费失败。一次性支付失败通常没有订阅周期要处理；订阅场景还需要考虑后续重试、客户权限、暂停或取消策略。客服应把订单账期、发票号和失败日期说清楚，不要笼统地告诉客户“Stripe 扣款失败”。


## 检查 Invoice 状态和失败记录

商家应打开具体发票查看其状态、应付金额、已付金额、付款尝试和 last payment error。Dashboard 可能在 Open 发票旁显示 Past Due 或 Retrying 提示，但这类徽标不一定是正式发票状态字段。核对页面中实际 Invoice status，再查看它所关联的 PaymentIntent 是否处于 requires_payment_method、requires_action、processing、succeeded 或其他状态。

若发票仍为 Draft，可能尚未最终确定，不能简单理解为客户逾期；若为 Open，仍需查看付款方式和账期；若为 Paid，应检查客户付款记录和订阅周期。Void 与 Uncollectible 也代表不同处理结果，商家需要依据自己的账务政策解释。把一次失败付款误当成最终欠款，或将仍开放的发票误标为已付，都会影响后续重试和对账。

客户支持可提供发票号、服务周期、当前应付金额和下一步链接，但不要要求客户通过非官方方式重复发送卡号。若发票由订阅自动生成，商家还要查看它是否是最新周期，或旧周期的重试账单。

## 检查付款方式和客户需要完成的操作

查看失败原因时，确认是银行卡被拒、余额不足、卡片过期、付款方式未设置，还是付款要求额外身份验证。Stripe 的 API 和 Dashboard 可能显示不同详细程度。不要把所有失败都归结为客户银行卡没钱。若是 3D Secure 或其他需要客户确认的流程，可能需要客户返回商家安全页面完成验证，而不是等待自动重试。

Stripe 官方帮助资料指出，对于因 3D Secure 身份验证问题而失败的订阅付款，系统可能不会根据普通重试设置自动再次尝试。商家可能需要在 Billing 设置中启用 Stripe 托管链接，以便客户确认付款。客户收到更新付款方式或确认付款的邮件时，应检查商家名称和域名，避免在仿冒页面输入信息。

客户可以从商家官网的账单页或 Customer Portal 更新付款方式。更换钱包默认卡不一定会更改特定订阅使用的指定付款方式。完成更新后，让商家确认它是否关联到正确 Customer 和 Subscription，并核实原来失败的发票是否需要手动重试。不要直接建立一份新订阅来绕过旧账单，这可能导致重复续费。

## 自动重试设置怎样影响状态

Stripe Billing 可按商家的设置在付款失败后安排重试。重试时间、次数和最终动作取决于 Dashboard 的 Billing 配置、订阅周期、支付失败原因以及所用付款方式。用户看到 past_due 时，先查看商家是否正在重试、下一次尝试时间以及是否需要用户操作；不要假设它会在固定天数内自动成功。

如果所有尝试失败，商家可以根据设置将订阅取消或标记为 unpaid。已发票的付款记录仍需按 Invoice 状态单独查看。商家应明确告知客户：付款方式更新后是否自动重试、是否需点击确认、服务是否在宽限期继续，以及何时可能暂停或取消。

重试时间如果跨越多个账单周期，可能出现不同发票的重试重叠。Stripe 官方支持文章说明，某张较早发票的最后一次重试失败，不一定会改变订阅状态；结果还可能取决于该订阅最新发票的付款状态。商家配置长于账期的重试计划时，应审查这种边界情况，避免较旧发票的最后一次失败错误取消刚刚续费成功的订阅。


## 免费试用结束时没有付款方式

新订阅在试用期结束时，如果客户没有保存可用付款方式，系统可能先生成首张发票并尝试付款，然后订阅转到 past_due 或其他由 Billing 配置决定的状态。客户可能看到试用已经结束，却没有立即收到清楚的失败原因。商家应在试用开始前说明是否需要提供付款方式、试用结束日期、首期价格以及付款失败后的服务访问规则。

如果客户认为试用仍在继续，核对订阅的 trial_end、发票日期和商家条款。某些定价或试用优惠可能让首笔账单金额、周期起点与用户预期不同。不要仅因订阅页面一度显示 active 就认为付款成功；确认 Invoice 与 PaymentIntent 最终状态。

对免费试用转付费的商家，提前发送试用结束提醒并提供管理订阅入口，能让客户更方便更新付款方式或取消。若首笔付款需要 3DS 或其他银行验证，发票失败后要让客户完成必要动作，而不是只等待普通重试。

## past_due 时服务是否应该继续

Stripe Billing 的付款状态本身不会自动决定所有商家应用的访问权限。商家系统可能继续给 past_due 客户一段宽限期，也可能在收到特定 Webhook 后暂停部分服务。Stripe Dashboard 上的订阅状态和商家产品中的服务权限需要通过集成逻辑同步，因此两者短暂不一致是可能的。

开发者应明确服务权限策略：哪些状态保留访问，哪些状态限制新功能，哪些状态完全暂停；还要考虑客户刚完成付款但 Webhook 尚未更新、发票等待处理或银行扣款异步处理的情况。不要收到一条 PaymentIntent 失败事件就立刻删除账户数据，后续可能会重试成功。

使用 Webhook 更新订阅状态时，要处理重复事件和事件顺序。先持久化事件，按 Subscription 和 Invoice ID 关联，再根据最新对象状态和业务规则更新访问权限。对发票重试，分别记录每期账单结果，不要将上期 unpaid 自动等同于当前期间没有付款。

## 客户怎样恢复订阅付款

消费者首先检查商家发来的付款失败通知和订阅门户，确认具体欠费周期、金额和付款方式。若通知提示需要验证银行卡，使用商家官网或 Stripe 托管的官方结账页完成身份确认。不要通过邮件回复银行卡完整信息，也不要把一次性验证码告诉客服。

如果你刚更新了付款方式，确认商家账户里的保存状态和当前订阅的默认方式。然后联系商家询问旧发票是否会自动重试，还是需要他们重新开放付款链接。先确认 Stripe 中尚无成功付款或待处理交易，再尝试补缴，避免同一账期出现两笔付款。

若你认为发票金额错误，或你已经取消订阅但仍收到旧账期账单，向商家提供取消确认、Invoice ID 和订阅周期，让商家解释费用对应的服务时间。取消订阅不一定会消除取消前已经产生的发票；同样，payment method 失败也不代表服务自动取消。

## 长重试计划的特殊情况

如果商家的重试周期比订阅账单周期更长，上一期发票的重试可能和新一期发票同时存在。Stripe 官方支持中心描述了这种可能性：较早发票最后一次重试失败时，如果该订阅最新发票已成功付款，订阅状态可能保持不变；如果最新发票仍未支付，订阅则可能依最终设置取消或进入 unpaid。

商家应测试这种跨周期场景，不要仅根据旧发票的失败结果发出“订阅已取消”或“账号会立即停用”的通知。检查最新 Invoice、重试队列、订阅当前状态和客户服务状态，确认之后再通知客户。重试窗口可根据业务账期规划，减少多期发票同时处于重试中的复杂情况。

如果发票失败与付款方式需要用户操作有关，确保通知和托管确认链接已启用。对于需要 3DS 验证或其他安全确认的付款，客户可能要在银行或支付页面完成操作，普通自动重试不一定能代替客户确认。商家应提供清楚的下一步流程，而不是让客户无限等待。


## 客服如何解释欠费而不误导客户

通知客户时，引用准确的账期、金额、发票编号和当前状态，说明是否需要客户采取动作以及截止时间。不要仅发“付款失败”而不解释是更新卡片、进行身份验证还是等待再次尝试。也不要在 Stripe 仍处理中时要求客户用另一张卡立即付款。

## 商家上线前的核对清单

- 明确 Stripe Invoice 状态与 Subscription 状态的区别。
- 为每个 Customer、Subscription、Invoice 保存内部订单映射。
- 检查付款失败原因、PaymentIntent 和是否需要客户确认。
- 审核 Smart Retries、重试次数和最终动作设置。
- 明确 past_due、unpaid、canceled 时的服务权限与沟通规则。
- 测试旧发票重试与新账期成功/失败交叠的情况。
- 对 3D Secure 等需用户操作的失败设置有效通知入口。
- Webhook 处理应支持重复事件、异步结果和安全重放。
- 付款方式更新后确认它关联到正确订阅，不重复创建订阅。
- 保留客户通知、发票状态和服务权限调整的审计记录。

同时保留站内通知和邮件发送记录。

## 常见问题

### past_due 表示订阅已经取消吗？

不一定。past_due 表示付款存在问题或正在处理，最终状态取决于重试规则、用户动作和商家配置。查看 Subscription、最新 Invoice 和 Dashboard 中的下一步提示。

### unpaid 代表发票已经作废吗？

不一定。Subscription 为 unpaid 与 Invoice 的 open、void 或 uncollectible 是不同对象状态。逐个检查发票是否已付款、仍可重试、作废或被标记为无法收取。

### 更新银行卡后会自动补扣吗？

取决于发票、重试策略和付款是否需要额外客户验证。更新后请确认商家是否安排自动重试，或需手动从托管页面确认付款。不要只换卡而不核实发票状态。

### 订阅显示 past_due，我还可以使用服务吗？

服务访问由商家系统策略决定，Stripe 状态本身不保证你的产品一定继续或立即暂停。查看商家账户说明或联系服务商，确认宽限期和处理日期。

### 为什么旧发票重试失败，订阅仍显示正常？

若最新发票已经成功，Stripe 对订阅状态的处理可能与旧发票的最终失败不同。检查最新账单和商家重试设置，不要只看某一张历史发票。

## 总结

Stripe 订阅 past_due 或 unpaid 时，必须将 Subscription、最新 Invoice、PaymentIntent 和服务权限分开核对。past_due 可能仍在重试或等待客户验证；所有重试失败后，最终动作由 Billing 设置决定。3D Secure 需要用户确认的付款可能不会按普通策略自动重试，跨越账期的重试也可能与最新发票状态交错。商家需设计清楚的重试、Webhook 和访问权限流程；客户更新付款方式后，应确认对应发票是否已补缴或仍待确认。
