面向多个国家销售时，支付页面是否使用顾客熟悉的语言会直接影响理解和完成付款的体验。商户启用 Stripe Checkout 后，有时发现结账页仍显示英文，有时同一条支付链接在不同浏览器中呈现不同语言，也有人以为切换 Checkout 的 locale 就能把商品名称、税务说明和商户自己的网站一并翻译。实际上，支付页面界面的本地化与商户提交的商品资料、品牌信息、货币和订单文案是不同层次。

本文说明 Checkout 的 locale 应如何选择，自动语言识别与显式语言设置的区别，哪些文本需要商户自行提供翻译，以及如何测试不同地区顾客看到的页面。Stripe 支持的语言和页面元素会随产品更新而变化；上线前应核对当前官方文档，并使用真实的测试环境验证自己采用的 Checkout 模式。

## 先区分界面语言和商户内容

Checkout 的界面语言包括 Stripe 托管表单中的按钮、字段标签、提示和部分验证文案。商户传给 Session 的商品名称、商品描述、价格名称、优惠说明、品牌名及自定义文字则由商户提供。若商户只创建了中文的商品数据，Checkout 界面自动切换成另一种语言后，商品名称仍可能是中文；如果商户商品标题只有英文，选择中文 locale 也不会自动把它翻译成中文。

因此，多语言支付通常需要同时管理两类资源：一类是 Stripe Checkout 本身可本地化的固定界面，另一类是商户网站和订单数据中由商户维护的内容。商品、税费、运费、退款政策和客服说明尤其需要与当前语言版本一致。不能把 locale 参数当作整个网站的机器翻译开关。

还要区分界面语言和货币。顾客选择法语页面，不代表付款金额必然变成欧元；页面以当地语言呈现，也不意味着商户具备向该国家收款、配送或开票的资格。语言、币种、配送范围和税务是关联但独立的业务设置，应分别配置和测试。

## 自动识别 locale 的作用

Stripe Checkout 可以使用 auto 等自动设置，根据顾客浏览器等环境选择页面语言。自动方式适合面向多个语言市场、顾客可能从不同设备访问、商户不想维护每条支付链接的固定语言时使用。顾客浏览器首选语言不同，页面呈现也可能不同，这是自动模式的预期效果，不一定代表 Session 配置异常。

自动识别并不能确保每个顾客都看到商户希望的语言。浏览器语言可能与顾客居住地、网站语言或付款方式国家不同；顾客也可能使用共享设备或浏览器设置为另一种语言。若业务需要把结账语言与顾客在网站主动选择的语言保持一致，可以考虑在服务端创建 Session 时显式指定受支持的 locale。

确定使用哪种方式时，先定义语言来源优先级。例如尊重顾客在网站主动选的语言，其次使用账户保存的语言偏好，最后回退到浏览器自动识别或默认语言。不要仅根据 IP 地址推断语言，因为旅行、代理和跨境用户都可能导致地址与语言偏好不一致。

## 显式设置语言前的检查

Session 创建代码中的 locale 参数应该来自服务器端认可的语言选项，不应直接把任意浏览器字符串原样传入。建立语言白名单，将网站语言代码映射到 Stripe 支持的 locale。顾客选择的语言、网站语言和 Stripe locale 之间有时需要映射，例如网站内部代码的命名与 Stripe API 接受值不完全一样。

如果传入不受支持的语言值，系统可能返回参数错误，或回退到另一种体验，具体行为应以当前 API 版本和文档为准。测试过程中要检查 Session 创建接口实际返回的 locale，而不仅仅检查前端按钮上显示的语言选择。将合法的语言映射写入配置或共享模块，避免不同服务使用不一致的大小写或代码格式。

创建新的 Checkout Session 才能按照该次请求的语言设置渲染结账页。不要假设修改网站语言后，已创建的 Session 链接会自动更新到新的 locale。对于已发送给顾客的会话，先确认 Session 状态和订单金额；需要重新创建时，应依据商户订单系统生成新 Session，并正确处理原来的支付尝试。

## 网站语言、Checkout 和返回页面的一致性

良好的结账体验应让顾客从商品页到支付页面再到订单确认页都知道自己在哪个流程中。顾客在中文网站上点击购买，却进入全英文结账页，会增加不确定感，尤其是税费、退款和配送条款也被切换时。应尽可能将网站当前语言传递到 Session 创建服务，并使 success_url、cancel_url 返回对应语言的页面。

但返回页面本身也要通过服务器确认订单结果。success_url 的语言可以根据网站路由选择，却不能因为用户浏览到中文成功页就认定付款成功。服务端应根据 Session ID 查询当前对象，或者等待经过签名验证的 Webhook 更新订单后，再显示准确状态。

取消付款时，也应返回原语言版本的购物车或订单页面，保留顾客已选商品和必要的非敏感信息。若顾客再次发起结账，服务端需要重新核验价格、库存、币种和优惠，不能只用旧 URL 构造新的付款请求。每次新 Session 的语言选择应与当前站点和顾客偏好一致。

## 翻译商品名、价格和自定义文案

如果商户在 Stripe Products 中只维护单一语言的名称，Checkout 可能仍按该商品名称原样展示。多语言产品目录可以在商户自己的商品系统中维护不同语言的标题和描述，并根据顾客选择构造或选择对应 Stripe 商品及价格。要确保不同语言版本代表同一商品、同一价格政策和同一履约内容。

价格名称、发票描述、自定义字段提示和 Checkout 自定义文字也要逐项梳理。某些对象的文本用于订单收据或发票，不一定与 Checkout 页面上的字段共享翻译。应准备一份文案清单，记录文字出现的页面、由哪个系统提供、支持哪些语言、谁负责更新。

翻译不应只追求字面一致，还要符合支付场景的表达。比如“订阅将自动续费”“税额根据地址计算”“付款后何时发货”等内容，若翻译模糊，顾客可能误解收费频率或履约条件。费用、税费和续订条款应准确清楚，重要条款不能因为空间不足而只保留一个短标签。

## 品牌信息和语言信任感

Checkout 的品牌名称和标识要与顾客在商店、订单确认邮件和银行账单上看到的信息保持一致。语言切换不应让商户突然变成顾客无法识别的品牌名。使用顾客认得的商户名称和一致的标志，有助于顾客判断这笔付款来自哪里，也能减少陌生扣款疑虑。

检查 Stripe 账户里的业务展示信息、图标、Logo、支持邮箱和客服网址。品牌图像要符合官方的格式和尺寸要求；文字中的公司名称、商标和产品名要在不同语言间统一。若商户品牌名保留拉丁字母，也可以在描述文字中补充当地语言的说明，但不要在未经审核的地区使用可能造成误认的名称。

同时检查银行账单描述符、收据和订单邮件。Checkout 中文界面不代表银行账单一定展示中文商户名；账单描述符也有长度、字符和卡组织规则。通过测试流程和官方 Dashboard 设置核对各处显示效果，避免收款页面写一个名称、邮件写另一个名称、账单又出现第三种拼写。

## locale 与多币种的关系

语言选择和币种展示是两套配置。即便顾客看到本地化页面，Session 金额仍可能使用商户指定的币种。商户想向顾客提供本地币种价格时，需要配置多币种价格、适用的本地定价能力或相应的货币转换方案，并确认账户和产品支持。不要仅通过切换 locale 来推断实际扣款货币。

价格转换可能涉及汇率、手续费、商户承担费用方式和退款换算结果。页面上应让顾客在付款前看到明确货币代码或金额符号，并在订单确认和后台对账中记录扣款币种与商户结算币种。不同货币可能存在小数位规则差异，服务端金额计算应按照 Stripe 对支持币种的要求处理。

本地语言和本地货币一致不一定是最优选择，但顾客需要理解实际会从卡上扣哪种货币。避免用仅有符号、没有代码的方式造成歧义，例如多个货币都使用相同的符号。订单和客服记录保留 ISO 货币代码，便于跨地区处理争议和退款。

## 语言回退和缺失翻译

商户网站可能支持多种语言，但 Stripe Checkout 不一定支持所有网站语言。应制定一个明确回退策略：无法提供目标 locale 时，使用哪一种可读语言；商品名称是否沿用原始语言；顾客是否可以回到网站切换语言。回退不能悄悄让顾客进入无法理解的页面，特别是涉及授权、订阅和付款条款时。

建议在 Session 创建服务记录选择过的语言、最终传给 Stripe 的 locale、订单语言和网站语言版本。这样顾客反馈页面语言异常时，客服可以确定是顾客浏览器、服务器映射还是预设策略导致。记录语言信息时遵循数据最小化原则，不需要保存完整浏览历史或不必要的设备指纹。

当商户新增语言时，要同时检查商品目录、税务文案、配送说明、邮件模板、退款政策和客服支持能力。只有支付按钮翻译了，而售后页面仍无法回应该语言，会造成体验断层。上线前应让熟悉当地市场的人审阅重要的价格和法律说明，而不是仅依赖机器翻译。

## 多设备和浏览器测试

语言测试至少应覆盖主流浏览器、桌面和移动设备，以及顾客主动切换网站语言、浏览器语言不一致和浏览器使用默认语言等场景。测试用例要验证实际 Checkout 页面语言、商品名、价格、按钮、验证信息、取消返回地址和成功页内容，而不是只断言 Session API 返回了某个 locale 值。

为每种目标语言准备独立测试订单，并记录 Session ID、预期语言、实际展示和金额。支付可以使用 Stripe 测试模式中的测试支付资料，避免用真实银行卡。也要验证顾客完成 3D Secure 或切换到银行页面后，返回商户站点时语言和订单上下文仍然正确。

若嵌入式 Checkout、托管 Checkout 或 Payment Links 的行为不同，应对实际使用的每种模式分别测试。不要因为某一种集成显示正常，就假设其他模式使用同样的 locale 参数和可定制范围。升级 API 版本、前端 SDK 或改变结账方式后，重新执行关键语言回归测试。

## 常见问题排查

如果页面始终显示英文，先检查创建 Session 时的 locale 实际值和是否采用 auto，再确认浏览器首选语言、目标语言是否受支持、链接是否为旧 Session。用新的测试 Session 对比，避免旧链接缓存或顾客打开了其他订单的页面。

如果界面变成中文，但商品仍是英文，检查 Product 名称、line item 数据和商户自定义文字来源。这些内容可能需要由商户自己维护多语言版本，并根据顾客选择的语言提交。检查网站当前语言是否正确传到后端，以及后端是否用了默认商品记录。

如果按钮语言正确而条款和返回页仍是另一种语言，分别检查 Stripe 端界面文案、商户自定义文字、网站路由和邮件模板。不要把所有内容都归因于 locale 参数。若付款页和账单币种不符合顾客预期，应独立核对货币设置和订单价格，而不是通过语言配置修正。

如果切换语言后创建了重复订单，检查前端切换是否意外重复调用创建订单接口。语言本身变化不应重复产生收费请求。结合内部订单 ID、幂等键和 Session ID 确认只创建了必要的会话，并在顾客重复提交时返回已有的有效订单上下文。

## 运营和合规注意事项

多语言支付文案属于交易说明的一部分。续费周期、试用结束后的扣费、不可退费用、税费和配送限制等重要条款，应该在顾客授权前清楚展示。商户应确保翻译与实际业务政策一致，并根据目标市场的法律要求审核相关表达。

不要用语言或地区猜测顾客的身份、支付能力或风险水平。语言选择用于改善顾客体验，不应自动触发不公平的风控拒绝。风险决策应使用合法、合理且与交易相关的信号，并遵守适用的数据保护规则。

对客服而言，多语言记录应包括订单编号、Stripe 对象 ID、顾客所选网站语言和付款状态，而不应包含完整卡号、CVC 或密钥。跨语言处理退款和争议时，准确保存顾客授权时看到的价格及文案版本，有助于解释订单条款。

## 上线清单

- 明确采用浏览器自动识别还是根据网站语言显式传入 locale。
- 服务端维护网站语言到 Stripe locale 的白名单映射。
- 确认目标 locale 当前受支持，并测试实际使用的 Checkout 模式。
- 商品名、价格说明、自定义字段和重要条款都有适当的多语言版本。
- 语言切换不会重复创建订单或付款对象。
- 成功与取消返回地址使用顾客当前语言，但付款状态由服务端确认。
- 语言配置与币种、运费、税务、配送范围分别管理。
- 测试浏览器语言、网站语言和账号偏好不一致的回退行为。
- 品牌名称、Logo、账单描述符和收据保持可识别的一致性。
- Webhook、订单和客服记录保存必要语言上下文，不记录支付敏感信息。
- 每次 SDK、API 版本或 Checkout 集成变更后复测多语言流程。

## 总结

Stripe Checkout 的 locale 主要决定支付界面中 Stripe 提供的本地化部分。它不会自动翻译商户商品名称、自定义文本、网站页面或所有账单内容，也不会自动把金额换成顾客本地货币。商户需要决定自动识别还是显式指定语言，并分别管理本地化界面、商品文案、币种、订单邮件和售后信息。

排查语言不一致时，检查 Session 实际 locale、浏览器设置、网站语言映射、商品文本来源和当前 Checkout 模式。用新建的测试 Session 验证真实展示，并确保切换语言不造成重复订单。清楚的语言回退、准确的价格条款和一致的品牌信息，才能让跨境顾客更放心地完成付款。
