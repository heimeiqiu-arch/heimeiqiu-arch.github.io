# Stripe Quotes 报价单怎么用？客户接受后创建 Invoice 或订阅的流程

面向企业客户销售时，商家往往需要先提供一份包含产品、价格、折扣、税费和服务周期的报价，等客户确认后再开账单或启动订阅。若报价、邮件和正式 Invoice 分别在不同系统维护，很容易出现客户接受的是旧价格、账单却使用新价格，或者客户已经付款但 CRM 仍显示未成交的情况。

Stripe Quotes（报价单）可以把报价内容和 Stripe 产品、Price、客户及后续 Billing 对象关联起来。客户接受报价后，Stripe 可以创建相应的 Invoice、Subscription 或 Subscription Schedule，具体取决于报价内容。本文介绍报价生命周期、客户接受后的账单行为、API/Webhook 同步和对账要点。Quote 的可用字段、接受流程和 Dashboard 入口会变化，实施时以当前 Stripe 文档为准。

## Quote 适合哪些销售流程

Quotes 适用于客户先审阅商务条件，再决定是否购买的场景，例如企业软件套餐、按数量定价的服务、一次性项目、按周期付费服务或包含一次性费用与订阅费用的组合。

报价单能帮助商家将销售阶段和计费阶段衔接起来，但不替代商家的完整合同审批、电子签名、采购订单和法务审查。若业务合同还有服务等级、数据处理、责任限制或额外条款，应继续使用相应合同流程，并确保报价中的商品和价格与合同引用一致。

报价设计前先确定：

- 报价对应的 Customer 与联系人；
- 使用哪些 Product 和 Price；
- 是否包含一次性项目、订阅或混合收费；
- 是否需要折扣、税费、运费或平台费用；
- 报价何时生效、何时到期；
- 客户接受后是自动扣款还是发送账单；
- 是否需要试用期或未来生效；
- 由哪套系统负责创建 CRM 商机、Invoice 和服务权限。

## 报价的生命周期

Quote 通常会经历草稿、最终确定、客户接受或取消/过期等阶段。草稿阶段适合内部准备内容；最终确定后，商家可以将报价发送给客户查看；客户接受后，报价的接受状态和后续创建对象会被记录。

常见生命周期可概括为：

1. 为正确的 Stripe Customer 创建 Quote；
2. 添加产品、价格和数量，核对折扣、税和收款方式；
3. 生成报价预览并由销售/财务复核；
4. 最终确定报价，并发送客户可查看的链接；
5. 客户在报价有效期内接受；
6. Stripe 创建对应 Invoice、Subscription 或 Subscription Schedule；
7. 商家系统通过事件和对象 ID 同步成交状态；
8. 后续按照 Invoice 和订阅的付款状态开通服务或履约。

Quote 到期后，客户可能无法继续按原报价接受。若商家需要延长有效期或变更价格，应明确这是继续原报价还是创建新版本，并让客户重新确认，而不是在后台静默改动已经发送的商务条件。

## 接受报价后会创建什么

Stripe 接受报价 API 的结果会返回已接受 Quote，并创建相应的 Invoice、订阅或订阅计划。具体创建对象取决于 Quote 的组成和计费配置。报价接受并不一定等于已经收款：如果后续对象是 Invoice，Invoice 仍可能处于待付款状态；如果创建订阅，首次 Invoice 可能成功、失败、需要认证或等待客户付款。

客户接受报价之后，系统应保存：

- Quote ID 和报价编号；
- 报价接受时间；
- 创建的 Invoice ID；
- Subscription ID 或 Subscription Schedule ID（若适用）；
- 客户、币种、总额及折扣/税额；
- 收款方式和账单到期规则；
- 商家内部合同或商机编号。

履约触发条件要明确区分“客户接受了商业条件”和“支付已成功”。服务可以在签约接受后启动，也可以要求 Invoice 付款成功后开通；这是商家业务规则。不要因为 Quote 状态变为 accepted 就自动假设款项已收取。

## 报价金额、税费与折扣复核

报价是客户会依据做采购决策的材料，发出前应逐项确认金额、数量、币种、一次性费用和循环费用。若配置了自动税或折扣，确认客户地址、税务信息和适用规则能产生预期结果。

检查时注意：

- Quote 总金额与各行项目相符；
- Price 是正确的币种和计费周期；
- 数量符合合同中的席位或服务规模；
- 折扣持续时间与文案一致；
- 订阅部分与一次性收费部分清楚区分；
- 税费计算依赖的客户资料齐全；
- 付款方式和到期日符合合同；
- Connect 场景下收费账户、转账与应用费配置正确；
- 客户看到的品牌、支持信息和商业主体一致。

不要只用前端报价页面的数字作为最终账务依据。客户接受后检查 Stripe 返回 Quote 的 subtotal、total、税费、折扣和 Invoice/Subscription 字段，再与商家自己的报价快照比较。

## 自动扣款和发送 Invoice 的区别

Quote 后续可以采用自动扣款或发送 Invoice 的收款流程，二者对客户体验不同：

- **自动收款：** 后续 Invoice 尝试使用客户默认支付方式收款。客户接受报价不保证卡片会成功扣款，也可能需要认证。
- **发送账单：** 客户收到 Invoice 和付款说明，需要按期限完成付款。Quote 接受后创建账单，仍不等于账单已经支付。
- **订阅计划：** 报价可能包含周期性收费，接受后创建订阅或计划；首期和后续周期的付款状态要分别管理。

销售团队应在报价说明中写清付款方式、账期、发票发送时间和服务启动条件。财务系统则将 Quote、Invoice 和 PaymentIntent/Subscription 分开记录，避免客户问“我已接受报价，为什么服务还没开通？”时无法解释。

## 通过 API 管理 Quote

Stripe Quotes API 提供创建、检索、更新、最终确定、接受和取消等操作。API 集成时要按当前文档检查各操作可用于什么 Quote 状态，以及接受报价时会创建哪些对象。不要在客户端直接调用敏感接受或收费逻辑；服务器应验证当前用户、报价归属和内部销售审批结果。

可以按下列方式建模：

- CRM 记录有一个内部 quote_request_id；
- Stripe Quote 的 metadata 保存内部商机或合同 ID；
- 最终确定前生成不可变的内部报价快照；
- Quote 接受事件或读取到 accepted 状态后，保存 Invoice/Subscription ID；
- 使用幂等键避免重复创建报价或重复接受处理；
- API 超时后先查 Quote 状态，而不是无条件再执行接受；
- 订单与账单之间保留一对多或一对一关系，按真实对象建模。

对于更新报价，要区分尚未发送、最终确定但未接受、已经接受等不同状态。已接受 Quote 的后续价格变更应通过新的报价、合同变更或受支持的订阅更新流程完成，不应直接改写历史成交记录。

## Webhook 与 CRM 同步

Stripe 事件参考中包含 Quote 创建、最终确定、接受、取消和到期相关事件。商家可监听当前账户和集成支持的 Quote 事件，把销售流程与 Stripe Billing 对象连接起来。处理时要验证签名、记录 Event ID，并以 Quote 当前状态和相关对象为准。

推荐同步流程：

1. 收到 Quote 相关事件后查询内部商机；
2. 幂等处理事件，避免重复创建合同或服务工单；
3. 如果 Quote 已接受，保存 Quote、Invoice、Subscription 的 ID；
4. 如果创建 Invoice，继续监听账单付款与失败状态；
5. 若为订阅，监听订阅更新和 Invoice 付款事件；
6. 如果 Quote 到期或取消，标记报价无效并阻止旧链接继续成交；
7. 对事件乱序或重复情况重新读取 Stripe 对象状态。

Webhook 事件代表 Stripe 对象发生变化，不代表 CRM、合同签署和付款都已经全部完成。对企业销售，可以把“报价被接受”“合同完成签署”“首笔账单已付”和“服务已开通”作为不同的里程碑。

## 报价过期、重新发送和版本管理

报价有效期应与商务审批和价格策略匹配。过期后，如果需要继续洽谈，可重新评估产品、价格、客户资料、税额和付款条款，再创建或更新适用的报价流程。不要把过期报价链接通过客服临时转发给客户，却没有确认 Stripe 是否仍允许接受。

对报价版本建立清晰规则：

- 已发送报价保存版本号和发送时间；
- 修改报价前检查客户是否已经接受；
- 价格变化时让客户清楚看到新旧差异；
- 过期报价不应继续触发成交和履约；
- 客户接受后保存不可变的成交快照；
- 后续续费或增购使用新的 Quote 或正式变更流程；
- CRM 中记录发送、查看、接受和取消等节点。

这种版本管理能减少销售和财务看到不同报价内容，也方便后续争议或审计时还原客户接受时的商业条件。

## 测试与上线检查

在测试模式里构建单次付费报价、订阅报价、混合报价和发送 Invoice 的场景，核对接受后生成对象及金额。测试覆盖：

- Quote 创建和最终确定；
- 客户查看并接受；
- 接受后自动生成 Invoice、Subscription 或 Schedule；
- 首次付款成功、失败或需要认证；
- Quote 到期后接受操作的返回结果；
- 同一报价 API 重试不重复生成对象；
- Webhook 事件重复和乱序；
- Connect 账户和客户资料使用正确；
- 客户看到的报价金额与 Invoice 一致；
- CRM 在“接受”和“付款成功”两个节点分别更新。

进入真实模式前，再检查账户配置、商家品牌、税费、客户邮件和合同审批步骤。真实报价应先由销售或财务人员确认，再发送给客户。

## 常见错误

**把报价接受当成已付款。** Quote 被接受后仍可能只生成一张开放 Invoice 或一份订阅，继续确认付款状态。

**最终确定后仍直接改报价内容。** 应按允许的状态变更或重新报价流程处理，保留已发送版本。

**没有将 Quote 与内部商机关联。** 后续难以从 Stripe 对象定位合同、订单和 CRM 记录。

**过期报价链接仍用于新交易。** 重新核价并确认报价仍有效后再创建新的客户接受流程。

**只检查 Quote 总额，不核对 Invoice。** 接受后继续确认 Invoice、折扣、税费和付款对象与报价一致。

**重复接受或重复生成后续对象。** 对 API 请求和 Webhook 实施幂等，并在超时后先读取现有状态。

## 总结

Stripe Quotes 可以将企业销售报价和 Billing 对象连接起来。先在草稿中准备产品、价格、数量、折扣、税和收款条件，最终确定并发送客户；客户接受后，Stripe 可以创建 Invoice、Subscription 或 Subscription Schedule。报价被接受并不等于付款成功，商家应继续跟踪实际 Invoice 和订阅状态。

通过保留报价版本、关联 CRM ID、Webhook 幂等和付款状态分层，可以减少销售承诺与实际账单不一致。报价到期或内容变更时重新核对并让客户确认新版本，再按合同约定决定何时履约。
