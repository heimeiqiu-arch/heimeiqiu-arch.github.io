咨询服务、项目交付、企业采购或账后收费常常需要先确认工作内容，再向客户发送账单。Stripe Invoicing 可以管理客户账单、行项目和付款状态。与 Checkout 一次性收款不同，手动 Invoice 通常先创建草稿，复核内容后定稿，再通过 Stripe 提供的方式交给客户付款。商家仍需确认合同、税务、账期和客户沟通规则。

Invoice 状态与订单状态并不相同。草稿还可编辑；定稿后成为对客户可见的账单；发票可能处于未付、已付、作废或无法收回等状态。本文介绍手动发票的服务端流程、客户体验、Webhook 和对账，具体状态和操作以 Stripe 当前 API 与 Dashboard 为准。

## 一、先准备 Customer 和账单明细

创建 Invoice 前，确认客户是否已有正确 Stripe Customer，账单联系人、邮箱和账单地址是否准确。企业客户常有付款负责人、采购编号、税务资料和不同的付款期限，商家需在报价或合同阶段收集必要信息。不要仅凭客户邮箱自动假设公司名称和账单地址。

每个 Invoice 由一个或多个 Invoice Item 组成。行项目说明商品或服务、数量、单价、币种和适用税务设置。项目描述应让客户看懂收费内容，避免只显示内部代号。服务项目金额由服务端可信报价计算，不接受浏览器随意传入最终金额。保存内部项目 ID、订单号、Stripe Invoice Item ID，便于后续核对。

如果客户有合同价或折扣，创建账单时核对价格、税额、币种、付款条件和优惠。服务费、运费、税费和折扣应按财务规则展示，不要把不同币种金额相加。草稿阶段可以让有权限的员工审核，确认内容无误后再定稿。

## 二、草稿、定稿和发送的区别

Draft Invoice 是尚未最终确认的发票，适合添加行项目和复核客户信息。Finalize 会将草稿转换为可收款的开放发票，并固定发票内容。发送 Invoice 与定稿是相关但不同的步骤，取决于 collection_method 和账户配置。Stripe 可能在发送或尝试收款时自动定稿；如果需要人工复核，应明确控制自动推进设置。

定稿前检查客户、币种、行项目、金额、税费、付款期限、账单邮箱和备注。发票一旦定稿，后续更正通常需要使用 Stripe 支持的更新、作废、贷项或退款流程，不应直接在自己的数据库改一个总金额来掩盖差异。定稿操作本身应记录操作人、时间和内部审批状态。

选择自动扣款或 send_invoice 等收款方式时，确认客户已经授权相应支付方式和付款周期。发送账单邮件前确认客户邮箱正确、可访问发票链接和付款方式。对于企业客户，如果使用采购订单号、合同号或自定义字段，在定稿前验证其显示位置。

## 三、服务端创建与幂等

后端负责创建 Invoice Item 和 Invoice，验证用户或员工权限、Customer 归属、金额、币种和付款条件。不要让客户端指定任意 Customer ID 或金额后直接生成发票。为每个内部开票申请建立唯一 ID，创建 API 请求使用稳定幂等键，避免网络超时后重复生成账单。

保存 Stripe Invoice ID、相关 Invoice Item、内部订单或项目 ID、金额明细、状态与负责人。API 返回成功后写入数据库失败时，使用幂等键或对象检索恢复，不要盲目创建第二张发票。若客户要求修改地址或项目描述，在定稿前更新草稿；定稿后则按当前 Stripe 支持的操作流程处理。

审核应有角色和审计。销售人员可以提交开票申请，财务或管理员批准高金额发票。管理员手工调整金额时，记录原因和审批人。对重复开票风险高的业务，可以为同一订单设置唯一开票约束，除非明确有分期或追加收费。

## 四、客户付款与状态同步

Invoice 发送后，客户可以查看账单并按支持方式付款。客户访问页面或邮件不等于已付款，服务端应依据 Stripe Invoice 与相关 PaymentIntent 状态更新业务。若发票使用自动扣款，付款也可能需要认证或失败；若采用客户自行支付方式，则需要等待客户完成操作。

配置 Webhook 事件，验证签名并可靠保存事件。处理 Invoice 付款成功、失败、更新或作废等状态时，按 Invoice ID 找到内部项目和订单，校验金额和客户关系后更新记录。事件可能重复或延迟，幂等处理可避免重复发货、重复开通服务或重复发送收款通知。

对外页面分开显示“账单已发送”“付款处理中”“已付款”“已逾期”或“已作废”。不要把邮件已发送等同于客户已收到，也不要把付款 API 的请求提交等同于银行资金已到账。若发票长期未付，业务可以提醒客户、联系采购或按合同暂停后续服务。

## 五、逾期、部分付款、退款和作废

若客户逾期，按合同与业务策略进行提醒、暂停服务或升级人工跟进。Stripe 发票可能提供到期时间和付款状态，内部 CRM 也应记录催款沟通。避免对客户重复发送多封自动邮件，或在付款正在处理时再次要求其付款。

部分付款、客户付款不足、过付款或重复付款需要单独核对。不要将 Invoice 直接标为已付而忽略剩余金额；记录已付和未付部分，必要时由财务决定后续处理。若客户取消项目，确认服务是否已交付，再决定作废未付发票、退款已付账单或另建调整记录。

退款与贷项处理需关联原 Invoice 和付款对象。Refund 创建后等待最终状态，通过 Webhook 更新本地。对于已定稿发票的更正，按 Stripe 当前文档判断应使用作废、贷项或其他方式；保留原发票和修正关联，便于审计和财务报表核对。

## 六、测试与对账

测试草稿创建、增加行项目、定稿、发送、付款、付款失败、客户未付、发票作废、退款、Webhook 重复和网络超时。核对 Dashboard、客户可见发票、本地数据库和财务报表中的客户、金额、币种、税额和状态。检查测试和生产 Customer 不会混用。

对账时比较 Invoice、Invoice Item、PaymentIntent、Refund、余额交易和内部项目记录。发现差异先保存报告，判断是重复开票、付款事件未处理、客户资料变化还是退款调整，再按受控流程修复。保留 API 对象 ID 与操作历史，不删除已发生的金融记录。

## 总结

Stripe 手动 Invoice 适合先确认服务和金额、再向客户开账单的流程。先创建或核验 Customer，准备准确的 Invoice Item，在草稿阶段审核，定稿并发送后再通过 Webhook 同步最终付款状态。发票定稿后不要通过覆盖本地总额来修改历史，使用 Stripe 支持的更正方式并留下审计记录。

把发票、付款、退款和内部订单关联起来，设置催款、逾期和取消规则，并定期对账。通过清楚的服务描述、正确的客户资料和安全的权限控制，企业客户与财务团队都能更容易理解账单，开发团队也能追踪每笔收费的来龙去脉。
