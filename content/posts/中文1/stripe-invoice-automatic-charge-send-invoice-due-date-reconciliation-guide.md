Stripe 发票既可以在账单生成时尝试自动扣款，也可以发送付款说明，由客户在到期日前自行支付。两种方式都会形成发票记录，但客户需要做什么、系统何时认为款项已到账、财务如何催收和对账，都有明显差异。把“发票已生成”误当成“发票已付款”，或者误用发票到期日判断自动扣款时间，都会产生权限开通错误、重复催收和账面不一致。

本文说明 Stripe Invoice 的自动扣款与手动收款模式，讨论订阅和一次性发票中的配置、付款期限、状态同步、提醒与逾期处理，并给出可直接用于上线检查的流程。API 字段名称和可用行为可能随 API 版本变化；请在测试环境验证，并以当前 Stripe 文档和账户设置为准。

## 两种收款方式的核心差异

Invoice 的 collection_method 常见值包括 charge_automatically 和 send_invoice。前者表示 Stripe 尝试使用客户默认付款方式收取款项；后者表示向客户提供发票和付款说明，由客户完成支付。send_invoice 通常会配置 days_until_due 或 due_date；自动扣款发票的 due_date 通常为空，因为它不是按客户主动付款期限管理。

在自动扣款模式中，生成发票、尝试扣款和付款成功是不同阶段。即使系统已经创建发票，也可能因卡片拒付、缺少可用付款方式、要求客户完成验证等原因而未能收款。业务系统应根据 invoice.paid 或相应支付结果确认账款，而不是根据订阅仍为 active、发票存在或扣款请求已发出就发货。

手动收款模式适合企业对企业账单、采购审批、银行转账或需要客户依据合同付款的场景。Stripe 可以发送包含付款说明的发票，但“已发送”不代表客户已经付款。到期日期也只是付款期限，不是扣款执行时间。商家需要安排提醒、识别实际到账，并在收款后更新订单与权限。

## 自动扣款模式的设置与判断

在 charge_automatically 模式下，Stripe 会尝试从订阅或客户配置的默认付款方式收取款项。创建订阅或发票前，确认付款方式确实绑定到正确的 Customer，并处于可使用状态。对订阅而言，还要确认订阅级别的默认付款方式和 Customer 的 invoice_settings.default_payment_method 是否符合预期；配置优先级和支付方式支持情况应以当前 API 文档为准。

自动扣款失败后，不要自行假设 Stripe 会无限重试或立即停止订阅。重试规则取决于 Billing 设置和账户配置。系统应处理 invoice.payment_failed、invoice.payment_action_required 等事件，向客户展示可执行的修复方式，并通过当前账单状态决定是否继续提供服务。对于需要客户再次认证的情况，单纯后台重试并不能代替客户完成必要步骤。

若付款成功，监听 invoice.paid 作为账务完成的重要事件，并把 Invoice ID、Customer ID、Subscription ID、货币、已付金额及支付关联记录在内部账本。一次发票可能经历多次付款尝试，所以将同一 Invoice 的金额累计到收入时必须避免重复记账。将付款状态、退款和后续贷项通知分开处理，才能让财务追溯原始发票与调整记录。

## 手动收款与付款期限

在 send_invoice 模式下，发票会携带付款期限。订阅可以用 days_until_due 表示客户有多少天付款；单张发票也可能以 due_date 指定到期日期。设置期限时应与合同、发票正文、催收政策和所在地区要求相一致。不要仅在网站上写“30 天”，却在 Stripe 发票上配置了不同的期限。

手动发票的流程通常包括：准备客户与项目、创建草稿发票、检查行项目和税额、完成最终确认、发送发票、跟踪客户支付、核对付款状态。若发票由 API 创建，建议先验证金额、货币、客户邮箱、税务信息、采购单号和服务周期，再最终确认。已最终确认的发票不应被当作随时可编辑的草稿；需要调整时，按 Stripe 的发票修订、作废或贷项流程处理。

客户可能通过托管发票页面完成付款，也可能通过其他约定渠道转账。若企业通过线下转账收款，必须使用一致的对账依据，例如银行流水、汇款参考号和发票编号。只有确认资金已实际到账且归属正确，才把发票标为已支付或在内部确认收款。不要因为客户上传付款截图就自动完成结算。

## 订阅中的收款方式选择

订阅的 collection_method 会影响周期性发票如何收款。自动扣款订阅会按照默认付款方式尝试收款；send_invoice 订阅会向客户发送发票，并按配置的付款期限管理应收款。选择前应明确客户类型、收款渠道、账龄管理方式，以及未付款时是否继续服务。

更改已有订阅的收款方式时，先确认改变会影响哪些未来发票，以及当前未结发票是否需要单独处理。不要只更新本地的付款方式标签而不读取 Stripe 返回结果。对于账单周期、税率、折扣或欠款同时变化的情况，先在测试模式或预览环境核对即将生成的发票，再执行修改，避免配置变更造成意外账单。

如果采用手动发票，还需要定义未付款后的产品行为。例如，发票尚未到期时提供完整服务，逾期后进入宽限期，超过宽限期再暂停部分功能。无论规则如何，都应把发票状态和权限状态分别建模，并在客户界面显示欠款金额、到期日及付款入口，避免客户不知道如何恢复服务。

## Webhook 与账务对账

Webhook 接收端要验证签名、保存 Event ID，并对重复事件实现幂等。自动扣款通常重点关注 invoice.paid、invoice.payment_failed、invoice.payment_action_required；手动收款还可关注 invoice.sent、invoice.voided、invoice.marked_uncollectible 等与业务有关的事件。不同集成方式可能触发不同事件，因此应按实际流程订阅，而不是复制一份固定事件清单后不再维护。

建议把事件处理划成四层：事件接入、Stripe 对象快照、内部账务分录、客户通知。事件接入层保证验签和幂等；快照层保存 Stripe 返回的发票状态、金额和关联对象；账务层按唯一发票和付款记录记账；通知层通过队列异步发送邮件或站内信。这样，当通知服务失败时，账务更新不必重复；当 Stripe 重试 Webhook 时，也不会再次发货或记收入。

每日对账可以按 Stripe 发票编号和付款对象核对内部订单、银行流水及 Stripe 余额交易。重点检查已付款但内部未开通、内部已开通但发票未付款、金额或币种不一致、部分付款、贷项和退款未关联原单等异常。对账记录中保存差异原因和处理人，不要直接用总额对总额掩盖逐笔错误。

## 常见故障排查

**自动扣款发票已创建，却没有扣款。** 检查 collection_method、auto_advance、默认付款方式和发票状态；查看是否需要客户操作，或是否已经产生失败事件。

**客户说没有收到手动发票。** 查看 invoice.sent 相关记录、客户邮箱、Stripe 邮件设置及发票 hosted URL。确认地址正确后，可通过受控流程重新发送，避免不必要地创建重复发票。

**手动转账后仍显示未付款。** 先核对资金是否到账、汇款参考信息是否可匹配，再检查 Stripe 对应付款方式是否支持自动识别。线上转账的入账状态可能异步更新；在状态确定前应让订单进入待核对状态。

**自动扣款发票 due_date 为空。** 这通常是自动收款模式的正常表现，不应把空值当成“没有期限所以未付款”。应使用发票状态、付款尝试和收款事件判断结果。

**发票已付款却重复触发业务动作。** 检查 Event ID 去重、发票 ID 唯一约束和下游队列幂等键；把“收到事件”与“业务动作成功”分开保存，便于安全重放。

## 上线前核对表

上线前分别创建一张自动扣款发票和一张手动发票，验证 Stripe Dashboard、API 响应、本地数据库、客户邮件及权限变化一致。测试成功付款、拒付、需要额外认证、超过到期日、退款、作废、重复 Webhook 和线下转账待核对。核对发票号、金额、币种、付款方式、收款期限和客户信息，并确定客服如何查询与解释每种状态。

自动扣款减少了客户主动支付步骤，但仍需要对失败进行跟进；手动发票适应企业付款流程，却要求商家管理应收账款和到账核对。选择合适的 collection_method，并用发票状态和支付结果驱动内部账务，才能让 Stripe 收款、客户体验和财务报表保持一致。
