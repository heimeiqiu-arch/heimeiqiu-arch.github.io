对于同时经营线上和线下业务的商家，门店刷卡、移动读卡器和手机 Tap to Pay 需要与现有订单系统连接。Stripe Terminal 提供线下支付集成能力，可让应用管理支付意图、门店位置和读卡器，并将线下交易纳入 Stripe 账户。硬件可用性、国家和币种要求会因地区变化，开始开发前先确认目标市场和设备支持情况。

Terminal 不是简单的“连接读卡器然后扣款”。门店系统需要创建订单、处理客户交互、管理设备连接、确认 PaymentIntent 状态，并通过 Webhook 更新订单。线下网络可能中断，设备也可能断开或需要更新，因此产品要有重试、取消和人工排查流程。本文介绍主要对象、服务端与客户端职责、地区检查和测试办法。

## 一、先确认地区和设备支持

在采购读卡器或规划门店之前，查看 Stripe 当前 Terminal 地区支持表。可用读卡器、Tap to Pay 设备和付款方式会因国家而异。Stripe 文档说明，处理 Terminal 付款时，接收资金的 Stripe 账户和与 Reader 关联的 Location 需要处于同一国家，通常还需要使用当地货币。不要根据其他国家的集成经验推断自己的账户可用。

门店选址也属于支付配置的一部分。Location 应记录真实业务地点，并把 Reader 关联到正确位置。多个国家或城市运营时，订单系统要知道这笔线下付款在哪个门店发生，以便客服、税务与对账查询。若商家账户国家与设备 Location 不匹配，可能无法按预期处理交易。

硬件选择要结合门店网络、移动场景、电池、收银系统和操作人员培训。采购前检查设备型号、连接方式、固件更新和平台兼容性，确认设备状态可由目标应用管理。Tap to Pay 也受手机型号、系统和国家支持条件影响。上线计划要安排备用设备或人工收款预案。

## 二、理解 Location、Reader 和 PaymentIntent

Terminal Location 表示业务地点，Reader 表示具体读卡设备或受支持的手机收款端，PaymentIntent 表示一笔付款流程。将对象区分开可以帮助排查问题：Location 配置不正确，不代表 PaymentIntent 有错；Reader 离线也不等同于客户付款失败；支付成功之后还需要订单系统完成履约。

服务端负责计算可信金额、创建 PaymentIntent 和存储订单关联。客户端或 POS 应用负责连接 Reader、展示支付交互和执行相应的确认流程。客户端不应决定最终金额或访问 secret key。每笔交易保存内部订单号、PaymentIntent ID、Reader ID、Location ID、币种、金额和操作员标识，以便之后追踪。

如果产品支持多门店或多商户，校验当前操作人员能使用哪个 Location 和 Reader。不能让任意终端通过传入别的门店 ID 操作设备或查阅交易。管理员调整门店或设备归属时，记录变更人、时间和原因，避免后续报表无法解释交易位置。

## 三、设计线下支付流程

典型线下流程是收银员在 POS 建立订单，后端根据商品、折扣和税费计算金额，再创建 PaymentIntent。应用将付款请求交给 Terminal SDK 和 Reader，客户插卡、刷卡或使用适用的非接触方式完成付款。Stripe 返回的状态再由应用和后端同步到订单。具体客户端 SDK、连接模式和确认方式应按当前 Stripe 示例选择。

支付前核对订单、金额和币种。若客户在付款过程中更改商品或取消订单，应用应正确取消或更新未完成流程，并避免同时存在多个可成功的支付意图。网络断开时，不要立刻重新扣款；先查询现有 PaymentIntent 状态和设备状态，确认上一笔是否已成功，再决定恢复或创建新的尝试。

收据与客户沟通也要纳入流程。商家可根据业务配置电子或纸质收据，并提供订单查询方式。收据中的商品、金额、税费和门店信息应与 Stripe 交易与本地订单保持一致。退款、换货和取消要引用原始交易，而不是直接手工改订单金额。

## 四、连接方式和离线场景

Terminal 支持的连接模式和设备功能不完全相同。集成前先决定 POS 应用运行在哪类设备，Reader 通过互联网或本地网络如何连接，是否需要移动收款，以及网络不稳定时业务如何处理。阅读对应 SDK 的安装和连接指南，确认客户端平台、操作系统和设备型号受支持。

离线付款能力若适用于特定设备和集成，应仔细阅读其限制、风险和存储要求。不能默认断网时所有交易都能安全稍后提交。离线期间可能发生付款失败、设备丢失或额度限制等情况，商家需评估风险，并确定操作员如何提示客户。若产品不启用离线能力，网络不可用时应明确提示暂停收款或使用批准的备用流程。

Reader 状态需要监控。后台可展示在线、连接中、需要更新或离线等信息，并给出简单的重连和支持步骤。对于门店高峰期，建立操作手册，说明怎样切换备用终端、避免重复扣款，以及怎样从订单号查找上一笔尝试。

## 五、Webhook 和支付状态同步

线下付款最终状态应由 Stripe 对象和 Webhook 驱动，而不是只看 POS 屏幕上短暂的“成功”提示。服务器接收事件时验证签名、保存 event ID 和 PaymentIntent ID，再更新内部订单。重复事件处理要幂等，乱序事件不能把已成功订单回退为处理中。异步支付方式还可能在稍后发生成功或失败状态变化。

若 POS 应用在付款确认后崩溃，商家仍需要从服务器恢复订单状态。保存足够的对象 ID 和操作记录，并提供按订单检索 PaymentIntent 的后台工具。订单与支付状态应分开：付款成功不代表库存已经扣减或服务已交付；履约任务失败时可以重试，但不能再次向客户收费。

日终对账对线下业务很重要。按门店、操作员、Reader 和币种核对内部订单、Stripe 支付对象、退款与手续费。报告应区分付款尝试、成功交易、失败、取消和退款。发现差异时先标记并查找事件或设备日志，不要通过手工覆盖数字来结束问题。

## 六、退款、取消和店员操作

退款应关联原始 PaymentIntent 或 Charge，并记录申请人、金额、原因和操作时间。若部分退款，检查累计退款是否超过可退金额。使用后端权限和幂等键防止店员重复点击造成重复退款。需要主管批准的金额，应在应用中做角色权限限制并留下审计记录。

取消未完成的付款与退款成功付款是两种不同操作。收银员取消订单时，确认 PaymentIntent 当前状态；如果客户已完成付款，需走退款流程。客户在设备上重复刷卡时，先查询上一笔状态，不要马上再发起一笔相同金额支付。后台应显示原交易和新尝试之间的关联。

线下退货可能需要实物验收、库存更新和税额核对。Stripe 退款不会自动完成商家所有退货流程。POS 系统要分别更新付款退款、订单履约、库存和客户通知，并通过幂等任务避免重复入库或多次发送消息。

## 七、测试与部署检查

测试创建 Location、注册或连接 Reader、设备发现、支付成功、支付被拒、客户取消、重复请求、网络中断、客户端重启、退款、Webhook 重复和日终对账。测试环境的设备与生产环境配置要区分，确认测试对象不会误用于真实门店。针对实际使用的国家和硬件型号逐一核对支持条件。

上线前确认账户国家、币种、Location 地址、Reader 型号、SDK 版本、后端密钥、Webhook endpoint 和员工权限。检查终端能否在网络恢复后重新连接，门店是否知道如何处理设备离线。做好测试刷卡与真实客户收款的区分，避免用生产设备进行不必要的测试交易。

先在一个门店进行小规模试运行，观察支付成功率、平均收款时长、设备断连、重复付款、退款和客服工单。发现问题时按 Location、Reader、PaymentIntent 和操作员查询，而不是只凭客户描述。逐步扩大门店范围，并保留设备替换和配置回滚计划。

## 八、内容维护与官方资料

Stripe Terminal 相关内容可以围绕 Reader 连接、Location 配置、线下 PaymentIntent、Tap to Pay、退款和离线模式建立专题。标题说明设备和地区前提，正文明确列出必须核实的支持条件。不要承诺某种读卡器在所有国家均可购买，也不要把某个 SDK 示例当作所有平台的通用代码。

硬件型号和地区支持会更新，文章需定期复查官方页面。更新正文时注明复核时间，并链接到 Stripe 的区域考虑与集成文档。对于设备采购建议，先查当前可用型号和所在国家支持，不要根据旧截图下单。

官方资料：[Terminal 概览](https://docs.stripe.com/terminal)、[地区支持](https://docs.stripe.com/terminal/payments/regional)、[Terminal 读卡器](https://docs.stripe.com/terminal/readers)、[Terminal Webhooks](https://docs.stripe.com/terminal/events)。具体支持条件以账户 Dashboard 和最新文档为准。

## 总结

Stripe Terminal 把线下读卡设备和 Stripe 支付对象连接起来，适合需要统一管理线上线下交易的商家。集成前先确认国家、当地货币、Location 和 Reader 支持条件，再明确 POS、后端和 Webhook 各自职责。服务端计算金额并保存支付对象，终端负责客户交互，最终订单状态由服务器核验。

线下网络、设备断连和店员重复操作都可能造成订单与支付状态不一致。通过幂等请求、状态查询、权限控制、退款关联、日终对账和门店操作手册，可以降低重复扣款和漏单风险。先在测试环境和单店试运行验证完整流程，再逐步扩展。
