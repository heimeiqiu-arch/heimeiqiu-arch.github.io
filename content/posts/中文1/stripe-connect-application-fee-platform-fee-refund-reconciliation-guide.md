市场平台通常需要从商家交易中收取佣金、服务费或软件平台费用。Stripe Connect 的 application fee 可用于在适用的 Connect 付款中记录平台收取的费用，并将相应资金转至平台账户。它是 Stripe 资金流程中的对象或参数，不等于平台与商家之间的完整商业合同，也不会自动替平台决定税务、退款政策或收入确认方式。

应用手续费的设置与收费类型、API 对象、付款方式和账户配置有关。平台需要先画清资金流，再确认费用计算公式、退款时是否返还平台费、转账如何调整以及账本怎样对账。本文介绍 application fee 的产品概念和实施注意事项，具体字段和支持范围应以当前 Stripe Connect 官方文档与账户能力为准。

## 一、Application Fee 的作用

Application Fee 表示平台在符合条件的 Connect 交易中收取的平台费用。它可能与直接收款、目的地收款或订阅发票等不同场景相关，但每种模式的 API 参数、资金流和对象归属并不完全一样。不要仅凭“平台费”这个业务词就假设任何 Stripe 付款都可以使用相同字段。

平台应区分客户支付总额、Stripe 处理费用、平台 application fee、商家净额和后续 Transfer。它们的计算和资金移动不是一个数字。比如客户支付 100，平台佣金按订单规则计算为 10，Stripe 处理费用另行计入，而商家应收与退款后金额还受付款方式和 Connect 模式影响。务必在测试模式验证实际余额交易。

Application Fee 也不是从平台的商业条款自动推导的。平台要通过合同和商家设置说明佣金比例、固定费、适用商品、退款处理及争议发生时的安排。Stripe API 接收的是平台计算后提交的金额，平台负责正确计算和保存依据。

## 二、设计抽佣规则

先定义佣金基数：是商品小计、含税金额、扣除折扣后的金额，还是加上运费后的总额。再定义比例、固定费用、最低和最高额度、舍入规则、币种和生效日期。不同商家或产品可以有不同费率，但规则要有版本并能按交易发生时间追溯。

服务端使用订单的可信商品明细计算 application fee。金额用最小货币单位整数表示，避免浮点数四舍五入造成几分钱差异。多币种时按币种分别计算，不能把美元和欧元等金额放在一个统一数字里直接比较。若佣金基于优惠后金额，折扣和退款如何分摊也要明确。

对于多商家订单，逐个收款方计算应得金额和平台费用。每笔费用应关联具体订单项目、商家和支付对象。将计算过程记录到内部资金账本，保存佣金费率版本、基数、金额、币种和计算时间。若平台后来修改费率，不能改变历史交易中已经确定的佣金。

## 三、与收费模式和对象的关系

Connect 收费模式决定支付对象创建在哪个账户、资金如何转给关联账户，以及谁负责处理部分退款或余额问题。直接收款、目的地收款和分开收款与转账的流程不同。创建付款或发票时使用的 API 参数应按当前模式核对，不能把一种示例复制到其他模式。

某些场景中，application fee 会在付款或发票实际成功收款时收取或转给平台；如果付款失败，平台不能把尚未收到的佣金当成已确认收入。应根据 PaymentIntent、Invoice、Application Fee、Transfer 和 Balance Transaction 等对象的最终状态更新账本。尤其是订阅账单，发票创建、定稿和付款是不同阶段，抽佣相关数据需要在相应事件后核实。

在平台内部设计资金状态，不要用一个“已结算”字段表示客户付款、平台费用收取、商家转账和银行提现全部完成。客服和财务应能分别查到客户付款、平台费、商家净额以及后续转账对象 ID。不同对象相互关联，但有各自的失败和更新流程。

## 四、退款和费用返还

客户申请退款时，需要分别处理客户退款、Transfer reversal 和 application fee 返还。它们是不同的资金动作，具体联动规则取决于收费方式和 Stripe 参数。不要假设创建 Refund 后平台费一定自动按业务期望返还，也不要假设撤回商家转账会自动向客户退款。

平台需决定全额退款和部分退款时如何处理佣金：按比例退还、退还全部平台费、保留部分处理费，或依据商品/服务合同采取其他规则。规则应在交易前说明，并由财务与业务负责人审核。对于已经定稿的订阅账单或已分给多个商家的订单，应分别核对各方资金。

发起退款时，先查原支付和 application fee 对象、累计退款金额、币种和转账状态，再计算待返还金额。使用幂等键防止重复退款和返费。Webhook 更新最终结果后，保存 Refund、Application Fee Refund 或相关资金调整对象 ID。若商家余额不足、转账撤回失败，进入人工处理队列，不能把客户退款显示成整个资金链路都已经完成。

## 五、Connect 平台的争议和负余额

争议、退款、处理费和商家余额会影响平台与关联账户的最终净额。平台应根据收费类型、账户配置和协议确认谁负责哪些损失和成本。不要从 Application Fee 参数本身推断 Stripe 会替平台承担退款或争议责任。

若一个争议发生在商家已收款后，平台要核实客户付款、Transfer、application fee 和余额变化。必要时按 Stripe 当前规则处理资金调整，并记录商家应付金额或人工豁免。商家合同、客户政策和财务处理应一致，避免平台在退款时才发现佣金或资金回收规则没有定义。

对 Connect 付款使用 Webhook 同步相关对象。签名验证、事件去重和账户上下文检查不可省略。一个事件可能与平台或关联账户对象相关，处理时保存其账户标识，防止将某商家的费用记到另一个账户。定期对账 Stripe Dashboard 和内部账本，尽早发现手续费差异。

## 六、测试和审计

测试不同佣金比例、优惠、税费、不同币种、付款失败、部分捕获（若适用）、全额与部分退款、争议、应用费返还、多商家分账和 Transfer reversal。对每种案例检查 Stripe 对象、平台余额、关联账户余额、客户账单与本地账本。仅看到 API 请求成功，不足以证明资金分配符合合同规则。

记录抽佣配置变更、操作人、审批、适用起始时间、计算输入和结果。财务后台提供订单级明细和周期汇总，区分客户总额、平台费、Stripe 费用、商家转账、退款和待处理金额。导出包含 Stripe 对象 ID，便于审计与支持工单追踪。

## 七、常见错误和 SEO 维护

常见错误包括用浮点数算费、让浏览器提交佣金金额、把平台费当作 Stripe 处理费、付款未成功就记佣金收入、退款后没有检查 application fee 返还、把 Transfer 和 Payout 混为一谈，以及没有保留抽佣规则版本。出现差异时应追溯订单明细和 Stripe 对象，而不是手工改总额。

围绕 Connect 平台抽佣的内容，应讲清费用基数、对象关联、收费模式差异和退款资金动作。标题不要承诺“平台自动获得全部佣金”，描述注明适用条件。Stripe 参数和账户能力会更新，内容应链接官方资料并定期复查。

官方资料：[Application Fees](https://docs.stripe.com/connect/marketplace/tasks/app-fees)、[Direct Charges](https://docs.stripe.com/connect/direct-charges)、[Destination Charges](https://docs.stripe.com/connect/destination-charges)、[Separate Charges and Transfers](https://docs.stripe.com/connect/separate-charges-and-transfers)。

## 总结

Application Fee 为平台收取交易费用提供 Stripe Connect 相关能力，但平台仍要设计准确的费率、币种、计算基数和退款规则。先明确订单资金流，再由服务端计算费用、保存规则版本，并关联付款、发票、商家和转账对象。

退款、费用返还和商家转账调整是不同动作，应分别测试并通过 Webhook 更新最终状态。通过幂等资金操作、审计记录和周期对账，可以解释每笔佣金如何产生、如何变化以及最终进入哪个账户。
