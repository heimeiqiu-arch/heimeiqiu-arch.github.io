# Stripe 争议怎么提交证据？材料准备、API 提交与截止时间管理

当持卡人向发卡行提出拒付，Stripe Dashboard 通常会显示一笔争议（Dispute），并提供回应期限、争议原因和可提交的证据。此时商家需要快速弄清楚：客户具体质疑什么、交易是否确实符合订单约定、有哪些材料可以证明事实、以及如何在期限内提交。仅仅上传一堆截图并不能自动提高胜算；证据必须与争议原因对应，能够让不了解你业务的审核人员按时间顺序看懂交易。

本文介绍 Stripe 争议证据的整理方法、Dashboard 和 API 的提交思路、常见原因下的材料选择，以及如何减少错过期限、误提交和重复处理。发卡行和卡组织的具体规则会变化，争议类别也有差异。本文是操作参考，不构成对结果的保证；每笔争议都应以 Stripe Dashboard 显示的期限、可用字段和当前官方文档为准。

## 收到争议后先确认什么

不要一看到争议就立即上传所有文件。先打开争议详情，记录以下信息：

- Stripe Dispute ID、相关 Charge 或 PaymentIntent ID；
- 争议金额、币种、发生时间及当前状态；
- Dashboard 显示的争议原因和回应截止时间；
- 是否已经全额或部分退款，退款是否完成；
- 商品是实物、数字内容、订阅还是服务；
- 订单、物流、访问日志和客服沟通分别保存在什么系统；
- 该笔交易是否由 Connect 账户处理，是否需要由正确的账户上下文回应。

争议的原因决定了材料重点。例如，“未收到商品”需要说明发货和交付，“商品与描述不符”需要解释商品页面承诺与交付内容，“重复扣款”要逐笔比较两笔交易，“订阅已取消”则要提供客户当时看到的续费和取消条款。用一份通用说明回应所有类型，容易遗漏发卡行真正关心的事实。

及时联系客户有时可以了解误解、查明重复扣款或协商退款，但不要因为已经发出邮件就忽略正式回应期限。沟通结果应记录在争议档案中；客户没有回复，也不意味着银行会自动撤销争议。

## 建立围绕交易时间线的证据包

证据包的目标是让审核人员快速回答四个问题：客户购买了什么、客户在购买前看到了什么、商家实际交付了什么、争议所称问题是否有记录支持。通常可以按以下时间线整理：

1. **购买前：** 商品或服务说明、价格和币种、退款和取消政策、续费频率、交付范围，以及客户如何看到并接受这些条款。
2. **购买时：** 订单号、客户资料、账单地址、支付时间、付款凭证、结账页面展示内容和 Stripe 交易标识。
3. **购买后：** 发货记录、签收信息、数字产品访问或下载日志、服务开始记录、客户使用情况和订单确认。
4. **问题处理：** 客服往来、取消请求、退货或退款请求、商家回复、退款凭证及交易状态。

内部调查摘要要简短、客观，尽量按日期排列。先写争议主张，再用每一项证据回应它。例如：“争议原因是未收到数字课程。订单于某日购买，客户在某日登录并观看了课程第 1 至第 4 节；登录时间和账户 ID 见附件 A。”避免写情绪化结论、推测动机或无关的公司介绍。

每个附件应有清楚的文件名和说明，如 `01-order-summary.pdf`、`02-delivery-tracking.pdf`、`03-customer-email.pdf`。避免上传未裁切的整页后台、模糊截图、重复材料，或包含其他客户个人信息的导出文件。对敏感资料应遵循最少披露原则，只提交理解本次争议所需的信息。

## 按争议原因选择材料

### 欺诈或持卡人称不认识交易

重点是说明交易与该客户账户、设备或既有使用行为之间的关系。可能相关的资料包括订单与收据、购买时 IP 地址、客户账户信息、地址验证和安全验证结果、数字商品的访问记录、客户此前的沟通，以及与历史交易的关联。若使用了 3D Secure 等验证，不要只写“通过风控”；提供可核实的认证结果和交易上下文。

IP 地址或设备信息本身并不能单独证明持卡人本人授权。应把技术记录与订单、收据、客户沟通和服务使用记录结合起来，并说明时间是否一致。不要提交未经授权获取的设备隐私信息。

### 商品或服务未收到

实物订单可准备承运商、运单号、寄出时间、送达时间、配送地址和签收情况。若快递显示送达，应确保地址与客户提供的收货地址相符，并突出配送记录中的关键日期。数字商品可提供账户创建、登录、下载或访问记录，并对应到购买客户。服务订单可提供合同、排期、工作单、服务开始记录或双方确认的完成情况。

对于“尚未到预计送达日”的争议，也应按真实时间线解释预期日期、发货日期和当前物流状态，不要把尚未发生的送达写成已经完成。只有与该订单相关、可以解释争议的记录才有帮助。

### 商品或服务与描述不符

将客户购买时看到的描述、规格、演示、报价和实际交付内容并列起来。实物商品可提供发货前的规格记录、产品照片和订单明细；数字服务可提供课程或软件的功能说明、客户开通内容和服务日志；咨询或项目服务可提供双方确认的范围、里程碑和交付成果。

不要只说“我们的质量没有问题”。更有效的说明是逐项回应客户提出的差异：页面承诺是什么、交付了什么、哪份材料能够验证。若商家确实发现错误，应如实说明已采取的退款、换货或修复措施。提交不真实或相互矛盾的陈述会损害可信度。

### 客户称已经取消订阅或订单

准备购买时展示给客户的订阅周期、续费金额、取消政策和退款政策，以及客户同意条款的记录。对于后续续费，提供订阅创建时间、每个账期的 Invoice、取消请求时间、取消生效时间和服务可用状态。若客户在续费扣款后才取消，清楚说明实际时间点；不要仅上传一张当前 Dashboard 截图而不解释时间线。

如果你确实在扣款前收到有效取消请求，却没有正确处理，应先调查系统故障和客户影响，再选择符合事实的回应方式。争议证据不是掩盖错误的工具。

### 重复扣款或退款未处理

对比被争议交易和另一笔看似相同的交易：金额、币种、日期、订单 ID、商品、付款方式以及是否已经退款。若是两笔不同订单，说明差异并提供各自订单和交付证据；若确实重复收费，说明哪笔已退款并提供退款状态和凭证。对于“退款未处理”，记录客户请求、商家处理时间和 Stripe 中退款对象的状态。

退款请求创建、退款处理完成以及客户银行账单显示退款，可能发生在不同时间。提交前核对 Stripe 中实际退款状态，并谨慎使用“已到账”表述。银行入账时间受支付方式和金融机构处理影响，避免承诺无法确认的具体日期。

## 在 Stripe Dashboard 中处理

Dashboard 适合人工逐笔审核，尤其是争议数量不多、证据需要人工判断的场景。处理步骤通常是：

1. 在 Stripe Dashboard 打开 Disputes 或争议列表；
2. 选择相应争议，确认争议原因、金额和截止时间；
3. 联系客户或内部订单系统，收集并核实对应材料；
4. 在争议回应页面填写与原因相关的说明、上传文件；
5. 检查每个字段和附件是否对应正确的订单；
6. 在页面确认最终回应内容后提交；
7. 保存提交时间、争议状态和内部案件编号，设置后续复查。

Stripe 允许通过 Dashboard 或 API 管理争议，但可用字段取决于当前争议与功能。Dashboard 的页面提示通常比照抄旧教程更可靠。确认资料无误后再提交；银行审查开始后，修改空间可能受到限制。不要拖到最后几分钟才准备附件，也不要在截止时间不明确时假设还有额外宽限期。

## 使用 API 提交证据时要留意的字段和状态

对于需要自动化管理的商家，可以使用 Disputes API 更新争议对象的证据字段。官方 API 文档中的 `evidence` 包含多种面向不同原因的字段，例如 `shipping_tracking_number`、`shipping_carrier`、`customer_communication`、`service_documentation`、`refund_policy` 和 `product_description`。文件型字段通常需要先上传 Stripe File，再引用文件 ID；不能把本地文件路径直接填进证据字段。

特别注意 `submit` 参数。将其设为 `false` 可以先暂存证据，之后在 Dashboard 或再次调用 API 检查并提交；提交给发卡行后，就进入正式审核流程。官方文档也说明，更新证据对象中的字段会把该证据集合提交审查，因此程序应先准备完整证据，再发起最终提交，而不是把每个字段分成许多不完整请求逐步覆盖。

API 集成建议采用以下步骤：

- 使用争议对象的最新状态，避免在旧数据上覆盖更新；
- 在内部数据库保存 Dispute ID、证据版本和审核人；
- 将文件先上传到 Stripe，并确认返回文件 ID；
- 对长文本检查字段长度限制，避免超过 API 上限；
- 暂存后由人工复核姓名、订单号、日期、币种和争议原因；
- 只有审核通过后才提交，记录提交响应和 Stripe 返回状态；
- 使用幂等机制防止自动重试导致重复的内部案件或通知；
- 对 API 错误、权限问题和截止时间告警单独处理。

不要根据教程中旧版参数臆测争议字段。Stripe API 版本和证据字段会演进；在开发时核对当前账户实际 API 版本与官方参考，并在测试环境验证文件上传和争议更新行为。

## 截止时间与团队处理流程

争议通常有回应期限，但具体期限取决于争议和网络规则。以 Stripe Dashboard 显示的截止时间为准，不要把某个网上流传的固定天数套用到所有案件。建立以下运营机制：

- 新争议事件到达时立即创建案件记录；
- 记录 Stripe 显示的截止时间，并按业务时区转换后同时保存原始时间戳；
- 设置至少两次提醒：材料收集提醒和提交前复核提醒；
- 指定一名负责人和一名备用审核人；
- 将订单、物流、服务日志和客户邮件链接到同一案件；
- 预留审核和修正时间，避免在截止前才首次整理材料；
- 提交后继续跟踪结果、后续证据请求和财务影响。

如果商家使用 Webhook 自动创建争议工单，应对事件进行签名验证和幂等处理。争议事件可能重复送达；不要因此创建多个独立任务，也不要自动用同一段通用文案提交证据。自动化可以负责通知、拉取交易信息和预填材料，最终陈述与附件仍应由熟悉订单事实的人核验。

## 提交前复核清单

提交前逐项确认：

- 争议原因与回应内容一致；
- 争议交易、订单和客户完全匹配；
- 金额、币种、日期和时区无误；
- 每个陈述都有材料支持，没有猜测或夸大；
- 退款、取消和交付状态与 Stripe 对象及业务系统一致；
- 物流单号或服务时间线可读且能对应本次订单；
- 附件没有其他客户数据、无关隐私或内部机密；
- 文件清晰、格式可打开、页面方向正确；
- 说明内容对不熟悉你业务的人也容易理解；
- 尚有足够时间完成最终提交，且提交状态已保存。

可以让另一位团队成员只看证据包和争议原因，检查他是否能在几分钟内理解发生了什么。如果仍需大量口头解释，说明摘要或材料顺序还不够清晰。

## 常见错误

**提交大量无关截图。** 文件数量不等于证据强度。保留最相关的材料，并在摘要中解释每份材料证明什么。

**只上传付款成功凭证。** 成功扣款能证明交易发生，不一定能证明商品已交付、订阅政策已披露或退款已处理。

**将账户风控评分当作最终证明。** 风控评分只是决策信号，应结合客户验证、服务使用和订单上下文。

**等客户回复后才准备材料。** 联系客户有助于查明事实，但不要因此错过正式时限；并行收集系统和业务记录。

**把未提交的草稿当成已回应。** API 暂存或 Dashboard 保存与正式提交是不同状态。检查争议当前状态并保存提交确认。

**重复发送互相矛盾的回应。** 团队应指定单一案件负责人，集中维护证据版本和提交状态。

## 总结

Stripe 争议回应的核心不是“尽可能多地上传文件”，而是围绕具体争议原因，按交易时间线提供相关、清楚且可核实的材料。先确认 Dispute 状态和 Dashboard 截止时间，再分别整理购买前条款、交易记录、交付证明和客户沟通。实物、数字产品、订阅与服务所需证据各不相同。

使用 Dashboard 时逐项核对页面要求；使用 API 时先上传文件、准备完整证据、利用暂存状态复核，再决定是否正式提交。通过案件负责人、截止提醒、Webhook 幂等和提交前双人检查，可以减少错过回应时间、提交错误材料和重复操作。争议结果由相关机构审核，任何证据策略都不能保证赢得争议。
