Off-session 支付是指客户当前没有打开商家网站或应用时，商家使用之前保存的支付方式发起扣款。订阅续费、约定分期、订单发货后结算以及客户授权的自动充值，都可能采用这种流程。它可以让付款不依赖客户每次都回到结账页面，但并不意味着银行卡以后一定能无交互扣款。

发卡行、卡组织和当地法规可能要求客户对某次付款进行额外认证，例如 SCA（强客户认证）或 3D Secure。客户保存银行卡时成功完成一次 SetupIntent，并不能保证未来每一笔 off-session PaymentIntent 都会成功。实现上应先取得明确授权，再按 off_session 场景发起支付；如果发卡行要求客户参与认证，就把支付转成需要客户回到页面完成的流程，而不是不断后台重试。

## 先区分 on-session 和 off-session

On-session 表示客户正在商家的结账或账户页面中，可以响应银行认证、修改支付方式或确认金额。Off-session 表示商家发起请求时客户不在当前流程中，系统可能无法立即展示 3DS 挑战窗口。把支付意图标记为 off_session，是向 Stripe 说明真实交易场景，并非跳过认证的开关。

Stripe 建议使用 SetupIntent 在尚未收款时保存支付方式，或在首笔付款时按未来用途设置 PaymentIntent。若之后可能在客户不在线时扣款，配置未来使用方式时应选择 off_session。支付方式要关联正确 Customer，商家还要保存内部客户 ID 与 Stripe Customer、PaymentMethod 的映射，避免把一个客户的卡误用于另一个账户。

SetupIntent 的成功代表支付方式设置流程完成，并不代表该卡永远不会被银行拒绝，也不代表未来扣款不需要再次认证。首次设置时 Stripe 可能收集授权或触发必要认证，以改善后续使用条件；然而银行风控、卡片状态、支付金额、地点和监管规则都可能变化。

## 在保存时取得清晰授权

商家有责任遵守适用法律、卡组织规则和本地监管要求。收集银行卡时，应清楚说明保存用途，并提供相应的授权选择。对于客户离线时发起扣款，条款需要说明客户允许商家发起一次或一系列付款、预期时间和频率、金额如何确定，以及订阅服务如何取消。

授权文案应匹配真实产品，而不是笼统地写“同意使用本网站”。例如，按月订阅要说明续费周期和取消方式；发货后结算要说明何时计算最终金额；按用量计费则要说明使用量如何记录和换算为应付金额。用户勾选授权后，系统应保存同意时间、条款版本、客户身份及适用场景，便于处理争议或客服请求。

如果客户只同意在每次购买时手动付款，就不能据此推断其同意未来自动扣款。客户撤销授权或关闭订阅后，也要停止后续扣款任务，并在后台留下状态变更记录。

## 创建离线 PaymentIntent 的状态处理

后台创建 PaymentIntent 时，应从内部账单或订单中读取准确金额、币种、Customer 和已授权的 PaymentMethod。对真实离线付款，将 confirm 设为 true 并声明 off_session 使用场景；应使用 Stripe 官方 SDK，并在服务端操作，不要把 Secret Key 暴露给浏览器。每笔扣款还要关联内部账单编号，避免定时任务重试时创建重复账单。

支付成功时，PaymentIntent 进入 succeeded，系统可依据业务规则将账单标记为已付款。若银行卡需要客户操作，支付可能进入 requires_action，或者 API 返回需要处理的认证错误。此时不要把账单记为已付款，也不要把这笔付款标成永久失败。创建客户补付任务，并通过邮件、站内通知或登录后账单页面引导客户重新进入可交互的付款流程。

其他结果也要区分处理：requires_payment_method 表示当前付款方式无法完成支付，需要客户更换或更新；processing 表示处理仍在进行，应等待后续状态更新；canceled 表示 PaymentIntent 已取消，不应继续当作有效支付尝试。系统的订单状态不应只保存一个布尔值 paid，而要保留“待认证”“等待支付结果”“需要换卡”“已取消”等可操作状态。

## 客户返回后如何完成认证

当离线扣款需要认证，客户回到网站后，服务端应先查找原账单和对应 PaymentIntent，再由前端通过 Stripe.js 或 Payment Element 展示所需操作。不要在客户返回时直接创建另一笔金额相同的 PaymentIntent；重复创建会令系统难以判断哪个账单仍有效，也可能造成两次扣款。

认证成功后，应以服务端收到的 Stripe 事件和对象状态更新账单。客户可能关闭浏览器、网络中断或认证失败，因此跳转页面不应作为唯一依据。对于仍未完成的账单，要提供重新尝试、更新支付方式或联系支持的路径，并设置明确的订单履约规则。

如果 PaymentIntent 已经取消或其状态不再允许确认，应按 Stripe 当前状态创建新的支付尝试，而不是对旧对象反复 confirm。新旧尝试都应与同一个业务账单关联，但在数据库中保留各自的 PaymentIntent ID、创建时间和结果。这样客服可以判断客户是否已完成认证，财务也能排查重复扣款。

## 自动重试与订阅的特殊考虑

后台任务可以对暂时性网络问题进行有限重试，但不能把所有失败一概视为可重试错误。银行卡余额不足、账户关闭或被银行拒绝，可能需要客户换卡或联系银行；SCA 认证要求则需要客户参与；系统超时则应先查询 PaymentIntent，确认 Stripe 是否已处理请求，再决定是否创建下一次尝试。

对重复请求使用稳定的业务幂等键，将一次账单扣款操作与重试分开管理。幂等键不能每次网络重试都随机生成，否则相同业务动作可能创建多个独立扣款。定时任务也要检查本地账单是否已经付款或已有处理中 PaymentIntent。

订阅扣款可利用 Stripe Billing 的发票和失败付款机制管理后续动作。不要在自己的定时脚本与 Stripe Billing 同时为同一张发票扣款。发生续费失败时，按发票状态、PaymentIntent 状态和订阅状态更新访问权限，并按照产品规则提醒客户补付或更新卡片。

## 测试与监控要点

在测试环境中覆盖首次保存卡片、常规离线成功、需要身份验证、卡片被拒绝、客户取消认证、网络超时及重复 webhook 等场景。Stripe 提供专门的测试 PaymentMethod 用于模拟离线扣款需要认证的情况；在测试环境验证从后台请求到客户完成补付的整个闭环，而不只是验证 API 返回一个错误对象。

生产环境中至少观察离线扣款成功率、requires_action 比例、补付完成率、卡片拒绝原因、同一账单的重复尝试数和 webhook 延迟。若认证要求突然增多，应按地区、卡组织、账户配置和交易类型排查。不要用强制关闭 3DS 或伪装为 on-session 的方式规避银行或法规要求，这可能导致支付失败、争议或合规风险。

## 常见实现错误

**把保存卡片当作未来扣款保证。** SetupIntent 成功只说明本次设置成功，后续扣款仍由银行和支付规则决定。

**未取得离线扣款授权。** 保存付款信息和同意商家以后主动扣款是两个不同事项，授权内容应具体且留有记录。

**把 requires_action 标成失败或已付款。** 前者通常需要客户补做认证，后者只有在 PaymentIntent 确认成功后才成立。

**遇到 SCA 就在后台无限重试。** 用户不在线时无法完成交互认证，重复请求不会替代客户认证，反而会产生更多无效尝试。

**让客户补付时另建重复账单。** 应定位原始账单及 PaymentIntent，根据其状态恢复认证或创建受控的新支付尝试。

**从浏览器跳转判断付款结果。** 页面可能未加载成功或被关闭，订单更新应由经过验证的 webhook 和服务端查询负责。

## 上线检查清单

- 保存卡片时选择与实际未来使用方式一致的 SetupIntent 或支付参数；
- 条款明确说明扣款目的、频率、金额计算和取消方式；
- 记录客户同意的时间、账户和条款版本；
- 每次离线扣款对应唯一内部账单和幂等键；
- 将 requires_action、requires_payment_method、processing 和 succeeded 分开处理；
- SCA 需要时向客户提供安全的交互认证和补付入口；
- Webhook 验证签名并对重复事件进行幂等处理；
- 订阅发票和自建定时扣款不会重复收取同一账单；
- 测试身份验证、拒绝、取消、网络超时和重复请求；
- 用服务端确认结果后再恢复订阅权益或履行订单。

## 总结

Stripe off-session 支付适合客户已授权的续费、分期和后续扣款，但保存卡片不会消除未来的 SCA 或 3DS 要求。商家需要在保存时取得与实际扣款方式相符的授权，并把客户离线扣款声明为 off_session。PaymentIntent 成功、需要认证、需要更换支付方式和仍在处理中，是不同的业务状态。

当银行要求客户认证时，应用应保留原账单关联，向客户提供重新进入付款流程的路径，并通过 Stripe 对象状态和 webhook 完成账务更新。把授权、账单、支付尝试和订阅状态分开记录，可避免重复扣款，也能让客户清楚地完成补付。
