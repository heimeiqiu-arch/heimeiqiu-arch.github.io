# Stripe PaymentIntent 多次部分捕获（Multicapture）：分批履约与剩余授权管理

有些订单不是一次性发货：商品分仓配送、预订服务分阶段完成，或者商户需要先取得卡片授权，再按实际履约情况分次收取资金。普通手动捕获可以在授权后捕获一笔不超过可捕获金额的款项；Stripe PaymentIntent 的 multicapture 能力则允许在符合条件的流程中多次捕获，并保留尚未捕获的授权金额以便后续处理。

两者很容易混淆。普通部分捕获通常会结束本次授权，并释放剩余未捕获金额；若要后续继续捕获，需要确认 PaymentIntent 和支付方式是否支持多次捕获，并按 API 参数保留授权。是否可用可能受账户、支付方式、网络和业务类型限制，不应假设所有卡交易都能使用。本文从状态模型、捕获金额、最终捕获和订单对账说明设计要点。

## 普通部分捕获与多次捕获的差别

PaymentIntent 使用手动捕获时，授权通过后进入可捕获状态。商户可提交小于或等于当前可捕获金额的 amount_to_capture。若按照普通的一次捕获处理，未捕获的授权金额会按常规流程释放，商户不能把后续发货简单当成同一笔仍在有效的授权。

在支持 multicapture 的流程中，商户可进行多次 capture，并在捕获时将 final_capture 设为 false，以表示这次捕获后仍计划保留未捕获部分。最后一次捕获需要结束授权；具体字段默认行为及 API 规则请核对当前文档。multicapture 并非“把授权金额无限延长”，授权到期时间、剩余金额、可执行次数以及卡网络规则仍然适用。

因此，首要问题不是“怎么多次调用 capture API”，而是“这笔授权是否允许并且适合多次捕获”。如果你的业务只是最终金额低于授权金额，普通部分捕获可能就足够；如果确实要分批收款，再确认账户和支付方式的适用范围，设计好各批金额与最终完成条件。

## 先定义订单的捕获计划

在创建 PaymentIntent 之前，订单系统应明确授权金额的依据和捕获计划。保存总授权金额、每批次预计履约金额、每次捕获的业务原因、操作人或仓库、捕获截止时间，以及什么条件表示订单最终履约完成。不要让客服或后台员工临时输入任意金额而没有订单规则。

分批发货场景可以为每个履约批次创建内部 capture record，包含 order_id、PaymentIntent ID、批次 ID、计划金额、实际金额、API 请求标识、Stripe 返回的累计已捕获金额、当前可捕获金额和状态。捕获成功后再推进批次状态；失败则保留错误，避免后台重复点击造成重复扣款。

授权金额也不能随意放大以覆盖无限可能的订单变化。金额应与顾客同意的购买内容和实际业务条款一致。若最终金额可能超出原始授权，需要按 Stripe 支持的增额授权或重新付款流程处理，不能通过多次部分捕获突破原授权上限。

## final_capture 与剩余金额

捕获 API 中的 final_capture 表达是否还有后续捕获计划。设为 false 时，Stripe 文档说明这是通知 Stripe 不释放剩余未捕获资金、以便未来请求继续捕获的方式；只有在 PaymentIntent 的 multicapture 能力可用时才能使用。设置为 true 或省略后，是否结束本次授权应依据 API 文档当前默认和具体流程确认。

系统要管理“已捕获金额 + 当前剩余可捕获金额 + 已释放金额”，确保累计捕获不超过授权和订单可收金额。对最后一批，如果实际金额低于剩余授权，明确选择最终捕获并释放余额；不要为了保留授权而一直把 final_capture 设为 false。一直开放剩余授权会让客户看到未完成交易，也可能在授权有效期结束时失效。

不要只用 PaymentIntent.amount 判断还可以捕获多少。检查 Stripe 返回的 amount_capturable、amount_received 和当前状态，并将 Stripe 侧的最终对象数据同步到自己的账本。并发请求可能同时尝试捕获同一余额，因此在数据库中对 PaymentIntent 和批次加锁或设置状态约束，串行处理捕获请求。

## 请求失败、重试和重复捕获控制

在发起捕获前记录内部操作，使用适当的幂等策略防止网络超时后重复发起同一业务动作。若请求超时，不要立即换一个请求标识重复扣款；先查询 PaymentIntent 当前状态、已捕获金额和相关事件，再决定是使用原幂等键重试还是创建新的业务批次。Stripe API 幂等键保护同一请求重试，但不能代替内部批次状态和金额核对。

Stripe 事件可能重复或延迟到达。不要只靠 webhook 更新“第几批已经捕获”，应关联到明确的 PaymentIntent、Charge 和业务批次记录。Webhook 处理器需验证签名、保存事件 ID、处理重复事件，并对乱序通知采取状态校验。若事件和 API 响应先后次序不同，服务端账本要根据 Stripe 对象当前状态进行收敛，而非把较旧事件当成最终状态回滚订单。

如果一次捕获成功但本地数据库写入失败，恢复任务应能通过 PaymentIntent ID 查询 Stripe 的累计金额并与内部记录核对。不要因本地金额仍为零就重新执行同一批捕获。对出现账实不一致的订单暂停自动履约，并通知财务或运营人员。

## 对退款、取消和争议的影响

多次捕获会让交易有多个资金收取动作，客服、会计和退款逻辑需要能识别总捕获额和各次批次。部分退款应以已经捕获的资金为基础，确认可退金额和对应行项目；尚未捕获的授权余额不能被当作已付款金额直接退款。订单取消时，要同时检查是否还有有效授权、已捕获多少以及剩余金额是否需要释放。

在对账报表中分别展示授权金额、每次捕获金额、累计已捕获金额、剩余可捕获金额、最终捕获时间和退款金额。这样才能解释顾客账单上某笔金额对应哪批商品，也能避免把授权金额误记成已结算收入。若涉及 Connect 平台费用或转账，需同时核对费用和转账如何跟随捕获分配；具体行为取决于所用 Connect 收款类型。

## 上线前的资格与测试

Stripe 文档指出 final_capture=false 只能在 multicapture 可用于 PaymentIntent 时使用。测试前先确认账户和目标支付方式资格，查看 Dashboard、集成文档或 Stripe 支持给出的当前要求。沙盒能完成请求并不必然证明正式账户对所有地区和卡片都具备相同能力。

在测试环境覆盖：
1. 授权成功后进行第一次部分捕获，检查余额是否仍可捕获。
2. 再次捕获不同金额，并核对累计已捕获金额。
3. 最后一笔显式结束捕获，确认剩余未捕获授权按预期释放。
4. 金额达到上限、授权即将到期、请求重复和并发操作。
5. API 超时后状态查询、Webhook 重放和本地账本恢复。
6. 退款、取消以及多次捕获后的财务报表呈现。

为每种失败路径准备人工处理流程。若 PaymentIntent 状态不允许再次捕获，先解释是授权被释放、过期、已最终捕获，还是账户与支付方式不支持，不要循环重试。

## 总结

Stripe multicapture 是受条件限制的多次部分捕获能力，与一次普通部分捕获的后续授权处理不同。实施前先确认资格和支付方式支持，再建立明确的分批计划，以 final_capture 控制是否保留剩余授权，记录每次捕获并以 Stripe 当前对象状态对账。做好幂等、并发控制、退款和最终释放流程，避免把授权、已捕获资金和订单履约混成一个状态。
