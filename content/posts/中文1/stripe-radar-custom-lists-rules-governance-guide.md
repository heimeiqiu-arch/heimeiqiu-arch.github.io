# Stripe Radar 自定义列表与规则联动：从维护名单到误拦截复盘

当商户开始处理较多支付时，风控规则很容易出现两类问题：一类是每增加一个邮箱、IP 或客户编号，就新增一条单独规则，规则数量越来越多；另一类是团队把观察名单、可信名单和已确认的欺诈对象混在一起，导致判断标准不清晰。Stripe Radar 的列表功能可以把同类型的数据集中维护，再由规则引用这些列表，让配置更容易阅读和更新。

列表并不会自动替代完整的风控判断。它的价值在于把业务已知信息结构化，并将这些信息接入规则。启用前仍要明确数据来源、适用范围、回滚方式以及对真实客户体验的影响。本文按照“识别需求、建立列表、关联规则、检查结果、持续治理”的顺序，说明一套可执行的管理方法。

## 先区分列表、规则和 Radar 评分

可以把 Radar 的职责拆成三个层次：

| 组成 | 主要职责 | 需要回答的问题 |
| --- | --- | --- |
| Radar 风险评估 | 根据支付上下文和风险信号进行判断 | 这笔支付的风险信号是什么？ |
| 列表 | 保存同一类型、可重复引用的数据 | 哪些邮箱、客户编号或 IP 已经被业务识别？ |
| 规则 | 定义命中条件后的处理动作 | 命中这些数据时，应该允许、阻止还是人工审核？ |

列表本身只是数据集合。建立一个名称为“已确认欺诈邮箱”的列表，并不会自动拒绝任何付款；需要在适用的 Radar 规则中引用该列表并指定动作，规则才会改变处理结果。同样，可信客户名单也应该有清楚的边界，避免把“曾经成功付款”误解为永久可信。

Stripe 文档说明，可在 Radar 规则中引用列表来允许、阻止或审核匹配的支付。具体可用能力取决于账户的 Radar 方案和 Dashboard 当前提供的功能。上线前先确认账户是否支持目标功能，并在 Dashboard 的规则预览中查看影响范围。

## 哪些信息适合放进自定义列表

Radar 支持创建多种类型的自定义列表，例如普通字符串、区分大小写的字符串、卡指纹、卡 BIN、Customer ID、邮箱、IP 地址、国家，以及 ACH 或 SEPA Direct Debit 银行账户指纹。应该按照列表类型保存匹配值，不要为了图方便把不同字段都塞入一个普通字符串列表。

可按业务目的设计分开的名单：

- **已确认欺诈**：只放入有可靠证据支持的邮箱、卡指纹或客户标识。记录来源和确认日期，避免仅凭一次失败付款就认定为欺诈。
- **待观察对象**：用于需要进一步核查的信号。若使用规则将其送入审核队列，应说明审核责任人和处理时限，不要默默将其升级成阻止名单。
- **业务可信对象**：例如经人工核验的固定客户或受控服务场景中的客户编号。明确名单仅适用的产品、市场或支付流程，定期复查是否仍然有效。
- **高风险来源**：例如经过内部调查的来源 IP。共享网络、企业代理和移动网络会让多个正常用户共用同一地址，因此 IP 名单应特别谨慎。

不要把支付卡完整号码、CVC、安全码、密码、访问令牌或其他不适合存储的秘密信息放入名单。名单只保存规则所需的匹配值，并限制有权限维护它的人员。需要保留调查材料时，将证据放在符合内部数据治理要求的位置，在名单中只保存必要的识别信息。

## 创建列表前先写清楚治理规则

创建前可以用一张简单的登记表把目的和责任固定下来：

| 字段 | 示例内容 |
| --- | --- |
| 名单名称 | 已确认欺诈邮箱 |
| 列表类型 | Email |
| 使用目的 | 在已核实的欺诈信号场景中阻止后续匹配支付 |
| 数据负责人 | 风控值班组 |
| 添加依据 | 已完成的争议调查、客户核验或内部案件记录 |
| 复核频率 | 每月检查一次；收到申诉时立即复核 |
| 移除条件 | 误关联、身份更正、风险证据失效或业务流程变化 |
| 关联规则 | 规则页面中的阻止规则名称及生效状态 |

这份登记表不需要与 Stripe 列表混为一体，但应当可以追溯每条值为何被加入、谁作出判断以及何时复查。Stripe Dashboard 的列表项目会显示加入时间和添加者，并允许按值、作者和添加日期筛选；官方文档还指出，每个列表最多可包含 50,000 个项目。达到规模上限前，应考虑清理过期值或调整维护流程。

## 在 Dashboard 中创建和维护列表

官方文档介绍的 Dashboard 流程是：进入 Radar 列表页面，点击 **New**，填写列表名称，选择匹配的数据类型，然后保存。系统会为列表生成用于规则引用的别名，创建者可以按团队命名规范调整别名。建立后，再去规则页面配置引用该名单的规则。

命名最好包含用途和类型，避免含义模糊。例如“confirmed-fraud-email”比“名单A”更便于审查。名称表达业务用途，别名保持简短且易于规则阅读。若多个市场、团队或产品拥有各自不同的处理标准，应拆分名单并在名称中标明适用范围，而不是依赖一份没有边界的全局名单。

维护名单时，建议遵循以下顺序：

1. **确认字段类型。** 邮箱名单放邮箱，客户名单放 Customer ID，IP 名单放 IP 地址。类型错误会让规则无法按预期匹配。
2. **确认值的来源。** 检查是否有工单、争议结论、人工核验或其他可复核依据。把临时猜测标记为观察信号，不要直接当作已确认事实。
3. **处理重复和格式。** 统一团队输入方式，并留意大小写敏感列表的匹配差异。不同类型的标准化方式不完全相同，不能一概认为大小写或字符格式会自动折叠。
4. **记录新增与移除理由。** 新值要有负责人和日期；移除时记录原因，便于解释规则结果发生变化的时间点。
5. **定期复查。** 业务客户可能换邮箱，IP 可能重新分配，旧卡指纹也可能不再适用。按照风险和业务变化设置复核周期。

对大批量名单更新，使用 API 前应先核对目标账户、列表类型、数据格式和当前 API 文档。先用小批量或测试环境确认流程，再扩大范围。不要把批量更新脚本的执行成功等同于数据正确，也要准备变更记录和回滚方案。

## 在规则中引用名单，并先检查结果

添加规则时，选择与名单类型相匹配的字段，再使用列表别名表达匹配条件，最后选择允许、阻止或审核等动作。Stripe Radar 规则使用其规则语法，字段可用性和语法以 Dashboard 的规则编辑器及官方规则参考为准。不要直接复制其他账户中的规则，因为不同业务可能使用不同支付方式、字段和风控计划。

正式启用前，逐项检查：

- **匹配对象正确吗？** 确认规则引用的是对应字段和名单，而非名称相似的旧名单。
- **动作符合名单目的吗？** 已确认的欺诈值、待观察值和可信值不能共用同一动作逻辑。
- **影响范围明确吗？** 规则是否覆盖所有支付方式、地区、产品或结账入口？是否会影响合法客户？
- **审核队列有承接能力吗？** 如果动作是审核，团队是否有值班安排，能否及时查看并采取后续行动？
- **回滚路径存在吗？** 负责人是否知道如何暂停规则、删除误加值或恢复上一版本？

Radar Dashboard 提供规则测试或预览能力时，先查看过去交易上的预计匹配结果，并抽样检查命中的交易是否符合业务预期。测试结果是帮助评估规则的材料，不是对未来表现的保证。规则涉及高金额、重要客户或关键市场时，可先小范围运行并持续监控，再决定是否扩大适用范围。

## 用误拦截反馈更新名单，而不是盲目加严

当客户反馈支付被拒绝时，先定位 PaymentIntent 或 Charge，再检查该笔交易当时的风险结果、命中的规则、关联名单值以及值的录入依据。检查时不要只看客户说“这是本人操作”，也不要把一次拒付直接转化成新的阻止名单项。需要验证身份、交易上下文和相关历史记录，并区分发卡行拒绝、Radar 规则拦截、认证失败等不同原因。

如果确认是误匹配，可以按顺序处理：

1. 暂停或调整会造成误拦截的规则，视影响范围决定是否立即操作。
2. 从对应名单移除错误值，检查同一值是否被添加到其他名单或规则。
3. 记录被影响的交易数量、时间范围和原因。
4. 复核同类客户是否也受到影响，观察规则修改后的效果。
5. 将判定方法写入团队操作手册，避免后续人员重复加入错误值。

对于疑似欺诈但证据不足的情况，可考虑让规则将支付送入人工审核，而非直接阻止。Radar 审核队列可提供支付相关风险上下文，但应先确认支付方式支持人工审核。Stripe 当前文档说明，ACH 和 SEPA Direct Debit 支付不能使用该人工审核流程；不支持审核的支付方式应查看可用规则和 Dashboard 的测试结果，设计适当处理方法。

## 常见配置误区

### 建立了名单，却没有规则引用

名单只存储值。若没有规则引用它，支付处理可能不会有任何变化。检查列表与规则两处配置，不要仅以列表页面显示“已创建”判断风控已经生效。

### 把所有异常都加入永久阻止名单

异常不等于已确认欺诈。账户共用邮箱域、企业网络、家庭网络和移动运营商出口都可能造成关联。如果用过于宽泛的值做强阻止，正常用户可能被连带拦截。给名单设置证据标准、复核周期和移除条件。

### 可信名单成为无期限豁免

可信客户的身份、支付习惯和账户安全状态会变化。允许名单可能改变规则行为，应明确其作用范围，定期核验来源，并且不要因为客户历史上有过成功付款就自动加入。更不能把允许列表当成跳过全部风险控制的万能开关；实际结果取决于规则配置和 Radar 的相关处理机制。

### 规则与名单改动没有留痕

当名单或规则变化后，支付结果也可能变化。没有变更记录，团队便难以区分是模型评分变化、规则调整还是错误名单值造成的影响。把变更时间、操作者、理由、受影响场景以及回滚操作写入内部记录。

## 一份可执行的上线检查清单

在将 Radar 列表规则用于生产前，逐项确认：

- [ ] 名单名称、数据类型和用途都清楚。
- [ ] 每条值都有可追溯来源和添加依据。
- [ ] 负责人、复核周期和移除条件已经确定。
- [ ] 规则引用了正确名单，并且动作与业务目标一致。
- [ ] 已检查规则预览或测试结果，并抽样核对可能命中的交易。
- [ ] 误拦截处理、客户申诉和紧急回滚有明确负责人。
- [ ] 名单中没有不应保存的敏感凭据或超出目的的数据。
- [ ] 更新名单或规则时会留下审计记录。

## 总结

Stripe Radar 的自定义列表适合集中维护同类风控信息，规则则负责把这些信息连接到支付处理动作。稳健的做法是先明确名单用途和证据标准，再选择合适的数据类型，建立可追溯的维护流程，最后通过规则预览、交易抽样和上线后的指标观察效果。把“已确认欺诈”“待观察”和“可信对象”分开管理，并为误匹配设定快速纠正路径，能让名单随着业务变化保持准确，减少因旧数据、宽泛条件或缺少审核造成的误拦截。
