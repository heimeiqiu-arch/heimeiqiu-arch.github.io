# Stripe Refund 状态怎么看？Pending、Failed、部分退款与客户通知

客户提交退款申请后，商家通常会先在 Stripe Dashboard 或 API 中创建 Refund。创建成功并不等于客户银行已经显示退款，也不一定意味着整笔付款都已退款。不同支付方式的退款处理速度和状态变化不同，退款对象还可能经历 pending、成功或失败。若商家把“退款请求已提交”直接显示成“退款已到账”，容易引发客户投诉和财务差异。

本文说明 Stripe Refund 的基本对象关系、常见状态、部分退款、Webhook 同步与对账策略。银行入账时间取决于支付方式和金融机构；Stripe 对退款的处理方式也可能随国家和支付渠道不同。请以 Refund 对象当前状态、Dashboard 显示和相关支付方式的官方文档为准。

## Refund 退款对象和原始支付的关系

Stripe Refund 对象代表对某笔 PaymentIntent、Charge 或其他适用支付来源发起的退款。退款需要关联原支付，且不能超过可退金额。一个支付可以有多笔部分退款，但累计退款不能超出原始可退余额；系统还要考虑已经进行的其他退款、争议和调整。

排查一笔退款时，至少需要关联：

- 内部订单 ID；
- PaymentIntent ID 或原始 Charge ID；
- Refund ID；
- 退款金额和币种；
- 退款原因和请求来源；
- 当前 Refund 状态；
- 相关余额交易和费用；
- 客户通知状态及发送记录。

在客服对话中，内部订单号更容易使用，但后台应保留 Stripe 对象 ID，方便通过 Dashboard 搜索和 API 查询。不要用客户邮箱或末四位卡号作为唯一记录键，因为同一客户可能有多笔交易。

## 常见退款状态的含义

Refund 状态反映 Stripe 退款流程当前进度。常见状态包括：

| 状态 | 操作理解 | 客户沟通方式 |
|---|---|---|
| `pending` | 退款仍在处理或等待支付渠道完成 | 告知退款已发起/处理中，勿承诺已入账 |
| `succeeded` | Stripe 已将退款处理为成功 | 告知 Stripe 处理已完成，银行账单展示仍可能有延迟 |
| `failed` | 退款失败，金额可能返回 Stripe 余额 | 调查失败原因，安排其他退款方式或联系支持 |
| `canceled` | 退款流程被取消（适用场景下） | 重新核对原支付和退款记录，不能当作已退 |

具体支付方式的退款状态可能有额外行为。例如某些支付渠道需要客户提供退款资料；延迟支付或银行转账的处理也可能与银行卡不同。不要把以上状态当成所有支付方式的完整状态机，应根据对象返回字段和支付方式文档确认。

## 创建退款前的金额与订单核对

创建退款前，先确认业务规则和资金事实：

1. 订单已满足退款政策，且退款请求由有权限的人员或系统提出；
2. 退款关联的是正确的 PaymentIntent/Charge；
3. 退款金额使用正确币种，并按该币种的最小单位传入；
4. 累计退款不会超过原支付可退金额；
5. 已存在的 Credit Note、退款、争议或账外补偿已核对；
6. Connect 场景下平台、connected account、转账和应用费的影响已确认；
7. 退款后订单、库存、订阅权益和服务访问规则已经确定；
8. 同一退款申请有唯一内部 ID 和幂等键。

若退款请求因网络超时没有收到响应，先查询现有 Refund，而不是直接创建第二笔。Stripe API 幂等键可以帮助安全重试，但你的内部退款申请也要建立唯一记录，避免客服和自动化系统分别重复操作。

## 全额退款和部分退款

全额退款通常将剩余可退金额全部退回。部分退款只退回订单的一部分，需要明确剩余款项如何处理，以及账单或 Credit Note 是否要同步调整。

适用部分退款的情况包括：

- 客户退回多件商品中的一部分；
- 服务只完成了部分工作；
- 商家对延迟或故障提供部分补偿；
- 订单中有不参与退款的费用或产品。

计算时不要忽略折扣、运费、税额、订阅周期和手续费的业务规则。Stripe Refund 的金额是资金退回的数值，Invoice 或 Credit Note 的会计处理是另一层问题。若退款对应已最终化 Invoice 的贷项调整，应按账务流程考虑 Credit Note，不能假设创建 Refund 会自动完成所有会计或税务凭证。

退款额度应基于服务器保存的订单与支付记录计算，不能信任用户提交的金额。若同一 PaymentIntent 已有一笔部分退款，第二次退款前重新读取原对象和相关 Refund 列表，确认剩余可退金额。

## 客户需要多久能看到退款

退款成功后的银行账单展示时间依支付方式和金融机构处理。Stripe 对象达到成功状态时，Stripe 退款流程已完成相应阶段，但客户银行账户或信用卡账单可能不会立即显示。商家应使用准确措辞，例如“退款已由 Stripe 处理，银行显示可能需要额外时间”，并避免承诺一个无法保证的到账日期。

当 Refund 仍为 pending 时，客户需要知道退款还在处理；若失败，应说明商家正在调查并给出后续方案。不要仅根据创建时间推算到账日期，也不要把 Stripe 余额中的资金变化直接等同于客户账单已经更新。

退款邮件应包含退款金额、币种、对应订单或收据引用、处理状态以及客服渠道。避免在邮件中索要完整卡号或安全码。如果使用 Stripe 自动邮件与商家自建邮件，应确认发送责任，防止客户收到内容重复或状态互相矛盾的通知。

## Webhook 处理 refund.created、refund.updated 和 refund.failed

Stripe 事件参考包含 `refund.created`、`refund.updated` 和 `refund.failed` 等退款事件。可以用 Webhook 更新订单退款状态，减少依赖人工刷新 Dashboard。事件处理逻辑应：

- 验证 Webhook 签名；
- 保存 Event ID 和 Refund ID，防止重复处理；
- 通过 Refund 关联原支付和内部订单；
- 区分退款对象创建、状态更新和失败；
- 仅在符合状态条件时发送对应通知；
- 退款失败时创建调查任务，不要自动重新退款；
- 定期重新读取 Refund 对象核对最终状态；
- 对 Connect 交易检查对应账户上下文和转账影响。

Webhook 可能重复投递，事件也可能异步到达。若先收到退款更新事件、后收到其他相关事件，不要假设事件抵达顺序就是业务发生顺序。幂等更新应基于 Refund 当前状态和内部状态转换规则，避免旧事件把已成功退款覆盖为处理中。

## 退款失败后的处理方式

退款失败时，不要只把订单标记成“已退款”。检查：

- Refund 的 `failure_reason`、错误信息或相关字段；
- 原始支付渠道是否允许退款；
- 客户付款方式是否已关闭或不再有效；
- 是否需要通过其他方式返还资金；
- Stripe 余额是否已收到失败退款对应金额；
- 商家是否需要联系客户确认可用的退款方式；
- 是否有税务或账务单据需要调整。

官方 Stripe 文档对某些支付方式说明：退款失败后 Refund 状态会变为 failed，金额返回 Stripe 余额，商家需要另行安排退款。这个行为并不保证对每个支付方式都完全相同，应以该支付方式的退款指南和对象结果为准。

如果改用银行转账或其他外部方式退款，保存付款凭证、收款人核验和内部审批记录。确认 Stripe 中没有仍待处理的退款，再执行外部退款，防止客户收到双重返还。

## Stripe 余额和财务对账

退款会影响 Stripe 余额和相关 Balance Transaction。对账时要区分：

- 客户原始付款；
- Stripe 手续费是否返还（按当前规则和支付类型确认）；
- 退款金额及其余额交易；
- Refund 失败后金额是否返回余额；
- Payout 与退款跨期的处理；
- Invoice/Credit Note 的会计调整；
- Connect 平台与关联账户的 transfer reversal、应用费退款等。

不要只看某一天的余额变化判断某笔 Refund 是否成功。通过 Refund ID 关联原始 Charge/PaymentIntent、Balance Transaction 和订单，再与会计系统的退款记录、银行流水或外部退款凭证匹配。

对自动化报表，应保留金额和币种，避免将不同币种直接求和。涉及外汇时同时记录客户支付币种、退款币种及 Stripe 余额结算币种，并采用财务团队认可的汇率和记账时间。

## 客户通知和客服话术

建议根据退款状态选择不同文案：

- **退款创建：** “我们已提交退款申请，Stripe 正在处理。”
- **退款处理中：** “退款仍在支付渠道处理，请稍后查看银行账单。”
- **退款成功：** “Stripe 已完成退款处理，银行展示时间因发卡机构而异。”
- **退款失败：** “退款未能完成，我们正在核查并会联系您确认后续方式。”

不要将成功邮件和失败邮件都映射成通用“退款已提交”。客服需要在系统中查看 Refund 的最新状态，并能看到最后一次更新日期、退款金额、原订单以及是否存在其他退款。

## 常见错误

**创建 Refund 后立刻标记客户已收款。** 创建对象只说明请求发起，需跟踪最终状态。

**对同一订单重复退款。** 请求超时或多客服协作时先查现存退款，使用幂等键并锁定内部申请。

**部分退款金额计算错误。** 核对折扣、税、运费和之前退款，不能只按商品价格估算。

**退款成功就忽略 Credit Note。** 支付资金和 Invoice 会计凭证是不同处理对象，财务流程可能需要同时记录。

**退款失败后自动重新提交。** 先确认失败原因和资金是否返回 Stripe 余额，再选合适的退款方式。

**承诺客户银行的固定到账日期。** 银行和支付渠道处理时间不同，应使用保守且准确的说明。

## 测试清单

- 创建全额和部分退款，检查 Refund 与原始支付关联；
- 处理 pending、succeeded 和 failed 状态；
- API 超时后查询现有 Refund，避免重复创建；
- Webhook 重复事件不会重复发通知或更新账务；
- 退款失败时工作流不会把订单错误标记为已退款；
- Connect 交易退款后检查转账和应用费影响；
- Invoice 已最终化时核对 Credit Note 等财务处理；
- 不同币种和零小数货币的金额单位正确；
- 客户邮件状态与 Stripe Refund 当前对象一致；
- 将 Refund、Balance Transaction 和内部订单加入月末对账。

## 总结

Stripe Refund 是一笔针对原始支付的资金返还对象。创建退款不代表客户银行已经显示金额；退款可能处于处理中、成功或失败，具体状态和后续处理依支付方式而异。商家应在创建前核对原支付、累计退款、币种、客户、订单权限和已有退款记录。

通过 `refund.created`、`refund.updated`、`refund.failed` 等事件同步状态，使用签名验证、幂等键和后台对象核对来防止重复操作。对账时将 Refund 与原 Charge/PaymentIntent、Balance Transaction、Invoice/Credit Note 和外部银行记录关联，客服则依据最新状态告知客户，避免把请求已提交误说成银行已到账。
