# Stripe Radar Review 人工审核队列：状态同步、审批与退款处理

自动风控可以评估大量交易，但有些订单仍需要人工结合业务背景判断。Stripe Radar Review 为支持的付款提供 Dashboard 审核队列，团队可查看交易风险线索和业务上下文，并决定批准、退款或退款并标记欺诈。它适合作为自动化风控之外的一层复核，尤其适用于金额较高、国家异常、客户信息可疑或需要人工确认的订单。[Stripe Review payments 指南](https://docs.stripe.com/radar/transaction-reviews)。

一个重要的集成事实是：进入 Review 的付款通常已经成功处理，除非集成采用授权后稍后 capture 的方式。因此，“订单正在审核”不一定意味着款项仍未扣取；批准、拒绝、退款和后续履约是不同的业务动作。平台若只保存一个 `review_status` 并把它当成支付状态，容易造成已退款订单仍发货、已经收款订单被误当未付款等问题。

## Review 队列是什么，不是什么

Review 队列用于补充 Stripe 自动化风控的人工判断。团队可为符合条件的付款建立筛选规则，并在 Dashboard 中集中查看队列。列表或详情视图可能显示风险等级、客户与付款方式信息、金额和时间，以及其他可用于判断的上下文。队列聚焦付款风险决策，不是一个通用工单系统，也不会替代平台自己的客服、订单审计、仓储拦截和退款对账流程。

Review 能否用于某个付款方式与账户配置有关。Stripe 当前文档说明多数受支持的 Radar 付款方式可以人工审核，同时列出 ACH 和 SEPA Direct Debit 等不支持人工 Review 的情况。产品可用性会演进，上线前应核对当前支持列表；不能因为卡支付能出现在 Review 队列，就推断所有银行扣款或本地支付也会进入同一流程。[支持的付款方式](https://docs.stripe.com/radar/supported-payment-methods)。

## 先建模付款状态与审核状态

建议将支付状态、审核状态和履约状态拆分为不同字段或状态机。支付状态描述 PaymentIntent/Charge 是否成功、需要验证、授权待 capture 或已退款；审核状态描述是否进入队列、等待人工决策、已批准或已拒绝；履约状态描述订单是否准备、发货、交付或已取消。三者之间可以有业务约束，但不是同一个状态。

例如，Review 进行中且款项已经成功时，平台可以暂缓发货，但财务账本仍应记录已收款。若人工审核后选择退款，支付对象会进入退款流程，退款可能异步完成；订单状态不能在“点击退款”时就伪装成“退款已到账”。如果是授权待 capture 的交易，则审核策略可能是先批准再 capture，或拒绝后取消授权。具体流程取决于支付集成和业务政策，应检查 PaymentIntent、Charge 和 Refund 的实际状态再更新订单。

把这些状态拆开以后，客服可以回答“款项已扣但订单未发出”，财务可以识别退款是否真正完成，仓库也能只根据明确的履约许可出货。仅依赖 Stripe Dashboard 标签或页面按钮的视觉变化，不足以保证后台订单和第三方仓储系统已同步。

## 为人工审核提供有用且克制的上下文

审核人员需要的信息，应帮助判断订单是否符合正常业务模式，例如商品或服务类型、客户历史、订单金额、交付方式、账户注册时间、内部风险信号和客户支持记录。可使用 Stripe Radar Review 页面支持的 metadata 或其他展示能力提供适量上下文，但要确保内容及时、可读且不含不必要的敏感数据。[Review 最佳实践](https://docs.stripe.com/radar/transaction-reviews#best-practices)。

metadata 应保持简洁且稳定，例如内部订单号或业务分类，不能把身份证件内容、卡号、密码、访问令牌或不必要的个人信息写入。支持人员在 Stripe Dashboard 查看付款详情时，也应遵循最小权限原则。若内部审核工具复制了付款信息，要控制角色授权、访问日志和保留时间。

同时，给审核人员一份明确的判断策略：什么情况可批准、什么情形需要补充验证、何时应退款、何时可以标记欺诈并升级安全团队。规则应反映真实业务，不应只因为某个国家或邮箱域名就自动认定所有订单为欺诈。Stripe 提供风险线索，但最终操作仍需结合订单上下文和团队政策。

## 用 Webhook 同步 Review 生命周期

服务端可以订阅适用的 Review 事件，例如 `review.opened` 和 `review.closed`。当 Review 打开时，将事件记录到审计表或任务系统，并将关联订单标为需要复核；当 Review 关闭时，重新读取 Review 对象和关联付款对象，判断最终决策如何影响本地业务。Stripe Event 类型文档列出了 Review 相关事件；事件结构会按所创建 event 的 API 版本生成。[Stripe Events API](https://docs.stripe.com/api/events/types)。

Webhook 接收端首先验证签名，确认模式、账户上下文和事件 ID，然后快速写入持久化队列并返回成功。后台任务负责关联订单、检查当前对象状态、创建审核任务或更新本地记录。以 event ID 实现幂等，避免 Stripe 重试导致重复通知或重复退款。对延迟和乱序事件，不能简单按接收顺序覆盖数据库；可通过当前 Review 与付款对象状态重新核对。

需要区分“审核决策已关闭”与“退款已成功”。Review 被关闭可能意味着审核者批准，也可能意味着退款或其他处置；平台应读取 Review 的实际结果，再检索关联的 PaymentIntent/Charge/Refund 来确认资金状态。不要仅凭 `review.closed` 就自动向客户宣布退款到账，也不要把所有关闭状态映射为拒绝。

## 批准、退款与标记欺诈

Stripe Review 流程提供批准付款、退款、以及退款并标记欺诈等人工决策。批准可以允许订单进入后续流程，但平台仍应检查付款本身是否处于可履约状态。若交易处于“先授权后 capture”的模式，批准后可能还有捕获步骤；如果交易已经 capture，批准只是风险处置决策，不会再次扣款或替代支付成功事件。

退款路径需要和订单、账本及客服通知联动。人工审核者选择退款后，后台要记录操作人员、时间、原因和关联对象，并等待 Stripe Refund 状态变化更新最终记录。部分退款和全额退款对库存、订阅权益或服务访问可能有不同影响。若退款请求失败，订单不能被误标记为已退款；应进入待处理或人工跟进状态。

“标记欺诈”也不能被当作普通退款按钮的同义词。它意味着团队认为付款具有欺诈性质，相关操作可能影响 Stripe 风险系统的后续判断。审核规范应要求必要证据和内部审批，并确保客服、财务和风控对这种决策的含义一致。若因误操作标记，应按平台与 Stripe 的正式流程处理，不应在内部数据库悄悄删除审计记录。

## 规模化审核与队列管理

审核队列要有 SLA 和分派机制。根据订单风险和潜在损失，定义优先级、工作时段、升级方式和超时处理。例如高金额、即将发货的订单可以优先处理；低风险且尚未履约的订单可进入常规队列。应监控 Review 待处理数量、平均处理时间、批准比例、退款比例、后续争议率和误判复核量。

如果 Review 数量突然增长，先确认是规则变更、业务营销活动、支付方式占比变化，还是实际欺诈上升。自动规则过宽会让人工队列拥堵，审核变慢又可能影响正常客户体验。调整筛选规则前，可以使用 Dashboard 的规则测试或内部历史数据回放评估影响；不能仅通过把所有订单都放进 Review 来规避风控判断。

团队还要定义假期和非工作时间策略。付款已经处理但订单卡在审核时，用户可能需要获得准确的状态说明和联系客服路径。不要在审核未完成时承诺固定时间或保证一定放行，也不要把“已付款”表达成“订单已发货”。

## 常见问题排查

**订单已付款，为什么仍显示 Review？**  
Review 关注交易是否需要进一步人工判断。Stripe 文档说明被放入 Review 的付款通常已经成功处理，除非采用手动捕获授权款的方案。分别查询付款状态、审核状态和履约状态。

**Dashboard 已批准，网站仍不发货：**  
检查 `review.closed` webhook 是否送达、worker 是否关联到正确订单、订单服务是否订阅更新，以及 fulfillment 是否还需要检查其他条件。必要时检索当前 Review 和 PaymentIntent 状态进行补偿同步。

**收到重复 Review 通知：**  
检查 event ID 去重、Webhook 投递重试和工单系统的幂等键。若新事件 ID 对应同一订单和同一审核周期，应该按 Review ID 与业务状态做合理聚合，而不是盲目丢弃。

**Review 关闭但退款仍显示处理中：**  
检查 Refund 对象和退款相关事件。审核动作和退款最终资金状态是两件事，需等待退款状态确认后再更新用户通知和财务记录。

## 上线检查清单

- 将付款、Review 决策与履约状态分开存储和展示。
- 确认目标账户、套餐及付款方式支持人工 Review。
- 只向审核人员提供完成决策所需的最少上下文。
- 对相关 Webhook 签名校验、持久化、幂等和乱序处理。
- 从 Review 事件关联并重新核对当前付款、退款状态。
- 退款完成前不显示退款已成功，付款批准后也不跳过履约校验。
- 为 Review 队列设置负责人、优先级、SLA 和异常升级路径。
- 定期分析误判、审核耗时和后续争议，改进规则与团队策略。

## 总结

Radar Review 是自动化风控与人工专业判断之间的补充层。集成时要把审核和支付、退款、订单履约状态分开，通过 `review.opened`、`review.closed` 等事件更新审核队列，再以当前 Stripe 对象确认最终付款或退款状态。做好事件幂等、审核审计、隐私控制和队列 SLA，才能避免误发货、重复退款或用户收到不准确的处理结果。

Stripe Radar Review 的支持能力、界面和事件细节可能随账户计划、支付方式和 API 版本变化。请以账户当前 Dashboard 和官方文档为准。
