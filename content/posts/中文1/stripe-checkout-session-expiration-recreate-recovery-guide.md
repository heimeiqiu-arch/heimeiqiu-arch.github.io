# Stripe Checkout Session 过期处理：订单保留、重新创建与防重复支付

客户打开 Checkout 页面后暂时离开、关闭浏览器或网络中断，原有 Checkout Session 最终可能过期。过期意味着这条支付会话已不能继续按原状态完成付款，但它不应该让商家丢失订单上下文，也不应该触发错误发货。成熟的处理流程需要把订单生命周期和 Session 生命周期分开：保留购物车或待付款订单，根据当前价格和库存重新校验，再为客户创建新的支付会话，并确保旧会话无法重复履约。

Stripe 会在 Checkout Session 过期时发送 checkout.session.expired 事件。Session 过期、付款完成和延迟支付最终成功是不同状态，应分别处理。通过 webhook 观察 Session 变化，可更新订单状态、释放过期预留或向客户提供重新结账入口；对于异步支付方式，还需要关注相应的异步成功和失败事件。Webhook 处理仍要校验签名、去重，并以 Stripe 对象状态完成最终核对。[Stripe 事件类型参考](https://docs.stripe.com/api/events/types)；[Checkout Session API](https://docs.stripe.com/api/checkout/sessions)。

## Session、订单与付款尝试的状态拆分

不要用一个数据库字段同时表示“订单不存在”“Checkout 页面已过期”和“付款失败”。建议至少拆成三类记录：

- **商家订单**：购物车快照、商品、数量、客户账号、金额计算版本和履约状态。
- **支付尝试**：关联的 Checkout Session、PaymentIntent 或订阅对象、Stripe 模式、最近状态与创建时间。
- **订单履约**：是否可以发货、开通服务、发放数字权益或完成订阅初始化。

订单可以在首次进入 Checkout 前就有自己的本地 ID。创建 Session 时，把不敏感的本地订单标识写入可用于对账的引用字段或 metadata，再保存返回的 Session ID。客户端完成付款后，Webhook 依据 Session ID 或安全的内部关联查找订单。这样即使客户关闭页面，后台仍能知道哪一笔业务等待付款。

Session 过期后，支付尝试可转为 expired 或需要重新结账，但订单可以继续保持待付款状态一段业务设定时间。库存是否保留、优惠是否继续有效、未付款订单何时自动关闭，应该由商家的订单规则决定，而不是由 Stripe Session 过期事件单独决定。

## 收到 checkout.session.expired 后做什么

Webhook 到达后，先验证 Stripe 签名并检查事件对象属于预期账户、环境和订单。随后确认 Session 的最终状态，判断本地订单是否已经通过另一个 Session 付款、是否已经取消、是否正在履约。如果订单仍待付款，可以标记对应的支付尝试过期，并释放临时库存预留或把购物车标记为可恢复。

不要因过期事件直接把整个订单设置为永久失败。客户可能仍想购买相同商品，只是当前支付链接已不能继续使用。向用户提供“继续结账”入口时，服务端重新验证登录身份和订单归属，根据当前商品价格、折扣、税费、配送费用、库存和可用支付方式创建新的 Checkout Session。不能简单复用旧 Session URL，也不能只拿浏览器传来的旧金额再次创建会话。

当订单已经由其他支付尝试完成时，旧 Session 的过期事件只应关闭旧支付尝试，不得回滚已支付状态。Webhook 可能重复投递或与成功事件交错到达，所以状态迁移应该按订单状态机进行，优先保护已经验证的已支付和已履约状态。

## 重新创建 Session 的安全恢复流程

客户点击恢复按钮时，应用应根据当前登录用户读取服务端保存的待付款订单。若用户尚未登录，可通过高熵、短时有效且一次性使用的恢复令牌定位待付款订单，再要求额外验证邮箱或账号。不要把 Customer ID、金额、商品列表或 Stripe secret 放到公开恢复 URL 中。令牌要能撤销、限制访问范围，且不应长期保存在访问日志和分析工具中。

创建新 Session 前执行订单重新定价。商品可能涨价，促销码可能失效，库存可能不足，税额也可能依据客户地址改变。页面应在支付前向客户展示最新总额和关键变更，并要求重新确认。若业务承诺在一定时间内锁定价格，则由商家系统明确保存锁价规则及有效时间，而不是依赖 Session 是否仍打开。

为避免连续点击创建多条支付尝试，服务端可以对“订单 ID + 创建尝试操作”应用幂等机制，并在开始前检查是否已有尚可使用的未完成 Session。幂等键应按稳定业务操作生成，不应把随机请求 ID 当作跨重试不变的键。如果上一请求超时，应先查询或恢复该操作记录，再决定是否创建新 Session。

## 防止两个 Session 都完成付款

虽然过期和用户离开通常会让付款机会减少，但用户可能打开多个浏览器标签、同时使用旧链接和新链接，或两条会话在状态更新间隔内都被客户完成。因此，订单要支持多次支付尝试，但只有一个被选为最终履约付款。每个成功支付对象都要记录到订单；若同一个订单出现多个成功付款，应进入重复付款处理队列，及时人工核对和按退款政策处理，而不是重复发货。

在 webhook 处理中使用事务或分布式锁，以订单 ID 为粒度确保状态更新原子化。履约逻辑要有自己的幂等键，例如“订单 ID + fulfillment”，使多个 Session 的成功事件无法发出两次发货任务或两次开通权益。对于订阅订单，还要额外检查 Subscription ID 和首次 Invoice 状态，不要只根据 Checkout Session 完成就创建另一份本地订阅记录。

用户回到成功页面时，网页可以展示付款处理中，并向服务端查询该订单状态。只有服务端验证支付对象成功后，才应触发最终履约。客户浏览器被关闭不影响 webhook 入库；反过来，用户访问 success_url 也不能单独证明已收款。

## 库存、折扣和通知策略

是否在 Session 过期时释放库存取决于库存预留策略。高需求限量商品可能需要较短的预留时间；普通商品可以允许用户稍后回到购物车重新购买。收到过期事件前后都要考虑 webhook 延迟：本地定时任务也许先释放了库存，而 Stripe 的 Session 过期通知随后到达。将库存预留看作有时效的独立记录，并通过事务协调订单和库存，避免重复释放或库存变成负数。

折扣码也要在恢复时重新验证。若优惠只对首次购买有效、数量有限、针对特定客户或已过期，恢复旧购物车不等于继续享受优惠。客户需要在付款前看到恢复后的价格。税额和运费也应重新计算，不能只保留旧 Session 的 total_details 作为新 Session 金额来源。

通知可分为订单即将关闭提醒、Session 已过期通知和恢复结账链接。发送前要检查订单仍待付款，避免客户刚刚在另一会话付款后又收到“付款失败”的邮件。通知内容应简洁说明商品、当前待付款状态、恢复入口和有效期；不要包含完整支付凭据或长期有效的 Stripe client secret。

## 与异步支付方式的关系

checkout.session.expired 与 async_payment_succeeded、async_payment_failed 等事件表达不同的业务阶段。某些支付方式在客户完成交互之后还需要处理时间；不要仅根据页面离开或暂时未看到成功页面就认定支付未完成。将支付状态标记为处理中，等待 Stripe 后续事件，直至最终成功、失败或过期。

同一订单如果允许客户在异步支付处理中重新开一个 Session，可能产生并行支付。应该根据所用支付方式和订单政策决定是否禁用重复支付、展示处理中状态，或等待一段时间后提供替代方案。若客户重复支付后两笔都成功，必须有明确的重复付款核查流程。

## 测试和故障排查

在测试环境构造正常完成、客户放弃、Session 过期、webhook 重复和延迟、成功事件与过期事件先后交错、恢复时价格变化、库存变化、两个 Session 成功等情形。检查支付尝试状态、订单状态、库存、折扣、邮件和履约任务是否保持一致。

如果过期事件没有更新订单，检查 webhook endpoint 订阅的事件类型、签名验证、事件是否进入失败队列，以及业务是否正确用 Session ID 查找订单。如果客户恢复后仍被带回旧 Checkout 页面，检查服务端是否返回了缓存的 Session URL，恢复链接是否误保存旧 Session ID，以及页面是否重新执行服务端创建流程。

如果过期后库存仍被占用，排查订单定时任务、Webhook 状态迁移和重复事件逻辑；如果付款成功却订单显示过期，检查成功事件是否因乱序被过期事件覆盖，以及是否对 Stripe 对象当前状态进行了核验。

## 上线检查清单

- 订单、支付尝试和履约状态分开存储。
- checkout.session.expired 与 completed、async payment 事件分别处理。
- Webhook 签名验证、去重、幂等和失败重放可用。
- 恢复付款时重新核对身份、订单归属、价格、折扣、税费和库存。
- 客户无法通过 URL 修改订单金额或指定他人 Customer。
- 并行 Session 只允许一次履约，并能识别重复成功付款。
- 库存预留释放可重复执行，不会重复扣减或重复释放。
- 恢复链接短时有效、可撤销，且不携带 secret。
- 邮件发送前再次确认订单仍处于待付款状态。
- 测试事件乱序、延迟支付和 webhook 重复后仍能正确恢复。

## 总结

Checkout Session 过期首先表示支付入口不再处于原先有效状态，不应被当作订单自动作废或失败的充分依据。将 Session 与本地订单分开管理，收到过期事件后关闭旧支付尝试，再通过服务端重新检查订单并创建新会话，可以让客户安全恢复购买。结合事件幂等、订单状态机、库存预留和履约去重，能够减少放弃订单、误发货和重复扣款之间的冲突。

本文为工程实现参考，Checkout Session 的具体字段和有效期设置应以当前 Stripe API 文档及账户配置为准。
