# Stripe Tax 商品税码怎么选：Product tax code、价格税务行为与目录治理

启用 Stripe Tax 后，团队往往先检查客户地址和自动税开关，却忽略商品目录中的分类。Stripe Tax 需要结合商户的税务设置、客户所在地、产品税码和价格税务行为等信息计算税额。若产品税码空缺或分类与实际商品不符，计算结果可能和业务预期不同，即使 API 调用成功、付款也能继续完成。

商品税码不是商户登记义务的替代品，也不能单独决定企业在某个地区必须收什么税。它提供的是商品或服务的类别信息，供 Stripe Tax 的计算逻辑使用。本文解释 Product tax code 与 Price tax behavior 的区别，介绍如何维护商品目录默认值，以及如何验证发票和 Checkout 中的计算结果。具体商品分类与税务义务需要结合商户事实和适用地区规则确认。

## Product tax code 和 tax behavior 分别描述什么

Product tax code 描述出售的商品或服务属于哪类税务商品。它通常关联 Product，适用于该商品的税务分类。税务规则会根据商品类别、客户位置、商户登记情况和当地规则共同决定是否征税、税率和税额。某些平台在 Stripe Tax 设置中还可以配置默认 tax code，但默认值只适合作为有依据的兜底，不能替代对目录中不同产品的准确分类。

Price tax behavior 则说明价格金额与税款之间的关系：价格是含税（inclusive）、未税（exclusive），还是使用账户或系统推断的行为。它关联价格，而不是产品分类。同一个产品在不同市场或销售策略中可能有不同的价格和税务展示方式，因此税码和价格行为不要混成一个字段。将“数字服务”选成对应税码，不会自动决定展示的价格是含税还是税外加税。

可以用两个独立问题进行审核：
1. 这项产品实际提供什么商品或服务，适合哪个税务类别？
2. 商品标出的价格是否包含税，还是税会在结账时加到价格上？

任何一项配置错误都会影响顾客最终看到的金额或税务记录。Stripe 文档说明，Price 的税务行为在指定后通常不能直接更改；如果产品定价策略变化，需按当前 API 和 Dashboard 能力创建或调整价格，而不是假设历史价格可无损重写。

## 先整理商品，再在 Stripe 中映射税码

规模较小的商户可以直接在 Dashboard 产品页面维护 Product tax code 和 Price tax behavior；使用 API 管理目录的团队则应把对应字段纳入商品同步流程。无论通过哪种方式，都应先建立商户自己的商品目录表，至少记录内部 SKU、产品名称、主要交付内容、实体或数字属性、服务周期、目标市场、Stripe Product ID、Stripe Price ID、tax code 和 tax behavior。

商品名称往往不足以判断税务类别。“专业服务”“会员”“礼包”这类标题可能包含不同内容。需要审查实际合同、交付方式和客户获得的权益。例如，同一个软件产品可能同时出售软件访问、人工咨询和实体设备；如果这些项目被合并成一个 SKU，团队要确认这种组合是否适合一个商品税码，还是应该拆成多个可独立分类和定价的行项目。

新建产品的流程可以是：先由产品或财务负责人描述实际交付内容；再由熟悉业务税务情况的负责人选择 Stripe 税码；随后在测试环境确认税码、价格行为和可计算地区；最后由负责目录的系统发布 Product 与 Price。配置不确定时，不要简单套用“标准税率”或“非应税”默认分类，也不要把上一个相似商品的税码直接复制到新商品。

## 默认税码何时有用，何时会造成风险

默认税码可以降低目录中没有单独设置税码时的配置负担，但对混合商品目录存在风险。假如默认值代表数字产品，而目录里还有实物、运输服务或咨询项目，未分类商品可能被当作数字产品计算。相反，把默认值设为不征税也可能掩盖遗漏。默认配置应反映“最常见且经确认的商品类型”，并建立监控找出仍使用默认分类的商品。

建议在内部目录中区分“人工审核后的明确分类”和“由默认值补齐的分类”。上线门禁可以要求正式销售的每个 SKU 都有分类负责人、税码审核日期和适用说明；新建 Product 时如果没有明确税码，就不允许进入正式收款目录，或者必须进入待审核队列。不要仅依赖 Stripe 中有一个默认值就认为目录已完成税务审核。

如果使用第三方税务应用而不是 Stripe Tax 计算，Stripe Product 与第三方应用内部税码之间可能还需要映射。不要认为 Stripe 税码会自动控制第三方应用的所有分类；应按所用连接器的说明配置映射，并测试应用不可用时订单、Checkout、订阅和发票分别如何处理。

## 在 Checkout、订阅和 Invoice 中核对计算结果

同一产品可能出现在 Payment Links、Checkout、订阅发票、手动创建的 Invoice 或 Tax Calculation 中。每条销售路径都要确认税务设置是否启用，行项目有没有正确带出 Price 与 Product 税务信息。产品目录正确不等于所有既有订阅或旧付款链接都会自动采用当前设置；存量对象可能保留创建时的配置，需按 Stripe Dashboard 的迁移功能和 API 能力逐项检查。

建议在测试模式准备一组具有代表性的场景：不同产品分类、含税与未税价格、不同客户地址、客户税号（如果业务收集）、多个商品混合的购物车以及订阅续费发票。逐个比较税前金额、税额、总额、税务可征收原因和发票行项目。对账时既要看总税额，也要看各行项目的 taxability reason 与具体税率，发现零税时要判断是没有登记、商品不征税、地区不支持还是客户免税等不同原因。

不要只用一个测试地址来确认全部商品。Stripe Tax 的计算会依赖位置和所用产品；客户地址信息不足时，还可能无法得到预期的计算结果。对实际客户地址字段要求和每个产品的支持范围，应依照当前文档与账户设置验证。Checkout 页面显示的税额、Webhook 事件中的对象和最终 Invoice 记录应能互相核对。

## 产品变更和历史价格的管理

商品税码发生变更时，记录变更内容、生效时间、负责人和商业原因。不要只更新 Stripe 目录后就假设历史交易会跟着改算；已完成付款和已 finalized 的发票应按其当时的交易记录解释。对尚未完成的订单、草稿发票和未来订阅续费，则要确认具体对象何时读取产品与价格配置，以及变更是否会影响客户已看到的报价。

对于价格的 tax behavior，需特别留意可变更限制。若历史 Price 使用了错误行为，往往需要按当前 Stripe 支持的流程创建新的 Price，并把产品购买入口迁移到新价格；已有订阅如何切换、是否需要客户同意和如何处理价格差异，应单独规划。不要未经测试直接停用旧 Price，以免已有链接、报价或订阅无法继续工作。

审计商品目录时，至少报告以下异常：缺少税码的 Product、仍使用默认税码的 Product、未明确税务行为的 Price、Stripe Product 与内部 SKU 映射缺失、活跃链接引用旧 Price、过去一段时间税务原因异常的交易。定期把这些清单交给产品目录负责人和税务负责人复核，而不是每年报税前才发现目录存在多年未处理的默认值。

## 上线检查清单

- 盘点所有真实销售的 Product、Price 和内部 SKU，确认目录映射完整。
- 分别审核 Product tax code 与 Price tax behavior，避免把两项设置混为一谈。
- 对实物、数字内容、订阅、服务和组合商品检查税码是否基于实际交付内容选择。
- 明确默认税码的用途，统计并审查仍依赖默认值的活跃产品。
- 验证 Checkout、Payment Links、订阅发票和手动 Invoice 等所有实际销售路径。
- 用多个地址和不同产品场景测试税额、税务原因及发票明细。
- 为新商品、价格迁移和税码修改设置负责人、审批和变更记录。
- 对不确定的分类和登记义务，请商户税务顾问结合适用地区确认。

## 总结

Stripe Tax 商品分类需要把 Product tax code 和 Price tax behavior 分开治理：前者描述商品类别，后者描述价格是否含税。先整理业务 SKU 和实际交付内容，再逐个映射税码，谨慎使用默认值，并在 Checkout、订阅与发票路径验证每个行项目的税务结果。对历史价格、旧链接和存量订阅也要单独盘点，不能把更新目录等同于所有历史对象已自动迁移。
