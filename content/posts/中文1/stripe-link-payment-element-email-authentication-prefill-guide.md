# Stripe Link 与 Payment Element 接入指南：邮箱预填、身份验证和结账体验

Stripe Link 是 Stripe 提供的数字钱包体验，可以让已经使用 Link 的客户复用其保存的信息，缩短结账流程。商家通过 Payment Element 集成时，Link 可以出现在支付表单中；客户可能通过邮箱识别或验证自己的 Link 账户，并选择使用已保存的付款和联系信息。

Link 的价值不只是显示一个钱包按钮。是否提前收集邮箱、是否把邮箱传给 Payment Element、客户如何完成认证、页面中已有的电子邮件字段如何避免冲突，都会影响实际流程。本文重点介绍两种邮箱接入方式、前端信息同步和测试要点，帮助工程团队在不重复询问客户的情况下完成清晰、可控的结账体验。

## 一、理解 Link 在 Payment Element 中的角色

Payment Element 是 Stripe 的嵌入式支付组件，能展示适用于当前交易的付款方式。启用 Link 后，客户可在支付表单中发现 Link，并使用自己的 Link 账户完成付款。对已保存信息的客户，Link 有机会自动填充或复用可用信息；对新用户，流程会提示其通过邮箱进入或注册 Link 体验。

Link 与商家网站的客户账户不是同一概念。客户可能在另一家商户使用过 Link，但并未在当前网站注册。商家也不能因为看到 Link 已认证，就跳过自身业务要求的账户授权、订单确认或服务资格检查。Link 帮助完成付款和已保存信息复用，不会自动替代商家的身份系统或履约规则。

Payment Element 启用了 Link 后，集成还要妥善处理电子邮箱。Link 使用邮箱帮助客户识别账户，因此邮箱字段是否已在前置流程中收集，会决定最顺畅的接入方式。不要在页面上同时创建多个含义不同但标签相同的邮箱输入框，也不要未经客户同意就用一个旧邮箱覆盖他们当前订单使用的地址。

## 二、两种邮箱集成方式

第一种方式是在进入付款页之前收集客户邮箱，然后将该邮箱提供给 Payment Element。这通常适合注册、报价、订单确认或购物车步骤已经收集邮箱的流程。Stripe 文档推荐在可行时向 Payment Element 传递客户邮箱。这样客户可在组件中直接继续 Link 的认证或使用流程，而不是再看到一个独立的邮箱收集步骤。

第二种方式是在 Payment Element 流程中收集邮箱，适合支付页是网站第一次需要客户邮箱的场景。组件可完成必要的邮箱交互，商家应在提交后读取正确的支付和客户信息，并按当前 Stripe 集成指南处理结果。选择这种方式时，确保自己的前端没有另外显示一个空邮箱字段，让客户误以为必须重复填写。

做选择时要基于实际页面顺序，而非偏好某一种技术实现。若客户已在创建订单时提供邮箱，将其传入组件可以减少重复输入；若用户直接从支付链接进入，页面没有可靠的邮箱数据，则应允许在付款步骤完成邮箱收集。若传入邮箱来自账户档案，且用户当前订单可能使用其他联系地址，页面应清楚展示并允许客户按业务规则修改。

## 三、邮箱预填和数据一致性

前端组件需要收到当前订单期望使用的邮箱。不要依赖 DOM 扫描或隐藏输入框作为唯一的数据传递方式。页面上可能存在订阅邮件、登录账号、收货人邮箱和支付联系邮箱等不同字段，组件无法知道哪个才是本次付款应使用的地址。通过集成代码显式传入对应数据，能让流程意图更明确。

如果客户在 Link 流程中验证了一个邮箱，而商家订单使用另一个邮箱，后端需要有明确规则：以客户本次提交的结账邮箱为准，还是把账户联系邮箱作为交易联系地址。不能因 Link 钱包登录就静默更换商家订单联系人。保存订单时，可分别记录客户账户邮箱、交易联系邮箱和 Stripe Customer 信息来源，减少客服处理“收据发送到了哪里”的歧义。

邮箱格式校验与邮箱所有权也需要区分。前端格式正确不代表邮件地址归客户所有；Link 认证也不一定满足商家自身的账户验证要求。若履约或监管要求更严格的验证，应由商家系统建立独立流程并明确向客户说明。

## 四、Stripe 对象与订单关联

创建 PaymentIntent 或其他相关 Stripe 对象时，商家应保存其 ID，并关联内部订单。付款成功后，服务端根据 Stripe 可信事件更新订单、发放数字商品或通知仓库；浏览器客户端只负责呈现进度和引导客户，不应单独决定订单已付款。

如果使用 Customer Session 或保存付款方式功能，应遵循适用的 Customer 和 Payment Element 文档，明确客户同意、可展示的已保存方式以及是否允许删除方式。Link 的钱包资料和商家账户中的保存付款方式在用户体验上有关联，但不同集成能力、对象和同意流程应按各自 API 规则处理。不要把支付一次成功等同于商家获得永久保存客户付款信息的许可。

Webhook 处理需验证 Stripe 签名、去重事件并记录关键对象 ID。事件可能重复送达或与浏览器返回顺序不同，所以账单邮件、订单履约和客户通知都应通过内部订单状态机防止重复执行。若客户刷新页面或返回旧订单链接，页面应从服务端查询当前状态而不是重新创建订单或重放付款。

## 五、页面设计和失败恢复

支付页应清楚呈现商品、应付金额、币种、税费、退款或取消规则，以及如何联系商家。Link 认证过程中，客户可能需要通过一次性验证码或其他方式确认邮箱；页面应让客户知道这是钱包认证的一部分，并提供返回、换用其他支付方式或重新输入邮箱的路径。

测试失败情形时，不要只测试一个已登录 Link 的客户。还应覆盖：尚未使用 Link 的新客户、已有 Link 但邮箱不匹配的客户、客户更改邮箱、认证码收不到或过期、支付失败、付款被取消以及浏览器关闭后再打开订单页。对客户可解释的错误，应显示下一步指引；对内部故障，应记录 request id、PaymentIntent ID 和订单 ID，避免把敏感令牌写入日志。

移动端尤其需要验证键盘、邮箱自动填充和滚动行为。若支付页使用自定义布局，应确保 Link 元素不会被弹窗、遮挡层或焦点管理逻辑盖住。组件更新或页面重新渲染后，应避免重复挂载造成事件监听器堆叠、多个付款表单或无法提交的问题。

## 六、常见集成问题

**客户已填写邮箱，Link 又要求输入。** 检查该邮箱是否以 Stripe 要求的方式传入 Payment Element，而不是只出现在自己网站的文本框里；同时确认前置步骤的数据在跳转或刷新后仍可取得。

**Link 预填的联系信息与订单不同。** 明确当前交易联系人字段的业务规则，并在订单确认页展示其来源。不要将钱包资料作为不可编辑的真值覆盖订单数据。

**测试中看不到 Link。** 检查账户设置、Payment Element 配置、当前设备和浏览器环境、测试数据及付款方式适用条件。使用新的 PaymentIntent 和最新前端配置复测，排除旧客户端缓存或页面仍加载历史配置的情况。

**浏览器返回后订单仍未更新。** 确认服务端 Webhook 订阅及签名验证正常，按对应事件和 PaymentIntent 状态更新内部订单。成功返回 URL 本身不能替代服务端支付确认。

**客户担心提供邮箱。** 说明邮箱用于识别 Link、发送交易信息或完成订单联系的具体用途，并提供隐私政策。营销订阅仍应单独收集，不能因为客户使用 Link 就加入促销名单。

## 七、上线前检查清单

1. 确认 Link 已在 Stripe 付款方式设置和 Payment Element 流程中启用。
2. 根据页面流程决定由前置步骤传入邮箱，还是在支付组件流程中收集。
3. 不使用页面 DOM 搜索作为唯一邮箱传递机制。
4. 清楚区分账户邮箱、支付联系邮箱和收货人邮箱。
5. 确认邮箱发生变化时，订单与 Customer 更新规则一致且可审计。
6. 使用服务端状态和已验证 Webhook 确认付款与触发履约。
7. 测试已保存 Link 用户、新用户、邮箱变化、认证失败和付款失败场景。
8. 测试刷新、浏览器返回、移动端和重复提交的恢复行为。
9. 按相关 API 规则处理保存付款方式和客户同意，不将一次支付等同于永久授权。
10. 检查日志、隐私说明和客服流程，不记录一次性验证码或敏感认证数据。

## 总结

Stripe Link 可以与 Payment Element 结合，为客户提供钱包认证和已保存信息复用。接入时，应围绕邮箱是否已收集来选择集成方式：前置流程已有邮箱时显式传入；支付页首次需要邮箱时，让 Payment Element 完成相应的收集。这样可以减少重复输入，也能避免把不同用途的邮箱字段混为一谈。

上线质量还取决于订单关联、服务端支付确认和失败恢复。商家应让 Stripe 对象与内部订单保持可追踪，使用 Webhook 更新状态，并清楚说明 Link 和交易邮箱的用途。钱包认证不会自动替代商家的账户验证、营销授权或履约决策。
