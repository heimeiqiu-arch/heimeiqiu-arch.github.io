Satispay 是在意大利消费者中使用的电子钱包。Stripe 支持符合条件的商家通过 Satispay 收款：客户在 Checkout 选择该方式后会被重定向到 Satispay 网站完成交易，Stripe 会通知商家付款是否成功。对于计划进入意大利市场的 B2C 商家，增加本地钱包可能为客户提供熟悉的结账选项；不过，商家资格、客户国家和币种都有明确范围，还需要提前设计异步退款和争议处理。

Stripe 当前文档将 Satispay 列为钱包类支付方式，支持重复使用和经常性付款，也支持手动捕获和部分捕获。退款为异步操作，争议规则另有时间窗口。本文介绍 Satispay 的资格判断、Checkout 流程和日常运营注意事项，实际可用性、价格和规则以 Stripe Dashboard 与最新官方页面为准。

## 先判断商家和客户是否符合条件

Satispay 面向意大利客户，展示币种为 EUR。Stripe 支持的商家账户国家范围比客户使用国家更广，账户位于多个欧洲、北美和亚太地区的商家可能具备资格，但这不代表任何地区客户都能使用。Stripe 文档列出的客户国家为意大利，商家业务模型支持 B2C，不支持 B2B。

在计划接入时，需要分别确认：

- Stripe 商家账户所在国家和账户类型是否有资格；
- 目标客户是否位于意大利；
- 商品价格是否按 EUR 展示；
- 商家业务是否为消费者交易；
- 商家的业务类别是否存在受限或禁止的 MCC；
- Connect 平台场景是否满足账户和资金流条件。

Stripe 文档还列出一批受限或禁止行业类别。商家应在申请启用前查看当前 MCC 规则，并确认自己的业务分类是否需要提供额外信息。不要把“Dashboard 可以看到开关”当作类别审查已完成。

## Checkout 跳转支付流程

客户选择 Satispay 后，Stripe 将客户重定向至 Satispay 网站完成付款。Stripe 文档将其确认时机描述为即时通知，但浏览器跳转仍可能被客户中断。商家应先创建待处理订单，等服务端确认支付结果后再履约。

对托管 Checkout，常见实现是先在 Dashboard 启用 Satispay，再让 Stripe 动态支付方式根据客户和交易上下文决定是否展示。如果现有集成手动设置 payment_method_types，要核对当前迁移指南并更新允许的支付方式。后端创建 Checkout Session 时应从商品目录读取价格、币种和数量，避免接受前端任意金额。

前端跳转返回与服务端状态可能不同步。用户付款后关闭浏览器，商家仍可能收到成功事件；用户返回成功页面时，支付也可能仍在确认。订单状态应通过 Stripe 对象和 webhook 更新，不要只把 success_url 的访问当成收款凭证。

## 金额和产品能力

Stripe 文档列出的 Satispay 展示币种为 EUR，当前单笔金额范围从 0.50 EUR 到 999,999.99 EUR。实际交易仍需受到账户资格、业务规则和支付方式限制。价格页面应清楚展示欧元金额，结账和收据也要与订单记录保持一致。

Satispay 支持经常性付款、手动捕获和部分捕获，但不支持多次捕获、超额捕获或某些延长授权能力。若业务需要先授权、后确认最终金额，应验证 Satispay 的捕获能力是否符合订单流程。不能因为银行卡支持某种 PaymentIntent 操作，就假设 Satispay 也支持。

若用于订阅，应测试首次付款、后续续费、付款失败和取消路径。支付方式是否可复用并不代表每个客户或市场都可使用相同的重复扣款逻辑。商家需要依据 Stripe 订阅与发票状态决定是否保留权益，避免只根据创建订阅成功就判断续费一定成功。

## 异步退款与钱包余额

Satispay 支持全额和部分退款。Stripe 文档当前说明退款需要在原始付款后的 180 天内提交，退款为异步处理，可能需要最多约 5 分钟。退款不能取消，且不是通过冲正原交易来完成；退款金额会返回客户的 Satispay 钱包余额。

客服和后台应把退款过程拆分为“已提交”“处理中”“成功”或“失败”。客户提交退款申请后，不能立即承诺资金已经到账。应用应读取 Refund 对象的状态，并监听 refund.updated 或 refund.failed webhook。退款失败时，Stripe 会将金额退回商家 Stripe 余额，商家需要通过其他方式向客户退款。

部分退款要记录原始订单金额、已退金额和可退余额，避免多名客服并行处理超过可退金额。若退款与订阅取消同时发生，还要分开记录已退费用和未来续费状态：退款不会自动取消未来账单，取消订阅也不一定退还已支付金额。

## 争议窗口与证据处理

Satispay 客户可在购买后最多 120 个日历日内发起争议。Stripe 文档说明，争议发生后会立即从商家余额中暂扣争议金额，商家通常有 15 个日历日提交证据；Satispay 会在争议创建后的一段处理时间内作出最终决定。具体日期和当前 Dashboard 展示的截止时间应优先于内部估算。

争议流程应由 Stripe webhook 和运营队列驱动。收到 charge.dispute.created 等相关通知后，客服或风险团队应立即关联订单、商品、客户沟通和履约记录。实体商品可以准备物流跟踪、发货时间和送达信息；数字商品可以保留购买记录、交付时间和账户访问记录；服务类订单可保存合同、预约和服务完成证明。

应提前保存证据，而不是等争议发生后才从多个系统中拼凑。平台还需设置明确责任人、提交时限提醒和复核人。不要提交不相关或未经核实的信息，也不要将争议当作普通退款直接处理。

## 对账与运营监控

日常对账时，建议关联内部订单 ID、Stripe PaymentIntent、Checkout Session、Refund、Dispute 和 Balance Transaction。分别核对收款总额、退款、争议暂扣、手续费和净余额，避免仅以银行结算金额判断订单是否成功。

监控指标可以包括意大利访客中 Satispay 的展示率、选择率、授权成功率、跳转取消率、退款率和争议率。若有大量客户点击后未完成授权，检查移动端跳转、支付提示和返回页面；若退款处理中工单增加，则检查客服承诺和 webhook 更新延迟。确保这些指标按支付方式和客户市场拆分，才能判断该钱包是否适合业务。

## 上线测试清单

- Dashboard 已启用 Satispay，且账户资格符合当前范围；
- 目标客户为意大利消费者，价格以 EUR 显示；
- 测试支付成功、失败、取消和关闭页面；
- 后端仅在 Stripe 确认成功后履约；
- webhook 签名验证、事件去重和订单关联正常；
- 全额和部分退款都经过测试；
- 退款成功与失败均能更新 Refund 状态和客服提示；
- 运营团队知道 180 天退款提交窗口；
- 争议告警能在证据截止前通知负责人；
- 使用手动捕获或订阅时验证对应能力；
- 按当前 MCC 规则检查业务类别；
- 财务能够区分余额、退款、争议和结算流水。

## 总结

Stripe Satispay 适合符合资格、面向意大利消费者且使用 EUR 收款的商家。客户通过跳转完成钱包付款，Stripe 可即时通知交易结果；但订单履约仍应由服务端状态确认驱动。该方式支持经常性付款和部分捕获，也支持部分与全额退款，但退款异步、不可取消，并会返回至客户的钱包余额。

接入前确认 B2C 业务资格、客户市场、MCC 和币种。运营中监控 180 天退款窗口与 120 天争议窗口，及时处理退款 webhook 和举证流程。对所有金额、期限和可用能力，以 Stripe 当前 Dashboard 与官方文档为准。
