# Stripe Issuing 授权与清算交易有什么区别：金额变化、撤销和对账

通过 Stripe Issuing 发出的卡片进行消费时，系统中会先出现授权，再出现后续交易记录。授权代表商户在刷卡当时向发卡方请求批准一笔消费；最终清算可能稍后提交，金额也可能与最初授权不同。若应用只把授权当成已经扣款，或者把授权撤销当作交易退款，卡片余额、用户账单和内部财务账本就容易出现差异。

Issuer 系统需要区分“允许这次消费”“等待商户提交交易”和“资金最终记账”几个阶段。本文解释 Authorization 与 Transaction 对象的职责，说明部分捕获、撤销和金额变化该如何映射到内部交易状态，并提供 webhook 与测试检查清单。具体清算周期、网络规则和可操作能力会受卡网络、交易类型和账户配置影响，应以 Stripe 当前文档和账户记录为准。

## Authorization 是消费请求，不是最终交易凭证

Issuing Authorization 对象反映商户发起的授权请求及其处理结果。实时授权集成中，Stripe 可以向你的授权端点发送同步请求，由业务逻辑判断批准或拒绝；其他情况下，授权流程可能由配置规则处理。授权成功意味着此次消费请求获得批准，但清算之前，交易金额、状态和最终记录仍可能变化。

发卡系统可以据授权占用持卡人可用额度或账户余额，用户界面应将其显示为“待处理”或“授权中”，不要直接计入最终已入账支出。授权对象保留商户名称、类别、授权金额、币种、卡和持卡人引用等信息，可用于即时风控、额度控制和客服查询。

授权后来可能被撤销、过期或由商户提交清算。商户也可能提交小于或不同于原授权的金额，具体规则要看交易场景和 Stripe Issuing API 支持范围。客户端显示的授权金额不应被财务报表永久视为最终支出金额。

## Transaction 记录清算后的消费

Issuing Transaction 表示已提交处理的交易记录，可用于账单展示、余额更新和财务对账。它与授权对象有不同生命周期。应用应通过 Stripe 返回的关联标识或 API 关系，将授权和交易连接起来，而不是仅按商户名称、金额和相近时间猜测两条记录属于同一笔消费。

如果内部账本记录授权时就生成“正式支出”，后续收到交易时可能造成重复记账。更清晰的方式是分开保存授权 hold 和清算 transaction：授权通过时记录待处理金额；清算交易到达时创建或更新正式交易；授权撤销或释放时关闭 hold；交易冲正或退款则建立反向资金记录。这样可以区分可用余额变化和已入账消费。

| Stripe 记录 | 内部账本建议状态 | 业务含义 |
| --- | --- | --- |
| Authorization 创建并批准 | pending_authorization | 商户请求获批，等待后续结果 |
| Authorization 更新或金额变化 | authorization_updated | 当前授权信息变化，刷新 hold |
| Authorization 被撤销或关闭 | authorization_released | 未清算授权不再占用待处理额度 |
| Issuing Transaction 创建 | posted_transaction | 清算交易已进入正式消费账本 |
| Transaction 后续调整 | transaction_adjusted | 对既有交易进行核对或调整 |

表格是内部设计思路，具体 Stripe 事件和对象状态应依据当前集成选择。不要假设每种业务路径都会按一个固定时间顺序收到所有事件，也不要用授权的 approved 布尔值替代交易最终状态。

## 为什么最终金额可能与授权金额不同

商户在授权时可能不知道最终结账金额，例如餐饮小费、交通费用或分批服务的最终费用；某些商户会对较大金额先发起预授权，再按实际金额完成后续提交。Stripe Issuing 的测试文档包含针对授权的测试捕获操作，并允许模拟金额变化或多次捕获情形；生产可用规则需结合账户和网络场景确认。

当交易金额变化时，内部系统需要保存原授权金额、后续捕获或清算金额、当前 hold 和最终交易金额。不要把所有变化都解释成第二笔消费。有些授权可能因金额更新而产生新的授权记录或更新事件；最终应通过 Stripe 对象关系和交易 ID判断，而不是简单对金额求和。

如果持卡人消费余额不足以覆盖最终金额，或授权与清算结果异常，应根据账户和 Issuing 配置处理拒绝、负余额或人工调查。发卡平台可以设置自己的交易策略和持卡人支出控制，但不能修改卡网络已经提交的清算结果。对于在系统里显示金额不符的交易，先核对 Stripe Transaction、Authorization、余额交易和 webhook 事件，再决定是否需要调整账本。

## 撤销、冲正和退款不能混为一谈

授权撤销用于释放未清算的授权，不等于对一笔已入账 Transaction 退款。退款或交易冲正针对已清算的消费，其对象和账务影响不同。用户看到一条 pending 授权消失，并不一定意味着发生了退款；它可能只是商户没有提交该笔授权，或授权在一定时间后释放。

应用应根据对象类型展示状态和时间线：授权发起、批准或拒绝、金额更新、授权关闭、清算交易创建、退款或其他调整。客服工具可提供这条时间线，同时标明哪些金额影响可用额度、哪些已经正式记入账单。

财务账本应保留来源对象 ID 和币种，不要只写“扣款”或“退款”一条不可追溯的记录。多币种交易时，还应分别保存交易币种与 Stripe 余额币种金额，避免汇率换算后误以为对象金额不匹配。日结报表可以将待处理授权、清算交易、释放和退款分栏呈现。

## Webhook 和状态同步设计

使用 Issuing 事件时，为业务明确订阅授权创建、更新和交易创建等所需事件。Webhook 接收端需要验证签名、保存 Stripe event ID，处理重复投递并将事件与卡、持卡人和内部账户关联。授权实时决策请求与普通异步 Webhook 不同：同步授权端点需要在规定流程中快速返回决策，不能把它放入普通的长时间异步队列后再响应。

异步事件处理时，尽量从 Stripe API 获取对象当前状态并核对金额和关联关系。事件的到达顺序不等同于资金生命周期的绝对顺序；如果某个授权更新先于本地授权记录到达，可以按 Stripe 对象 ID检索并补建映射。对重复或延迟事件使用幂等处理，避免重复发放余额、重复扣减额度或重复发送交易通知。

状态机至少要容纳授权中、已批准待清算、授权被拒、授权关闭、交易已清算、交易调整和退款等不同阶段。对于未知事件类型，安全保存其 ID 和类型并告警，避免把它默认转换为已完成交易。

## 余额、通知和客服核对

卡片持有人需要知道哪些金额只是待处理。移动端可以把授权展示为暂挂项目，并在清算后用最终交易替换或关联该记录。若最终金额比授权高或低，提供“授权金额”和“最终记账金额”的解释，减少客户误认为重复扣款的情况。

客服排查时通常需要卡片 ID、持卡人、Authorization ID、Transaction ID、商户名称、交易币种、授权金额、最终金额、发生时间和事件 ID。敏感字段应按角色控制访问。不要把卡片完整号码或认证数据写入普通日志，优先使用 Stripe 对象 ID与内部参考号。

测试时应模拟批准、拒绝、金额变化、授权撤销、清算延迟、重复事件和 webhook 失败。核对可用余额、待处理授权、正式账单和 Dashboard 交易记录。Stripe Issuing 的测试助手可模拟特定授权与捕获行为，但测试结果应与当前生产账户支持范围分开判断。

## 总结

Stripe Issuing Authorization 表示消费请求获批或被拒，Issuing Transaction 表示后续清算交易；授权撤销释放待处理金额，而退款针对已清算支出。把这些对象分别映射到内部账本，通过 ID关联而不是金额猜测，并以 webhook 幂等和当前对象状态推进订单与余额，才能准确解释授权金额与最终入账金额的差异。

请参阅 Stripe 的[Issuing 授权文档](https://docs.stripe.com/issuing/authorizations)、[Issuing Transaction API](https://docs.stripe.com/api/issuing/transactions)、[Issuing 授权测试指南](https://docs.stripe.com/issuing/testing)和[事件类型目录](https://docs.stripe.com/api/events/types)。
