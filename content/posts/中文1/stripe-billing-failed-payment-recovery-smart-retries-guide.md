# Stripe Billing 续费失败如何恢复？Smart Retries、催款邮件与状态同步

订阅续费失败后，问题往往不止是“再扣一次”。卡片可能临时余额不足、已经过期、需要持卡人认证，或者发卡行明确要求不要再次尝试。与此同时，客户可能仍在使用服务，后台可能还有未付 Invoice，客服也需要知道是否已经给客户发送提醒。若没有清晰的恢复流程，就会出现无限重试、客户不知道如何更新付款方式、账单已付但服务仍被暂停等情况。

Stripe Billing 提供自动收款、重试设置和客户邮件等工具，可以帮助商家组织续费失败后的恢复动作。本文说明如何搭建欠款恢复流程、Smart Retries 的适用范围、催款邮件与付款链接的设计，以及如何通过 Webhook 更新订单和服务权限。不同账户与支付方式的能力可能不同，本文给出的是实施思路，实际选项以 Stripe Dashboard 与官方文档为准。

## 先理解订阅账单失败后的状态变化

订阅续费通常会创建 Invoice，并按订阅的收款设置尝试付款。一次付款失败后，Invoice 和 Subscription 会进入相应状态；是否自动重试、何时重试、最终怎样处理，取决于 Stripe Billing 的账户设置和订阅配置。失败并不意味着所有账户都会立即取消，也不意味着客户可以无限期继续使用服务。

常见状态含义可以这样理解：

- **Invoice 尚未尝试付款：** 新账单刚创建，支付尝试可能尚未发生。不要仅因为账单刚出现就把客户标为欠费。
- **付款尝试失败：** 记录失败原因和下次可能的付款尝试时间，判断是自动重试还是需要客户处理。
- **Invoice 仍有未付余额：** 客户尚未完成付款，业务系统需要按服务政策处理访问权限。
- **付款需要客户操作：** 例如需完成认证或更新卡片，后台重试不能代替客户确认。
- **Invoice 已付：** 确认当前账单达到已付状态后，再恢复受限权益或结束催款任务。
- **订阅进入宽限、未付或取消状态：** 依据当前订阅状态和业务约定决定服务访问，不要只看一次 PaymentIntent 失败事件。

Invoice 的 `attempt_count` 与下一次付款尝试时间等字段有助于分析重试进度，但要注意它们的语义受自动重试计划影响。手动尝试并不一定与自动计划计数方式相同；不可重试的返回码也可能需要新的付款方式才能继续。开发者应参考当前 Invoice API 对字段的定义。

## Smart Retries 与自定义重试计划

Stripe Billing 的 Smart Retries 会根据 Stripe 的重试策略，为失败付款选择重试时机。账户也可能允许配置自定义重试规则，包括重试次数、时间间隔以及达到重试上限后的订阅处理方式。具体是否可用、界面位置和当前可配置项，应以账户 Dashboard 为准。

设计重试计划时，先区分失败类型：

1. **可能暂时恢复的失败：** 可以在适当间隔后再次尝试，避免短时间密集扣款。
2. **需要客户更新信息的失败：** 例如卡片过期、资料错误，先提示更新付款方式。
3. **需要客户认证的失败：** 让客户回到可完成认证的流程，不能单靠离线任务解决。
4. **明确不应重试的建议：** 遵守网络或 Stripe 返回的建议，不要继续自动扣款。
5. **账户或支付方式限制：** 让客户联系发卡行，或提供其他合适的支付方式。

重试不是越多越好。卡组织对同一笔交易的再次尝试可能有限制，频繁重试可能增加客户投诉，也可能让合法交易看起来可疑。Stripe 文档提供具体重试建议，商家应以当前文档为准，而不是将固定次数应用到所有支付方式和国家。

自动重试还应与客户通知同步：如果系统决定在两天后重试，邮件应告诉客户账单尚未支付、服务状态以及如何主动更新付款方式；如果客户已成功付款，则应撤销尚未发出的重复提醒。

## 催款邮件应该说明什么

Stripe 可以根据 Billing 和客户邮件设置发送账单或付款相关邮件；商家也可以通过自己的邮件系统提供更贴合产品的提醒。无论哪一方发送，都应明确通知目的，避免同一失败同时触发多封内容重复的邮件。

建议的邮件内容包括：

- 本次账单的金额、币种和对应订阅周期；
- 当前付款状态是失败、待客户操作，还是仍有自动重试计划；
- 客户可以安全更新支付方式或重新完成付款的入口；
- 服务可能受影响的时间点及具体规则；
- 客服联系方式和对争议账单的处理途径。

避免使用误导性标题，例如账单尚未付清却写“付款成功”。也不要在邮件里要求客户回复完整银行卡号或安全码。可以使用 Stripe Hosted Invoice Page、Customer Portal 或商家自己的安全页面让客户更新付款方式；会话链接应按照敏感链接保护，不要长期公开。

如果 Stripe 和商家系统都会发送邮件，先指定每类通知的负责人：Stripe 负责账单/支付流程，业务系统负责服务暂停时间与产品权益说明。也可以反过来安排，但不能两边都发送同一类“扣款失败提醒”。

## Webhook 驱动的欠款恢复流程

不建议在用户浏览器返回页面时直接判断账单是否已付。订阅续费通常发生在客户不在线时，支付结果与前端页面无关。服务器应根据 Stripe Webhook 接收异步事件，并从对象状态更新本地系统。

可按以下分层处理：

- **Invoice 付款失败事件：** 建立或更新欠款记录，保存 Invoice ID、订阅 ID、金额和失败原因；根据事件类型决定是否提示客户。
- **Invoice 需要客户操作：** 创建高优先级通知任务，生成可安全继续付款的入口。
- **付款方式发生更新：** 记录变化，等待后续真实支付结果，不要在仅更新卡片后就把 Invoice 标为已付。
- **Invoice 付款成功或已支付：** 清除欠款标记，恢复应恢复的服务，并取消还未发送的催款任务。
- **订阅状态变化：** 更新本地访问权限，但要结合取消时间、试用状态和欠款政策。
- **达到重试上限：** 依照产品规则进入宽限期、暂停服务或终止订阅，通知客户下一步。

不同事件可能重复到达或发生在不同顺序。处理器需要验证 Webhook 签名，使用 Event ID 做幂等，并在更新订单状态时检查当前 Stripe 对象。自动化任务也应查询 Invoice 当前状态，避免在任务执行前客户已付款而仍发出催款邮件。

## 建议的状态机和业务表

为了避免把所有问题塞进一个 `paid` 布尔值，可以为本地账单维护更明确的状态，例如：

| 本地状态 | 含义 | 典型动作 |
|---|---|---|
| `pending` | 账单已生成，尚无最终结果 | 等待付款尝试或账单通知 |
| `past_due` | 付款失败，仍有余额 | 启动恢复任务并按政策保留服务 |
| `action_required` | 需要客户认证或补充动作 | 通知客户并展示恢复入口 |
| `paid` | Stripe 确认账单已付 | 恢复权益，关闭催款任务 |
| `uncollectible` / `canceled` | 按策略停止收款或订阅终止 | 结束重试并执行终止规则 |

状态命名应与 Stripe 对象的真实状态清晰区分，避免员工把自定义业务状态误认为 Stripe 官方字段。数据表至少保存 Invoice ID、Subscription ID、Customer ID、金额、币种、最近一次失败信息、下次尝试时间、通知发送记录和业务处置时间。

同时保存“账单状态”和“服务权限状态”。例如，业务可能在短暂宽限期内允许客户继续使用服务，但账单仍然是未付；也可能在高风险业务中立即限制访问。只有拆开两种状态，才不会因为暂时保留服务而错误地把欠款标记为已结清。

## 欠款后的服务宽限与恢复规则

宽限期是产品政策，不是“付款失败就由 Stripe 自动替商家决定”。商家需要根据服务性质、合同约定、客户体验和风险确定：

- 宽限期多久，何时开始计算；
- 试用期结束未付款是否进入同一流程；
- 欠款期间哪些功能仍可用，哪些功能受限；
- 客户支付后多久恢复访问；
- 已删除或暂停的数据如何恢复；
- 多张订阅或多 Invoice 并存时，是否按客户、订阅或产品分别处理；
- 最后重试失败后，订阅如何取消或标记为未付。

支付成功后不要只更新 Invoice，还要确认订阅和本地用户权限是否同步。反过来，客户取消订阅也不一定会清除此前已经产生的欠款；对账时应分别处理已结束订阅和未结账单。

## 测试和监控应该覆盖的路径

在测试模式或合适的模拟环境中验证完整的失败恢复流程，而不是只验证“第一次扣款失败”：

1. 付款方式临时失败并进入自动重试；
2. 需要客户认证，客户完成后支付成功；
3. 客户更新卡片，但账单仍然未支付；
4. 系统计划重试前，客户主动付款；
5. 重试计划达到上限，触发宽限期结束规则；
6. Webhook 重复到达时不重复发送邮件或恢复服务；
7. 多个 Invoice 同时欠款时，不将一个账单的成功误判为全部结清；
8. 用户取消订阅后，仍正确处理已产生的余额；
9. 邮件投递失败时保留任务并限制重试次数；
10. Dashboard 手工标记或补款后，本地系统能够重新同步。

监控指标可包括续费成功率、重试后恢复比例、不同失败原因的占比、从首次失败到付款成功的时间、催款邮件投递率、需要客户认证的账单数量和过期未付金额。分析时区、卡片类型和账户国家可能影响结果，不要只看总体数字就贸然更改所有重试策略。

## 常见错误

**把 `invoice.payment_failed` 当作永久失败。** 它表示一次付款尝试失败，账单可能还会重试或等待客户行动；应结合 Invoice 状态和当前计划判断。

**把账单生成当成已经尝试扣款。** Invoice 创建后可能尚未进入第一次尝试，尤其要留意 Webhook 创建时序和 Invoice 的 attempted 字段。

**付款方式更新后立刻恢复服务。** 更新支付资料并不等于账单成功，服务恢复应基于正确的付款或业务政策状态。

**为所有失败设置同一重试间隔。** 资料错误、需要认证和可稍后重试的问题，应走不同路径。

**只依赖 Stripe 邮件而不定义服务规则。** 客户可能收到付款提醒，但不知道账号会在什么时候受限；产品政策和邮件内容需要一致。

**在欠款恢复中重复扣款。** 检查 Stripe 当前对象状态、已有重试计划和请求幂等键，避免前端与后台各自创建收费请求。

## 总结

Stripe Billing 续费恢复应将重试计划、客户通知、支付方式更新、Webhook 状态同步和服务宽限期作为一个流程设计。Smart Retries 或自定义规则可以减少人工操作，但不能替代对拒付原因的判断，也不能覆盖需要客户认证或更新资料的情况。

正确的实现要区分 Invoice 是否尝试、是否仍欠款、是否需要客户行动、订阅是否继续有效，以及本地服务是否处于宽限期。通过幂等 Webhook、及时的付款入口和清楚的催款通知，可以减少客户流失和误停服务；通过限制无效重试并对账当前 Stripe 状态，可以避免重复收费与不一致的账务记录。
