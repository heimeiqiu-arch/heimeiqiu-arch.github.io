# Stripe Apps 与 App Marketplace 指南：权限、数据访问和安装前检查

Stripe Apps 可以将应用功能集成到 Stripe Dashboard，帮助商家查看或操作支付、客户、订单、发票等业务数据，也可以将 Stripe 数据同步到其他系统。企业可以从 Stripe App Marketplace 选择应用，开发者则可以构建供自己账户使用或面向其他 Stripe 用户分发的应用。

安装一个 Dashboard 应用并不只是“增加一个按钮”。应用可能需要读取或写入 Stripe 对象，也可能需要访问第三方服务。企业在安装前应检查应用要求的权限、数据流向、连接方式和 Connect 账户边界；安装后要定期复核应用是否仍有必要，以及授权是否与实际功能相符。

## 一、Stripe Apps 的基本组成

许多 Stripe Apps 同时包含 Dashboard 前端和应用后端。前端可通过 UI Extensions 在 Stripe 用户界面中提供功能；后端用于保存应用状态、执行后台操作或连接外部服务。前后端之间需要适当的认证和授权。也有不需要独立后端的前端应用，在当前用户的 Dashboard 会话和权限范围内调用 Stripe API。

对商家而言，应用显示在 Dashboard 中，不代表它只能读取当前屏幕展示的数据。真正的数据能力取决于应用请求的 Stripe 权限、已授权的第三方服务范围、用户本身权限以及应用的架构。审核时应关注应用是否需要访问交易、客户、余额、订阅或发票等对象，以及是否需要创建或修改这些对象。

## 二、Stripe 权限和第三方权限

Stripe Apps 需要明确申请数据权限。权限决定应用可以读取或写入哪些 Stripe 对象，以及可以执行哪些 API 操作。读取客户信息和创建退款属于不同风险级别的能力，应用不应为了少数功能而申请与用途无关的广泛权限。

除了 Stripe 数据权限，应用还可能连接第三方系统。企业应确认这些服务会接收哪些字段、数据用于什么目的、保存多久、如何删除，以及是否会由该服务继续共享。Stripe Apps 开发文档说明，第三方目标 URL 和权限应在应用配置中明确列出；企业安装时也要阅读 Marketplace 应用的隐私政策、权限说明和供应商条款。

判断权限合理性时，可将每个权限映射到业务功能。例如，发票同步应用可能需要读取 Invoice 和 Customer；如果它要求修改付款方式或发起退款，商家应理解该权限为何必要。若无法从功能描述解释某项写入权限，应向应用提供方询问，或选择权限更窄的替代方案。

## 三、Dashboard 用户权限与应用权限

应用本身拥有的权限和当前登录用户拥有的 Dashboard 权限需要一起理解。UI Extension 代表当前登录用户调用某些 API 时，应用和用户都需要有相应访问能力。应用不应因为某位用户缺少操作权限，就通过界面绕过组织的审批制度。

若应用后端使用自己的授权流程执行操作，企业还应了解谁能触发后台动作、是否记录操作员身份，以及发生退款、客户数据导出或修改账单时如何审计。对于高影响动作，建议保留明确的人工确认与二人复核机制，而不是让任何拥有 Dashboard 查看权限的人都可以触发。

企业可在内部建立应用权限表，列出应用名称、业务负责人、读写权限、第三方系统、批准人、安装日期和复核日期。员工离职、业务变更或应用替换后，及时检查应用是否仍被需要，并移除不再使用的连接。

## 四、Connect 账户的数据边界

Connect 平台与连接账户之间有明确的账户边界。Stripe Apps 官方文档指出，如果 Connect 平台安装某个应用，该应用可以访问平台的数据，但不能因此访问平台旗下 Connect 账户的数据，也不能代表这些 Connect 账户调用 API。若某个连接账户自己安装应用，能力和数据访问范围又可能不同，并取决于该账户的 Dashboard 使用方式和产品配置。

因此，平台不能把安装在平台账户上的应用当作自动处理所有商家子账户数据的工具。若需要读取或操作连接账户数据，应使用 Stripe Connect 支持的授权和 API 模式，并遵守相关账户权限和产品要求。平台方在采购应用前，应确认其是否支持当前 Connect 架构，而不是只看到产品页面上写着“支持 Stripe”便假定可覆盖 Standard、Express 或 Custom 账户。

测试时使用代表性的测试账户类型，确认应用能够看到的数据和它实际发起的 API 调用与预期一致。不要用平台测试账户成功安装作为所有连接账户均兼容的证明。

## 五、安装应用前的审查清单

安装前先回答以下问题：

1. 应用解决的业务问题是什么，是否可以由 Stripe 原生功能满足？
2. 应用请求读取和写入哪些 Stripe 对象，分别对应什么功能？
3. 应用是否连接外部系统，哪些数据会离开 Stripe？
4. 应用如何认证前端用户和后端服务，如何保管密钥？
5. 数据保存多久，能否导出或删除，服务终止后如何处理？
6. 是否支持当前账户结构，尤其是 Connect 各类连接账户？
7. 退款、导出、删除或修改客户信息等敏感动作是否可审计？
8. 应用供应商是否提供安全联系渠道、隐私政策和故障处理说明？
9. 谁负责审批、使用和周期性复核该应用？
10. 出现数据泄露或未授权写入时，企业如何停用应用并处理受影响数据？

如应用提供免费试用，也应把试用期间的权限当作正式数据访问处理。只在测试数据中验证功能和权限边界，不要使用真实客户个人信息来做无必要的产品试用。

## 六、安装后的监控与卸载

安装后，确认应用功能只在批准的账户中启用，并检查实际生成的对象、Webhook 事件或第三方同步记录。对客户数据同步，比较应用内部字段与 Stripe 对象是否符合预期；对写入功能，在测试环境验证错误与撤销路径。若应用执行了未经授权的改动，先停止相关权限或卸载应用，再依据 Stripe 和供应商支持流程调查事件。

卸载应用前，确认是否需要导出企业业务记录、清理第三方系统中的数据、撤销 OAuth 授权或轮换相关密钥。卸载后，检查应用是否仍持有有效连接、Webhook 或外部服务访问。数据删除范围和时限要依据应用条款与企业政策核实，不能假设从 Dashboard 删除应用会自动删除供应商已保存的所有数据副本。

## 七、常见误区

**认为 Marketplace 审核等于企业安全审计。** 应用商店的上架和产品说明不能替代企业对权限、数据流和合同条款的评估。

**认为 Dashboard 用户看不到的数据应用也一定读不到。** 具体能力取决于应用架构、权限和用户上下文，应该审阅实际授权设计。

**认为平台安装应用即可管理所有 Connect 账户。** 平台数据与连接账户数据具有不同访问边界，必须通过正确的 Connect 流程处理。

**认为删除应用会清除所有外部副本。** 卸载、撤销连接和供应商侧删除可能是不同操作，需要分别检查。

## 总结

Stripe Apps 把应用能力带入 Dashboard，但应用访问数据的范围取决于明确授予的 Stripe 权限、第三方服务连接、用户权限和账户结构。企业应在安装前核对权限是否与功能匹配、数据会流向哪里、应用如何支持自己的 Connect 架构，并指定业务负责人进行周期性复核。

安装只是生命周期的开始。对退款、修改和数据同步等高影响动作保持审计，对外部数据副本、OAuth 和密钥进行管理；不再使用时，分别处理卸载、授权撤销和供应商侧数据清理。这样可以让 Dashboard 应用带来效率，同时让数据访问边界保持清楚。
