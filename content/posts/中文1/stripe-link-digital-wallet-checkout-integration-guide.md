Stripe Link 是 Stripe 提供的数字钱包，客户可以安全保存并再次使用付款方式和联系信息，从而减少重复输入。对于移动端和跨境结账，缩短地址和银行卡输入步骤有助于改善购买体验。不过，Link 并不只是一个卡片自动填充按钮：客户需要完成身份验证，Link 账户可能包含多种付款方式，且它在 Checkout、Payment Links、Elements、移动端和发票页面中的展示与配置方式有所不同。

本文说明 Link 的核心体验、账户登录流程、支持的 Stripe 集成、如何启用和测试、如何读取实际付款结果，以及客服和隐私方面的设计。Stripe 官方文档将 Link 描述为可保存和重用付款方式的数字钱包；客户可以使用卡、银行账户、先买后付等可用方式，具体能力取决于地区和支付流程。[Stripe Link 指南](https://docs.stripe.com/payments/link)

## Link 与 Payment Link 不是一回事

Link 是消费者使用的数字钱包；Payment Link 是商家创建的托管付款链接。两个名称相似，但用途不同。商家通过 Payment Link 分享商品或账单结账入口，客户可以在支持场景中选择 Link 作为付款方式；Link 则用于识别客户并安全自动填充已保存的付款和地址信息。

用户可能在很多商家网站都看到 Link，因此结账时能够识别自己的账户并更快付款。商家不必自己保存客户的完整银行卡信息，也无需把 Link 账户凭证复制到本地数据库。平台仍需按照自身隐私政策处理 Customer、订单和付款状态，但敏感的支付凭证由 Stripe 的支付产品处理。

向客户介绍时，避免把 Link 说成“商家保存的卡”。用户管理 Link 资料和购买历史的入口与商家应用不同；商家应说明自己能看到哪些订单或付款信息，以及客户如何在商家账户中管理订阅、取消或收据。

## 客户如何通过 Link 验证和结账

Stripe 文档描述的 Link 登录流程会先通过邮箱、电话号码或浏览器 Cookie 识别已注册客户，再向客户发送一次性验证码完成身份验证；验证成功后，Link 可以自动填充卡片或银行付款信息以及配送资料。[Link 身份验证流程](https://docs.stripe.com/payments/link)

这意味着客户使用 Link 时，可能会在结账页面看到验证码步骤。页面应给用户留出输入验证码、重发验证码和更改邮箱或电话的明确路径。若用户使用了错误邮箱、手机号无法收码或更换设备，不能只显示笼统的“付款失败”；应允许返回常规支付流程，避免 Link 验证成为唯一通道。

完成 Link 注册后，客户可以添加备用付款方式或修改配送地址。商家不应把一次 Link 成功支付视为客户同意任何未来自动扣款。订阅和 off-session 使用仍需按相应合同和授权流程处理，并通过自己的 Subscription 与 Invoice 状态判断后续续费结果。

## 可在哪些 Stripe 集成中使用

Stripe 文档列出 Link 可与 Checkout、Payment Links、Web Elements、Mobile Elements 和 Invoicing 配合。启用前先确认具体集成中 Link 的显示控制方式、支持的付款类型和支付页面行为，再在 Dashboard 的 Payment Methods 设置里检查状态。[Link 支持的集成](https://docs.stripe.com/payments/link)

### Checkout

Checkout 的托管页面可以提供 Link 支付体验。商家还需要确认 Dashboard 中的支付方式设置、动态支付方式、客户信息收集和本地币种策略。不要单凭一次成功的测试客户就认定所有用户都能使用 Link；测试不同地区、已注册和未注册用户、不同设备以及不同支持方式。

### Payment Links

Payment Links 可作为无代码付款入口，客户可能在可用时选择 Link。因为链接可能被广泛分享，商品、价格和订单归属应由商家配置，而不是从 Link 的邮箱推断。付款完成后的履约仍应基于 Stripe Session 与 Webhook，而不是浏览器回跳或 Link 显示的账户资料。

### Elements 和移动端

Payment Element 与移动端集成可将 Link 和其他支付方式放在统一页面中。自定义结账页面需要处理 Link 验证和后续跳转状态，确保用户取消验证后仍能选择其他付款方式。移动端还要考虑应用切换、浏览器返回和验证码自动填充体验。集成方式不同，页面控制和客户信息预填行为也会不同，不能把 Checkout 的设置直接照搬到 Elements。

### Invoicing

Link 也可以在 Hosted Invoice 页面使用，但要确认商家允许的付款方式、账单币种和客户体验。客户通过 Link 完成某张发票付款后，财务状态仍以 Stripe Invoice 与实际付款事件为准。Link 身份验证成功不等同于发票已支付，必须读取发票和支付对象状态。

## Link 可提供的付款方式与地区差异

Link 除了卡片，也可能提供银行账户、先买后付或其他付款方式。Stripe 文档指出可用方式取决于市场、客户和集成；Link 在印度不可用，在巴西与泰国的 Payment Element 集成存在特定支持限制。[Link 国家可用性](https://docs.stripe.com/payments/link)

客户看到哪些选项不应由本地应用硬编码。使用 Stripe 的动态支付方式设置时，让 Stripe 根据结账场景、客户位置和商品属性展示适用选项；商家仍要检查自己账户启用了哪些方式，以及特定国家的支付方式是否符合业务需求。不能因为 Link 账户中保存了某个付款方式，就假定当前 PaymentIntent 或发票一定接受该方式。

若想通过 Link 提供 Instant Bank Payments 等方式，应阅读该付款方式自身的可用性、确认速度和退款或争议特征。Link 只是钱包入口，不代表里面所有支付类型有相同的确认时间、结算方式或风险特征。

## Link 对支付状态和对账有什么影响

Stripe 文档说明，Link 确认的交易会即时确认，成功款项按与卡支付相同的时间线进入 Stripe 余额，资金来源方式不改变该处理说明。[Link 支付确认说明](https://docs.stripe.com/payments/link) 但平台仍应根据集成实际的 PaymentIntent、Checkout Session 或 Invoice 状态做判断，不要从“客户用 Link 付款”推断所有付款方式都会同步结算。

Webhook 应关联到具体 Session、PaymentIntent、Invoice 和本地订单。事件处理验证签名、以事件 ID 去重，并在付款成功后触发订单履约。若是延迟支付方式，依旧要根据该方式的真实异步事件状态处理，不能把所有 Link 内付款方式简化成同一个成功路径。

数据库可以保存 Stripe Customer ID、PaymentMethod ID、付款方式类型和必要的安全摘要，但不应保存完整卡号或 Link 登录凭证。客户切换 Link 中的默认付款方式后，商家已有 Subscription 是否使用新方式，需要核对订阅级默认设置与 Customer 级设置；不要假设 Link 自动更新商家所有已有订阅。

## 转化体验和回退路径

Link 的价值在于少填资料，但也增加了一步验证码验证。衡量时同时观察 Link 展示率、开始验证率、验证码通过率、付款完成率、常规卡支付回退率和客服咨询，而不是只统计 Link 使用次数。如果客户常在验证码步骤退出，可能是手机号或邮箱收不到信息，也可能是页面没有明确说明为何要求验证。

在结账页面保持清楚的替代方式。客户不想登录 Link 时，应能用常规卡片或其他启用的方式完成购买；客户不能使用某支付方式时，展示明确且可理解的失败提示。不要将用户强制引导到 Link，也不要因为 Link 注册失败就丢弃其已填写的订单信息。

测试时使用未注册和已注册客户、不同邮箱和手机号、浏览器 Cookie 命中与清理、切换设备以及验证码错误等路径。检查客户地址和配送信息自动填充后是否允许修改，是否符合本次订单要求；自动填充的数据不一定是最新的，发货前仍应让用户确认关键地址。

## 隐私、数据最小化和用户支持

使用 Link 能减少商家自行收集敏感支付资料的需要，但并不意味着商家无需保护客户个人信息。订单、邮箱、电话和地址仍然可能属于个人数据。只将完成订单、收据和必要客服所需字段存入业务系统，并按隐私说明管理留存时间和访问权限。

客服应能区分 Link 验证、付款授权、支付成功和订阅续费。客户在 Link 上修改联系方式，未必自动更新商家 CRM 中所有资料；客户更换 Link 付款方式，也未必改变当前订阅的默认方式。客服根据 Stripe Customer、PaymentMethod、Subscription 和 Invoice 的关联信息核对，而不是要求用户提供完整卡号或登录验证码。

如果客户联系 Link 官方支持，商家可以提供自己的订单号和 Stripe 付款对象 ID，说明交易在商家系统中的状态。不要要求客户把验证码转发给客服，也不要让客服代为登录客户的 Link 账户。一次性验证码是用户身份验证凭证，不应进入聊天记录、邮件或工单系统。


## Link 与已保存付款方式的界限

Link 中保存的方式与商家 Customer 上附加的 PaymentMethod 不是完全相同的概念。客户可以在 Link 账户中管理已保存方式，而商家只能在具体交易流程及 Stripe 对象允许的范围内使用与自己业务相关的支付信息。不要假设客户在一个商家使用 Link 后，另一个商家就能读取同一张卡片的原始数据。

如果商家已有 Stripe Customer 和 PaymentMethod，Checkout 也可能提供保存卡片的预填体验；其条件与 Link 身份验证不同。预填的已保存卡片取决于 Checkout 模式、卡片的 redisplay 设置、账单资料完整性和客户默认卡片等条件。排查“卡片为什么没自动显示”时，应先确认用户走的是 Link 还是 Stripe Customer 的保存卡片流程，再对照相应设置和对象状态。

用户在 Link 中管理自己的付款方式，不代表商家已有的订阅必定自动切换。订阅账单实际使用哪种方式，要结合 Customer 默认方式、Subscription 默认方式、Invoice 设置和付款失败策略判断。商家在账户页面提供“更新订阅付款方式”入口时，明确说明更新会作用于哪一个订阅，避免用户更新了 Link 钱包资料却仍收到旧方式扣款失败通知。

## 适用于不同设备和结账渠道的测试

真实客户会从手机邮件、社交媒体内置浏览器、桌面浏览器和应用内 WebView 打开结账。某些环境会清除 Cookie 或阻止弹窗，Link 识别客户的方式可能因此不同。测试矩阵中应包含常见浏览器、已登录和未登录状态、客户从 Payment Link 和商家 Checkout 入口进入，以及从 Link 验证页面返回原订单等路径。

记录测试中客户是否看到验证码、自动填入了哪些字段、是否能编辑配送地址、是否能切换到常规支付，以及订单最后关联到哪个 Customer。不要只测研发人员自己的熟悉设备和邮箱；让客服或产品同事按客户视角走一遍，检查错误提示是否能让非技术用户理解。

若结账页面显示 Link 但客户选择其他方式付款，订单也应正常创建和履约。支付页面的可选方式可能动态变化，应用不能把某个方式的展示状态写死成订单要求。对于发生身份认证中断的用户，保留可恢复的购物车和服务选择，减少重复填写商品信息。

## 常见问题排查

**客户没有看到 Link。**检查 Dashboard 的支付方式设置、集成类型、支持国家、客户设备和浏览器环境；确认本地币种或其他过滤规则没有导致当前方式不可用。

**验证码收不到。**提示客户核对注册的邮箱或手机号、垃圾邮件或短信拦截，并允许切换到常规卡支付。不要让客户把验证码发给商家。

**Link 付款成功但订单没有更新。**检查 Webhook 签名验证、事件投递状态、Session 与本地订单映射及幂等逻辑。不要只依赖客户返回确认页面。

**客户修改 Link 里的卡，但订阅仍用旧卡。**核对 Customer 默认付款方式和 Subscription 级默认方式，确认目标订阅实际使用的付款对象。

**客户以为取消商家订阅会关闭 Link 账户。**解释 Link 账户和商家订阅是两套关系。商家负责自己的订阅、订单和退款；Link 账户或其保存方式由客户在相应 Link 管理界面处理。


## 付款方式成本和业务选择

Link 可让客户访问某些其他付款选项，例如 Stripe 文档列出的 Instant Bank Payments。商家应分别比较各方式的确认时间、结算特点、退款和争议处理，而不是把所有 Link 付款都当作卡片交易。不同资金来源的交易手续费可能不同，成本评估应以商家账户当前价格表和实际 Balance 交易为准。

对比 Link 与直接卡支付时，除平均费率外，也观察认证流失、支付成功率、退款比例和客户支持时间。某种方式单笔费用较低，但若用户更常失败或需要客服协助，整体获客成本未必更低。将支付方式选择权交给客户，并持续观察真实交易数据，通常比仅按费率强制引导更稳妥。

按国家和设备分别抽样，不要只用单一客户类型下结论。

## 上线检查清单

1. 明确 Link 与 Payment Link 的不同含义。
2. 在 Dashboard 检查商家支持方式和集成设置。
3. 测试 Link 登录验证码和常规付款回退。
4. 覆盖未注册、已注册、换设备和数据不匹配场景。
5. 验证自动填充的姓名、地址和付款方式仍可核对。
6. 用 Webhook 和真实付款对象确认订单，而非回跳页面。
7. 分开记录 Link 验证、PaymentIntent 成功和发票支付状态。
8. 核实 Customer 与 Subscription 付款方式的优先级。
9. 不收集或请求客户的 Link 验证码和完整卡信息。
10. 监控验证完成、支付成功、退出率和客户支持问题。

## 总结

Stripe Link 是可保存和复用付款方式的数字钱包，可与 Checkout、Payment Links、Elements、移动端和 Invoicing 等集成配合。它通过邮箱、手机号或浏览器信息识别客户，再用一次性验证码完成验证并自动填充可用的付款和地址资料。商家应配置适当的集成、测试地区差异、提供常规支付回退，并通过 Stripe 实际付款对象和 Webhook 确认订单结果。

开始配置前可查看 [Stripe Link 指南](https://docs.stripe.com/payments/link)、[Link 与 Checkout](https://docs.stripe.com/payments/link/checkout-link) 和 [现有客户 Checkout 流程](https://docs.stripe.com/payments/existing-customers?platform=web&ui=stripe-hosted)，再在测试环境中验证验证码、自动填充和付款失败恢复。
