# Stripe 卡片付款被拒怎么办？拒付代码、重试策略与客户引导

客户在结账时看到“银行卡被拒”，并不一定说明商家系统出错。发卡行会根据卡片资料、账户状态、余额、交易行为和验证结果决定是否授权。Stripe 会把它能够获得的错误信息展示在 Dashboard 和 API 对象中，但有时发卡行只返回笼统原因，商家无法从一个代码还原全部决策过程。

处理拒付的目标是让客户知道下一步该做什么，同时避免对同一笔交易不断重复扣款。本文介绍 Stripe 常见卡片拒付代码、前台与后台的诊断方法、PaymentIntent 与 Webhook 的处理方式，以及如何为订阅付款设计重试。拒付代码和网络建议会根据银行卡组织、支付方式和地区有所不同，最终判断应以当前交易对象及 Stripe 官方文档为准。

## 先看清楚是哪一类付款失败

“付款失败”可能发生在不同阶段，先区分状态再决定行动：

- **卡片资料错误：** 号码、有效期、安全码或账单地址填写有误，用户可检查后重新输入。
- **发卡行拒绝授权：** 可能与余额、账户限制或发卡行风控有关，商户通常不能直接解除。
- **需要客户认证：** 例如需要完成 3D Secure 或其他验证，用户必须返回结账流程完成操作。
- **网络或 API 异常：** 请求超时、临时系统故障或连接中断，不一定代表发卡行明确拒绝。
- **异步支付仍在处理中：** 某些支付方式不会即时给出最终结果，不能把 processing 当作成功或失败。

查明失败类别后，才能选择重试、要求补资料、让客户联系发卡行，或稍后检查状态。不要因为页面显示“失败”就立刻创建第二笔新 PaymentIntent；原请求可能已经被处理，而客户端只是没收到结果。

## 常见拒付代码怎么理解

Stripe 的代码是辅助诊断信息，并不是银行对客户的完整解释。部分常见代码可以按下面思路处理：

| 代码或提示 | 常见含义 | 推荐的下一步 |
|---|---|---|
| `incorrect_number`、`invalid_expiry_month`、`invalid_expiry_year` | 卡号或有效期信息不正确 | 请客户核对并重新输入，避免后台反复尝试旧资料 |
| `incorrect_cvc` | 安全码未通过验证 | 让客户核对安全码；不要要求通过不安全渠道发送完整卡片资料 |
| `insufficient_funds` | 发卡行认为可用余额或信用额度不足 | 建议客户确认余额，稍后尝试，或改用其他付款方式 |
| `expired_card` | 卡片已经过期 | 提示客户更新卡片信息或选择其他方式 |
| `do_not_honor`、`generic_decline` | 发卡行拒绝，但返回原因不具体 | 检查其他交易数据；客户可能需要联系发卡行确认 |
| `authentication_required` | 交易需要持卡人完成身份验证 | 恢复用户在场的认证流程，不要进行无条件后台重试 |
| `card_not_supported`、`currency_not_supported` | 卡片不支持该交易类型或币种 | 检查支付方式和商家账户支持情况，提供替代付款方式 |
| `fraudulent` 或疑似风险拒绝 | 发卡行或风险判断不接受交易 | 不要鼓励客户短时间重复提交；按风控流程调查 |

这些解释是常见方向，不构成对每一笔交易的确定性判断。特别是 `generic_decline` 和 `do_not_honor`，发卡行可能不会向商家提供具体理由。Stripe 建议在卡片信息正确时，请客户向发卡行了解具体拒绝原因，因为银行通常只向持卡人解释其风控决定。

## 同时检查 decline_code、advice_code 和 network 信息

API 集成不要只读取前端给用户显示的一句错误文案。可在服务端检查 PaymentIntent 的 `last_payment_error`，其中的 `decline_code`、错误信息和关联 Charge 有助于判断本次失败。若可用，也应查看交易结果中的建议代码和网络拒付代码。具体字段位置取决于当前 API 版本与对象结构，集成时应参考 Stripe 最新 API 文档。

网络 advice code 可以提供进一步行动方向。Stripe 文档中常见的建议方向包括：

- `do_not_try_again`：不应对同一交易继续尝试；
- `try_again_later`：可以稍后再试，但不能无限重复；
- `confirm_card_data`：先让客户核验卡片资料。

网络代码并非每笔交易都会返回；某些字段可能为空。网络代码含义还可能因卡组织而不同。因此系统应把它当成决策信号，不要将一个代码写死成绝对规则，更不要把技术字段原样暴露给客户造成困惑。

## 在 Dashboard 中排查一笔拒付

人工排查时可以按照从交易到配置的顺序：

1. 通过 PaymentIntent、Charge、订单号或 Dashboard 搜索定位付款；
2. 查看付款是否已经有授权、是否尝试过多次、最后错误是什么；
3. 核对卡片类型、国家、币种、账单地址验证与 CVC 检查结果；
4. 检查客户是否完成了认证、页面是否返回、Webhook 是否收到状态更新；
5. 对照商户自己的 API 请求日志，确认是否出现超时后重复创建请求；
6. 查看同一客户或卡片指纹在短时间内的尝试次数；
7. 向客户提供适当的恢复路径，而不是让客户盲目反复点击付款按钮。

对于 `do_not_honor` 这类笼统拒绝，商家往往无法从 Dashboard 查到确切银行原因。此时应明确告诉客户“发卡行未批准本次付款”，建议联系发卡行，或者提供另一种付款方式。避免告诉客户“你的卡肯定没钱”之类没有证据的判断。

## 设计用户在场的重试体验

客户仍在 Checkout 页面时，可以让其修正输入、重新选择付款方式或完成认证。使用 Stripe Checkout 或 Payment Element 时，优先遵循组件反馈与 PaymentIntent 的客户端确认流程，让客户明确看到付款结果。失败后再次尝试时，应确保原支付状态已核实，必要时继续使用合适的支付对象，而非让页面无条件创建新的收费请求。

用户界面的文案建议做到三点：

- **描述可确认的事实：** 例如“发卡行未批准这笔付款”，而不是猜测原因。
- **提供可执行的选择：** 检查卡片资料、联系发卡行、改用其他卡或其他支付方式。
- **保护客户资料：** 不要要求客户通过聊天、邮件或客服表单发送完整卡号和安全码。

如果错误代码明确表示卡片资料不正确，提示对应字段即可；如果是泛化拒绝，不要给客户展示过于技术化的代码。面向客服的后台则可保存 decline code，便于趋势分析和工单分类。

## 订阅续费失败与自动重试

订阅的付款失败常发生在客户不在结账页面时，也就是 off-session 场景。此时可能需要通知客户回来验证付款或更新支付方式。Stripe Billing 提供自动收款和 Smart Retries 等能力，商家可根据业务设置重试节奏，并通过通知或 Hosted Invoice Page 引导客户处理欠款。

自动重试策略应该区分“适合稍后重试”和“需要客户先行动”的情况：

- 对余额不足等可能暂时性问题，可以按配置等待一段时间再尝试；
- 对卡片过期或资料无效，先让客户更新付款方式；
- 对需要认证的付款，应给客户明确链接或恢复流程；
- 对明确不允许再次尝试的建议，不应继续循环扣款；
- 对连续失败的订阅，按产品政策决定暂停服务、进入宽限期或取消。

Stripe 文档提醒卡组织会限制同一笔收费的尝试次数，过多重试可能被看作可疑活动，也可能提高合法交易的拒绝率。不要因为“再试一次总有可能成功”而设置过于密集的重试计划。具体上限和建议应按当前 Stripe Billing 文档及账户设置确认，不要把某个固定数字当作适用于所有国家和交易的通用保证。

对于订阅，应监听 Invoice 与 PaymentIntent 相关事件，确认本期账单最终状态后更新服务访问权。账单创建不代表付款成功，付款失败也不必立刻永久关闭客户账户。可设计“失败通知—客户更新付款方式—重试结果—宽限期结束”的清晰流程。

## 用 Webhook 更新状态，而不是只依赖前端

付款失败后，Stripe 可以通过 `payment_intent.payment_failed` 等事件通知集成系统。Webhook 处理器应验证签名、幂等记录事件，并从 PaymentIntent 或 Invoice 的当前状态更新本地订单。网络请求可能重试，事件可能重复到达，因此不能每次收到同一事件就重复发客服邮件或重复创建欠款任务。

推荐的处理逻辑是：

1. 保存事件 ID 与对象 ID，判断是否已经处理过；
2. 获取支付对象的最新状态，而不是仅依赖某个旧事件内容；
3. 区分失败、需要操作、处理中和成功；
4. 只在需要用户处理时创建通知任务；
5. 若客户更新了支付方式，跟踪后续付款结果；
6. 记录每次尝试的时间和原因，避免无限重试；
7. 在支付成功之后才把订单更新为已付款并触发履约。

如果前端请求超时而服务端没有收到响应，客户端应先查询原 PaymentIntent 或通过自己的幂等键重试创建请求。这样可以降低“客户以为失败，系统却产生两笔交易”的概率。前端显示错误、PaymentIntent 状态和 Webhook 最终状态之间，应有明确的同步策略。

## 降低合法付款被拒的整体比例

不能保证每次付款都成功，但可以从数据质量、客户体验和风控配置着手：

- 在 Checkout 中收集支付流程真正需要的客户信息，避免冗余输入导致体验变差；
- 对地址、邮编和安全码等字段提供明确的格式提示；
- 对跨境用户提供适合目标市场的支付方式和币种；
- 必要时使用支持的客户认证方案，例如 3D Secure；
- 根据业务风险收集额外信息，而不是不加区分地要求所有用户填写大量资料；
- 通过 Stripe Dashboard 或 Sigma 分析拒付原因和重复尝试，关注卡片指纹而不只是 Charge ID；
- 比较不同国家、卡品牌、结账页面和支付方式的失败情况；
- 对高频失败设置限速和风控观察，避免攻击流量制造大量请求。

增加字段并不总能提高授权率；影响可能因卡组织和地区不同。风控规则也应以合法交易体验和账户安全为平衡，避免因为个别拒绝就对所有客户增加阻碍。

## 常见错误做法

**收到 `generic_decline` 就马上再扣几次。** 这会增加客户困惑和网络风险。先检查交易状态、建议码和尝试历史，再决定是否提示客户稍后重试。

**把拒付解释成商家 API 出错。** 发卡行拒绝与商家系统异常不是同一类故障，应该分类统计与展示。

**后台反复重试需要客户认证的支付。** 需要客户操作时，必须让客户回到在场流程完成验证。

**把 PaymentIntent 创建成功当成付款成功。** 对象存在不代表资金已收取，履约逻辑必须基于最终支付状态。

**在日志中保存不必要的完整卡资料。** 敏感支付信息应由 Stripe 提供的组件和受支持流程处理，商家日志只保留诊断所需字段。

**在订阅里忽略客户通知。** 离线扣款失败后，客户需要知道如何更新付款方式或完成认证；自动重试不应代替沟通。

## 上线前检查清单

- Dashboard 和 API 日志都能定位 PaymentIntent 与关联订单；
- 前端能够区分资料错误、需要认证和通用发卡行拒绝；
- 失败时不会把订单误标为已付款；
- Webhook 验签、幂等和重复事件处理已设计；
- off-session 失败会通知客户并提供安全的付款更新入口；
- 重试次数和间隔符合 Stripe Billing 与卡网络建议；
- 无法重试的场景不会进入循环任务；
- 邮件、客服和日志不会暴露完整卡号或 CVC；
- 测试模式已验证成功、失败、需要认证与超时等分支；
- 对拒付原因趋势建立了监控，而非只看单笔交易。

## 总结

Stripe 卡片拒付是发卡行和支付流程共同作用的结果，单一代码未必能说明全部原因。排查时先判断失败阶段，再查看 PaymentIntent 的错误信息、可用建议代码、网络信息和尝试历史。资料错误应让客户核对；泛化拒绝应提示联系发卡行或使用其他付款方式；需要认证的交易必须回到客户在场流程。

订阅付款应把重试、客户通知、付款方式更新和服务宽限期连成完整流程；普通结账则要处理超时、重复请求和最终状态核对。结合 Webhook 幂等、合理的重试频率和清楚的用户提示，能避免误扣款与无效重试，也让客户知道下一步该怎么做。
