发票已经定稿或客户付款后，商家有时需要降低账单金额、取消部分服务、退还款项或修正行项目。直接在自己的数据库里把原发票金额改小，会让 Stripe 记录与商家账本不一致，也会丢失调整原因。Stripe Credit Note（贷项通知单）用于关联已定稿发票记录一定的贷项调整；它与退款、发票作废和新建一张发票不是同一个动作。

不同情况下，贷项可能用于减少客户仍需支付的金额、记录已付款发票的调整，或配合退款与客户余额处理。具体可用行为取决于 Invoice 状态、付款情况和账户配置。本文介绍如何判断是否使用 Credit Note、如何保存调整关联、怎样处理退款和对账。会计确认方式与当地税务处理应由财务专业人员决定。

## 一、Credit Note 与 Refund 的区别

Credit Note 是对发票金额或应收账务的调整记录；Refund 是把已收取的资金退还给客户。若发票尚未付款，减少客户应付金额可能需要贷项或其他发票调整，而不是创建一笔并不存在的退款。若客户已付款并需要资金退回，则要检查是否需要同时创建 Refund。一个对象不会自动替代另一个对象。

Invoice 作废、贷项调整和退款也有不同含义。作废可能表示不再收取该张未付款账单；贷项说明账单金额或客户应收发生调整；退款表示已发生付款返还。系统应根据当前 Invoice 与 PaymentIntent 状态选择操作，并保存各对象 ID。不要因为 UI 上都显示负数就把它们当作同一资金事件。

财务先确定业务原因：价格录错、部分服务未交付、客户取消、折扣补偿、税额更正或整笔订单撤销。再判断使用贷项、作废、退款或新账单。把业务理由记录在申请中，避免员工只凭“修正金额”的口头要求直接修改数据。

## 二、创建贷项前需要核对

先读取原 Invoice，确认客户、金额、币种、状态、关联订阅或订单和已付金额。检查是否已经存在 Credit Note、Refund、贷项余额或其他调整。部分更正需要明确调整哪些行项目和税额；不要只输入一个总额而无法解释其组成。对于多币种客户，按原始发票币种处理。

已定稿发票通常需要通过 Stripe 支持的更正流程，而不是普通更新草稿字段。保存原 Invoice ID、Credit Note ID、关联 Refund ID、客户 ID、调整金额、币种、原因、操作者和时间。若原发票来自订阅，还要判断调整是否影响未来订阅付款；历史账单修正不应无意取消后续续费。

金额由服务端根据订单和审批结果计算。限制谁可发起高金额贷项，必要时要求财务批准。每次请求使用内部调整申请 ID，并对资金相关操作做幂等控制，避免客服因超时重复提交创建多个调整。

## 三、处理部分调整、退款和客户余额

部分服务未交付时，计算实际应退或应减的金额，并保留原账单行项目和调整后的明细。若同时退款给客户，核对 Stripe 创建的 Refund 是否对应原付款，避免贷项金额与退款金额重复计算。若调整金额暂存为客户余额而不是现金返还，产品要清楚说明其用途和后续抵扣方式。

全额取消时，确认客户是否已支付、发票是否允许作废，以及是否还需创建退款。不要仅凭订单状态已取消就假设资金已返还。退款可能需要异步确认，Credit Note 与 Refund 的状态也需分别更新。客户支持页面可以显示“账单调整已记录”和“退款处理中”等不同状态。

税额和折扣也要纳入调整。原发票的税费、折扣分配、运费或按比例计费可能影响贷项明细。不可假定总金额减少一笔固定数字后税额就自动符合财务规则。让财务确认是否需调整税额、报告期间和客户发票展示，再在测试环境核对生成结果。

## 四、Webhook 与本地账本

为 Invoice、Credit Note 和 Refund 相关事件配置 Webhook。接收端验证签名、持久化事件、按 event ID 去重，再更新内部调整记录。事件重复或乱序时，状态机应避免把已完成调整回退。若需要，可以重新读取 Stripe 对象确认最终状态。

内部账本将原 Invoice、Credit Note、Refund、PaymentIntent 和订单相互关联。贷项申请、审批、Stripe API 操作和客户通知分别保留时间线。服务端写入 Stripe 成功但本地写库失败时，通过幂等键或对象检索恢复，不要再创建一笔新的贷项。

定期对账比较 Stripe 发票余额、贷项金额、退款金额、客户余额与内部订单。发现差异时生成差异报告，先判断对象状态和历史事件，再由财务审批受控修复。不要删掉原发票记录或覆写交易总额来“对平”报表。

## 五、常见错误和测试路径

常见错误包括：把 Credit Note 当成退款；对未付款发票创建不相关的现金退款；同时创建贷项和退款却没有匹配金额；更正税额时遗漏行项目；已付款发票只在本地改状态；重复点击导致创建多个调整；退款成功但客服仍显示待退款；贷项影响未来订阅却没有告知客户。

测试草稿与已定稿 Invoice、已付款和未付款账单、部分贷项、全额调整、退款关联、客户余额、税额、订阅发票、Webhook 重复和请求超时。检查 Dashboard、发票 PDF 或托管页面、财务报表与内部账本，确认调整金额、币种和状态一致。生产环境的会计确认仍应依财务政策执行。

## 六、SEO 与官方资料

解释 Stripe 发票调整时，内容要区分 Credit Note、退款和作废，标题明确面向已定稿发票或已付款订单。避免承诺“创建贷项就能立刻退款”，因为退款与银行到账存在各自状态。页面需链接官方 API，并标注更新时间。

官方资料：[Credit Notes API](https://docs.stripe.com/api/credit_notes)、[Create Credit Note](https://docs.stripe.com/api/credit_notes/create)、[Refunds API](https://docs.stripe.com/api/refunds)、[Invoice 对象](https://docs.stripe.com/api/invoices)。

## 总结

Stripe Credit Note 用来记录已定稿发票相关的贷项调整，不等同于 Refund 或 Invoice 作废。创建前先确认原发票状态、付款情况、币种、行项目、税费和已有调整，再由服务端按审批结果计算金额并保存对象关联。

通过 Webhook 同步贷项与退款状态，将每次调整放入可追溯账本，并做周期对账。对已付款账单，要分别确认客户资金是否实际返还；对未付款发票，要清楚显示应付金额的变化。让财务确认会计和税务处理，能避免本地记录与 Stripe 对象出现无法解释的差异。
