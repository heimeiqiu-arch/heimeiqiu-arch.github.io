# Stripe Terminal 离线支付怎么设计：网络恢复、待同步交易与风险控制

门店网络不稳定时，收银设备无法及时访问支付服务，可能让队伍停滞，也会让店员难以判断交易是否已经完成。Stripe Terminal 的离线模式针对特定集成和环境提供离线采集能力：支持时，SDK 可以在终端与 Stripe 暂时失去连接时保存待处理的付款数据，并在连接恢复后继续提交。它并不意味着每台读卡器、每个地区和每种支付流程都能无条件离线收款，也不代表离线时已经取得发卡行授权。

实施前首先确认账户是否可使用、目标读卡器和 SDK 是否支持、应用集成方式是否匹配，并阅读最新的官方要求。离线交易会改变收银端对“已收款”的理解：顾客可能已经离店，交易稍后才被提交，也可能最终被拒绝。本文从流程状态、库存和订单处理、设备数据保护及演练测试等角度，说明如何设计这条链路。

## 离线采集不等于实时授权成功

正常在线支付时，POS 应用通过 Terminal SDK 与 Stripe 服务通信，并按集成流程创建或确认 PaymentIntent。离线时，如果相应功能已启用且条件满足，SDK 可以暂存付款信息，待网络恢复后再向 Stripe 提交。此时门店看到的结果是“已离线采集，等待同步”之类的中间状态，而不是银行已经批准的最终成功状态。

因此，收银 UI 不应继续显示与在线支付完全相同的“付款已完成”。可展示清楚的待确认提示，并把本地订单标记为 pending_offline 或类似内部状态。何时允许顾客带走商品，需要由商户按商品价值、欺诈风险、门店规则和当地流程决定；软件不能把离线采集转换成授权成功的事实。

一旦重新连接，离线交易可能成功，也可能因卡片、余额、验证或其他处理原因失败。结算后的事件和 PaymentIntent 状态才是最终对账依据。设计履约时，要覆盖“收银员已放行商品，稍后交易被拒绝”的情况，例如记录客户联络方式、门店负责人、交易凭证和后续催收策略。对于高价值、不可追回的商品，门店可决定中断时暂停交易或改用其他在线支付方式。

## 先确认功能、SDK 与读卡器适用范围

不要把“Terminal 支持线下刷卡”理解成“离线模式默认已开”。支持范围会随国家、读卡器型号、集成类型、SDK 版本和账户资格而变化。Dashboard 中独立模式（standalone mode）与应用通过 Terminal SDK 管理的流程也不是一回事；Stripe 支持文档指出独立模式需要网络，且不支持离线支付。

上线前逐项检查：
- Stripe 账户和门店所在地是否符合 Terminal 使用要求。
- 当前读卡器型号及固件是否支持目标离线功能。
- iOS、Android 或 JavaScript Terminal SDK 版本及其离线 API 是否匹配。
- Stripe 账户是否已获准使用相关功能，是否还需要 Stripe 开通或配置。
- 使用的是 SDK 驱动的应用集成，还是读卡器自带的独立收款模式。
- 当前业务所用的卡片读取方式和交易参数是否被支持。

官方支持范围可能变动；如果你的 Dashboard、SDK 文档和旧教程内容不一致，以当前账户实际可用能力和 Stripe 支持渠道确认为准。不要仅凭开发环境中的模拟器成功就认为生产设备已经启用。

## 为离线交易设计独立状态机

将离线支付流程显式建模，避免只靠一个布尔值 isPaid。至少区分“收银端创建订单”“在线处理中”“离线暂存待提交”“已提交等待结果”“成功”“失败”“需要人工核对”几种状态。不同 SDK 的回调和对象字段有所差异，内部状态名称可以自定义，但含义要与 Stripe 返回的真实状态对应。

每笔交易在本地应关联一个稳定的订单 ID、金额、币种、门店、读卡器、操作员和离线采集时间。交易重新提交后，再将 Stripe 的 PaymentIntent ID 和最终状态写回订单。设备或应用重启后，应能恢复尚未同步的记录；如果当前 SDK 负责本地安全存储，仍要按官方要求保持 SDK 版本、设备数据和应用生命周期兼容，避免自行复制敏感支付数据到普通本地文件。

离线提交不应让应用重复创建两笔订单。网络恢复时，应用可能同时收到恢复回调和服务端 webhook；两条链路都应以内部订单 ID、Stripe PaymentIntent ID 和 Stripe event ID进行幂等关联。不要因为前端等待超时就新开一笔付款，也不要在结果未明时提示顾客再次刷卡。先检查读卡器当前状态、离线队列和 Stripe 侧对象，再决定是否重试或重新收款。

## 网络恢复后的同步和对账

网络恢复不代表所有待处理交易已经上传完毕。应用应持续跟踪 SDK 报告的离线状态、队列数量和上传结果，向操作员显示哪些交易仍在等待、哪些已完成、哪些失败。后台监控则可以按门店、设备、时间段和 SDK 版本聚合待同步数量，发现队列长时间未清空、交易失败率突然上升或设备离线异常时通知负责人。

每笔离线交易建立从本地 POS 订单到 Stripe 对象的映射。必要的对账字段包括内部订单 ID、金额和币种、门店及读卡器标识、操作员、离线采集时间、同步时间、PaymentIntent ID、最终状态以及错误原因摘要。不要在普通日志中写入完整卡号、磁道数据、密钥或 PaymentIntent client secret。日志要能帮助定位交易，同时遵守最小化敏感信息原则。

通过 webhook 更新正式订单状态时，处理逻辑应兼容事件重复或先后顺序变化。对账任务可定期检查本地“等待同步”订单是否已在 Stripe 有最终结果，发现长时间不一致时进入人工队列，而不是悄悄把所有 pending 标成成功。财务报表要能单独区分离线采集日和 Stripe 实际确认日，否则跨日同步会造成门店日结差异。

## 门店操作和风险管理

员工培训要解释不同状态的含义：离线采集成功表示设备按离线流程保存了交易，不代表最终一定收款。收银屏幕应提醒员工不要重复刷卡，也应告知顾客订单仍待网络确认。门店需有明确的升级渠道，例如联系主管、切换到另一条网络或使用备用在线支付方式。

商户承担离线交易稍后失败的运营风险，应根据客单价和业务类型制定离线限额、单设备待处理交易上限、停用条件和人工审批规则（功能是否提供相关控制项，以 Stripe 当前文档为准）。不要自行在 UI 中加入“离线无限收款”而没有队列容量和风险分析。考虑丢失或被盗设备的处理流程，保护设备锁屏、应用数据和操作员账户，并验证离线数据不会因卸载、更新或清除设备而意外丢失。

如果恢复后交易被拒绝，售后流程要能找到顾客和原订单，生成合适的补款通知或重新收款指引。重新发起支付前，先确认原交易确实未成功，避免顾客同时被离线交易和新交易扣款。涉及争议、退款或重复扣款时，保留原始内部订单、Stripe 对象 ID和门店操作记录供客服调查。

## 上线前的故障演练

测试不能只拔掉网络看页面是否能继续。应在 Stripe 和 SDK 支持的测试方法中验证整个生命周期：离线采集、应用关闭与重启、网络恢复、队列提交、成功和失败结果、webhook 到达、后台对账和门店日结。测试时使用专门的测试环境和明确标记的订单，避免演练交易混入正式销售报表。

推荐演练以下情况：
1. 交易发起前设备离线、付款收集过程中断网，以及网络恢复时再次断开。
2. 多笔待同步付款积压，设备重启或应用被系统回收后恢复。
3. 同一交易的前端回调与 webhook 重复到达，确认只履约一次。
4. 离线交易最终失败，客服能通过本地订单找到顾客和处理记录。
5. 读卡器、应用版本和后台配置不匹配时，门店能识别并转用备用流程。
6. 门店日结时仍有待同步付款，财务能区分待处理金额和已确认收入。

演练后记录终端型号、OS、SDK 版本、门店网络条件和操作步骤。正式升级 SDK 或设备固件前，阅读对应版本的变更日志，确认与离线存储、迁移和状态回调相关的变化，并在少量设备上先行验证。

## 总结

Stripe Terminal 离线模式的价值是让符合条件的线下集成在网络中断时暂存交易，而不是把每一笔暂存都当成已授权付款。先确认账户、国家、SDK 和读卡器的实际支持范围，再把本地状态、恢复同步、幂等订单、最终对账和门店风险规则设计完整。只有当员工、订单系统、财务和客服都能识别“待同步”和“最终成功”的区别，离线流程才有可控的运营边界。

实施前请阅读 Stripe 的[Terminal 文档](https://docs.stripe.com/terminal)、[离线功能相关 SDK 说明（iOS）](https://github.com/stripe/stripe-terminal-ios)及[独立模式说明](https://support.stripe.com/questions/standalone-mode-for-terminal)，并根据账户当前可用状态确认适用条件。
