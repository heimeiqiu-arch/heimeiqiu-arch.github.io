# Stripe Checkout Session 过期后怎么办？弃单跟进、重新创建与订单状态同步

客户打开 Stripe Checkout 页面后没有完成付款，是不是订单失败了？Session 过期后能不能继续使用原链接？要不要给客户发一封恢复邮件？这些问题看起来只是页面行为，实际涉及库存预留、价格有效期、支付状态和重复订单。把 Checkout Session 的过期与 PaymentIntent 失败混为一谈，可能导致系统错误取消订单，或者让客户收到多个可支付链接。

Stripe Checkout Session 是一次结账流程的会话对象。它有自身状态和有效时间，客户可能打开页面后离开、关闭浏览器，或者在页面仍有效时完成付款。本文说明如何识别过期 Session、如何建立安全的弃单跟进、如何重新创建 Session，以及通过 Webhook 确保订单和支付状态一致。具体 Session 时间限制和可用配置以当前 API 文档为准。

## Session 过期不等于付款失败

要区分三种结果：

- **客户未完成结账，Session 过期：** 客户没有完成该会话流程，系统可以考虑创建新的 Checkout Session。
- **客户提交付款但支付被拒：** Checkout 已经开始付款尝试，PaymentIntent 或支付对象可能处于失败、需要认证等状态。
- **支付方式延迟确认：** 客户可能已经提交付款，但最终结果稍后才确定，不能仅凭页面关闭就认定弃单。

Session 的 `status` 表示会话状态，`payment_status` 或相关支付对象反映资金收取状态。不同模式下可观察字段有所区别。若需要处理某个订单，必须同时读取 Checkout Session 与 PaymentIntent、Invoice 或 Subscription 等关联对象，而不是只看一列状态。

订单数据库也要把“购物车未完成”“结账会话过期”“付款失败”“支付处理中”和“已支付”分成不同业务状态。Session 到期可以结束当前付款入口，但不能证明客户没有使用其他链接完成了另一笔交易。

## 过期后通常创建新 Session

过期的 Checkout Session 不应被当成永久支付链接继续展示。若客户回到商家网站需要重新结账，通常由服务端检查购物车和订单是否仍有效，再创建新的 Session，并把客户重定向到新 URL。

重新创建前先核对：

1. 该订单是否已经通过原 Session 或其他付款方式成功；
2. 商品价格、数量、折扣和税费是否仍然有效；
3. 库存是否仍然可用；
4. 客户身份、币种和地区信息是否需要更新；
5. 是否存在同一购物车的其他有效 Checkout Session；
6. 订阅商品是否已被客户购买，是否应进入门户管理而非再创建订阅；
7. 内部订单状态是否仍允许付款。

不要无条件在每次页面刷新时创建新 Session。按钮双击、网络超时或前端重试可能导致多个会话并存。建议在内部订单上保存当前有效 Session ID，并通过幂等逻辑避免短时间内重复创建。

## 监听 checkout.session.expired

Stripe 支持 `checkout.session.expired` 事件，用来通知已过期的 Checkout Session。收到事件后可执行以下动作：

- 根据 Session ID 查找对应内部订单；
- 更新当前会话状态为已过期，而不是直接标记订单付款失败；
- 释放仅为当前会话预留的库存；
- 关闭只与该 Session 关联的待付款任务；
- 如产品允许，创建待客户确认的弃单跟进任务；
- 保存过期时间、订单金额、购物车版本和客户来源；
- 通过幂等处理避免同一事件重复释放库存或重复发送邮件。

事件到达可能有延迟，也可能因 Webhook 重试重复送达。处理器应验证签名、保存 Event ID，并确认 Session 与当前订单仍然对应。过期事件到来时，如果订单已经由另一个 Session 支付，应保留订单的已付款状态，不要因为旧 Session 过期事件将它覆盖为取消。

## 弃单跟进需要先做业务决策

弃单邮件或站内提醒不应只依赖“session expired”。商家应先决定该提醒是否符合客户预期和适用的营销规则。交易通知与营销提醒的用途不同；如要发送促销或再次营销，需要遵循适用的同意和退订要求。

一个清晰的跟进流程可以是：

1. 客户创建结账会话，商家保存订单草稿和 Session ID；
2. Session 完成并支付后，停止弃单任务并进入履约；
3. Session 过期且订单仍未支付时，等待短暂的系统同步窗口；
4. 再次确认没有其他相关支付对象处于处理中或已付款；
5. 检查库存和价格是否仍可售；
6. 若客户同意接收此类联系，发送一封简洁的恢复说明；
7. 链接回商家网站，由服务端创建新 Session；
8. 新 Session 支付成功后取消旧的提醒任务。

恢复邮件最好引导用户回到商家网站登录并恢复购物车，而不是把数据库里保存的旧 Session URL 当成长效链接发送。这样可以重新确认当前价格、库存和客户身份，并避免已过期链接或旧订单状态造成困惑。

## 重新创建 Checkout Session 时保持订单一致

服务端应使用内部订单作为价格与商品的权威来源。创建 Session 前重新读取订单，检查总金额并确定支付模式。不要把浏览器传入的商品价格、税额、折扣或 Customer ID 直接作为可信值。

建议在本地保存以下映射：

- 内部订单 ID；
- Stripe Customer ID（如适用）；
- Checkout Session ID；
- PaymentIntent、Invoice 或 Subscription ID；
- 购物车内容版本；
- 价格和税费快照；
- Session 创建和过期时间；
- 订单当前支付状态。

如果购物车内容在两次结账之间变化，应创建新的订单版本或更新内部订单快照，避免旧 Session 金额与当前购物车不一致。对已有支付对象的订单不要直接换一个新 Session 重收款；先确认原对象是否仍在处理，尤其是延迟支付方式。

## 完成事件与异步支付

Checkout Session 的完成事件可用于业务侧记录结账流程完成，但不同支付方式的资金最终状态可能不同。延迟支付方式可能先有 Session 完成，稍后才成功或失败。因此履约应结合支付状态和相关事件。

常见处理思路：

- 对即时成功的付款，确认对应 Session 和 PaymentIntent 后记录已付款；
- 对延迟支付方式，保持处理中，等待异步成功或失败事件；
- 对需要客户认证的支付，向客户展示继续完成支付的流程；
- 收到失败事件时，让订单进入可重试状态，但先检查是否已有其他成功支付；
- 收到过期事件时，只结束相应 Session，不覆盖其他会话或已支付订单；
- 订单履约任务使用唯一键，防止同一订单因多个事件重复发货。

不要只依赖 Checkout 成功页面的浏览器跳转来发货。客户可以关闭浏览器，网络也可能让页面请求失败；服务器端 Webhook 和 Stripe 对象状态更适合做可靠状态同步。

## 库存、折扣和价格时效

如果商品库存有限，Session 过期时是否释放库存取决于商家的库存模型。可以选择只在付款成功时扣库存，也可以短暂预留库存，但必须为预留设置到期时间，并确保旧会话不会永久锁定库存。

折扣码和优惠活动可能有使用次数或有效期限制。Session 创建后若优惠过期，再次恢复结账时应重新计算当前价格，并在用户确认前清楚展示变化。不得用旧 Session 作为绕过价格变化或库存规则的后门。

对有明确报价有效期的 B2B 订单，可将报价版本号和有效时间保存在内部系统，Session 过期后要求重新核验报价。若价格变化，重新创建支付会话前向客户展示新金额。

## API 主动过期和会话管理

Checkout Session API 提供查询和过期相关操作（具体适用范围依 Session 状态和支付流程而定）。商家可以在订单取消、购物车变更或库存释放时结束不再需要的会话，但应谨慎操作：不要在另一个可能仍被客户使用的会话中途过期订单付款入口，也不要假设主动过期会自动取消关联订单或撤销所有支付操作。

在主动过期前，先确认 Session 仍处于可过期状态，并核对是否已经关联支付尝试。操作之后重新读取 Session 状态，更新本地记录，并等待相关 Webhook。对 API 超时的请求，应查询现有 Session 状态，不要循环创建新会话造成并发支付入口。

## 常见错误

**Session 过期就把订单标记成付款失败。** 客户可能另一个会话已付款，或使用异步方式仍在处理。

**给弃单客户发送旧 Session 链接。** 它可能已经过期，且不能反映最新价格、库存或订单内容。

**每次点击结账都创建新 Session。** 会造成重复会话和多个付款入口；应在服务端管理有效会话和幂等请求。

**通过浏览器成功页履约。** 页面跳转不可靠，支付结果应由 Webhook 和服务端对象状态确认。

**Webhook 事件覆盖较新的状态。** 旧会话过期事件不应覆盖后来付款成功的新会话。

**不检查购物车内容是否变化。** 恢复前重新核对价格、税费、折扣和库存。

## 上线测试清单

- 创建 Session 后离开结账，确认过期事件更新正确的订单；
- 同一订单创建第二个 Session，验证旧 Session 到期不会覆盖新状态；
- 客户通过另一条路径成功支付后，旧 Session 过期事件仍保持订单已付；
- 延迟支付在 Session 完成后稍晚成功或失败，订单状态正确变化；
- API 创建请求超时并重试时不会重复收费或履约；
- 商品价格、折扣、库存变化后，恢复流程展示最新规则；
- 库存预留在 Session 到期后按设计释放；
- Webhook 重复事件不会重复发货、邮件或释放库存；
- 恢复邮件遵循客户通知偏好和适用营销要求；
- 日志保存 Session ID、订单 ID 和事件 ID，不记录敏感支付凭证。

## 总结

Checkout Session 过期代表当前结账会话结束，不代表订单支付失败、客户没有付款或关联的所有支付都已终止。正确流程是监听 `checkout.session.expired`，按 Session ID 更新对应会话，保留订单级支付状态，并在重新结账前核对已有支付、价格、库存和购物车版本。

弃单恢复应从商家系统生成新的、有效的结账会话，配合 Webhook 幂等和服务端履约。区分 Session 状态、支付状态和订单状态，能减少重复扣款、误释放库存和发送失效链接的问题。
