# Stripe Machine Payments 入门：MPP 与 x402 的按调用计费流程

传统 API 收费通常要求用户先注册账户、选订阅方案、填写付款资料，再创建 API 密钥。对于自动执行任务的软件代理，这些步骤需要人工介入。Stripe Machine Payments 提供另一种模式：客户请求付费 API 时，服务端返回 HTTP 402 和付款要求；代理取得付款凭证后重试请求，服务端验证付款，再返回受保护的资源。

这类方式适合按次收费的数据接口、内容服务、计算任务和自动化工具。它并不意味着任何网站只需返回 402 就能安全收钱。商户还要确定协议、钱包或卡片来源、付款验证、资源交付、退款处理、价格单位和滥用控制。Stripe 当前文档支持 Machine Payments Protocol（MPP）和 x402 两种协议，并支持银行卡凭证与稳定币支付的不同组合。

## HTTP 402 付费请求如何工作

可将一次按调用付费请求拆成五个步骤：

1. 代理请求某个受保护 API，但没有提供有效付款凭证。
2. 服务端返回 HTTP 402，并附上金额、币种、付款方式和该资源的付款要求。
3. 代理根据其授权的钱包或支付凭证完成付款。
4. 代理带着付款凭证重试原始请求。
5. 服务端验证付款；付款有效后返回资源和收据。

服务端要先鉴别请求路由、价格和所需访问范围，不能只看请求中“有付款数据”就交付内容。需要定义付款确认与资源响应之间的关联，记录请求 ID、资源、金额、支付方式和收据，防止同一凭证被用于不相关的请求或重复领取资源。

一种简化的状态关系如下：

| 请求状态 | 服务端处理 |
| --- | --- |
| 首次请求无凭证 | 返回 402 付款挑战，不返回受保护数据 |
| 凭证已提交、待验证 | 调用协议或 facilitator 验证付款 |
| 验证失败或过期 | 拒绝资源访问，允许客户端按协议重新尝试 |
| 验证成功 | 记录 Stripe 付款并返回资源 |
| 资源处理失败 | 按业务约定返回重试信息，避免造成重复收费 |
| 退款或争议申诉 | 使用 Stripe PaymentIntent 和内部请求记录进行售后核对 |

付款挑战应明确资源和价格，避免让代理在提交凭证后才发现费用或用途不匹配。对于高成本任务，可以在请求层把每项服务拆分定价，而不是只暴露一个无法解释的总额。

## MPP 与 x402 的主要区别

MPP 和 x402 都支持通过 HTTP 402 协商按请求付款，但其集成流程和支付能力不同。

| 维度 | MPP | x402 |
| --- | --- | --- |
| 协议定位 | Machine Payments Protocol，为代理支付服务和 API 的开放协议 | 互联网按请求支付协议，借助 facilitator 验证和结算 |
| 典型流程 | 服务端返回 402 challenge，代理授权后重试；服务端将支付记录到 Stripe | 服务端返回付款要求，客户端付款并携授权重试；facilitator 链上结算和验证，再由 Stripe 记录 PaymentIntent |
| 支付方式 | 可通过 Shared Payment Tokens 使用银行卡，也可接入稳定币 | Stripe 当前文档重点说明稳定币支付 |
| 适合场景 | 希望同一接口同时接受卡片和稳定币代理付款 | 需要在支持链上以 USDC 收取按次付款 |
| 主要依赖 | Stripe profile/network ID、MPP 服务端库和付款验证 | x402 middleware、稳定币 deposit address 和 facilitator |
| 生产要求 | 需要验证 challenge、付款凭证、重放与退款流程 | 需要管理 facilitator 凭证、网络、地址和链上支付验证 |

MPP 文档描述的工作过程是：API 返回 402 challenge，代理提供付款凭证，服务端验证后向 Stripe 记录 PaymentIntent，再返回资源。x402 的流程则涉及 facilitator 验证并在链上结算，然后 Stripe 记录付款。两者都需要开发者把“付款成功”与“安全交付资源”紧密关联。

如果服务也希望接受银行卡付款，Stripe 文档建议同时集成 MPP。只做稳定币收款时，可以按照 x402 或 MPP 的对应指引选择。不要把 x402 等同于 Stripe Checkout，也不要把 MPP 的 challenge 机制误认为浏览器里的传统结账表单。

## Stripe 账户和可用地区

Machine Payments 当前依赖 Stripe 的账户、支付方式和访问审批。Stripe 文档列出：

- Stablecoin 支付目前向美国所有州的企业开放，纽约州除外。
- 美国以外的企业可以通过 Stripe 联系团队，申请在其他支持地区访问；当前文档说明该能力覆盖 30 多个国家/地区的申请范围。
- Stablecoin and Crypto 支付方式需要在 Dashboard 申请，状态可能先显示 Pending，Stripe 审核通过后才启用。
- SPT（Shared Payment Token）卡片支付按国家和 Stripe 币种支持范围执行；SPT 是有使用范围和到期限制的支付授权，不是代理直接获得的永久银行卡信息。

这意味着开发者所在地、公司注册地、Stripe 账户国家和顾客支付网络都要分开核实。公开文档和审核状态可能变化，不能假设仅因为 API 能运行在美国之外，就代表商户可以在该国家使用 stablecoin payment。

在正式设计产品前，先在 Dashboard 检查当前账户是否能请求 Stablecoins and Crypto，并评估公司所在地、客户范围和支付方式。不要把审核尚未通过的支付选项展示为已上线能力。

## Stripe 余额以法币结算，稳定币退款回到原钱包

Stripe Machine Payments 文档说明，收到的付款会进入 Stripe 余额并以法币结算，报表、余额和多币种付款流程与其他 Stripe 付款相似。稳定币支付的退款则会以稳定币形式退回到客户原始钱包。二者之间的资金形式不同，订单系统应同时保存 Stripe 支付对象、金额和客户钱包付款网络信息，以便客服和财务核对。

Machine Payments 支持小额交易：Stripe 文档当前列出 stablecoin 支付的最低金额为 0.01 USDC；MPP 可以按低于一美分的工作量计费，但最低结算额仍为 0.01 USDC。使用卡片 SPT 时，最低金额为 0.50 USD。不同协议、网络和支付方式有各自限制，金额单位不要混用。

Stablecoin payment 当前不支持传统 chargeback 争议流程，但商户仍要提供客户支持、订单记录和退款处理。Stripe 文档说明支持部分和全额退款；对稳定币付款，退款返回原始钱包。上线前需确认产品是否能处理客户钱包变更、退款地址核验和重复退款请求。

## 资源交付与重复请求控制

付费 API 经常需要处理代理重试。代理可能没有收到第一次请求响应，于是重复提交同一付款凭证；服务端也可能在付款验证成功后、返回资源前发生故障。若没有幂等和收据，商户可能重复收费或同一笔付款交付多次不一致的结果。

建议为每次付费调用定义：

- 内部请求 ID 和资源 ID；
- 价格版本、计量单位和请求时间；
- MPP/x402 协议与付款网络；
- Stripe PaymentIntent ID 或可追踪的支付记录；
- 付款凭证的验证结果及收据；
- 资源是否成功生成或返回；
- 退款和客户支持状态。

可以将资源生成结果缓存到与已验证付款关联的请求 ID 下。当客户端重试时，先检查是否已有成功付款和可复用结果，而不是再次尝试扣款。对于不可缓存的任务，可设计“已付款、待生成”“生成中”“已交付”“失败待重试”状态，并保留人工或自动恢复流程。

## 计价和滥用防护

按调用收费并不能替代 API 安全。服务端应对 402 资源要求签名或校验来源，设定最大金额、可用网络、请求有效期和允许的路径。代理付款后也只能访问该挑战所对应的资源，不要让同一付款凭证变成通用的长期访问密钥。

需要考虑：

- 对大额调用设置上限或二次确认；
- 对昂贵任务先给出准确价格和预计资源消耗；
- 使用服务器端身份验证区分公开端点和付费端点；
- 防止请求参数操纵价格、绕过授权或重放旧收据；
- 对重复请求实施限速和幂等处理；
- 记录异常付款网络、失败率和高频请求；
- 保留撤销、退款和客户投诉处理入口。

按微额收费时，手续费、网络延迟、任务成本和退款处理成本仍可能影响商业可行性。建议用真实业务的请求分布进行模拟，确认价格能覆盖模型调用、数据许可、计算和运营成本，而不要仅凭“最低可收一分钱”决定定价。

## 部署前测试

在 Sandbox 或 Stripe 推荐的测试环境中，覆盖完整客户端和服务端流程：

1. 无付款凭证请求返回规范的 402。
2. 合法付款凭证可以重试并返回资源。
3. 无效、过期或金额不足的凭证不能访问资源。
4. 同一挑战或付款凭证重复提交时不会重复收费。
5. Stripe 付款成功，但资源服务出错时，可以恢复交付或退款。
6. 稳定币支付和卡片 SPT 分别按支持规则处理。
7. 退款记录会关联原始 PaymentIntent 和钱包付款。
8. 日志不暴露 Stripe secret key、SPT 或协议敏感凭证。

稳定币和机器支付属于新兴且持续变化的接入能力。API 版本、网络支持、允许国家和审核流程都应按当前官方文档及账户 Dashboard 验证。

## 总结

Stripe Machine Payments 让 API 和服务可以通过 HTTP 402 进行按调用收费，MPP 适合同时接收卡片与稳定币的代理付款，x402 侧重通过 facilitator 完成链上验证和结算。服务端必须把付款验证、Stripe 支付记录和资源交付绑定起来，并处理重复请求、资源生成失败、退款和权限审核。

接入范围仍取决于 Stripe 账户资格和支付方式审批。上线前先确认 Dashboard 的稳定币访问状态，再按协议文档完成测试：
