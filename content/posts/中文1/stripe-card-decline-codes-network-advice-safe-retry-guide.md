# Stripe 卡片拒付排查：decline_code、network advice 与安全重试

银行卡付款失败时，商家往往只看到“支付未成功”，却不知道应该让客户修改卡片信息、换一张卡，还是停止对这笔付款继续尝试。Stripe 可能返回支付失败原因、卡组织网络代码和建议码，但这些字段的详细程度取决于发卡行和卡网络提供的信息。可靠的处理逻辑应分开“给客户的提示”和“内部诊断信息”，依据失败类型采取行动，避免对同一笔交易盲目重复扣款。

卡片拒付可能来自余额不足、卡号或安全码错误、发卡行风控、账户状态、地区限制或需要额外认证等原因。即使卡片信息没有错误，发卡行也可能给出 generic_decline 或 do_not_honor 等通用原因，不会把具体判断理由披露给商户。Stripe 官方建议，商户可检查 PaymentIntent 的 last_payment_error、关联 Charge 的 outcome 信息、decline code 和网络建议码，并通过 payment_intent.payment_failed 等事件掌握失败状态。[Stripe 卡片拒付指南](https://docs.stripe.com/declines/card)；[PaymentIntent API](https://docs.stripe.com/api/payment_intents)。

## 先理解几类错误字段

PaymentIntent 描述支付流程状态。支付确认失败时，可查看 last_payment_error 中的错误代码、decline_code、提示信息等字段。不同失败情况可能只提供部分字段；不要假设所有拒付都有相同结构，也不要把错误 message 当作稳定程序接口，因为文案可能因地区、语言和 API 版本变化。

关联的 Charge outcome 中可能包含 Stripe 或网络提供的拒付信息。network_decline_code 通常是发卡网络返回的代码，具体含义要结合卡品牌解释；network_advice_code 提供网络侧关于后续如何处理的建议。网络没有返回代码时，这些字段可能为空。Stripe 的 advice_code 则可能提示不要再次尝试、稍后再试或确认卡片数据。字段名称相似，来源和含义并不完全相同，处理代码应按官方对象字段定义分别解析。

常见实现错误是只保存一个 decline_reason 字符串，之后就丢弃原始结构。建议在经过访问控制的支付诊断记录中保存 PaymentIntent ID、Charge ID、错误代码、网络代码、建议码、请求时间和本地订单号。不要记录完整银行卡号、安全码或不必要的原始请求内容。客服界面可以把这些字段转成易懂类别，内部支付分析仍保留可追溯的信息。

## 面向客户的提示怎么设计

客户在付款页面当场遇到拒付时，优先告诉他能采取什么动作。若是卡片资料不完整或无效，可以请客户核对卡号、有效期、账单邮编或安全码；若余额不足，可建议使用其他支付方式；若发卡行拒绝但原因不明确，可以提示客户联系发卡行或更换支付方式。不要把内部风控规则、完整网络代码或不确定的错误判断直接展示给客户。

对于 generic_decline 或 do_not_honor，发卡行可能没有向商家提供具体原因。此时不要编造“余额不足”或“涉嫌欺诈”的解释。适当提示“发卡行未批准这笔付款，请联系发卡行或使用其他付款方式”更准确，也能减少客户误解。

如果 PaymentIntent 返回需要客户认证的状态，不能将它当作普通的硬拒付处理。应按 Stripe.js 或 Checkout 流程引导客户完成必要的验证，然后再核实 PaymentIntent 最终状态。前端必须支持处理认证跳转、用户取消、超时返回和网络失败。服务端可以通过 webhook 与对象检索来补全结果，避免浏览器返回页面丢失后订单状态悬而未决。

## 安全地决定是否重试

重试之前先判断错误性质。网络 advice 表示不要再次尝试时，应停止对同一交易使用同一卡片的自动重试，并引导客户联系发卡行或更换支付方式。提示确认卡片数据时，应要求客户核对信息后再由客户发起新的付款尝试。允许稍后尝试的情形，也要结合 Stripe 返回的具体状态、业务规则和卡组织限制，采取有间隔、有上限的重试，而不是每隔几秒无休止地调用确认接口。

对在线付款，用户仍在结账页面时，可以让他检查资料、选择其他支付方式或重新确认。对离线自动扣款，客户不在场时，应发送通知并提供安全的登录入口，让客户处理认证、更新卡片或主动重新付款。不能把后台离线重试当作客户已同意进行无限次尝试。

同一业务订单应有自己的付款尝试记录和幂等策略。网络超时后，先查询原 PaymentIntent 当前状态，再判断要不要创建新对象；不要在无法确认上一次请求是否已到达 Stripe 时盲目创建多个 PaymentIntent。用户点击“再次支付”时，界面也要防止短时间重复提交。卡组织对同一笔付款的重试次数存在限制，频繁尝试可能被识别为风险行为或进一步降低成功率。

订阅续费与普通 Checkout 的重试策略不同。Stripe Billing 可以通过自动收款、Smart Retries 和订阅催收流程管理部分失败情况。不要在自己的后台又同时实现密集重试，造成 Stripe Billing 和自有任务互相叠加。先确认订阅的 collection_method、自动重试和通知流程，再由单一的业务策略控制后续动作。

## Webhook 驱动的失败处理

服务端可订阅 payment_intent.payment_failed，以便更新订单状态、释放库存锁定、记录失败原因或通知客户。Webhook 接收端必须验证签名，并按事件 ID 去重。重复事件不能重复发送多封邮件、重复生成订单尝试或重复释放资源。事件到达顺序也未必等同于浏览器体验的顺序，因此处理前应读取相关支付对象状态，或使用事件数据的当前版本规则判定。

适合采用状态机，而不是把订单设为简单的 success/failed 二选一。可包含等待付款、需要客户操作、处理中、付款失败、已支付和退款等状态。失败后如果客户更换卡片，继续使用原 PaymentIntent 还是创建新的尝试，取决于当前对象状态和集成方式。用明确的迁移规则避免错误地把失败的支付对象标记成功，或将较新的成功事件被旧失败事件覆盖。

邮件或站内通知可以带用户回到自己的订单页，但不要把 PaymentIntent secret 放入公开 URL 或长期邮件链接。页面应让用户先通过正常身份验证，再为当前订单生成新的支付流程。这样即使链接被转发或日志泄露，也不会直接授予访问其他客户付款记录的权限。

## 通过支付数据分析拒付模式

分析拒付率时，不要只按 Charge ID 统计。重复尝试会让同一张卡出现多个 Charge，因此可以利用 Stripe 提供的卡片 fingerprint 等字段，在符合隐私和数据使用政策的前提下识别重复尝试模式。统计分组可以包括地区、卡品牌、支付方式、金额区间、失败代码、设备类型和客户是否在场，但应避免把有限样本的相关性误当成因果。

若某个国家或卡品牌 generic_decline 明显上升，应检查支付方式覆盖、账单地址收集、3D Secure 适用场景、商户地区和交易风控规则。收集更多账单资料可能对部分卡品牌或国家有帮助，但也会增加表单负担；应结合实际转化与拒付数据评估。不要通过要求所有客户反复输入额外敏感信息来掩盖支付配置错误。

可将指标分成：首次尝试成功率、不同拒付类型的恢复率、客户更换支付方式后的成功率、认证完成率、每单重试次数和退款/争议率。只有同时看转化与风险，才能判断某个重试策略是否真正改善业务，而不是把失败从一个报表阶段挪到另一个阶段。

## 测试覆盖建议

Stripe 官方自动化测试文档提醒，Checkout 和 Payment Element 等前端界面带有防自动化措施，API 也有限流。开发者可以通过 Stripe 测试卡或模拟客户端错误对象来验证应用如何展示失败和恢复流程，不应通过重复调用真实支付来做压力测试。[Stripe 自动化测试文档](https://docs.stripe.com/automated-testing)。

至少覆盖以下情况：卡片资料错误、generic_decline、余额不足、需要认证、用户取消认证、网络超时、重复点击、webhook 重复投递、webhook 延迟到达、订阅续费失败和客户更新支付方式。检查每种情形下订单状态、邮件通知、库存释放和支付尝试次数。测试完成后确认测试数据没有进入正式账户，也没有把测试错误文案直接固化成生产处理规则。

## 常见排查问题

**只看到 card_declined，看不到更具体原因。** 发卡行可能只返回通用拒付信息。查看 Stripe Dashboard、PaymentIntent 的 last_payment_error 和关联 Charge 的 outcome 字段；如果来源没有提供更详细原因，联系发卡行通常比继续尝试更有效。

**network_decline_code 为空。** 这可能表示 Stripe 没有从卡网络收到对应响应代码，并不代表支付对象读取错误。按可用字段处理，避免代码将空字段解释成付款成功或系统故障。

**客户换卡后仍无法付款。** 检查新的付款方式是否关联正确 Customer，PaymentIntent 是否处于可再次确认的状态，是否仍有旧的失败信息影响页面判断，以及订单金额和币种是否正确。确认当前页面使用了与服务端一致的 Stripe 模式。

**Webhook 显示失败但订单页面显示成功。** 检查订单状态是否直接由前端回跳写入，是否存在旧事件覆盖新状态，及服务端是否根据 Stripe 对象最新状态做了最终核验。订单记录应能够追溯产生状态变化的来源。

## 上线前检查清单

- 解析 PaymentIntent、Charge outcome、decline_code 与 network advice 的不同含义。
- 客户端错误文案提供准确且可执行的恢复建议。
- 不因 generic_decline 推断具体的发卡行原因。
- 根据建议码和支付状态控制重试上限、等待时间和停止条件。
- 对同一订单建立 PaymentIntent 状态查询与幂等处理。
- Webhook 验签、去重、重试，并避免旧事件覆盖新状态。
- 处理 on-session、off-session 和需要额外认证的不同情况。
- 订阅续费重试不与自建任务重复叠加。
- 支付诊断日志不包含卡号、安全码或泄露凭证。
- 在测试模式覆盖失败、恢复、重复请求和延迟事件。

## 总结

Stripe 卡片拒付信息来自多个层次：PaymentIntent 错误、decline code、Charge outcome 和卡网络建议码。商家应在服务端保存必要的诊断字段，在用户界面提供诚实可执行的提示，并依据是否需要修改卡片、联系银行或稍后重试做分流。安全的幂等设计、webhook 驱动的订单状态、有限的重试策略和支付数据分析，能够减少重复扣款风险，也有助于更准确地判断拒付问题来自哪里。

本文为支付工程实现参考。拒付代码和网络建议因卡网络及地区而异，应以 Stripe 对应对象字段与当前文档为准。
