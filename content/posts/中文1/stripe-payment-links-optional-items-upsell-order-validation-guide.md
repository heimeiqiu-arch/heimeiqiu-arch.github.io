# Stripe Payment Links 可选商品怎么配置：加购、价格展示与订单校验

销售一个主商品时，有时希望客户在付款页面顺便选择相关附加项，例如礼品包装、延长服务、配件或一次性支持。若为每一种组合都创建独立付款链接，链接数量会迅速膨胀；若把所有商品都放进固定购物车，客户又可能无法只买主商品。Stripe Payment Links 支持在结账中展示可选商品的能力，可用于构建相对简单的加购流程。

可选项会改变最终购买内容和应收总额，因此它不只是页面上的营销开关。库存、税费、订单行项目、退款和履约系统都必须理解客户最终选择了什么。本文说明如何规划主商品与可选商品、如何验证付款后的真实行项目，以及哪些场景不适合依赖共享链接。可用能力、数量限制及界面位置可能更新，请以 Stripe 当前文档为准。

## 先区分固定商品、可调数量和可选商品

Payment Links 的固定行项目表示客户打开链接后，结账中包含的商品。可调数量允许客户改变某个商品的购买件数，但商品本身仍然是预先确定的。可选商品则让客户在结账时决定是否加入某些附加项。三种方式解决的是不同问题，规划前要写明顾客可以改变什么：是否只能买主商品、是否可以增加件数、是否可勾选配件，以及每种组合的最大销售量。

例如，主商品是一个课程，附加项是一次性辅导；或者主商品是实体设备，可选项是保护套。若附加服务需要不同的履约日期、收件信息、资格审核或订阅周期，就不能只看付款页面能否展示勾选框。要确认付款后的系统能把不同项目分派给不同流程，必要时应将复杂选项拆成单独的购买路径。

建立产品和 Price 时，先确认币种、金额、计价方式、税务行为以及是否为经常性价格。一次性商品和订阅价格的行为差别很大；把订阅附加项设计成一次性付款，或者把一次性配件误设为每月重复收费，都会造成客户不预期的账单。测试链接时要逐一核对主商品和可选商品的名称、单位价格、频率以及结账页合计。

## 用真实业务规则决定哪些项目可选

一个可选项适合在付款前由客户自主决定，且选择结果可以明确记录到订单行项目中的情况。比如礼品包装按件收费、安装服务适用于部分地区、下载资料是课程的单次附加内容。对每个选项，产品团队应回答：它与主商品有什么关系？可以单独购买吗？客户能选择几件？是否受库存限制？取消主商品时附加项怎么办？缺少这些规则时，客服往往只能人工猜测付款人想买什么。

可选商品不适合承载需要实时资格判断的权益。例如某个服务必须经过地址验证、库存预留或客服审核，仅靠客户勾选无法证明条件成立。对稀缺库存，如果链接本身没有为每次访问原子地预留库存，页面显示“还可以买”也不代表完成付款时仍有库存。应通过服务端库存系统校验付款结果，并明确超卖时如何退款或安排替代方案。

建议将附加项数量控制在顾客能快速理解的范围内，每个项目用清楚的名称和说明展示实际收费及计费周期。不要用“免费升级”描述会自动续费的项目，也不要把必选商品伪装成可选项。优惠码、自动税、折扣分摊与可选项一起使用时，更要在测试模式核对最终金额和发票明细。

## 创建付款链接后的页面测试

在 Dashboard 或 API 创建 Payment Link 时，按照当前支持的方式指定主行项目和可选商品。不同 Dashboard 版本的配置布局、API 字段和可用限制可能不同，不能只依据旧教程中的截图操作。保存后打开真实测试链接，分别验证不选择附加项、选择其中一项、同时选择多个项目的页面表现。

重点检查：

- 商品标题、说明和金额是否足以让客户区分主商品与附加项。
- 可选项目是否正确标注为一次性或周期性收费。
- 如果客户选择附加项，页面总额是否按预期更新。
- 是否出现意料之外的税费、折扣、运费或付款方式限制。
- 手机屏幕上的名称、说明和选择控件是否可读、可操作。
- 完成付款后，成功页面和电子邮件是否能表达实际买到的组合。

如果附加项是订阅，确认它会不会创建新的订阅项目、是否与主订阅使用相同账单周期，以及取消主订阅时附加服务的处理规则。不要假设“同时购买”在业务上一定会让它们共享完全相同的生命周期。实际的 Checkout Session、Subscription 和 Invoice 对象才是判断依据。

## 订单系统读取客户实际购买的行项目

不要在订单数据库中只保存 Payment Link ID，再假定每个客户买到的内容都相同。Payment Link 表示一个可重复使用的销售入口，而可选项意味着各次 Checkout Session 的购物内容可能不同。付款完成后，应从相应 Checkout Session 的 line items 中读取客户实际购买的商品和数量，必要时使用 Stripe 提供的分页接口完整获取行项目；不能依赖一个可能只包含部分内容的嵌套列表来处理大订单。

在服务端将每个行项目映射到内部 SKU 或服务代码。核对价格 ID、币种、数量、折扣、税额和总额是否与当前订单规则相符。产品名称适合展示给人看，但不应作为系统唯一标识，因为商品标题可能被编辑或本地化。通过稳定的 Product/Price 标识或你自己的映射表处理履约决策，并保存付款时的快照，方便日后解释当时的价格和购买内容。

如果某个项目要求实体发货，要确保每个相关行项目对应正确数量和地址；如果附加项是数字服务，确认系统只给实际购买该服务的客户开通权限。对退款也要有明确规则：只退附加项时是否保留主商品？部分退款后订单显示什么状态？若系统只存一条订单总额，财务和客服很难准确处理拆分退款。

建议将“付款成功”和“履约完成”记录为不同状态。Webhook 确认付款对象成功后，先保存会话和行项目，再由订单服务执行库存扣减、开通权限或安排发货。使用事件 ID 和订单 ID 做幂等保护，避免重复投递导致重复发货。若行项目缺少内部映射，不要默默跳过：把订单送入待人工处理队列并告警。

## 库存、链接状态与营销归因的边界

可选商品功能本身不是完整的库存预留系统。链接限制、完成会话次数和库存账本是不同机制；即便某个链接设置了可完成的会话数，也不应把它直接当成所有 SKU 的实时库存锁。若主商品和多个附加项库存独立变化，需在付款确认后对每个 SKU 做服务端检查，采用数据库事务或库存服务保证并发安全。出现售罄时，提前定义联系客户、部分履约、替代商品或退款流程。

同一付款链接可能被社交媒体、邮件和广告重复传播。若要衡量不同渠道的销售表现，应使用清晰的链接版本或受支持的归因方式，不要把不受支持的查询参数当作可靠订单字段。归因信息只能帮助分析，不能替代支付状态、顾客身份验证或订单授权。对于每个营销入口，可以记录付款链接 ID、活动标识和会话 ID，但这些关联应由服务端控制并能审计。

当价格或附加项配置发生重大变化时，先确认现有共享链接将如何影响新访问者，保存配置变更记录，必要时停用旧链接并创建新的版本。正式切换前，测试旧链接和新链接，避免邮件或外部网站仍然指向已停用链接，或者客户在购物车中看到与宣传页不一致的价格。

## 上线检查单

1. 确认每个附加项的 Product、Price、币种、计费频率和税务属性正确。
2. 测试只买主商品、选择单个附加项和选择多个附加项的组合。
3. 检查实际 Session 行项目、数量、优惠、税额和总额，而非只看付款页面。
4. 验证 Webhook 重复、延迟或失败时不会重复扣库存、发货或开通服务。
5. 检查库存不足、价格已变更和行项目未映射时的人工处理流程。
6. 让退款、客服和财务流程按具体行项目处理，而非只依赖订单总额。
7. 用手机和常用语言检查说明文字是否清楚地披露附加收费与周期。
8. 正式环境只开放已核对过的链接，并记录每次价格或商品配置变更。

## 总结

Payment Links 的可选商品适合简单、清晰、能通过订单行项目履约的附加销售。设置前应把可选性、计费周期、数量、税费、库存和退款规则讲清楚；付款之后从 Checkout Session 行项目确认客户实际购买内容，使用稳定的商品标识映射履约逻辑，并通过幂等事件处理保护库存和订单。对需要实时资格校验、复杂组合或独立订阅生命周期的交易，应评估更灵活的集成方式。

实施时请查看 Stripe 的[Payment Links 文档](https://docs.stripe.com/payment-links)、[Payment Link API 对象](https://docs.stripe.com/api/payment-link/object)、[读取 Payment Link 行项目的 API](https://docs.stripe.com/api/payment_links/line_items)和[Checkout Session 行项目文档](https://docs.stripe.com/api/checkout/sessions/line_items)。
