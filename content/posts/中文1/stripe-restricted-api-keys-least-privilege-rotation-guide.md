# Stripe 受限 API 密钥最小权限配置：按服务拆分、验证与轮换

Stripe API 密钥决定一个程序可以访问哪些账户资源。把拥有广泛权限的密钥复制到每个服务、脚本和外部供应商手里，一旦某个环境泄漏，影响范围就可能远超过那一个功能。受限 API 密钥可以按资源配置读取或写入权限，让不同系统只获得完成任务所需的访问范围。

实施时不要只把密钥名称改成“只读”就认为权限受限。需要在 Dashboard 中真正配置每一项权限，明确哪些系统使用它、密钥存放在哪里、如何测试权限，以及如何快速更换。本文按现状盘点、权限设计、部署、验证和应急轮换说明一套操作流程。

## 先区分几类 Stripe 凭证

Stripe 的公开密钥、受限密钥、标准密钥和 Webhook 签名密钥用途不同，不能互相替换：

| 凭证类型 | 常见前缀 | 应放在哪里 | 主要用途 |
| --- | --- | --- | --- |
| Publishable API key | pk_test_、pk_live_ | 浏览器或移动应用 | 由 Stripe.js、Elements 或移动 SDK 初始化客户端流程 |
| Restricted API key | rk_test_、rk_live_ | 服务器或受控服务端环境 | 按需要授予特定资源的读写权限 |
| Secret API key | sk_test_、sk_live_ | 服务器端秘密存储 | 对 Stripe API 提供广泛权限的认证 |
| Webhook 签名密钥 | whsec_ 开头 | Webhook 服务端 | 校验事件确实由 Stripe 发出 |

前端密钥可以公开使用；受限密钥和标准密钥仍然属于秘密，不能放进网站代码、App 包、公开仓库、浏览器存储或客户端日志。Webhook 签名密钥也不是 API 密钥，不能拿它去调用 Stripe API。Sandbox 和 live mode 的密钥及对象互相隔离，测试密钥创建的对象不会变成真实交易。

Stripe 当前文档建议大多数服务优先考虑受限密钥；标准 secret key 拥有不受限的 API 权限，只应在确实需要广泛访问的集成中使用。受限并不等于安全无忧：如果密钥被拿到，攻击者仍可使用它获准的权限，因此存放、访问控制和轮换仍然重要。

## 先按服务拆分密钥，而不是共享一把

先列出会调用 Stripe API 的系统和人员，例如：

- 生产支付后端：创建 PaymentIntent、读取付款状态。
- 退款管理后台：查询付款并创建退款。
- 财务报表任务：读取余额、付款、退款和发票。
- 客服工具：只读查看客户或支付信息。
- 外部争议服务：只读取争议所需数据。
- 开发和测试任务：仅访问 Sandbox 的测试对象。

然后给每个系统单独创建凭证。不同密钥可以拥有相近权限，但拆分后能够分别限制访问、撤销、轮换和查看用途。比如报表任务只需要读取时，不应因为复用支付后端的密钥而获得写入退款或客户资料的能力。

密钥名称应能看出环境、用途和负责人，例如“prod-payment-api”或“sandbox-reporting-job”。Dashboard 的密钥备注可以记录密钥保存在何处、由哪个服务使用、联系人和轮换计划。备注不要写入密钥值或其他秘密内容。离职人员或已停用的集成应触发权限清理，而不是让旧密钥继续留在系统中。

## 用最小权限表设计读写范围

创建受限 API 密钥时，为每个 Stripe 资源选择无权限、读取或写入。权限表应按照“服务要完成的实际操作”设计：

| 服务场景 | 需要访问的资源示例 | 常见权限思路 |
| --- | --- | --- |
| 支付创建服务 | PaymentIntents、Customers、PaymentMethods | 仅开放创建和查询流程实际使用的资源 |
| 只读分析任务 | Charges、Balance Transactions、Refunds | 只读所需数据，不开放创建退款或修改对象 |
| 客服退款工具 | 付款、退款相关资源 | 仅在业务确需退款时开放对应写入能力，并限制使用者 |
| 第三方争议查看 | Disputes 及关联付款信息 | 尽量只读；不要附带与其工作无关的资源权限 |
| Webhook 接收器 | 通常不需要调用 API 的写权限 | 通过签名密钥校验事件，若需回查对象再单独配置最少只读权限 |

上表只是设计起点，不能照抄成所有账户都适用的固定权限组合。Stripe 产品、API 资源和具体操作可能依账户使用方式不同。先检查请求日志和服务调用，列出实际端点，再依据 Dashboard 权限选项和当前 API 文档设置。某个服务遇到权限不足时，查看具体失败请求，补充最窄的必要权限，不要为了省时间直接升级成 secret key。

Connect 平台还要检查密钥的连接账户访问权限。某项资源权限可能同时有平台自身和连接账户范围的选择。必须确认系统是否需要以平台身份访问连接账户，避免无意扩展到所有连接账户。

## 在 Dashboard 创建受限密钥

Stripe Dashboard 的 API keys 页面可以创建和管理受限 API 密钥。常见创建步骤如下：

1. 确认当前处于正确账户和模式，先在 Sandbox 中进行测试。
2. 进入 API keys 页面，选择创建新的受限密钥。
3. 按服务用途命名，例如环境、系统名称和负责人。
4. 对每个 API 资源逐项选择无权限、读取或写入；Connect 场景另行核对连接账户权限。
5. 创建密钥后立即将值保存到服务器的秘密管理服务。Dashboard 可能只在首次展示时提供密钥值，遗失后需要轮换或重新创建。
6. 在备注中写明存储位置和使用服务，不要在备注里粘贴密钥本身。
7. 通过部署配置把秘密注入目标服务，禁止写入代码仓库或容器镜像。

只给单一服务发放一把密钥。如果多个环境共享一个凭证，测试任务可能误用生产权限，某项服务的权限也难以单独撤销。测试和 live mode 分开存储，变量名称也应能区分环境，避免依赖人工记忆。

## 迁移时分阶段验证，避免上线后才发现缺权限

从标准密钥迁移到受限密钥时，不要先删除旧密钥，再期待生产服务自行恢复。建议分三个阶段执行。

### 阶段一：盘点调用

为每个服务记录调用的 Stripe API、发起请求的环境、调用频率、是否需要读写和使用的账户范围。结合 Stripe Workbench 请求日志查找真实调用，避免只按代码搜索判断，因为密钥也可能来自环境变量、部署平台或第三方集成。

### 阶段二：Sandbox 验证

在 Sandbox 创建目标权限的受限密钥，更新测试服务并运行关键业务流程。至少覆盖支付创建、查询、退款、订阅更新、报告任务等该服务确实使用的操作。验证：

- 允许的操作能够成功完成；
- 未授权的操作按预期被拒绝；
- 错误日志不会打印密钥；
- 服务不会将测试对象 ID 误传给生产环境；
- 请求速率、Webhook 和重试流程没有依赖旧凭证的隐藏配置。

### 阶段三：生产灰度切换

选择低风险服务先切换，观察请求日志和失败指标，再迁移其他服务。应准备旧密钥的停用和新密钥的恢复方案，并记录切换时间。如果某个业务功能失败，先看失败的 API 端点与资源权限，再判断是否应补权限或调整调用方式，不要马上扩大密钥范围。

完成切换后，确认旧 secret key 是否仍被服务引用。只有在所有必要调用都迁移、日志和配置核查完成后，才撤销不再需要的密钥。不要仅因新密钥已生成，就假设旧密钥已经退出生产。

## 密钥保护和使用策略

在运行环境中，通过秘密管理服务向应用注入受限或标准密钥；没有秘密管理服务时，可由服务器环境变量提供。不要把密钥硬编码在源代码、客户端应用、配置样例、截图、日志、工单或聊天记录中。发布前启用密钥扫描，并检查 CI/CD 配置是否会把秘密打印到构建日志。

如果服务从固定服务器 IP 发出请求，可以在 Dashboard 中配置 API 密钥的 IP 访问策略，限制哪些地址或网段能够调用 API。使用 IP 限制前先核实出站地址稳定，并确认备用节点、灾备环境和任务调度器都包含在允许范围内。错误的 IP 限制可能让合法服务突然无法调用 Stripe，应该先测试并记录变更方式。

定期查看 Workbench 请求日志，关注不熟悉的请求、突然增加的写操作、非预期时间段的调用或来自异常环境的请求。日志可以帮助排查和识别问题，但不能替代访问控制。对于可能触发退款、提现或账户设置的高风险操作，还要在业务系统里限制谁能发起，并保留审批和审计记录。

## 发现密钥泄露后的应急处置

如果受限或标准密钥出现在公开仓库、构建日志或其他不应出现的位置，应把它视为已泄露并尽快轮换，不要等待确认是否有人复制。处理步骤可按以下顺序执行：

1. 在 Stripe Dashboard 中轮换或撤销受影响的密钥，防止后续继续使用。
2. 创建替换密钥并仅授予原服务确实需要的权限。
3. 更新秘密存储和生产服务配置，确认部署已加载新值。
4. 检查 Workbench 请求日志，识别异常 API 调用、退款、客户数据访问或配置修改。
5. 检查公开仓库和构建产物，移除密钥值并修复泄露路径。删除 Git 文件并不等于旧密钥失效，因此轮换仍是关键步骤。
6. 通知内部安全或财务负责人，按账户影响评估客户、资金和数据处理措施。
7. 验证应用恢复正常，并记录泄露发现时间、轮换时间、权限和检查结果。

如果轮换导致服务不可用，先回到已经验证过的配置和正确密钥版本，而不是把秘密写进代码作为临时绕过。对自动化服务而言，提前排练轮换流程能显著缩短应急恢复时间。

## 上线前检查清单

- [ ] 每个服务有独立用途和负责人，不共享不必要的凭证。
- [ ] 所有受限密钥都逐项配置了资源权限。
- [ ] 第三方集成使用独立、尽可能只读的权限。
- [ ] Sandbox 和 live mode 密钥分离。
- [ ] 密钥只存放在服务器秘密管理环境中。
- [ ] CI/CD 日志、应用错误页和调试接口不会泄漏环境变量。
- [ ] 固定 IP 限制覆盖生产和灾备出口，并经过连接验证。
- [ ] 标准 secret key 的使用有明确原因，迁移范围已记录。
- [ ] 密钥泄露时的轮换负责人和步骤已经确定。
- [ ] 定期复核人员、服务、权限和 Workbench 请求记录。

## 总结

Stripe 受限 API 密钥让团队能够按服务缩小 API 访问范围，但前提是权限确实按资源配置，密钥也没有被复制到不受控环境。先盘点服务调用，按环境和用途拆分密钥，在 Sandbox 验证权限，再分阶段迁移生产。配合秘密存储、必要的 IP 限制、请求日志审查和泄露后的轮换预案，可以缩小单个密钥失窃时的影响范围。
