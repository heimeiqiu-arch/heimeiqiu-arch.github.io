# Stripe Credit Note 是什么？与退款、客户余额和 Invoice 调整的区别

客户要求退还部分费用、商家发现账单金额需要冲减，或者已经发出的 Invoice 出现错误时，Stripe 用户常会遇到 Credit Note（贷项通知单）。它与退款有关，但两者不是同一个对象：退款会处理一笔支付资金，Credit Note 则用于对已最终化的 Invoice 作金额调整，并记录调整原因和对应的账务影响。若只创建退款而不更新账单记录，财务报表和客户账单可能对不上；若只开 Credit Note，也不能默认客户银行卡已经收到退款。

本文介绍 Credit Note 的业务作用、付款前后如何选择处理方式、信用金额如何应用于客户未来账单，以及如何通过 API 和 Webhook 做账务同步。Credit Note 可能涉及税务和会计要求，不同地区的正式凭证规则不同，商家应与财务或税务顾问确认使用方式。Stripe Dashboard 具体功能与 API 参数也可能随版本变化，实施时以当前官方文档为准。

## Credit Note 与退款不是一回事

可以把三类操作分开理解：

| 操作 | 主要目的 | 资金是否立刻退回支付方式 | 是否调整 Invoice |
|---|---|---|---|
| 退款（Refund） | 退回某笔已收款的一部分或全部 | 通常是发起退回流程，到账时间依支付方式和金融机构而异 | 不应假设退款自动替代 Invoice 的贷项处理 |
| Credit Note | 对已最终化的 Invoice 记载减少、冲销或其他信用调整 | 只有选择退款相关处理时才会发起相应退款 | 是，关联到 Invoice 并反映贷项金额 |
| 客户余额抵扣 | 把客户可用信用留在 Stripe 账单侧，供未来 Invoice 抵扣 | 通常不会将金额退回银行卡 | 未来账单可能使用客户余额 |

实际操作可以根据业务需要组合使用，例如对已付款的 Invoice 创建 Credit Note 并发起退款，或者把贷项留在客户余额中用于下次账单。选择哪一种取决于客户约定、财务流程、税务凭证需求和退款政策。

## 为什么已付款 Invoice 不能只改金额

Invoice 草稿可以在最终化前编辑。Invoice 一旦最终化，账单金额和主要交易信息通常不再通过简单编辑方式改变。若客户已经拿到正式账单，之后发现商品退回、服务范围调整、价格录入错误或给予部分补偿，通常需要用与原 Invoice 关联的 Credit Note 记录调整，而不是悄悄在数据库里改原账单金额。

这样做可以保留账单链路：原始 Invoice 记录最初开出的金额，Credit Note 记录后续贷项的金额、原因和资金处理方式。对于对账和客户沟通来说，保留这条关联关系比覆盖历史记录更清楚。

需要注意，Credit Note 的税额和行项目调整要与原 Invoice 对应。若涉及税费、折扣、部分退货或多币种，应仔细核对具体金额和币种，不要只按商品标价手工计算。

## 付款前后的处理选择

### Invoice 仍未支付

如果账单尚未支付，Credit Note 可以减少客户仍需支付的金额，或在必要时冲减全部未付余额。客户之后应支付更新后的应付金额。此时通常没有已收资金需要退回银行卡，但具体资金处理仍需按 Credit Note 的应用方式确认。

不要把“取消账单”“作废账单”“创建贷项”当成可以随意互换的动作。若整张 Invoice 都不应继续收取，检查当前 Invoice 状态与可用操作；若只对账单部分金额进行修正，则需要记录相应贷项理由。实际可用操作受 Invoice 当前状态影响。

### Invoice 已支付

已付款后需要决定贷项金额如何处理：

- **退回客户支付方式：** 对应发起实际退款流程。退款是否立刻完成取决于支付方式，客户银行到账可能晚于 Stripe 对象更新。
- **留作客户余额：** 客户的信用可以在未来符合条件的 Invoice 中抵扣。它适合客户明确同意将金额留在账户、继续购买或订阅的情形。
- **账外处理：** 商家可能已通过银行转账、现金或其他方式退款。此时需要按适用的 Credit Note 处理方式记录，但必须保存外部付款凭证，并确保不会在 Stripe 再退一次。

同一笔贷项金额不能被重复退还或同时既退款又作为完整的未来余额使用。提交前要核对已退款金额、已用余额、之前的 Credit Note 和原始 Invoice 的剩余可调整额度。

## 部分退款的金额核对方法

例如一个客户支付了包含两项商品的 Invoice，后来退回其中一项。商家可以先确定要冲减的 Invoice 行项目、税额和总贷项，再决定资金返回原支付方式还是留作余额。不要仅用商品价格乘数量作为 Credit Note 总额，忽略折扣、税、运费或按比例分摊规则。

推荐的核对顺序：

1. 获取原 Invoice 及行项目，确认币种和客户；
2. 找出需要冲减的商品、服务或账单期间；
3. 计算相应的未税金额、税额和贷项总额；
4. 检查原 Invoice 是已付、未付还是部分支付；
5. 核对之前已经创建的退款和 Credit Note；
6. 明确贷项是退款、客户余额还是账外退还；
7. 创建后核对 Credit Note、Refund 和 Customer balance transaction 的关联；
8. 对账系统记录每个对象的 Stripe ID 与内部订单 ID。

Stripe 金额通常以该币种的最小单位表示，例如许多货币使用分，但并非所有货币规则都相同。代码应依币种精度转换金额，不要把所有价格统一乘以 100。涉及税额和舍入时，使用 Stripe 返回的实际对象金额，而不是前端展示值作为唯一财务凭证。

## 在 Dashboard 中创建 Credit Note

人工处理时，在 Stripe Dashboard 找到客户和相关 Invoice，打开账单操作，按页面提示创建 Credit Note。提交前核对：

- 是不是正确的 Invoice 和 Customer；
- Credit Note 的原因和说明是否清楚；
- 各行项目金额、税额和总额是否正确；
- 是部分贷项还是整张账单冲减；
- 已付款时，资金是退款、留作客户余额，还是账外退还；
- 是否需要客户收到对应文件或通知；
- 操作是否符合商家退款政策和财务审批。

创建后不要只看弹窗成功提示。再次打开 Invoice 和 Credit Note，检查应付金额、已退金额、余额抵扣、状态和 PDF/客户可见记录。对于手工退款或已由外部渠道退还的交易，保存能对应到原订单的凭证，以便后续审计。

## API 集成与幂等设计

Stripe Credit Notes API 支持创建、查询和列出贷项通知单。创建时需要把 Credit Note 与正确的 Invoice 关联，并提交相应的金额、行项目、原因及资金处理选项。已付款 Invoice 的处理可能涉及退款金额、客户余额金额或账外金额；具体字段组合和限制应按当前 Create Credit Note API 文档核对。

后端应在内部事务中先建立操作记录，避免同一客户申请经客服、自动化和后台管理员重复创建 Credit Note。建议保存：

- 内部退款或调账申请 ID；
- 原 Invoice ID、Customer ID 和支付对象；
- 原始订单总额和当前剩余可贷金额；
- Credit Note ID 和金额；
- 关联退款 ID、余额交易 ID或外部退款凭证；
- 操作人、审批人、原因和执行时间；
- Stripe API 响应、幂等键和错误信息。

创建操作时为同一笔内部申请使用幂等键，防止网络超时后重放请求产生重复贷项。若 API 返回超时，不要直接再创建一份新的 Credit Note；先查询 Stripe 是否已有与该申请关联的对象，或重试同一幂等请求。

## 通过 Webhook 更新财务状态

可订阅与 Credit Note 创建、更新或作废有关的事件，以及 Refund、Invoice 和客户余额交易的相关事件。事件负责通知系统对象变化，但业务系统仍应通过 Stripe 对象 ID 关联到账单，并在处理时验证 Webhook 签名、记录 Event ID 和防止重复处理。

不要将 `credit_note.created` 直接解释为“退款已到账”。事件只说明 Credit Note 对象发生了相应变化。系统需要进一步检查 Credit Note 的资金应用方式、关联退款状态、客户余额变化和 Invoice 的金额状态。

可以将状态拆分为：

- **贷项已创建：** 原账单已经记录贷项；
- **退款已发起：** Stripe 中创建了退款对象；
- **退款已完成或处于其他状态：** 以 Refund 最新状态和支付方式实际流程为准；
- **余额已入账：** 对应客户信用已在 Stripe 账单侧记录；
- **财务已对账：** 外部银行、会计系统和 Stripe 记录匹配完成。

只有分层保存这些状态，客服才不会在退款尚未完成时告诉客户“银行卡已到账”，财务也不会把客户余额当成实际现金退款。

## 退款与账单对账

月底对账时，将 Credit Note、Refund、Invoice 和交易流水放在同一个订单上下文中核对。尤其要注意：

- Credit Note 总额不一定等于实际退回银行卡金额；
- 一份 Credit Note 可以涉及不同的信用应用，需按对象字段细分；
- 退款状态与客户银行实际入账时间可能不同；
- 客户余额被未来 Invoice 使用后，余额交易和 Invoice 行项目之间应能够追踪；
- 账外退款要有外部凭证，且不能又在 Stripe 创建重复 Refund；
- Connect 场景还需确认平台、关联账户、转账和应用费是否需要分别调整；
- 多币种交易要保留原交易币种以及可能的结算币种信息。

财务报表不应只汇总“退款”字段。退款是支付资金方向变化，贷项通知单是 Invoice 调整记录，客户余额是账单信用；会计科目和税务记录可能分别处理。与财务团队一起确定统一的报表口径，可以避免 Stripe Dashboard 和会计系统的“收入冲减”看起来不一致。

## 常见错误

**创建 Refund 后就认为 Invoice 已经调整。** 若业务需要正式冲减已最终化账单，还要考虑 Credit Note 和账务记录。

**创建 Credit Note 后就告诉客户钱已退回。** 先检查是退款还是余额抵扣，并查看退款对象的最新状态。

**为同一金额同时创建退款和余额。** 这会导致过度返还或重复抵扣，创建前应计算剩余额度。

**直接修改历史 Invoice。** 最终化账单应使用合适的贷项或其他支持流程保留调整轨迹，而不是修改内部副本掩盖历史。

**忽略税、折扣和货币单位。** 贷项金额需与原行项目和币种精度相符，不能只靠商品标价估算。

**Webhook 重试导致重复调账。** 对事件和内部申请都做幂等处理，并在超时后先核查现存对象。

## 总结

Stripe Credit Note 用于记录与 Invoice 相关的贷项调整；Refund 用于退回实际支付资金；Customer balance 则用于账单侧的未来抵扣。这三类操作可以有关联，但不能互相替代。付款前的贷项通常影响仍需支付的金额，付款后的贷项还需要明确退款、余额留存或账外退还的处理方式。

实施时按原 Invoice 行项目和税额核对金额，保存 Credit Note、Refund 和余额交易的关联，使用 API 幂等键避免重复创建，并通过 Webhook 分别更新贷项状态、退款状态和账务对账状态。涉及正式发票和税务时，还要遵循所在地区要求并与财务团队确认。
