# Stripe Billing Entitlements 权益管理：订阅产品与应用权限同步指南

订阅系统经常遇到一个实际问题：客户买了某个套餐，应用究竟应该开放哪些功能？如果权限规则散落在价格 ID 判断、数据库布尔字段和前端条件里，套餐一调整就容易遗漏。Stripe Billing Entitlements 提供一套将产品所包含功能、客户购买和当前权益关联起来的机制。商家可以在 Stripe 中定义功能，并把这些功能关联到产品，再根据客户的有效权益控制应用访问。

Entitlements 不会自动替代你应用中的身份验证和授权系统。它帮助维护“某个 Stripe Customer 当前拥有哪些产品功能”的订阅权益信息；你的服务仍需要把登录账号映射到正确的 Customer，并在后端执行权限检查。客户端隐藏一个按钮只是界面体验，不是权限保护。每个涉及数据导出、团队席位、API 调用或高级操作的请求，都应该由服务端按当前权益验证。

Stripe API 中有 feature、产品关联以及客户 active entitlements 等对象和操作；客户权益发生变化时，可以通过 entitlements.active_entitlement_summary.updated 事件同步到自己的系统。功能标识适合用稳定的 lookup key，而不是把展示名称或某个短期价格 ID 当成业务权限代码。[Stripe Entitlements 文档](https://docs.stripe.com/billing/entitlements)；[Entitlements 更新事件说明](https://docs.stripe.com/api/events/types)。

## 产品、价格与功能权益如何分工

Stripe Product 代表商家销售的产品或套餐，Price 描述定价、计费周期和金额。Entitlement Feature 则描述客户购买后可使用的一项能力，例如“高级报表”“每月 100 次导出”或“团队协作”。一个套餐可以包含多个功能；相同的功能也可以被多个不同价格的套餐包含。这样可以把销售包装和应用功能拆开管理。

举例来说，基础版和专业版都可能包含“保存项目”功能，但专业版还包含“高级分析”和“团队成员”。应用不应该在每个请求里写出“如果价格 ID 等于 price_x 就打开高级分析”，因为价格更换、月付年付同时存在、促销价格或旧客户迁移都会使判断复杂化。更稳妥的做法是根据稳定的功能 lookup key 判断，例如 app_advanced_analytics，然后将该功能是否属于当前 Customer 的有效权益作为授权输入。

功能的 lookup key 应当简短、稳定、由代码与产品配置共同遵守。展示名称可以修改为更清晰的营销文案，lookup key 则应避免轻易变更，因为应用和外部服务可能会用它做权限判断。创建新功能时，先确定含义、上线日期、废弃策略和所有使用方；若只是想修改前端显示文案，通常不需要改变功能标识。

## 在 Stripe 中配置权益模型

开始配置前，先列出产品矩阵，而不是先批量创建一堆功能。建议用业务语言整理每个套餐的功能、额度和限制，标明哪些是二元权限，哪些是有数量上限的计量额度。Entitlements Feature 适合表达“有没有某个能力”；例如每月可导出多少次，除了是否开放导出功能，还需要由你自己的计量和配额逻辑决定。不要把一个需要按使用量累计、重置和结算的复杂额度，误当成单纯的布尔权限。

接下来在 Stripe 中创建 Feature，并为其设置稳定的 lookup key。然后把 Feature 关联到相应 Product。月付和年付如果代表相同功能组合，通常应在产品设计上保持一致，并让所有对应销售 SKU 都关联正确的功能。产品变体很多时，可将配置维护为审阅过的清单，定期对照 Dashboard 或 API 中的 Product-Feature 关联，避免人工操作后出现套餐漏配。

管理功能配置时区分测试模式与正式模式。测试商品和正式商品是不同对象，开发环境里成功关联并不会自动出现在正式账户。建议在上线检查中验证两套模式的 feature、产品、价格和订阅对象，并为正式环境变更保留审批记录。Feature 的名称或元数据可用于运营管理，但业务程序应基于预先约定的 lookup key 和 Stripe 返回的当前权益。

## 将 Stripe Customer 对应到应用用户

所有授权计算的基础，是准确的用户与 Customer 映射。创建订阅时，服务端应将 Stripe Customer ID 写入自己经过认证的用户记录。收到 Entitlements webhook 后，事件中的 Customer ID 用来查找站内用户，再更新其权益缓存或触发重新同步。不要相信浏览器直接提交的 customer_id；否则攻击者可能通过更改请求参数来查询或冒用其他人的权益。

同一自然人可能有多个应用账号，也可能出现合并账号、团队购买和多人共享订阅等情况。要先定义你的业务身份规则：个人订阅绑定哪个登录账号？企业套餐是授权给 Customer、团队组织还是单个成员？如果一个组织购买套餐，其成员权限应从组织订阅映射产生，而不是把同一个 Stripe Customer ID 无条件复制给任意用户。

映射表可保存本地用户或组织 ID、Stripe Customer ID、当前权益同步版本和最后一次同步时间。它不应保存任何支付卡号或安全码。对于 Connect 等平台型架构，还需区分平台账户和 connected account 中的对象归属，确保事件来自预期 Stripe 账户上下文。

## Webhook 同步和幂等设计

Entitlements 的权益变化事件适合用来触发本地同步。Webhook 接收流程应先验证 Stripe 签名，再把事件可靠地放进队列或事务处理器。根据事件中的客户信息获取当前有效权益，转换为本地统一的权限标识集合，并更新缓存。事件投递可能重复，也可能在网络延迟下乱序到达，因此应记录 event ID、处理状态和对象更新时间，做到重复事件不会重复开通、乱序事件不会覆盖较新的状态。

推荐将“事件通知”当作同步信号，而不是把单个事件当作完整账本。处理 entitlements.active_entitlement_summary.updated 后，服务端可按文档读取该客户当前的 active entitlements，再覆盖或合并本地缓存。这样能降低错过某次历史事件后长期残留旧权限的风险。定期后台对账时，也可以重新拉取重点 Customer 的当前权益，修复 webhook 曾不可用时的差异。

更新本地权益时应考虑数据库事务：先保存事件处理记录和同步结果，再确认 webhook 已成功处理，或使用队列保证失败重试。若用户在付款成功页面立即访问高级功能，可能存在 webhook 尚未送达的短暂窗口。可以在关键权限校验失败时对 Stripe 或本地同步服务做一次安全的状态刷新，或展示“正在激活”的友好状态；不要因为页面回跳就直接给用户永久授权。

## 订阅生命周期和权限变化

订阅生命周期不只是 active 与 canceled 两种状态。试用、付款失败、宽限期、暂停、计划切换、按期取消和退款等情况都可能影响客户是否还应继续使用功能。Entitlements 汇总可以表达 Stripe 当前认定的有效功能，但你的业务还要明确“付款失败后立即停权还是保留宽限期”“客户提前取消后是否可以用到本期结束”“退款是否立即撤销权益”等产品规则。

不要只监听订阅删除事件。客户从基础版升级到专业版时，旧功能可能保留，新功能应及时开放；降级或取消时，某些功能需要立即收回，另一些可能在当前周期结束后再变化。权益更新事件有助于捕捉有效权益集合的变化，但应用也应记录订阅和发票事件，以解释为什么权限变化，并支持客服排查。

用户从付费套餐转到试用、从一个产品迁移到另一个产品，或者管理员手工赠送临时权益时，需规定 Stripe Entitlements 与本地优惠规则之间的优先级。可以把临时授权作为单独的本地 grant 记录，包含来源、到期时间和操作人；计算最终权限时，将 Stripe 购买权益和本地临时授权合并，并在到期后重新计算。不要直接改写 Stripe 返回的权益缓存而不留下来源，否则对账时无法分辨是订阅、赠送还是管理员错误。

## 后端授权与前端展示

前端可以根据服务端返回的权限列表，展示套餐标记、隐藏不适用的导航菜单或提示升级；但所有敏感操作必须由后端重新判断。比如导出接口要检查用户组织当前是否有 export_reports 权益以及是否超出额度；只在前端禁用导出按钮，攻击者仍能直接调用 API。

权限缓存需要定义更新时效。小型应用可在 webhook 后及时刷新，关键接口结合本地数据库查询；高并发应用可用 Redis 缓存用户或组织的权益集合，并设置合理过期时间。缓存键应包含用户或组织和环境，避免测试数据泄漏到正式系统。若 Stripe 同步故障，是否继续使用最近一次已知权限、暂时限制高风险功能，还是返回维护状态，应根据业务风险制定清晰策略。

API 权限不要仅用价格 ID 命名。使用稳定 feature key 可以让应用逻辑不受价格对象变化影响。例如后台只判断 feature key 为 api_access，并由独立配额服务计算调用上限。这样销售团队推出新的折扣价格或年付价格时，不必改变每一个 API 授权分支。

## 客户迁移、退款和人工处理

已有订阅系统通常已经在自己的数据库中保存套餐和权限。迁移到 Entitlements 前，先建立旧价格与新 Feature 的映射表，抽样核对活跃订阅、试用、取消但仍有效的订阅和逾期订阅。迁移完成后对比每个 Customer 的本地权限和 Stripe active entitlements，找出遗漏或多发权限，再逐步切换授权读路径。

退款并不总等于立即取消订阅或自动删除所有有效功能。一次性付款退款、订阅发票退款、争议和账单调整的业务含义可能不同，应用要按实际订阅状态和产品政策处理。客服后台应能看到 Customer、Subscription、Feature、事件时间和同步状态，并提供可审计的刷新功能。手动刷新只能重新计算当前状态，不能绕过权限策略或无记录地更改客户授权。

对账工作可以每天执行增量检查，也可以为所有当前活跃订阅定期抽样。若客户在 Stripe 中显示有权益、应用却无法访问，先检查 Customer 映射、Product-Feature 关联、webhook 失败队列和缓存；若应用权限多于 Stripe 当前结果，则检查本地手工 grant、重复 webhook、取消策略和同步时序。把常见差异分类后，客服和工程团队能更快定位问题。

## 设计和验收清单

- 每项 Feature 都有业务定义、稳定 lookup key、负责人和废弃策略。
- Product 与 Feature 的关联覆盖所有月付、年付和正式销售套餐。
- Stripe Customer ID 由服务端认证并映射到正确个人或组织。
- Webhook 完成签名验证、重复事件去重、失败重试和乱序保护。
- 收到权益变化后读取当前 active entitlements，刷新本地授权缓存。
- 前端只负责展示；所有高价值后端接口都执行权限和额度校验。
- 明确付款失败、试用结束、降级、按期取消、退款和争议后的权益策略。
- 测试模式与正式模式的产品、价格和功能关联分别验收。
- 有缺失事件后的重同步和定期对账流程。
- 客服能追踪权益来源、最后同步时间和状态差异。

## 总结

Stripe Billing Entitlements 可以把 Stripe 产品中的功能配置与 Customer 当前有效权益联系起来，减少应用按多个价格 ID 硬编码权限的维护成本。落地时需要先定义稳定的 Feature 标识，正确维护产品关联，把 Stripe Customer 安全地映射到应用用户，并通过签名验证的 webhook 同步当前有效权益。最终授权仍由应用后端执行，同时要明确订阅生命周期、退款、宽限期和本地临时授权的业务规则。把 webhook、缓存刷新与定期对账配合起来，才能让套餐变化及时反映到客户实际能使用的功能上。

本文介绍工程实现思路，具体对象字段和功能可用性请以 Stripe 当前文档及账户配置为准。
