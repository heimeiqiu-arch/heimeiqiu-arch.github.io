Stripe Checkout 可以为结账商品开放数量调整，让客户在托管结账页面直接增加或减少商品数量。对商家来说，这能减少用户返回购物车修改数量的步骤；但也会改变用户最终购买的数量和金额。若后端仍按创建 Checkout Session 时的初始数量发货，或者把“付款成功跳转”误当成订单全部数据，就可能出现少发、多发、库存不一致或客服无法核对的问题。

本文介绍如何规划 Checkout Session 的可调数量、设置业务限制，并将 Checkout 结果与库存、支付确认和履约系统可靠衔接。具体参数和支持范围应以当前 Stripe API 文档及所用产品为准。

## 可调数量适合哪些业务

可调数量适合单价固定、客户购买数量可变的商品，例如活动门票、礼盒、标准配件或数字许可席位。商家先在 Session 的 line_items 中配置商品价格、初始数量以及是否允许调整，Stripe Checkout 再向客户展示数量选择器。客户提交订单时，Session 会根据最终数量计算金额。

如果商品需要不同尺码、颜色、刻字内容、组合装或按客户属性改变价格，单纯的数量选择器并不能表达这些差异。此类需求通常要在购物车或自建商品选择页完成，再将明确的商品明细交给 Checkout。对体积计价、阶梯价或复杂折扣，也应确认 Price 的定价方式和 Checkout 展示结果符合预期。

允许调整数量前，先回答三个业务问题：用户最多可以买多少？库存应该在打开结账时还是付款成功后扣减？如果商品售罄，如何处理已经打开但尚未完成的 Session？这些选择应写入订单和库存规则，而不是只依靠前端界面。

## 在 Session 中设置数量上下限

Checkout Session 的 line item 可以配置 adjustable_quantity，并启用客户调整数量。可按业务设定最小值和最大值：例如每笔至少购买 1 件，最多 8 件。上线前请检查项目使用的 API 版本、Checkout 模式和所采用的产品是否支持该配置，并通过测试模式确认数量选择器在实际页面中的展示。

概念示例：

    line_items[0][price]=price_...
    line_items[0][quantity]=1
    line_items[0][adjustable_quantity][enabled]=true
    line_items[0][adjustable_quantity][minimum]=1
    line_items[0][adjustable_quantity][maximum]=8

初始数量、最小数量和最大数量需要共同符合商品规则。若初始数量不在有效范围内，Session 创建可能失败或页面行为不符合预期。不要把 maximum 设置成“很大的数字”来避免库存问题；界面上的上限只是一层约束，商家仍要在订单服务端验证商品是否可售以及数量是否超过实际库存。

对于数量差异会影响运输、折扣、税费或供货限制的商品，建议选择有代表性的数量进行端到端测试。例如测试最小购买量、普通数量、接近上限的数量和超过库存的数量，检查总价、税额、运费、折扣码和确认页面是否一致。

## 最终金额必须来自已完成的 Checkout 数据

创建 Session 时的 quantity 是初始数量，并不一定是客户最终提交的数量。支付成功后，商家应从已完成的 Checkout Session 及其 line items 获取最终购买商品和数量，再将其关联到自己的订单记录。对于包含多个商品或分页结果的 Session，应按 API 返回的完整 line items 校验，不要只取第一项，也不要用初始购物车数据替代最终结账数据。

订单记录至少应能关联：

- 内部订单号和 Checkout Session ID；
- 商品或 Price ID、最终数量；
- 最终小计、折扣、税费、运费和总金额；
- 货币和支付状态；
- 库存处理状态、履约状态与关键事件 ID。

客户回到 success_url 只代表浏览器完成了跳转流程。它不是可信的付款凭证，也不能保证所有订单字段都已同步。履约应由服务端确认 Stripe 的支付状态后触发。若支付方式存在异步确认，系统还要等待最终成功事件再交付商品。

Webhook 处理应有幂等机制。Stripe 可能重试通知，因此同一支付成功事件不应重复扣库存、创建两次发货单或重复发送数字权益。可保存已处理事件 ID，并以订单状态迁移作为第二道去重保护。对同一订单，只有合法的状态变化才允许进入已支付、已履约等阶段。

## 库存如何与数量变更协调

简单做法是等付款成功后再扣库存，但热门商品可能在多个客户支付过程中被超卖。另一种做法是在创建 Session 或进入结账时暂时预留库存，但需要为超时、用户放弃和支付失败释放预留。选择哪种策略取决于商品是否稀缺、库存同步速度、支付方式确认时间和商家的超卖容忍度。

若在创建 Session 时按初始购物车数量预留库存，客户之后在 Checkout 中增加数量，预留数量可能不足。商家可以采用其中一种策略：

1. 对可调数量商品只提供较宽松库存策略，成功付款后再次核查并处理缺货。
2. 不允许在 Checkout 中改变数量，要求客户回到购物车修改，让库存服务按最终数量预留。
3. 在允许的最大数量范围内预留足够库存，但要考虑大量用户同时占用库存造成的可售量下降。
4. 通过及时处理 Checkout 完成和过期事件更新库存预留，并以订单服务作为库存唯一权威来源。

不要把 Stripe Checkout 的数量上限当成实时库存锁。客户可能在库存变化期间完成付款，因此系统仍要定义缺货补货、部分履约、取消订单或退款的处理方式。若订单含多个商品，库存扣减应有事务或补偿方案，避免部分成功、部分失败后留下不一致记录。

## 处理 Session 过期与客户放弃

客户打开结账页后可能离开，Session 也会过期。商家应区分“购物车仍有效”“Session 已创建”“订单待付款”“付款完成”和“订单已取消”等状态。若业务对库存做了预留，要依据 Session 的过期时间和 Stripe 事件释放；在客户再次结账时，重新校验商品价格和库存，并创建新的 Session。

不要把旧 Session 的数量、运费或促销条件复制到新订单而不再验证。商品价格可能调整，优惠码可能失效，库存也可能变化。新的 Checkout Session 应从商家的当前商品目录和业务规则重新生成，Session 的 metadata 可以携带内部订单标识，帮助后端找回对应订单，但不要把 metadata 当作授权或金额可信来源。

## 退款与客服核对

当订单付款金额与客户最初看到的购物车总额不同，客服需要能解释数量调整带来的变化。支付详情、发票或收据、订单邮件和商家后台应显示一致的最终数量和总额。对于部分退款，应根据具体商品数量和政策计算退款，并同步更新已退金额、可退余额和库存状态。

如果客户下单时增加了数量，但商家只能部分发货，要清楚记录实际履约的商品数量，并根据退款或补发规则处理差异。财务对账时，可把 Stripe 交易与内部订单号关联，分别核对订单商品金额、折扣、税费、运费、手续费和退款，避免仅凭净入账金额判断订单价值。

## 常见实现错误

**按 Session 创建时的数量履约。** 用户在托管页面可能调整了数量。应读取完成后的 line items 并按最终数据更新订单。

**仅凭成功页面触发发货。** 页面跳转可以被刷新或重复访问。服务端应验证支付状态，并使用 webhook 处理状态更新。

**把 maximum 当库存锁。** 上限只控制客户可选数量，不代表库存被保留。库存仍由商家系统负责。

**Webhook 重试导致重复扣库存。** 使用事件 ID 和订单状态迁移做幂等，不能假设事件只送达一次。

**只处理单一商品行。** 购物车可能包含多个 line items，还可能涉及税、折扣和运费。订单服务要完整读取并验证。

**客户再次支付时沿用旧订单数据。** 创建新 Session 前要重新核实价格、促销资格、库存和客户选择。

## 上线测试清单

发布前至少完成以下检查：

- 最小数量、初始数量和最大数量设置正确；
- 用户能增加和减少数量，最终金额符合价格规则；
- 多商品订单中每项商品的数量都能保存；
- 折扣、税费、运费和币种根据最终数量正确计算；
- 成功支付后，服务端从完成的 Session 获取完整 line items；
- 重复 webhook 不会重复扣库存、发货或发放权益；
- Session 过期、用户取消和付款失败会释放或恢复库存；
- 库存不足时有明确的退款、补货或客服流程；
- 支付记录、客户邮件和订单管理后台展示相同数量与总金额；
- 测试环境与生产环境的价格、库存和 webhook 配置分开管理。

## 总结

Stripe Checkout 的可调数量能简化客户购买多件商品的流程，但它也让最终订单数量由客户在结账页决定。商家需要设置合理的最小值和最大值，并在支付完成后读取 Stripe 返回的最终 line items。库存检查、订单更新和履约都应由服务端执行，且必须处理 webhook 重试、Session 过期和异步支付。

把数量限制、库存预留和付款确认分别设计清楚，再进行端到端测试，可以避免“页面金额正确但发货数量错误”这类问题。具体参数是否适用于当前集成，请以 Stripe 最新 Checkout Session API 参考为准。
