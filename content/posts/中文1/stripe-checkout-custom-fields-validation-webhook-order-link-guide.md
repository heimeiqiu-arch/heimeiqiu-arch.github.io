Stripe Checkout 可以在托管结账页面中收集除付款信息外的少量订单补充信息，例如刻字内容、尺码偏好、企业采购参考号或配送备注。使用它可以减少自建结账表单的工作量，但自定义字段不是任意数据采集器，也不能代替订单系统、产品配置或客户身份验证。字段设计不合理时，商家可能拿到缺失或无法履约的信息，客户也可能在付款完成后才发现自己填错了内容。

本文说明 Stripe Checkout Session 自定义字段的适用场景、常见字段类型、如何将付款与订单对应、Webhook 的正确处理方式，以及敏感信息和输入验证方面的边界。Checkout 功能和字段约束会随集成类型与 API 版本变化；上线前请核对当前 Stripe 文档，并在测试模式完整走一遍购买流程。

## 自定义字段适合收集什么

自定义字段适合收集少量、与当前购买或履约直接相关的信息，例如礼品留言、产品定制文字、活动报名选择、公司内部采购编号或非敏感的订单备注。字段标签要让客户清楚知道用途和格式，避免用含糊的“备注”承载多种业务需求。

字段通常可以采用文本、仅数字或下拉选项等类型。文本适合有限长度的自由输入；数字适合确实只接受数字的编号；下拉项适合从一组固定选项中选择。若选项很多、字段关系复杂、需要实时校验或根据商品动态变化，应考虑自己的业务表单，而不是把全部规则塞进 Checkout。

不要收集支付卡号、安全码、账户密码、健康资料、政府证件号码等敏感、受保护或受法律限制的数据。支付卡信息应由 Stripe Checkout 的支付组件安全收集；其他个人信息则应只在确有业务需要、提供适当说明和保护措施时采集。字段旁边的文字要说明是否必填、如何用于履约，以及客户在哪里可以修改。

## 创建 Session 前确定数据模型

每个 Checkout Session 都应对应内部系统中已创建的订单或结账尝试。服务器生成唯一的内部订单号，将其保存在 Session 的 client_reference_id 或受控 metadata 中，并记录 Checkout Session ID。不要让浏览器随意提交订单金额或任意关联 ID，再由后端直接信任这些值。

在创建 Session 时，将自定义字段配置与商品、模式和客户信息一起从服务端传入。字段是否必填、字段类型及字符限制需要与履约流程相匹配。比如刻字字段可以允许有限长度的文本；尺码更适合下拉选项，防止出现“XL”“加大”“特大”等多种同义值，导致仓库无法处理。对于必须与具体商品绑定的选项，要在后端再次确认该选项对订单中的商品有效。

若是订阅订单，必须确认 Checkout Session 的 mode、Customer 与订阅配置正确。自定义字段的订单补充信息不应被误当成订阅协议、取消同意或税务资料的替代品。若信息对合同或退款政策至关重要，应使用清楚的单独条款和合适的业务记录方式。

## 客户输入不能替代服务器校验

Checkout 页面限制字段格式，可以改善体验，但服务器仍应验证收到的值。Webhook 或后续读取 Session 后，检查字段是否存在、是否在预期长度内、值是否属于允许范围、是否包含不适合展示的内容，并确认它与内部订单 ID 和商品配置一致。前端下拉选择不能防止被错误的集成代码、历史 Session 或其他数据入口绕过。

对自由文本实施输出编码和适当的内容处理，避免将客户输入直接插入 HTML、电子邮件模板或管理后台页面。对客户备注进行访问控制，明确哪些员工能查看；如果信息只用于履约，完成履约后依据企业的数据保留规则处理。切勿在日志里无差别打印所有 Session 字段，尤其是可能包含个人信息的内容。

如用户提交值有误，提供人工更正流程，并在修改时记录修改人、时间和原因。不要悄悄覆盖 Stripe 原始订单字段，造成“客户当时实际输入什么”无法追溯。对于金额、SKU、税额和付款状态等关键字段，始终以服务器端已创建的订单和 Stripe 对象为准，而不是以客户填写的备注为准。

## 使用 Webhook 同步而不是只看成功页

客户支付后会被重定向到网站的成功页面，但用户可能关闭浏览器、网络中断或直接访问成功页。因此，履约应由经过签名验证的 Webhook 或可靠的服务器端状态检查驱动。监听 checkout.session.completed，并根据订单模式和付款状态判断是否可以开始履约；使用延迟付款方式时，还需处理相应的异步成功和失败事件。

Webhook 处理建议包含以下步骤：验证 Stripe 签名；记录 Event ID 并做幂等；读取 Session ID、Customer ID 和 client_reference_id；按 Session ID 查找内部订单；校验付款状态与订单金额、货币；保存自定义字段；然后把订单转入待履约或已支付状态。对相同事件的重试不能重复发货、创建重复订阅或重复发送确认邮件。

对于付款尚未最终完成的延迟支付方式，Session completed 不一定意味着资金已经结算。根据付款方式处理异步状态，在支付成功事件后再交付有风险的数字产品或实体商品。失败事件则更新订单状态并告知客户后续操作。成功页可以提供即时反馈，但它不应成为唯一的履约控制点。

## 数据关联、元数据与字段的分工

自定义字段用于采集客户本次结账时输入的值；metadata 和 client_reference_id 用于把 Stripe 对象关联到内部业务记录。两者用途不同。不要让客户通过可编辑字段提交 Stripe Customer ID、付款状态或内部权限级别，也不要把自定义字段当作安全的身份验证机制。

保存 Session ID 与内部订单主键，通常比用电子邮件或姓名关联订单更可靠，因为邮箱可能被改写、共享或重复使用。对于需要售后查询的订单，可把关键字段同步到内部订单数据库，再由授权后台查看。若团队希望在 Stripe Dashboard 中查找业务记录，可以在合适的 Stripe 对象上保存受控的内部编号，但避免把敏感的自由文本重复写入多个对象。

## 常见问题排查

**付款成功后自定义字段为空。** 确认该 Session 是否由预期代码创建、字段是否配置到正确的 Checkout Session，以及 Webhook 处理是否读取了 Session 对象的 custom_fields。检查 Dashboard 中该 Session 的详情，并确认事件 payload 与当前 API 版本一致。

**字段出现在支付页面但订单系统没记录。** 检查是否只依赖浏览器成功页、Webhook endpoint 是否接收事件、签名验证是否失败，以及 Session ID 是否能够映射到内部订单。

**选项值格式混乱。** 将适合枚举的字段改为下拉项，限制自由文本字段的用途，并在服务端校验所有值。必要时为旧订单定义标准化映射，但保留原始值供审计。

**客户填入不合适的个人信息。** 限制字段用途和提示文案，避免敏感信息采集；对已经收集的数据按照企业的隐私和留存流程处置，并限制内部访问。

**重复 Webhook 导致重复履约。** 使用 Event ID 去重，并对订单履约设置独立的幂等键。处理事件失败后可以安全重放，而不会重复创建发货单或开通权益。

## 上线前核对清单

选取每种字段类型在测试模式进行一次付款，检查客户页面、Dashboard、Session 对象、Webhook payload 和内部订单记录。覆盖必填字段缺失、文本长度边界、客户取消、重复事件、异步支付失败和订单关联失败。确认履约团队能读懂字段含义，客服能处理修改请求，日志不会无差别保存不必要的个人信息。

Stripe Checkout 自定义字段的价值在于快速收集有限的订单补充信息。把字段用途限定清楚、由服务器校验、用 Session ID 关联订单，并由 Webhook 同步付款结果，才能让结账体验与履约数据保持一致。遇到复杂验证或敏感数据需求时，应使用专门设计的安全流程，而不是继续增加 Checkout 自由输入框。
