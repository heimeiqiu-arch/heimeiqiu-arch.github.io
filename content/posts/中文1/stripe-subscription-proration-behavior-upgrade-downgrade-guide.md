用户升级套餐时，商家要决定新功能何时开通、未使用的旧套餐金额如何计算，以及差额何时收取。Stripe Billing 使用 prorations（按比例调整）来反映订阅变更发生在周期中途的情况。它可能生成应收费用，也可能生成抵扣；但“生成调整行”“立刻生成发票”和“成功收款”是不同的事情。

如果业务只改了订阅价格，却没有明确费用策略，用户可能立即获得新权益，却要等到下次续费才支付差额；或者在更换套餐时收到意外的即时账单。本文讲解 Stripe 更新订阅时的 proration_behavior 三种选择，以及如何在 API、发票预览和权限系统中保持一致。

## 按比例调整如何产生

假设月费为 100 美元，订阅在 5 月 1 日开始。5 月 15 日客户升级到月费 200 美元的套餐。如果系统按比例计算，已用半个月的旧套餐和剩余半个月的新套餐会反映到下次账单中。Stripe 文档给出的示例中，6 月 1 日续费金额为 250 美元：200 美元的新月费，加上 50 美元的周期中途差额。

降级也可能产生抵扣，用于减少后续发票金额。订阅数量变化也可能触发按比例调整，例如席位数从 5 个变为 8 个。实际金额还可能受税、折扣、客户余额、价格结构和周期边界影响，因此需要用目标订阅数据计算，不要简单地把两个月费相减后手工乘以天数。

默认情况下，Stripe 会为订阅变化创建按比例调整。商家要关注变更 API、更新时间和订阅状态。旧周期中的 proration 行并不一定意味着客户已经完成付款；要检查对应发票及其付款状态。

## 三种 proration_behavior 选择

### create_prorations：创建调整，但不自动立即开票

这是默认行为之一。Stripe 会生成按比例调整项目，但不会仅因为生成这些项目就自动立即对客户开一张发票。通常调整会在后续账单中一并处理。如果业务希望升级当下就开通权益，但把差额留到下一张常规发票，这种行为可能更合适。

需要在续费日前单独收取差额时，商家还要创建并处理相应发票，不能认为 proration 行创建后款项自然已经到账。财务系统和客户通知也应区分“已计算调整”和“已收取款项”。

### always_invoice：为调整立即开票并尝试收款

如果升级时要立即向客户收取按比例差额，可以设置 always_invoice。Stripe 会创建 proration 并立即开具发票、尝试收款。适合权益升级应与当前付款同步的业务，但需要预先准备付款失败和额外认证流程。

若客户的支付方式需要认证，或付款被拒，订阅变更与发票可能进入需要后续处理的状态。商家应根据发票和订阅对象的实际状态决定是否授予新权益，而非 API 请求返回就默认已收款。产品体验可以暂时标记“升级处理中”，并引导用户完成支付或更新付款方式。

### none：不生成按比例调整

设置 none 后，不为这次变化生成 proration。对于从旧套餐切换到新套餐的普通周期中途变更，旧套餐剩余时间不会自动折算成信用额；新价格通常会在之后的正常账单中体现。不同计费间隔、从免费转付费或试用期变化等情况可能伴随账单日期变化或立即收费行为，因此仍要结合变更类型核对具体结果。

none 适合商家明确采用“更改从下个周期生效”或不返还旧套餐剩余时间的规则，但要在用户界面中解释。不要为了避免复杂费用而盲目设置 none；如果用户预期按剩余天数退款或抵扣，实际不生成信用额会造成纠纷。

## 何时可能立即改变账单日期

变更价格通常不会重置账单日期，也不会自动产生即时收款，除非变化涉及计费间隔改变、从免费转为付费、试用开始或结束等情形。此时 Stripe 可能对旧价格未使用部分做信用调整，按新价格收费并重置账单日期。具体效果要由目标配置和当前 API 行为决定，不能只看新的 Price ID。

在处理套餐切换时，建议先定义产品政策：

- **升级立即生效并立即收差额**：适合需要马上开通新服务的套餐。
- **升级立即生效、差额并入下次账单**：适合减少中途付款操作的产品。
- **降级下个周期生效**：适合不立即减少当前已购买权益的服务。
- **变更不做按比例抵扣**：只有在条款和用户页面明确说明时采用。

变更费用策略应与权益生效时间一致。若新权益已经开通而差额发票失败，需要明确定义是否保留权益、限制功能或回滚套餐，并向客户提供付款修复渠道。

## 变更前先预览发票

Stripe 提供发票预览接口来查看订阅更新可能带来的金额变化。常见安全流程是：服务端读取当前订阅和即将应用的新价格、数量或周期；生成预览；把费用、信用额、税和下次续费日期展示给客户；用户确认后再更新订阅；之后通过发票和支付事件完成状态迁移。

预览与正式更新之间，订阅价格、客户折扣或税务信息可能发生变化。因此预览可以帮助用户决策，但不能替代最终发票核验。后台应保存本次变更前后的 Price、数量、账单周期、proration 配置、发票 ID 和付款结果，方便客服说明“为什么这次扣了这个金额”。

不要仅用前端传来的套餐价格计算应收金额。新价格 ID、客户 ID 和订阅 ID 应由服务端校验它们确实属于当前客户和业务。前端只传客户做出的选择，服务端根据可信的产品目录构造更新请求。

## 更新失败与客户认证

自动收款并不代表每一次订阅变更都能立即收款成功。卡片可能需要 3DS 验证，银行借记可能需要客户授权，余额可能不足，支付方式也可能失效。采用 always_invoice 时要准备处理发票待付款、付款失败或需要客户操作的路径。

订阅权限不要只跟“订阅对象存在”或“套餐字段已经更新”绑定。更稳妥的做法是根据业务政策和 Stripe 当前订阅、发票及付款状态决定授权。对于必须先付款才能开通的升级，可将更新设计为待付款状态，在支付完成后再切换权益；对允许先开通的情况，也应设定重试、催款和暂停策略。

Webhook 也应幂等处理。发票更新、付款成功和付款失败等事件可能重试或乱序到达。保存事件 ID，并基于发票 ID、订阅 ID 和当前业务状态检查迁移是否合法，避免重复收款通知或重复开通权益。

## API 变更需要有限频率

Stripe 提醒，短时间内频繁更新订阅数量可能触发速率限制。如果业务的计费数量会频繁波动，例如 API 请求数、存储量或设备使用量，不应把每次变化都作为订阅数量更新。评估使用量计费模式，让系统记录用量事件并在账期内汇总，比每小时多次修改订阅 quantity 更合适。

对于普通席位套餐，数量调整通常较低频，但仍应防止用户连续点击造成重复更新。可以为更新操作增加幂等键或业务层请求去重，并在提交期间禁用重复按钮。更新完成后从 Stripe 读取最终订阅和发票状态再刷新页面，减少页面短暂显示与实际数据不一致。

## 上线检查清单

- 按升级、降级、数量变更和计费周期切换分别定义业务规则；
- 确认使用 create_prorations、always_invoice 或 none 的真实理由；
- 对代表性客户预览调整前后的发票行、税费、抵扣和续费日期；
- 测试付款成功、拒绝、认证中断和客户更新支付方式；
- 明确新权益是在更新成功、发票支付成功还是下个账期开始时生效；
- webhook 处理具有幂等性，客服可查到订阅更新与发票关联；
- 若数量频繁变化，评估用量计费而非高频修改订阅；
- 在价格页和确认页面说明即时收费、未来账单和退款规则。

## 总结

Stripe 订阅变更的 proration_behavior 决定按比例调整如何处理。create_prorations 会创建调整但不自动立即开票；always_invoice 会为调整立即开票并尝试收款；none 则不生成这次按比例调整。它们的差别直接影响客户何时付款、何时获得新权益，以及降级信用额如何体现。

先用发票预览确认费用，再根据发票和付款状态发放权益。遇到周期切换、试用期或免费转付费时，额外核对账单日期和即时收款。把价格变更政策、API 请求、Webhook 与客服说明统一起来，能减少意外扣款和订阅状态不一致。
