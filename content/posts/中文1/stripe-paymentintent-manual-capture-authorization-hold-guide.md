某些业务需要先确认客户的支付方式和可用额度，再根据实际履约金额完成扣款。例如酒店入住后结算、餐厅根据最终消费金额收款、仓库确认订单库存后再扣款。Stripe PaymentIntent 支持在受支持的场景中把授权和捕获分成两步：客户先授权，资金暂时保留；商家稍后捕获（capture）实际金额。它不是所有支付方式都支持的通用方案，授权有效期与发卡行规则也会变化。

先授权后捕获与立即付款不同。授权成功时不一定已经完成最终扣款；如果商家没有在有效期内捕获，授权可能过期或被取消。客户银行应用中可能短暂显示待处理金额，但最终交易金额尚未确定。业务页面需要准确说明状态，避免让客户把预授权当成已经结算或退款。

## 一、判断业务是否适合手动捕获

手动捕获适用于最终金额在客户授权后才能确定、商家需要先确认库存或服务是否可提供，或按实际消费金额收款的场景。若购买金额在下单时已固定且能够立即履约，自动捕获通常更简单。不要只为了“防止退款”或“先占住客户额度”而随意使用预授权，这会给客户造成不必要的资金占用。

确认目标付款方式是否支持 manual capture，并检查特定卡种、国家和账户能力的限制。Stripe 文档提示并非所有付款方式都支持手动捕获。授权保持时间也不应自行假设；不同网络和交易类别可能有不同规则。上线前确定业务流程能在有效期限内完成审核和捕获。

产品页面、订单确认和收据要明确区分“已授权”和“已扣款”。客户在银行账单看到待处理金额时，提供说明和客服入口。若最终价格可能变动，说明变化依据和上限，并取得相应的客户同意，不能在客户不知情时随意增加捕获金额。

## 二、PaymentIntent 的授权和捕获状态

后端创建 PaymentIntent 时，在支持场景中配置 capture_method 为 manual。客户使用 Stripe.js、Payment Element 或移动 SDK 确认付款后，PaymentIntent 可能进入 requires_capture，代表资金已授权但尚待商家捕获。后端应验证该状态和 amount_capturable，再决定是否捕获。

创建金额由服务端依据可信订单计算，不能让浏览器指定任意授权金额或客户 ID。保存 PaymentIntent ID、订单号、授权金额、币种、创建时间和当前状态。若请求超时，使用幂等键或查询既有对象，不要直接创建第二笔授权。

从 requires_capture 发起 capture 后，Stripe 会处理实际扣款。商家可以在符合规则时捕获全部或较小金额；实际可捕获金额不能超过可捕获余额。不同支付方式或 API 配置对部分捕获和多次捕获的支持不同，必须按当前文档核对。捕获成功后再更新订单为已付款，并创建发货或履约任务。

## 三、部分捕获与金额变化

部分捕获适合实际服务金额低于最初授权金额的场景，例如商品缺货后只发出部分订单。确认剩余未捕获金额会怎样处理：某些流程在最终捕获后会释放剩余授权，另一些支持按指定方式继续捕获。不要假设只要设置一个较小金额，剩余部分就会无限期保留。

订单金额增加时，不能默认在原授权上捕获更高金额。检查是否需要请求客户重新授权、创建新的付款流程或采用适用的增量授权能力。手续费、税费、折扣和配送变化都应进入最终金额计算，并在客户同意的范围内处理。

后台账本分别记录原始授权额、实际捕获额、未捕获额、币种和调整原因。若一个订单拆分发货或部分履约，按商品行项目记录相应的捕获和库存变化。Webhook 重复时，发货与账单动作要幂等，避免多次捕获或重复履约。

## 四、取消授权和过期处理

订单取消或商家无法履约时，应尽早取消未捕获的 PaymentIntent，让授权按 Stripe 与发卡行规则释放。取消请求成功与客户银行界面立即消失待处理金额不是同一时刻；银行显示更新可能需要时间。客服应使用准确表述，不承诺未经核实的固定释放时长。

未捕获 PaymentIntent 可能在一段时间后自动取消。为即将过期的授权设置后台提醒，避免仓库或客服延迟导致授权失效。过期后不要假设原授权仍可捕获；读取 Stripe 当前对象状态，必要时请客户重新付款。对长时间待审核订单，明确业务超时和取消策略。

如果订单已捕获，再取消就需要走退款流程，而不是再次取消原 PaymentIntent。退款对象、授权释放和订单取消要分别记录。客户已经看到扣款时，应根据真实状态解释是待处理授权还是最终收费，并给出合适的支持入口。

## 五、Webhook 和并发控制

配置适用的 PaymentIntent Webhook，验证签名并持久化事件。授权成功、捕获完成、取消或失败都要更新本地状态。事件可能重复或乱序，使用 event ID 去重，并通过状态机防止旧的授权事件覆盖捕获成功状态。对于资金动作，可以在执行前重新读取 PaymentIntent，确认当前可捕获金额。

防止两个后台任务或客服同时捕获同一笔交易。使用数据库事务或锁定订单，并将捕获申请 ID 作为幂等键。调用超时后先查询 Stripe 对象或使用同一幂等键安全重试，不要重新创建 PaymentIntent。保存操作人、捕获金额和业务原因，支持事后审计。

如果后台系统与 Stripe 状态不一致，先暂停会造成重复资金动作的任务，核对 PaymentIntent 和事件历史，再修复本地数据。定期扫描长期处于 requires_capture、processing 或未知状态的订单，确保无人遗漏。

## 六、测试与上线检查

测试授权成功、认证失败、客户取消、全部捕获、部分捕获、取消授权、过期、Webhook 重复、并发捕获、网络超时、实际金额小于或大于授权额等情况。检查 Stripe Dashboard、PaymentIntent、本地订单、库存和客户页面是否一致。测试环境行为不能替代对真实支付方式授权有效期的确认。

上线前确认目标支付方式支持手动捕获、授权期限适合业务流程、服务端金额由可信数据计算、capture 接口有权限和幂等、Webhook 可恢复、客服了解授权与扣款区别。对未捕获订单建立告警，确保库存或服务审核不会超过期限。

## 七、SEO 与官方资料

内容应说明适用场景和限制，避免将“预授权”写成“无风险保证扣款”。围绕酒店预授权、部分捕获、授权取消、PaymentIntent 状态和授权过期建立专题页面。每篇链接 Stripe 官方文档，并随 API 或卡组织规则变化复核内容。

## 总结

Stripe 手动捕获可以让商家先获得付款授权，再按实际履约金额扣款。服务端需以可信订单数据创建 PaymentIntent，确认 requires_capture 状态和可捕获金额后执行 capture。授权并非最终扣款，且可能过期或被取消，所以业务处理要及时并向客户说明资金状态。

使用幂等键、Webhook、并发锁和过期提醒保护资金操作。测试全部捕获、部分捕获、取消、过期和重复请求，再逐步上线。对于不需要等待最终金额的普通订单，自动捕获可能更直接；选择何种流程要与真实履约和客户授权相匹配。
