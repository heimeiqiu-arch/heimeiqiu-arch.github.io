销售实体商品时，结账流程除了收款，还要收集配送地址、计算运费、限制服务范围并把订单交给仓库或物流系统。Stripe Checkout 可提供托管付款页面，并支持在适用配置下收集配送信息和展示运输选项。它不会替商家决定哪些地区可送、库存如何锁定或包裹何时发出；这些业务规则仍需由商家明确处理。

如果地址或运费设置不准确，客户可能看到错误的总价，商家也可能在付款后才发现无法配送。本文从产品设置、Checkout Session、客户页面、订单履约和测试入手，说明如何把配送和收款流程连接起来。具体 API 字段、国家支持和 Dashboard 选项应以 Stripe 当前文档为准。

## 一、明确可配送地区和地址需求

创建 Checkout 之前，先定义商家能配送的国家、地区和邮编范围。不同商品可能有不同服务范围：易碎品、冷链商品或大件商品的限制可能不同。不能只在网站商品页面写“支持配送”，却让 Checkout 接受无法履约的地址。

服务端应在创建 Checkout Session 时使用适当的配送地址收集配置，并确认支持国家列表与业务政策一致。客户完成地址输入后，保存订单使用的完整地址摘要和 Stripe 对象关联。地址属于个人资料，限制内部访问，不在普通日志中打印完整信息。

账单地址和配送地址用途不同。账单地址可能用于付款方式或税费计算，配送地址用于实际发货。若客户选择礼物寄送给他人，应允许两者不同，但保留付款客户和收货人的业务关系。不要把 Stripe Customer 的历史地址当作当前订单收货地址，除非客户在此次结账中确认。

## 二、设置运费选项

根据产品和配送策略设置固定运费、地区运费或客户可选择的运输方式。Checkout 支持的 shipping rate 和运费配置，应从 Stripe 当前 API 或 Dashboard 文档中核对。若运费取决于重量、目的地或多商品组合，确认预设费率能够准确覆盖；复杂实时运费可能需要更定制的集成。

展示给客户的选项应包含可理解的服务名称、预计处理或送达说明，以及对应费用。不能把不确定的物流时间写成保证到货日期。若免费配送有最低消费或只覆盖特定地区，在结账前就说明条件，并在服务端再次校验。

总价由商品、折扣、税费和配送费用共同组成。将订单总金额与各行项目分别保存，避免之后只能看到一个总数。测试地址变化后运费和税额是否更新，并确保客户在确认付款前看到最终金额。不同币种或市场的运费策略应分别验证。

## 三、服务端创建 Checkout Session

前端向后端发起创建结账请求，服务端验证用户、商品、库存、配送国家和 Price，再创建 Checkout Session。客户端传来的商品编号和数量只是选择，服务器要重新读取可信价格和库存。不要允许浏览器随意指定运费金额、税率或任意 Stripe Price ID。

Session 中应设置合适的订单模式、地址收集、配送选项、客户信息和返回页面。会话创建使用稳定幂等键，防止网络超时或用户重复点击生成多笔结账。保存 Checkout Session ID、内部订单 ID、商品明细、预计运费和金额快照。若用户修改购物车，应按业务规则更新或创建新的支付流程，并处理旧 Session 过期。

设置 success URL 和 cancel URL 时使用可信站点地址。返回成功页不代表服务端订单已经完成；客户也可能关闭页面。后续订单更新要依赖 Stripe Webhook 和对象状态，而不是仅依赖 URL 中的跳转结果。

## 四、付款成功后履约

收到适用的 Checkout Webhook 后，服务端验证签名并读取 Session，确认付款状态、金额、币种、配送地址和商品明细与内部订单相符，然后创建发货任务。事件可能重复投递，因此发货任务要用订单 ID 或履约申请 ID 做幂等，避免重复发货。若库存扣减或物流系统调用失败，重试履约动作而不是重新向客户收款。

实体商品订单通常还需要订单处理、打包、发货、物流追踪和客户通知等状态。将“已支付”和“已发货”分开记录。若付款是异步方式，客户完成 Checkout 后可能还未最终成功，应等待对应异步事件再履约。不同支付方式的确认时序要在当前 Stripe 文档中核对。

当物流系统返回追踪号时，保存承运商和状态，并向客户提供订单查询入口。客户更改地址、取消订单或申请退款时，后台要检查包裹是否已发出，再决定如何处理。Stripe Checkout 负责支付体验，不会自动同步你的仓库或物流服务。

## 五、税费、退款与客户支持

配送地址可能影响税额，但具体计算取决于地区、商品税务分类、登记信息和 Stripe Tax 配置。不要只根据 IP 或账单地址推断税务处理。测试不同配送国家、含税价格、折扣、运费和税费如何共同形成应付金额，并与财务确认账单规则。

退款时核对原订单、商品行项目、运费、税额和已发货状态。全额退款与部分退款可能有不同的运费处理方式；这属于商家政策与适用规则，需要明确说明。退款创建后通过 Stripe 对象和 Webhook 同步最终状态，分别更新订单与物流履约，避免只改网站显示。

客服需要能从订单找到 Checkout Session、PaymentIntent、客户地址摘要、选择的配送方式和物流信息。客户声称地址错误或未收到商品时，按订单时间线查找付款、地址确认、仓库操作和追踪状态。不要要求客户通过不安全邮件发送完整支付信息或敏感身份资料。

## 六、测试矩阵和常见错误

测试有效配送地址、被拒绝地区、不同邮编、免运费条件、多个运输选项、优惠券、税费变化、地址修改、库存不足、付款失败、异步成功、Webhook 重复、订单取消、部分退款和发货任务失败。检查 Checkout 展示、Stripe Dashboard、本地订单和物流任务是否一致。

常见错误包括：只保存账单地址不保存实际收货地址；客户端自己提交运费；给所有商品使用同一运输选项；将付款成功页当作发货指令；付款处理中就立即履约；库存扣减没有幂等；运费变化后订单总额没有更新；退款后忘记处理已生成的物流单。上线前用真实地址样例走完整流程，并确认客服知道怎样处理异常。

## 七、SEO 与官方资料

实体商品页面应写清商品规格、配送范围、运费、处理时长、退换政策和客服方式。SEO 标题围绕实际任务，例如“Stripe Checkout 如何收集配送地址和运费”，描述说明流程和限制。不要只用支付链接替代商品内容，也不要承诺所有地区都可配送。

Stripe 官方资料包括 [Checkout 概览](https://docs.stripe.com/payments/checkout)、[收集客户配送信息](https://docs.stripe.com/payments/checkout/collect-customer-addresses)、[Checkout 配送费率](https://docs.stripe.com/payments/checkout/shipping-rates)、[Checkout Webhook 履约](https://docs.stripe.com/checkout/fulfillment)。配置细节和可用选项按当前 API 与账户设置核实。

## 总结

Stripe Checkout 可以帮助收集配送信息并完成付款，但商家仍需管理服务区域、运费、库存、税额和物流履约。服务端根据可信商品数据创建 Session，客户确认完整总价，Webhook 再验证付款状态并幂等触发发货。

将付款、订单和配送状态分开记录，测试地址变化、异步付款、库存失败和退款等情形。完善产品说明与退换政策，保证客户在付款前了解配送条件。通过清楚的账单明细、可追踪的物流和稳定的状态同步，可以减少漏单与售后争议。
