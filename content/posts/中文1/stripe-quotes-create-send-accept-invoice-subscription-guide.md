B2B 销售和定制服务常常需要先确认商品、数量、折扣和服务期限，再让客户批准后付款。Stripe Quotes 提供报价对象和客户可访问的报价页面；客户接受后，Stripe 可以根据报价生成 Invoice、Subscription 或相关订阅计划对象。它能连接报价和计费流程，但不能替代平台的销售审批、合同管理或履约系统。

报价和发票是不同阶段。报价通常表示待确认的交易条件；客户接受后，后端需要继续核对生成的账单或订阅、付款状态和内部订单。若只根据报价链接被打开就创建服务，或把报价金额直接当作已收款，可能导致未付款先履约。本文介绍报价准备、状态同步和客户体验。

## 一、确定报价与 Customer 的关系

创建 Quote 前，确认 Stripe Customer 映射正确，商品和 Price 已在服务端维护，客户联系人有权查看报价。报价中可包含一次性项目、经常性项目、数量、折扣、税务设置和说明等，具体支持项依当前 Stripe 产品配置而定。报价内容应与销售合同和内部审批一致。

为每个报价建立内部机会或订单 ID，并保存 Quote ID、客户 ID、创建人、审批状态、金额和币种。不要只用客户邮箱来查找报价。若客户要求修改价格、数量或折扣，应创建或更新合适的草稿版本，并明确最终发送给客户的是哪一份。已经发送或接受的报价不能通过覆盖内部记录来伪装成原报价未发生过变化。

对于订阅报价，清楚写明试用期、周期、后续价格和生效条件。对于一次性服务，注明交付范围和付款条件。Stripe 客户页面呈现的内容应足以让客户理解交易，但复杂合同条款仍应通过企业的正式合同流程确认。

## 二、创建草稿、预览和发送

服务器根据销售申请创建 Quote，验证客户、产品、价格、币种、折扣和权限。高金额或非标准折扣可以要求审批。草稿阶段检查小计、折扣、税费、总额、账单地址、有效期和付款条件，确保客户预览页面与内部报价一致。

发送前确认有效期限和联系信息。客户可能通过托管页面查看报价、接受或拒绝；链接应只发给正确客户，不要把公开报价链接当作任何人都可操作的无风险页面。发送记录保存时间、接收方和版本，便于销售与客服跟踪客户看到的具体条件。

如果客户没有在有效期内回应，按销售流程更新状态或重新生成报价。不要假设过期报价会自动变成新价格，也不要让长期有效的旧链接在价格调整后继续传播。停用或取消报价时同步网站、CRM 和客服记录。

## 三、客户接受后会发生什么

客户接受 Quote 后，Stripe 可创建相应 Invoice、Subscription 或 Subscription Schedule，具体取决于报价内容和配置。接受本身不是付款成功。一次性发票可能仍需客户付款；自动扣款订阅的首张发票也可能失败或需要额外认证。平台应监听报价、Invoice、Subscription 和 PaymentIntent 相关事件，并以最终支付状态决定是否履约。

接受报价后，把生成的对象 ID 写入内部记录，关联 Quote、Invoice、Subscription 和订单。若 API 请求超时，先根据原 Quote 和请求日志确认是否已经接受并生成对象，不要再次创建一份内容相同的新报价。使用幂等控制和数据库约束防止重复转换。

客户拒绝报价或要求修改时，销售系统更新机会状态，不要把拒绝等同于退款，因为可能尚未创建任何付款。若报价已接受但尚未付款，修改方式与已付款后的退款或贷项调整不同；按当前 Stripe 对象状态选择业务流程。

## 四、价格、折扣和税费核对

报价可能包含非标准数量、优惠和自动税费。销售和财务需要在发送前核对折扣生效范围、经常性项目、税额和后续发票金额。税务设置取决于商家的登记和产品分类，Stripe 的计算能力不能替代商家确认税务义务。

报价页面展示金额时，说明一次性金额与后续周期金额的区别。一个订阅报价可能既有 upfront 费用，也有 recurring 费用；客户应能理解哪个金额会立即支付、哪个金额会在后续周期收取。避免只展示总额而隐藏未来扣款。

客户接受后生成的 Invoice 或 Subscription 金额要与 Quote 预览对照。若优惠或价格在报价期间变化，确保接受的报价仍按批准规则处理。对账时保留报价版本和实际发票行项目，避免只依据报价金额修改最终账单。

## 五、Webhook 和销售状态同步

配置 Webhook 处理 Quote 状态变化及接受后生成的账单对象。接收事件时验证签名、可靠记录 event ID、按幂等方式更新销售机会和订单。事件可能重复或乱序，旧报价状态不应覆盖后续接受或取消状态。

销售 CRM 与 Stripe 各自负责不同数据。CRM 可以管理商机和销售负责人，Stripe 管理报价计费和支付对象。定期对账未接受、已接受未付款、发票支付失败和已转订阅的报价，发现双方状态不一致时进入人工处理队列。

邮件通知、订单创建和服务开通都要幂等。接受报价可能触发发票和订阅对象，而支付事件稍后才到；不要将“报价已接受”作为发货或开放全部付费功能的唯一条件。订阅商品按自己的权限规则等待正确账单状态。

## 六、测试与常见错误

测试创建草稿、发送、客户预览、接受、拒绝、过期、重复接受请求、生成 Invoice、生成 Subscription、付款失败、Webhook 延迟和折扣税额变化。检查 Dashboard、客户预览、内部 CRM、订单、发票和订阅对象的一致性。使用测试客户和 Price，不混用生产数据。

常见错误包括把 Quote 当成最终 Invoice、接受报价就开通服务、没有保存报价版本、客户链接发错人、报价过期后仍允许按错误价格交易、接受后重复创建订阅、忽略订阅首张发票失败，以及未将销售系统与 Stripe 状态关联。

## 总结

Stripe Quotes 可把报价条件连接到发票或订阅计费，但报价草稿、客户接受、Invoice 创建和付款成功是不同状态。服务端要核验报价内容与客户映射，保存版本和关联对象，并通过 Webhook 同步接受及支付结果。

把报价审批、有效期、税费、折扣与未来续费写清楚，接受后再检查生成的 Invoice 或 Subscription。通过幂等、对账和状态机避免重复转换或未付款先履约，能让销售、财务和开发团队追踪报价到收款的完整流程。
