门店的网络偶尔中断，并不一定意味着收银流程必须马上停止。Stripe Terminal 在符合条件的集成和设备上支持离线支付：终端或 SDK 在本地暂存支付信息，网络恢复后再把交易转发给 Stripe。顾客离店时，收银员可能已经看到本地收款流程完成，但这不等于发卡行已授权、款项已成功入账。离线支付的授权要等交易重新连接并转发后才会尝试，因此商家需要承担之后被拒绝、设备损坏或未能转发的风险。

这篇文章重点讲如何判断自己的 Terminal 方案能否使用离线模式、事前配置和配对要满足什么条件、断网时客户端如何反馈状态，以及恢复联网后怎样核对成功与失败。离线模式适合短暂网络故障期间维持收银连续性，并不等于保证交易最终成功，也不应被当作可以长期脱网营业的替代方案。设备、卡组织、国家地区和 SDK 支持情况会更新，实施前请以 Stripe 当前文档和账户实际可用配置为准。

## 先分清“没有互联网”和“没有局域网”

离线收款方案要先判断故障发生在哪一段。使用独立 POS 设备连接智能读卡器时，POS 和读卡器通常仍需要通过本地网络通信。此类场景下，可以是门店互联网连接中断，但局域网仍正常，POS 还能把指令发给读卡器，读卡器暂存交易数据，等互联网恢复再转发。

如果 POS 和读卡器之间的本地连接也不存在，普通智能读卡器方案就不一定能继续工作。Stripe 的移动读卡器与相应 Terminal SDK 方案对网络拓扑有不同要求；如果 POS 应用直接运行在读卡器上，也能减少外部 POS 与读卡器之间的通信依赖，但设备首次启动或同步配置仍可能需要本地网络。不要把“断开外网测试成功”直接等同于“Wi-Fi 故障、路由器故障和设备重启等所有场景都能离线工作”。

建议先画出门店收银链路：POS 应用在哪里运行，POS 到读卡器走蓝牙还是局域网，读卡器又怎样连接 Stripe。分别模拟 ISP 断网、门店路由器断电、POS 网络切换、读卡器重启，记录哪一层失效。这样可以判断是离线支付功能的适用场景，还是基础设备通信已经中断。

## 核对设备、地区和付款方式支持

离线模式不是所有读卡器和付款方式都自动具备的能力。Stripe 文档按移动读卡器、智能读卡器和 Tap to Pay 等设备类型列出支持情况，也会说明具体 SDK 平台和预览状态。Tap to Pay on Android 与 Tap to Pay on iPhone 的离线支持可能不同；同一设备类别在不同地区的可用能力也可能变化。上线前逐项检查自己的读卡器型号、SDK 平台版本、账户国家、门店 Location 和所用卡品牌，不要只根据一篇旧教程推断当前支持。

卡片读取方式同样有限制。离线模式不能简单按在线交易支持所有磁条、插卡、非接触式支付方式来理解。官方文档会列出支持和不支持的卡品牌，并注明某些地区需要插卡并输入 PIN。离线交易可能不允许刷磁条；在欧洲经济区等场景，客户可能必须插卡并输入 PIN。中国银联单标卡的离线支持也有明确限制。收银员培训材料要告诉员工哪些卡和读卡方式适用，避免顾客已经离开后才发现交易不能按预期处理。

设备支持范围和账户资格可能随 Stripe 文档、设备固件及账户配置变化。在正式购买或部署硬件前，用实际计划采用的读卡器型号和 SDK 检查 Stripe Terminal 离线支付页面，并联系账户支持确认不能在文档中明确判断的地区或预览资格。

## 在网络正常时提前配置与配对

离线功能需要提前准备，断网后临时开启往往来不及。Stripe 可以通过 Dashboard 或 Terminal Configuration 配置离线模式，并将对应 Configuration 应用到 Location。配置变更需要时间传播到 SDK 和读卡器，通常还需要断开并重新连接设备才会生效。上线清单应包含核对配置目标 Location、门店使用的读卡器和 SDK 实际加载的配置版本。

智能读卡器也需要在线预热。它会在联网连接时缓存必要的 Location 信息，之后在符合条件的离线连接中使用之前保存的资料。Stripe 文档指出，离线连接的前提包括：POS 近期曾使用有效的连接令牌在线连接过相应读卡器或符合要求的同类型设备；所需 Location 配置已经同步；POS 与读卡器处于之前使用的同一局域网。离线时更换网络，或者换到之前没有在线配对的读卡器型号，都可能导致连接失败。

读卡器软件也需要保持更新。设备较长时间没有联网更新时，Stripe 可能要求先在线完成软件更新，才允许继续离线收款。把“每家门店每天开门前读卡器至少在线连接一次”作为运营习惯，有助于同步软件、配置和必要设备信息，但具体频率和限制应以当前设备文档为准。

## 离线时的支付流程与客户端状态

离线流程整体仍围绕创建、收集、确认和必要时捕获 PaymentIntent 展开，只是请求和确认信息可能在本地等待联网后转发。应用必须区分至少几种状态：收银操作尚未完成、读卡器已在本地暂存、交易正在等待转发、Stripe 已收到并返回处理结果、交易被拒绝或转发失败。将这些状态都显示成“付款成功”会让顾客和商家误以为资金已经确认。

POS 界面可以使用“已记录，等待网络恢复确认”这类明确提示，提供本地订单编号和门店参考号，并说明收据或订单后续可能更新。不要把离线时得到的本地成功回调误当成 Stripe 后端已经授权。收银员应根据门店金额政策决定是否交付商品，以及是否需要额外的风险审核。

应用还需要实现 Terminal SDK 对离线状态和转发结果提供的监听或回调。通过这些事件更新界面、订单状态和本地队列。Stripe 文档指出，某些 SDK 在离线运行时仍会调用连接令牌提供器；如果 POS 后端此时无法连接，连接令牌回调需要按平台规定处理失败，以便 SDK 继续使用离线能力。这个行为必须在具体平台 SDK 文档中核对，不能照抄另一个语言版本的示例。

本地订单与 PaymentIntent 的关联非常关键。设计自己的订单 ID 或业务参考字段，在恢复联网、交易被转发后，根据 Stripe 返回的对象标识和支付结果更新原订单，避免另建一张“线上新订单”导致重复交付或重复收费。客户端重启、应用崩溃、读卡器重启之后，也要能恢复未完成队列并让员工看清哪些订单仍待处理。

## 交易转发后仍可能被拒绝

在线时，支付授权会及时返回结果；离线时，卡信息先在终端保存，等恢复连接后才发给 Stripe 和发卡行处理。授权被拒绝时，顾客可能已经离店，商品也可能已经交付。因此离线模式的经济风险由商家承担，不能通过应用显示“已收款”消除。

控制风险的常见方法包括限制单笔离线金额、限制允许暂存的累计金额、设置超过阈值后停止接收离线交易，以及尽快恢复网络完成转发。阈值应根据商品价值、门店客单价、可承受损失和客户离店后的追偿难度制定。高价商品、易转售商品或有严格交付要求的订单可以设置更严格政策；也可以规定离线交易只接受低金额、现场可交付并能联系到顾客的业务。

还要考虑设备完整性和本地数据保护。读卡器离线保存支付信息，若设备被篡改或无法安全转发，交易可能无法追回。应保护读卡器，限制员工权限，制定设备遗失、损坏或长时间未联网的处理流程。不要尝试从应用日志导出或留存卡片敏感数据来“备份”交易；应使用 Stripe Terminal 支持的机制和数据处理方式。

## 网络恢复后的核对与重试策略

恢复互联网后，读卡器或 SDK 会把暂存支付转发给 Stripe，并向应用发送相关状态更新。运营人员需要持续查看待转发数量、最早一笔等待时间、成功转发和失败交易数量。如果门店网络恢复但队列长期不减少，应检查读卡器是否重新连接、Connection Token 是否可用、读卡器与 POS 是否仍在原有局域网、设备是否需要软件更新，以及后端订单映射任务是否失败。

每次转发结果都应该更新原业务订单，而不是另创建新交易。对被拒绝的交易，记录可展示给客服和收银员的处理状态，再按商家流程联系顾客或采用其他付款方式。避免无条件自动重试同一笔被拒绝交易，因为再次扣款可能需要客户重新出示卡片或重新授权；应用要先判断 Stripe 返回结果和终端建议的后续操作。

建立一个离线交易日结表，至少记录本地订单编号、读卡器、Location、收款时间、金额、离线开始时间、转发时间、最终 Stripe 状态、拒绝原因分类和人工处理结果。定期将它与 Stripe Dashboard 或 API 中的支付对象核对。若只根据收银小票判断已收款，可能遗漏之后被拒绝的交易；若只看 Dashboard 当下未出现交易，也不能立即判断丢失，因为它可能还留在设备上等待转发。

## 测试与故障排查清单

在正式启用前，应在测试环境和实际型号的读卡器上演练断网。测试应包含在线预配后断网收款、同一网络离线重连、POS 与读卡器网络断开、读卡器重启、SDK 重启、配置更新后断开重连、较久未在线更新、网络恢复后交易转发成功，以及支付被拒绝后的订单状态变更。重点验证用户界面和本地队列能否说明真实状态。

**离线时无法连接读卡器**：先确认当前 Location 已启用离线模式，读卡器在线时曾和相应 POS 或兼容类型设备完成配对，在线配对时间符合文档要求，POS 和读卡器仍在之前的局域网，且未在断网时切换网络。若读卡器固件太旧，先恢复网络并在线连接完成升级。

**可以收款但恢复联网后未转发**：检查读卡器是否真正恢复网络、POS 是否重新连接、后台连接令牌能否正常工作，以及离线事件监听是否仍在运行。查看应用日志是否保存 PaymentIntent 和订单的对应关系。不要为了“清空队列”而删除本地订单记录。

**客户拿到商品但支付后来失败**：这属于离线风险控制问题。评估单笔和累计金额阈值、断网时是否允许高风险商品交付、员工是否清楚等待状态，并优化现场重新联网速度。对离线期间的失败付款，按客服流程联系客户或使用其他经客户同意的支付方式处理。

## 上线前检查表

- 核对读卡器型号、SDK 平台和 Stripe 账户的离线能力。
- 用 Dashboard 或 Configuration 为正确的 Location 开启并验证离线模式。
- 在网络正常时完成读卡器在线连接、配置同步和软件更新。
- 明确断外网与断本地网络的处理差异。
- 实现离线状态、等待转发、转发成功与失败的界面提示。
- 为单笔金额和累计未转发金额制定可执行的风险限制。
- 使用本地订单编号关联 Stripe 支付对象，并处理应用重启和重复通知。
- 建立待转发告警、失败处理、日终核对和设备损坏应急流程。
- 定期重新查看官方支持列表，确认卡品牌、国家地区和 SDK 版本限制。

Stripe Terminal 离线模式能帮助门店应对短时互联网故障，但它只是延迟联网处理支付，并不是离线授权或无风险收款。把“收银操作完成”“交易已暂存”和“Stripe 已确认支付”分开记录，再通过设备支持核验、金额限制、状态监听和恢复后对账管理风险，才能让门店在网络波动时维持流程，同时避免把未授权交易误当成已到账收入。
