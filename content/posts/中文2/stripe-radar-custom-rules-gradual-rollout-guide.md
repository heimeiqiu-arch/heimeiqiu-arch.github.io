Stripe Radar 会对受支持的支付方式执行风险筛查，并提供默认风险规则。很多商家在出现欺诈订单或拒付后，会很快想到增加一条“匹配某个国家就拦截”或“金额超过某个数就拒绝”的自定义规则。这样的规则看起来直接，却可能把真实客户一起挡在结账页之外。更稳妥的做法是先理解规则动作，再观察历史数据、评估误伤、逐步放量，并持续监控结果。

本文面向正在使用 Stripe Radar 的产品、支付、风控和工程团队，重点介绍如何制定自定义交易规则，以及如何用测试、观察模式和流量分配控制上线风险。不同 Radar 方案和账户具备的功能可能不同，规则语法和可用属性也会调整。请在 Dashboard 规则编辑器里确认当前账户能用的选项，并将官方文档作为最终依据。

## 先选动作，再写条件

Radar 规则的核心不是“条件写得越复杂越安全”，而是根据风险和业务成本选择正确动作。常见动作包括允许、拦截、人工审核和请求 3D Secure（3DS）。每个动作解决的问题不同，不能把它们当成等价的开关。

**允许（allow）**适用于明确可信且希望绕过其他匹配规则的交易。允许规则影响面很大，因为它可能覆盖 Stripe 默认规则以及同一笔交易匹配到的其他自定义规则。应尽量缩小允许范围，避免用过于宽松的条件把高风险交易整体放行。

**拦截（block）**适用于团队有充分把握不应处理的交易。拦截会直接影响转化，因此需要重点评估误杀。若证据不充分，可以先审核或观察，而不是立即拦截整个群体。

**人工审核（review）**适合疑似有风险、但自动决策信心不足的交易。符合规则的支付通常仍会正常进入授权流程，同时被加入审核队列。审核能补充人工判断，但队列过大时会拖慢处理、增加运营成本，也可能让真正重要的线索淹没在大量低价值案件里。

**请求 3DS**会尝试为支持该流程的卡片增加持卡人身份验证。请求 3DS 不代表发卡行一定实际执行完整验证，也不代表所有支付方式都支持。额外验证可能降低部分欺诈风险，也可能增加结账摩擦。Stripe 会在必要时根据监管或发卡行要求处理 3DS；关闭某条 Radar 规则不等于关闭所有必要的 3DS 流程。

实践上，可以把动作视为一条逐步升级的路径：先观察可疑模式，再对有价值的疑似交易进行审核，确认规律后再考虑拦截；需要额外持卡人验证时，评估是否请求 3DS。具体选择取决于商品价值、退款与拒付成本、用户体验以及团队处理能力。

## 规则条件由哪些部分组成

Dashboard 中的交易规则通常描述“何时发生什么”以及“满足什么条件”。条件由属性、比较运算符和值构成。例如，可以基于风险等级、金额、卡片类型、付款方式或自定义 metadata 创建条件。可用属性应以规则编辑器自动补全和官方文档为准，不能照抄别的账户的表达式后就默认适用于自己的支付流程。

规则默认可能适用于所有受支持的支付方式。如果规则只针对特定支付方式，应在条件中明确限定，而不是假设它只会影响银行卡。一次宽泛规则可能同时触及卡片和其他支付方式，导致团队在上线后才发现影响范围与预期不同。

metadata 可以用于承载业务侧标签，例如商品类别、风险分层或促销活动标识。但 metadata 的命名、值域和更新时间必须有稳定约定。若结账流程并未可靠写入相应字段，规则可能永远无法命中；若旧值残留或字段被错误复用，则可能误判新订单。上线前应先从支付对象确认字段实际存在、含义一致。

规则只影响未来处理的支付，不会回溯改变已经完成的交易。修改规则之后，老订单的状态不会因此自动更新。事故响应流程需要区分“未来请求的拦截行为”和“已经授权、结算或进入争议流程的历史交易”，并使用相应的退款、取消或争议处理机制。

## 写规则之前先定义业务假设

在规则编辑器输入表达式之前，先用业务语言写清楚假设。例如：“最近出现的争议支付集中在某一类订单，并且与某个可验证信号同时出现；如果该信号单独出现，正常客户也很多。”这句话比“封锁某国 IP”更有用，因为它迫使团队区分核心风险特征和相关但不充分的线索。

建议至少回答五个问题：

1. 要降低的是未经授权的支付、盗刷拒付、账户滥用，还是某种特定支付方式的欺诈？
2. 过去样本里有多少欺诈交易符合条件，有多少成功且未退款的真实交易也符合？
3. 命中规则后，拦截、审核或 3DS 哪个动作更适合当前风险？
4. 对转化率和客服量的影响由谁监控，达到什么阈值时停止放量？
5. 如果误杀增加，谁有权限关闭规则，关闭后如何通知相关团队？

回答这些问题时要注意相关性不等于因果关系。比如某个国家、预付卡、邮箱域名或订单金额可能与风险样本相关，但单独据此拦截可能会伤害大量正常客户。Stripe 的规则测试界面可以帮助估算潜在影响，但历史模拟只是参考，不是未来表现保证。促销活动、流量来源、业务季节性和攻击者策略都会改变交易分布。

## 用历史数据测试规则

创建规则时，先使用 Dashboard 的测试能力检查条件语法，再查看它对最近支付的潜在影响。Stripe 文档描述的规则测试会基于过去一段时间的交易进行模拟，并帮助评估成功支付、欺诈支付和已拦截支付可能受到的影响。测试结果应按支付方式和业务场景查看，避免只看一个总量数字。

重点关注三个问题：规则覆盖了多少欺诈交易；同时会影响多少成功、退款或争议交易；命中量是否超过团队的审核能力。对审核规则而言，如果规则每天制造大量低价值待审交易，队列就会失去作用。收窄条件时，可以把多个有依据的信号组合起来，减少单一弱信号造成的过度匹配。

历史模拟也应与实际业务口径对齐。退款不一定代表欺诈，争议也可能涉及服务履约或客户沟通问题；“未发生争议”也不意味着支付一定是合法的。不要把某个单一标签当成绝对真相。结合客服工单、物流或服务交付状态、支付方式和争议原因，才能判断规则到底识别了何种风险。

测试时还要确认动作顺序。请求 3DS 的规则在审核、拦截和允许规则前评估；其他规则之间也有覆盖和优先影响。尤其是允许规则，可能覆盖默认规则和其他匹配规则。团队应在 Dashboard 中检查规则优先级及实际命中结果，避免“安全团队以为会拦截，业务规则却先允许”的情况。

## 使用 0% 流量进行观察

自定义交易规则可以使用 traffic allocation 控制实际受影响的匹配交易比例。把流量分配设为 0% 时，规则仍会进行评估并报告如果启用会采取的动作，但不会实际对交易执行该规则动作。这种观察模式适合先了解命中数量和潜在影响，降低直接更改支付结果的风险。

观察模式期间，团队需要判断规则命中是否符合原始假设。可按天或周记录命中数量、支付方式、国家、金额区间及与欺诈或争议的后续关联。注意观察周期要覆盖有代表性的流量，而不是只看低流量时段或一次促销日。观察结果可以用来调整条件，但不要因少量样本就快速推导出稳定规律。

将规则设为 0% 并不等同于“风险为零”。它只是观察匹配情况，不会拦截交易。面对正在发生的攻击或监管义务，应结合 Stripe 提供的默认保护、账户设置和内部响应流程及时处理，不能把观察模式当成所有风险事件的替代方案。

## 小比例灰度，再逐步扩大

当测试结果和观察数据符合预期后，可以对部分匹配流量启用规则。Stripe 文档允许通过 traffic allocation 逐步控制自定义交易规则的影响比例，并举例说明可以先从较小比例开始，再根据实际表现提高比例。规则默认可能以 100% 流量执行，因此创建后不要忽略分配设置。

一种可操作的发布方式是：先确认规则语法和历史模拟；再以 0% 观察；随后启用一个足够小、但有代表性的比例；检查拒付、成功付款、转化和审核队列的变化；若表现符合目标再提高比例。具体分段应由团队根据交易量、风险严重程度和可承受损失设定，不必机械套用固定百分比。

Radar 会尽量让同一笔支付的重试保持在相同分配桶中，避免第一次尝试和重试因为随机灰度而得到完全不同的规则结果。对卡片支付，重试关联会使用 Stripe 文档描述的发票、客户与金额、卡片与金额等信号。监控时应关注支付或订单层面的最终结果，避免把每次重试都当成独立客户事件。

灰度的价值在于控制暴露面，不是替代监控。每次提高比例前，团队都应确认新增影响是否仍在预期范围内。若高风险攻击正在造成明显损失，可能需要更快采取措施；但快速放量应有明确负责人、回滚条件和事故记录。

## 监控指标与回滚条件

上线前先选定少量但有决策价值的指标。常见监控维度包括规则命中量、拦截支付量、成功付款率、欺诈相关争议率、误杀反馈、审核队列积压时间和支付方式分布。对于订阅业务，还要区分新支付与后续周期的续费场景；对于平台业务，还要区分平台账户和连接账户的规则适用范围。

定义回滚条件时，尽可能写成可以观测的事实，例如“某一类正常客户的成功付款突然明显下降”“人工审核积压超过运营可在时限内处理的数量”“错误拦截工单超过团队阈值”。达到条件时，先减少分配比例或停用规则，再检查请求属性、metadata 写入和规则版本。修改表达式前保存原始条件、模拟结果、发布时间和负责人，便于复盘。

规则只作用于未来支付，所以关闭规则不会自动恢复已经被拒绝的支付。产品可以为被误拦截的客户提供再次尝试、替代支付方式或联系客服的路径，但不要承诺原支付会自动重新处理。出现风险事件时，支付团队、客服和业务团队需要使用同一事实说明，避免客服将所有失败都解释成银行拒绝或卡片问题。

## 3DS 规则需要避免过度拦截

3DS 可能带来额外的持卡人验证步骤。请求 3DS 和强制所有支付必须成功完成 3DS 是不同的决策。并非所有卡片、钱包或付款场景都支持同一种认证流程；订阅的离线支付、钱包交易、监管豁免或处理错误都可能有不同结果。

如果业务计划根据风险等级、订单金额或 metadata 请求 3DS，要同步考虑后续允许、审核和拦截规则如何判断认证结果。Stripe 文档列出了诸如是否尝试 3DS、是否完成完整认证、是否预期存在责任转移等不同属性，它们含义并不完全相同。把“尝试过认证”直接等同于“客户已经完成认证”会造成错误决策。

逐条核对规则条件中对离线交易和数字钱包的处理。若某支付方式不支持 3DS，就不能简单地要求它完成一个无法执行的流程，再把它全部拦截。反过来，如果业务明确只接受经过特定验证的交易，也应确认豁免、认证边缘结果和支付方式例外都符合业务政策。规则设计应与合规顾问和支付团队共同评审。

## 上线操作流程

在 Dashboard 的 Radar Rules 页面添加规则时，选择交易尝试作为触发场景，选择命中后的动作，再填写条件。点击测试规则，先解决语法验证错误，然后审阅它对近期交易的模拟表现。确认影响范围后，再设置流量分配并启用规则。只有账户所有者、管理员和开发者等具备权限的团队成员才能创建规则；若团队成员看不到入口，应检查账户团队权限，而不是通过共享管理员密码解决。

上线记录至少保存：规则名称、业务假设、条件文本、动作、适用支付方式、历史测试时间、0%观察结果、灰度比例、审批人、监控负责人和回滚条件。每次修改都保留版本差异。若使用自然语言辅助生成规则，仍要人工检查生成条件，并留意 Stripe 关于该功能的训练数据使用说明；如果团队不接受相应数据使用条款，可以手动编写规则。

规则数量也有上限。Stripe 文档当前说明最多可创建 200 条交易规则和 100 条账户规则。规则多不代表更安全，规则之间可能重叠、互相覆盖或让排查变得困难。定期清理过期活动规则，合并重复条件，并为每条长期规则指定业务负责人。

## 一个务实的检查清单

**上线前：**确认目标风险和业务损失；确认可用属性与语法；限定支付方式和必要的金额或用户条件；检查 allow 规则优先影响；模拟历史交易；评估审核队列容量；确认是否涉及 3DS 和支付方式例外。

**观察与灰度：**先用 0% 观察命中结果；设定小比例试运行；监控转化、欺诈、审核积压及客服反馈；每次调整比例前记录决策；确认同一支付重试的处理符合预期。

**回滚与复盘：**定义停止阈值和有权限的负责人；保留规则原文与发布记录；发生误杀时立即降低比例或停用；处理已经拒绝的订单时提供合适的客户路径；复盘属性、数据质量和业务假设，而不只修改表达式。

## 常见问题

### Radar 默认规则是否需要全部替换？

通常不应因为短期欺诈就直接移除默认保护。先检查默认规则、账户风险控制和自定义规则分别承担什么职责，再通过历史模拟定位实际缺口。自定义规则可能覆盖其他规则，因此每次允许或拦截条件都要评估优先影响。

### 规则测试通过是否代表上线安全？

不代表。测试能验证语法并估计历史交易上的表现，但未来流量、促销活动和攻击方式可能变化。建议先观察、灰度并监控实际支付结果。

### 规则匹配了为什么仍然可能付款成功？

要检查命中动作、规则顺序、allow 规则、流量分配、支付方式范围以及 3DS 结果。若分配比例是 0%，规则只观察，不改变支付。规则也只作用于未来交易，不会改动已经处理的支付。

### 应该直接拦截还是先进审核队列？

如果团队对某类行为的欺诈判断很有把握，可以评估拦截；若误伤代价高或证据不足，人工审核或观察模式更适合起步。审核规则的规模必须与团队处理能力匹配。

## 总结

Stripe Radar 自定义规则应该从清晰的风险假设开始，而不是从一个看起来可疑的字段开始。选择 allow、block、review 或 3DS 时，要考虑转化、欺诈损失、支付方式支持和人工运营成本。通过历史测试、0%观察、小比例灰度和明确回滚条件，团队可以逐步验证规则是否达到预期。

上线后仍需持续检查误杀、拒付、转化和审核负荷，并清理过期规则。Stripe 默认规则和人工智能风险评估是支付保护的一部分，商家自定义策略需要与账户能力及当前产品文档配合使用。更多细节请参考 [Stripe Radar 官方指南](https://docs.stripe.com/radar)、[欺诈预防规则文档](https://docs.stripe.com/radar/rules)、[风险评估结果说明](https://docs.stripe.com/radar/transaction-risk-prevention) 和 [风险控制设置](https://docs.stripe.com/radar/risk-settings)。
