# Stripe Issuing 发卡指南：Cardholder、虚拟卡与实体卡生命周期

Stripe Issuing 让企业通过 API 创建和管理商业或消费者卡片项目。它适合有明确持卡人、资金来源、消费管理和客户支持流程的业务。启动前不应只把它看作“调用接口生成一张卡”：企业还要确认 Issuing 资格、可用国家、持卡人信息收集、余额资金安排、卡片交付和欺诈管理。

Stripe 官方文档将发卡项目拆分为选择卡种、建立 Cardholder、创建 Card、为消费准备 Issuing balance、测试交易和上线运营等步骤。本文按生命周期说明虚拟卡与实体卡的区别、Cardholder 与 Card 对象如何关联，以及发布前需要验证的状态和控制点。具体账户资格和 API 参数应以 Stripe 当前文档及销售团队确认结果为准。

## 一、确认项目资格和国家支持

Issuing 的商业项目在美国、加拿大、英国和欧洲经济区部分国家可用；消费者发卡和稳定币支持另有范围与发布状态。国家覆盖会按产品类型变化，所以不能仅根据 Stripe Payments 可用国家推定 Issuing 卡片项目也适用。项目启动前，确认企业和持卡人的所在地、卡项目类型、计划使用的卡网络及 Stripe 账户配置。

Stripe 文档建议先确认使用资格，再选择虚拟卡或实体卡、配置卡项目、为卡消费余额提供资金、建立欺诈管理措施，并在 Sandbox 测试交易。Connect 平台场景也要确认账户类型。Stripe Issuing 只支持特定条件下的平台连接账户；账户 onboarding、责任承担和损失责任安排需要符合产品要求。

## 二、Cardholder 与 Card 的对象关系

Cardholder 表示获准持有和使用卡片的个人或企业主体；Card 则是实际发出的卡片。创建 Cardholder 时需要提供其账单地址和名称，某些地区或卡片类型还要求额外身份、生日、手机号或条款接受信息。字段规则会随地区和项目而异，应按当前 API 文档收集必要信息，不要在自有数据库中无差别保存证件资料。

创建 Card 时需要关联对应的 Cardholder，并选择 virtual 或 physical 类型及适用的卡片参数。不要把 Cardholder ID 当作卡号，也不要把敏感卡片数据写入普通日志。业务数据库通常只需保存 Stripe 对象 ID、内部用户 ID、卡片类型、显示用途、状态和必要的非敏感识别信息。

持卡人和卡片之间可能是一对多关系：一个持卡人可以拥有多张虚拟卡或实体卡，用于不同团队、项目或消费场景。要建立清晰的数据模型，记录卡片用途、资金责任人、所属账户、创建人和审批人。若一个员工离职或项目关闭，需要按业务政策冻结、取消或替换相关卡片，并保留可审计的操作记录。

## 三、虚拟卡还是实体卡

虚拟卡适合线上采购、差旅预订、软件订阅或短期支出。它可以在 API 创建后用于受支持的支付场景，不涉及实体配送；企业仍需设置持卡人权限、消费控制、资金来源和客户界面。虚拟卡不代表没有泄露或滥用风险，卡信息应通过受控界面展示，并对查看权限进行限制。

实体卡适合线下门店、出差和需要实体支付凭证的场景。除了创建 Card 和 Cardholder，平台还要考虑设计、卡片套餐、邮寄地址、配送方式、发货状态、激活和遗失补发流程。实体地址变更后要按产品要求更新配送资料，不要将已寄出卡片的状态直接标记为可用。

企业可以按业务场景同时发行两种卡，但必须让客户理解其使用方式和限制。发卡前展示卡片用途、消费规则、持卡人身份要求和客服方式；实体卡则增加预计配送、收到后的激活步骤和遗失处理说明。

## 四、资金余额和消费控制

发卡项目需要有可用的资金来源。Stripe Issuing balance 为卡消费提供资金，平台需了解余额如何补充、交易如何扣减、余额不足时会发生什么，以及如何与银行或其他 Stripe 余额对账。创建卡片成功不表示账户已经准备好消费资金。

在允许持卡人消费前，应配置适当的 spending controls，例如周期限额、商户类别或地域规则。卡片授权请求可通过 Issuing 的实时授权能力处理，但这属于交易决策流程，与 Card 创建和激活是不同功能。已经有授权 webhook 处理经验的团队，仍需为卡片对象生命周期建立独立的状态管理。

发卡平台应定义授权负责人、余额预警阈值和对账时间。若多个部门或 connected account 共用卡项目，需要明确各自的余额所有者与消费归属，避免出现余额不足后无法判断哪笔支出造成缺口。

## 五、卡片状态和生命周期管理

卡片状态包括创建、激活、冻结、取消、过期或替换等操作。不同状态允许的付款行为不同，业务页面要准确显示 Stripe 对象当前状态，而不是仅根据用户本地的“已启用”字段推断卡可以消费。状态变更应由服务端完成并记录操作者、原因和时间。

遗失或被盗时，先根据项目政策冻结或取消卡片，再判断是否创建替换卡。替换卡要与正确 Cardholder 关联，旧卡交易与新卡交易也应保留在同一客户支持记录中。员工离职、供应商结束合作或部门预算关闭时，平台应检查相关卡片和未完成授权，避免只删除业务档案而留下仍可使用的卡片。

实体卡激活流程应验证操作人有权激活对应卡片，并让持卡人确认收到正确卡片。若卡片寄送失败、地址错误或被退回，应有清晰的补寄路径，不要重复创建多张实体卡而未取消旧卡。

## 六、测试与上线流程

测试环境中使用 Stripe Issuing 提供的模拟交易工具验证卡创建、授权、消费限制、撤销和退款等业务处理。测试 Sandbox 与正式项目的对象 ID、卡数据和资金不同，不能把测试卡用于真实付款，也不能将测试记录复制到生产客户账户。

上线前逐项验证：

1. 确认 Issuing 项目国家、账户类型和卡产品资格。
2. 完成 Cardholder 必需信息收集和隐私说明。
3. 测试创建虚拟卡与实体卡，并确认 Cardholder 关联正确。
4. 为交易资金建立余额补充和对账流程。
5. 设置卡片用途、持卡人权限和消费限额。
6. 测试激活、冻结、取消、遗失和替换卡流程。
7. 确认 Webhook 能幂等更新授权和卡片状态。
8. 检查 Dashboard 角色、API 密钥和生产访问权限。
9. 对实体卡验证设计、配送国家、地址和物流通知。
10. 用 Sandbox 进行端到端试运行，再按审批流程开启正式项目。

## 七、常见问题

**创建 Cardholder 成功，但 Card 创建失败。** 检查卡项目资格、必填字段、Cardholder 状态、账户权限和请求参数。不要重复创建同一个持卡人记录，先检查现有对象和错误响应。

**卡片已创建却无法消费。** 确认卡状态、Issuing balance、消费限制、商户类别、国家和授权处理流程。Card 对象存在并不意味着余额充足或交易会被批准。

**实体卡未送达。** 检查配送信息和订单状态，确认使用的实体卡产品与目标国家适用，并按 Stripe 提供的寄送/替换流程处理。

**持卡人信息需要更新。** 先确认是 Cardholder 基础信息、卡片配送信息还是税务/身份验证资料，再通过相应 API 或 Dashboard 更新，避免更改错误对象。

## 总结

Stripe Issuing 项目从资格确认开始，随后创建 Cardholder、发行虚拟或实体卡、准备消费资金、设置控制、测试并进入持续运营。Cardholder 是持卡人主体，Card 是具体卡片，两者的身份、状态和权限应在业务系统中清楚区分。

发卡成功只是生命周期的开始。平台还要处理激活、冻结、替换、资金补充、消费审计和客服支持。上线前核对国家与账户要求，严格保护持卡人信息，并在 Sandbox 中验证状态变化；正式交易则通过服务端状态、授权事件和内部对账共同管理。
