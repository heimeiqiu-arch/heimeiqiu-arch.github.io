门店顾客退货时，收银员通常要先找到原交易，再决定全额退款还是只退一部分。使用 Stripe Terminal 收款的系统，还需要把 Stripe 中的支付对象和自家 POS 订单准确对应起来。如果退款入口只按金额搜索，容易选错支付；如果用户连续点击退款按钮，可能发起多笔退款；如果看到“已提交”就立即认为顾客到账，也会产生客服争议。

Stripe 的退款针对已创建的 Charge 或 PaymentIntent，通常退回原始扣款所用的卡或支付方式。退款可以是部分金额，也可以多次分次退款，但累计不能超过原交易尚未退回的金额。退款对象的状态与银行最终向持卡人展示退款的时间并非同一件事，因此门店系统需要分别管理“退款请求已提交”“Stripe 处理状态”和“客户账单上已显示”的含义。

本文面向使用 Stripe Terminal 的门店和 POS 开发团队，重点介绍退款流程设计、退款对象关联、部分退款、重复操作保护、失败排查和日报对账。不同账户、卡组织和地区的退款处理时效可能不同，具体结果应以 Dashboard、API 对象和 Stripe 官方说明为准。

## 先识别原始支付

退款前先定位一笔原始支付。POS 订单应保存 Stripe PaymentIntent ID、本地订单编号、门店、读卡器 Location、实收金额、币种和支付完成时间。若系统还保存了 Charge ID，也要明确它与 PaymentIntent 的关系，避免把显示编号、订单号和 API 对象 ID 混在一个字段里。

收银员应通过订单号、收据编号、客户提供的交易时间或卡号末四位等安全且适当的信息找到原支付，再核对门店、金额和支付状态。卡号末四位只能作为辅助信息，不能单独用来判断退款对象。不要让前端提交一个任意 PaymentIntent ID 后，后端不做门店权限与订单归属检查就执行退款。

对于一笔支付涉及多件商品或多个退货原因的订单，业务系统需要记录退款明细。把“原支付金额”和“累计已退金额”分开计算，显示当前仍可退金额。若退款由 Dashboard 人工操作，也要在之后同步 Stripe 中的退款对象，避免 POS 仍将这笔支付视为可退全额。

## 用正确的 Stripe 对象创建退款

Stripe Refund API 允许针对 Charge 或 PaymentIntent 创建退款。新集成通常通过 PaymentIntent 建立关联，后端按原支付对象创建 Refund，并可传入部分退款金额。币种的金额单位遵循 Stripe 对应货币的最小单位规则，例如多数币种以最小货币单位提交；具体金额格式要按照当前币种说明，不能统一按“元”直接传入。

部分退款可以分多次进行，直到该支付的退款总额达到原扣款金额。达到全额退款后，继续退款或超过剩余可退款金额会返回错误。POS 在创建前应从可信支付记录确认原始金额、币种与已退金额，向收银员展示本次退款额和退款后剩余额，并在服务端再次校验金额边界。

退款金额不应仅由客户端计算后直接相信。后端应把传入的本地订单 ID 映射到保存的 Stripe 支付对象，计算本次可退余额，再发起 Stripe API 请求。对同一订单的并发退款请求，可以在数据库事务中锁定订单退款汇总，或采用其他一致性控制，防止两个收银终端同时对同一笔支付发起超额退款。

## 防止重复点击和重复退款

POS 页面在退款请求处理中应禁用重复提交，并显示清晰的进度状态。服务端需记录退款操作的业务请求 ID、本地订单 ID、请求金额、操作员、Stripe Refund ID 和最终结果。若网络超时，不能简单认为 Stripe 一定没有收到请求而立即再次创建一笔退款；应先按业务记录和 Stripe 对象核查上一次请求结果，再决定是否重试。

对于可以安全重试的请求，按照 Stripe API 对幂等请求的官方要求设计幂等键，并保证同一次业务退款重试使用稳定的键值。幂等键应与明确的退款操作记录关联，而不是每次点击都生成新键，否则无法避免重复操作。若请求返回明确的余额不足或支付状态错误，应先重新读取支付与退款对象，再向用户展示原因。

员工取消退款弹窗和撤销已经发送给 Stripe 的退款是不同操作。退款请求一旦创建，POS 上隐藏记录或把按钮恢复成可点击，不会自动撤销 Stripe 退款。界面需要让用户看到退款已提交、处理中、成功或失败，并对可以重新提交的情形提供有根据的提示。

## 部分退款和退货政策

部分退款适合处理仅退回部分商品、补偿部分金额或更正某一部分订单金额的情况。POS 需要记录本次退款对应的商品、数量、税额、折扣分摊和原因，保持商品级退货记录与 Stripe 退款金额相符。Stripe 支付对象知道款项退回多少，但它不会自动理解商店的商品退货规则。

如果一次订单拆成多笔 PaymentIntent 或多种支付方式，退款金额要按原支付拆分结果归还，不能随意从另一笔交易扣减。使用线下支付方式与卡片混合支付时，应逐个对象核对允许退款的金额、状态和币种。复杂的拆单、礼品卡、税费或优惠券场景，需要由商家自己的订单系统制定退款分摊规则。

税额、折扣、配送费与退款金额如何匹配，取决于商家的业务与税务规则。不要简单把退款金额平均分摊到所有商品。建议在 POS 中显示原单商品明细、已退数量、剩余数量、本次退货原因和本次实际退款额，并将这些信息写入自有审计记录。Stripe Refund 的 `metadata` 可以帮助关联本地业务信息，但不应存储不必要的敏感个人信息。

## 退款状态与顾客到账时间

Stripe API 返回的 Refund 对象包含金额、原始 Charge 或 PaymentIntent 关联和状态等字段。POS 应保存 Refund ID，并根据当前对象状态更新业务记录。提交请求成功只说明 Stripe 接收并创建退款对象，不应直接向顾客承诺银行账户立即显示入账。

顾客看到退款的时间可能受发卡行和支付方式处理影响。如果顾客表示尚未收到退款，客服先核对 Stripe 中是否存在对应 Refund、金额是否正确、退款状态是什么，再检查交易卡和原支付是否匹配。可以提供 Stripe 退款对象或收据中可供查询的信息，并说明银行侧展示时间可能不同。不要因为顾客暂时看不到账单记录，就未经核验重复创建退款。

如果退款状态异常或失败，先读取最新 Refund 对象和关联支付，再区分参数、余额、支付对象、处理机构等问题。对已经失败的请求，确认原扣款仍可退款以及没有另一个成功退款后，再由有权限的员工决定是否重试或改用其他处理方式。客服工单要记录查询时间、Refund ID、Stripe 状态与后续承诺，减少多人重复操作。

## Dashboard 人工退款与 POS API 退款

小型门店可以由有权限的员工在 Stripe Dashboard 的支付详情中发起退款；POS 集成也可以由商家服务端调用 Refund API。两种入口都能产生 Stripe 中的退款记录，但若 POS 与 Dashboard 同时开放退款，就必须考虑双向同步。否则后台人员在 Dashboard 已退款，POS 却仍显示可退全额；或收银员再次操作，造成重复退款。

确定一个主操作流程，减少员工在多个界面来回处理。若保留 Dashboard 作为紧急入口，应定期查询或接收相应 Stripe 事件，将人工创建的 Refund 更新回 POS 订单。事件处理需要根据退款对象 ID 幂等更新，同一个事件重复到达时不重复减少可退款金额。对账时以 Stripe 实际 Refund 对象为事实来源之一，同时保留门店自己的商品退货和审批记录。

退款还涉及权限控制。限制哪些员工能退全额、哪些员工需要主管批准；为高金额退款增加审批记录；在日志中记录操作人、时间、理由与关联订单。切勿把 Stripe 秘密 API 密钥发给前端 POS 或写在公开客户端配置中，退款 API 应由可信服务端调用。

## 门店日终退款对账

每天关店时，分别统计订单系统中的退款申请、Stripe 中创建的 Refund 和银行/支付结算记录。核对每笔退款的 PaymentIntent 或 Charge、Refund ID、金额、币种、创建时间、状态、本地订单号、操作员和商品退货记录。发现 POS 有退货记录但没有 Stripe Refund 时，检查操作是否失败或尚未提交；发现 Stripe 有退款但 POS 没有记录时，追查 Dashboard 人工操作或同步任务遗漏。

状态不同步时，不要通过直接修改 POS 汇总金额来“对平”。应先找到 Stripe 原始对象，确认是漏事件、重复请求、人工 Dashboard 操作还是本地任务延迟，再根据事实修复本地退款台账。对于一笔原支付多次部分退款的订单，应核对所有 Refund 对象的累计金额，确保未超过支付金额，也没有遗漏还在处理中的退款。

建议保留一份退款异常队列，包含等待确认、需要主管审核、API 失败、Stripe 与本地数据不一致以及顾客咨询未到账等类型。为每类异常定义责任人和处理时限，让退款问题能够被追踪，而不是留在聊天记录或收银员个人备忘录中。

## 常见问题排查

**提示退款金额超过可退余额**：重新读取原支付和所有 Refund 对象，确认本次币种最小单位、历史部分退款和是否有员工从 Dashboard 操作。不要只检查本地订单最初的支付金额。

**收银员点击两次后出现多笔退款**：按 Refund ID 和金额核查两笔请求是否都创建成功。评估前端防重复提交、服务端幂等键和退款并发控制是否正确。已经创建的退款不能通过删除 POS 按钮或订单记录撤回。

**POS 显示退款成功但 Stripe Dashboard 找不到**：检查请求使用的是正确测试或正式模式密钥、关联 PaymentIntent 是否正确，以及后端是否只根据 HTTP 请求已发送就标记成功。以 Stripe API 返回对象和 Dashboard 记录核对。

**Stripe 显示有退款，POS 仍显示可退款**：检查人工 Dashboard 退款是否同步到 POS，Webhooks 是否正常处理，事件是否被重复忽略或任务失败。通过退款对象 ID 进行幂等修复，不要重新创建退款。

**顾客仍未在银行账单看到退款**：查 Stripe Refund 的最新状态和关联原支付，确认金额和卡片，再说明退款展示时间可能取决于发卡机构。只有在确认原请求没有成功且仍有可退余额后，才考虑重新操作。

## 上线检查清单

- 每个 POS 订单都保存唯一的 Stripe PaymentIntent 或 Charge 关联。
- 退款操作先校验门店、订单、原金额、币种与剩余可退金额。
- 为同一笔支付的并发退款建立一致性控制。
- 记录本地退款操作、Stripe Refund ID、操作人和原因。
- 对网络超时先查退款对象，不立即重复提交。
- 使用稳定的幂等请求机制保护重试。
- 监听或定期同步 Dashboard 创建的退款。
- 将 Stripe 退款状态与商品退货台账、客服记录一起核对。
- 在收银端明确说明已提交与银行已显示到账的差别。
- 限制 API 秘密密钥只在服务端使用，并设置员工退款权限。

Stripe Terminal 负责线下卡片支付的采集，退款则应围绕已成功的 Stripe 支付对象和商家的退货订单处理。把原支付、部分退款、退款状态和门店商品退货分开管理，再用服务端校验、幂等记录与日终对账连接起来，能减少错退、重复退款和客服对账问题。
