发卡平台收到持卡人反馈“这笔交易不是我做的”或“我没有收到商品”时，处理路径与线上商户应对银行卡拒付并不相同。Stripe Issuing 的争议流程站在发卡方一侧：平台代表持卡人对交易提出争议，整理对应交易和原因证据，再通过 Issuing Disputes API 或 Dashboard 跟踪处理结果。

对使用企业卡或员工卡的平台来说，争议流程同时涉及持卡人沟通、企业内部核查、网络规则和资金账务。最重要的是先识别用户要申诉的具体交易，确认争议原因与交易事实相符，再提交结构化证据。不要把普通商户端 Stripe Disputes 流程与 Issuing Disputes 混为一谈：前者是商户回应买家向银行提出的拒付；后者是发卡方代表持卡人对购买交易发起申诉。

## 先确认争议对象和产品角色

Stripe API 将发卡方提出的交易争议表示为 Issuing Dispute 对象，常见对象 ID 以 idp_ 开头，并关联一笔 Issuing Transaction。API 提供创建、查询、更新以及提交争议等端点。平台应从持卡人反馈、卡片账单和交易记录找到准确 transaction ID，再建立争议记录，避免误将另一笔同金额或相似商户交易提交。

在创建前核对金额、交易货币、商户信息、发生时间、卡片和持卡人。Dispute 对象上的金额以卡片货币的最小单位表示，通常与交易金额相同，但可能因汇率变化而不同。对账时应同时保存卡片侧金额和商户侧原始币种信息，不能只靠显示名称或金额搜索。

平台要先明确自身在具体 Issuing 项目中的角色、账户权限和 Stripe 支持的争议功能。Issuing 交易争议的可用性、证据要求、处理时限和账户工作流以当前 Stripe Dashboard 与官方文档为准。不要根据普通线上支付争议的习惯推断发卡项目一定拥有相同的处理期限或证据字段。

## 受理持卡人申诉并收集事实

收到持卡人申诉时，客服首先记录交易 ID、商户名称、金额、币种、交易日期、卡片尾号、持卡人描述和可联系时间。询问用户是否认得商户的其他显示名称、是否有团队成员或管理员代为购买，以及是否存在酒店押金、交通服务、订阅续费或退款未到账等可能造成陌生账单的情况。

若持卡人确认从未授权交易，按照平台的卡片安全流程评估是否先冻结卡片、检查最近授权和交易、确认是否有其他异常交易，并告知用户下一步。若是商品未收到、重复扣款、取消后仍扣款或金额不符，应分别使用与事实相符的理由收集材料。把所有问题统一标记为 fraud 会让证据和后续数据失真。

调查记录要区分“持卡人陈述”“平台查到的事实”和“推断”。例如，卡片由某员工保管、该员工是否在当时出差、商户是否曾被员工使用、订单是否已交付，分别来自不同数据源。保留证据来源、查询时间和内部审核人，有助于后续复核，也避免把尚未证实的信息当作事实提交。

## 根据争议原因准备证据

Issuing Dispute 对象的 evidence 结构包含争议 reason 及其对应的证据字段。不同原因有不同字段，证据应围绕持卡人为什么提出申诉，而不是把能找到的所有文件都上传。

**未授权或欺诈交易：** 收集持卡人的说明以及可用于调查的交易上下文，确认卡片当时状态、交易渠道、持卡人是否承认相关设备或商户关系。不要只提交一句“持卡人不认识该交易”，而应说明为何判断交易不受授权，并附上与争议相关的材料。

**重复交易：** 找出争议交易与原始有效交易之间的对应关系，记录另一笔已支付的交易 ID，并准备订单或收据材料说明两笔交易的关系。若持卡人通过现金、其他卡或其他渠道已付款，也要根据实际情况整理相应凭证。

**商品或服务未收到：** 记录商品或服务描述、预期交付日期、订单沟通和实际履约状态。若服务已开始提供，整理服务日期和可核实的服务凭据；若实物已寄送，保存与订单匹配的发货和收件材料。材料必须针对争议交易，避免只附通用物流截图而无法证明收件人与订单相关。

**商品或服务与描述不符：** 记录商品交付时间、用户反馈、退货或退款沟通、商品描述和争议原因。若用户已申请退货，说明退货是否接受、何时处理；若商品存在问题，避免只重复营销文案，应提供实际订单和沟通记录。

**取消或退款相关问题：** 准备取消日期、取消原因、当时展示的政策、商户或平台处理记录，以及用户是否尝试退货。若争议与服务取消有关，说明实际取消请求和系统记录；若退货已完成，则提供状态和日期。最终应使用当前 API 对该 reason 对应的字段和数据结构进行提交。

## 草稿、提交和状态变化

争议可以先创建并补齐证据，再提交到 Stripe 处理。Issuing Dispute 对象的状态可能显示 unsubmitted、submitted、won、lost 或 expired。创建后仍未提交的案件应有内部待办和负责人，不要认为“已经写入 API”就等于网络已收到完整争议。

提交流程结束后，要通过对象查询、Dashboard 或 Webhook 更新内部状态。Stripe 事件列表包含 issuing_dispute.created、issuing_dispute.submitted、issuing_dispute.updated、issuing_dispute.closed、issuing_dispute.funds_reinstated 和 issuing_dispute.funds_rescinded 等事件。不同事件说明争议创建、提交、更新、结案或资金变化，不应只监听一个“closed”事件就忽略资金和案件状态。

提交前设置审核门槛。至少检查争议原因是否与持卡人事实一致、transaction ID 是否匹配、所有证据字段是否与当前 reason 对应、材料是否包含无关个人信息、提交后是否仍可编辑，以及团队是否已获得必要授权。留存证据版本和提交时间，便于复核 API 返回与 Dashboard 状态。

## 资金账务与持卡人沟通

发卡争议可能导致争议资金被扣留、返还或再次扣回，具体应以 Stripe 账户余额交易、争议对象和 Dashboard 为准。不要在持卡人尚未取得最终结果时承诺“提交争议就一定退款”，也不要把内部临时入账政策说成 Stripe 已判定争议胜诉。

业务系统应把卡片交易、争议金额、币种、争议状态及资金相关事件分别存储。争议金额通常使用卡片货币的最小单位，而账户流水也可能包含不同的资金交易类型。财务对账要能将余额变动关联至 dispute ID 和原 transaction ID。

对持卡人的更新可以拆成几个阶段：已收到申诉并正在核对；争议已创建但尚未提交；材料已提交并等待处理；Stripe 已返回阶段结果；资金已恢复或扣回。每个状态都要说明接下来由谁行动，以及用户还需要提交什么材料。若案件结案但持卡人仍有不同意见，应提供内部复核与升级渠道，不要直接承诺可以重新打开网络案件。

## API 与权限治理

通过 API 创建、修改和提交争议时，应使用后端受控密钥，不能让浏览器直接提交争议对象。对每次写操作检查当前账户上下文、交易对象归属和操作者权限。对外提供客服后台时，把“收集申诉材料”“创建争议草稿”和“提交争议”设计为不同权限，减少误提交和数据关联错误。

争议证据可能包括用户沟通、地址、订单描述和其他文件。按最小必要原则收集，只上传与争议原因相关的材料。文件应通过 Stripe 支持的文件上传方式并以 API 返回的文件 ID 引用；不要将身份证明、支付卡号或无关隐私复制进自由文本字段。内部存储需有访问控制和保留周期。

API 更新争议时，注意当前 evidence 结构和 submit 行为。通用 Payments Dispute API 与 Issuing Dispute API 的对象、字段及流程不完全相同。开发前查看对应 Issuing API Reference，不要复制商户端争议代码后简单改换路径。

## 状态监控与运营指标

可建立运营看板追踪新增争议、未提交草稿、已提交数量、平均补材料时长、即将超过处理期限的案件、won/lost/expired 结果以及资金恢复和扣回总额。每项指标都要按争议原因和项目区分。若某一类交易频繁被申诉，进一步检查卡片控制、商户信息呈现、持卡人通知或采购审批，而不仅仅是优化证据模板。

Webhook 处理应使用事件 ID 去重并记录对象 ID，但业务状态以最新可核实的 Dispute 对象和事件顺序为依据。对于迟到事件或重复通知，确保不会把已经结案的案件误改成待处理。出现事件积压时，定期通过 API 或 Dashboard 对账，补回遗漏状态。

## 常见问题

### Issuing 交易争议和商户拒付是同一个流程吗？

不是。商户拒付流程通常由商户对持卡人向发卡行提出的争议作回应；Issuing 争议则是发卡方侧代表持卡人对交易提出争议，使用 Issuing Dispute 对象和对应端点。

### 创建争议后是否已经提交？

不一定。Issuing Dispute 状态可能是 unsubmitted 或 submitted。团队需要按 API 和账户当前流程明确提交动作，并跟踪最终结果。

### 所有争议都应该选择欺诈原因吗？

不应该。只有持卡人陈述和调查事实支持未授权或欺诈时才使用相应理由。重复、未收到、取消或商品服务不符等情况应匹配实际问题及对应证据结构。

### 争议胜诉后资金一定立即到账吗？

资金状态要以 Stripe 争议对象和余额交易为准。用 funds_reinstated 或 funds_rescinded 等事件与账户流水完成对账，不要只依案件状态推断账务处理时点。

## 总结

Stripe Issuing 争议处理的核心，是在发卡方视角确认正确交易、匹配真实原因、提交相关证据，并将案件状态与资金变化分别跟踪。平台应将受理、调查、创建、审核、提交、结案和持卡人通知串成可审计的工作流，同时明确它与商户端拒付的区别。

不要把分数、客服描述或一条陌生商户名称当作争议结论。保留持卡人陈述、交易对象、证据来源和资金记录之间的关联，按当前 API 的 reason 与 evidence 字段准备材料。具体对象和操作请核对 [Stripe Issuing Disputes API](https://docs.stripe.com/api/issuing/disputes)、[Dispute 对象参考](https://docs.stripe.com/api/issuing/disputes/object) 和 [Stripe 事件类型说明](https://docs.stripe.com/api/events)。
