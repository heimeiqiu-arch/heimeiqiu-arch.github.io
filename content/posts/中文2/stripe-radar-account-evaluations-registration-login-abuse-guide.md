传统支付风控往往等到客户提交银行卡或发起支付后才介入。但不少服务的滥用行为发生得更早：攻击者反复注册账号领取新客优惠，或把一个付费账号同时分享给多个地点的用户。若平台直到收款时才识别问题，优惠、试用资源和服务能力可能已经被消耗。

Stripe Radar 的 Account Evaluations API 可以在注册或登录流程中请求账户风险信号，不需要先收集付款信息。它覆盖的典型信号包括多账号注册风险和账号共享风险。接入这类能力时，关键不只是调用 API，还要将设备上下文、稳定的客户标识、业务决策和最终结果反馈连接起来。本文介绍一个适合产品和工程团队评估的集成框架。

## Account Evaluations 解决什么问题

Account Evaluations 用于对账户注册和登录事件进行风险评估。多账号信号关注是否可能由同一欺诈行为者创建多个账户；账号共享信号关注同一个账户是否在多个地点被同时使用。它们补充了支付阶段的风险评估，让平台可以在授予优惠、开放敏感功能或允许异常登录之前获得信息。

这不是一个通用的“判定用户好坏”接口，也不能只凭分数永久封禁用户。风险分数是决策输入，平台还需要结合自己的账号历史、业务规则、行为上下文和用户体验。Stripe 文档中的 abuse reason 描述相关模式，例如邮箱、IP 或设备重复出现；这些原因用于调查和筛选，本身并不自动证明欺诈。一个家庭、公司或校园网络可能由许多人共用 IP，不能把共享网络直接等同于恶意行为。

Stripe 当前文档指出，沙盒中可使用 Account Evaluations API；实时模式要求 Radar Pro 或相应试用资格。功能权限、API 版本和可用性可能变化，团队应先核对自己的 Dashboard 和官方文档，再投入完整实现。

## 注册评估的数据流

注册流程大致包含四个服务环节。首先，浏览器或应用通过 Stripe.js 创建 Radar Session，以捕获设备上下文。接着，客户端把 Session token 连同用户注册表单提交给商家后端。后端创建或关联一个 Stripe Customer，并用该 Customer ID 与注册活动信息请求 Account Evaluation。最后，后端结合评分和自己的策略决定允许注册、增加验证或限制部分功能，并把决定结果报告给 Stripe。

Radar Session 应尽量靠近实际提交注册评估的时间创建，因为它会在短时间后过期。如果客户端创建 Session 超时或失败，官方文档允许在适用场景中用 IP、user agent 和 referrer 等信息作为替代上下文；但仅有 IP 的评估缺少设备层信号，评分准确性可能较低。若 Session 经常失败，应先调查广告拦截、浏览器限制、网络策略和脚本加载问题，而不是长期将弱上下文当作默认方案。

注册时若平台架构允许，建议创建 Customer 并在后续登录和付款中复用同一个 Customer ID。该 ID 连接了用户账户、登录活动和未来支付，有助于跨阶段理解风险。若业务暂时无法在注册阶段创建 Customer，可以参考官方支持的 entityless evaluation 方式传递联系方式，但这种方式无法通过既有 Stripe Customer 记录关联历史活动，团队要接受信号连续性较弱的限制。

## 登录评估和账号共享风险

登录评估通常关注同一账户是否出现可疑的多地点同时使用模式。登录前，客户端创建 Radar Session；后端以现有 Customer ID 和登录活动请求用户账号共享信号。收到结果后，业务可以决定正常放行、要求额外验证、暂时限制敏感功能，或在强证据下拒绝登录。

登录风险处理需要避免过度反应。合法用户可能旅行、使用 VPN、公司网络、移动运营商网络或在短时间内更换设备。若每次地理位置变化都触发阻断，支持团队会收到大量误报，用户也会失去对安全机制的信任。更合适的做法是把风险级别与额外验证、临时功能限制或异常活动告警组合起来，再根据业务风险选择处置强度。

客服和安全团队应能查看风险决策依据的类别、时间、设备会话和用户反馈，但不要把评分包装成无法解释的绝对结论。用户申诉时提供恢复账号的路径，例如重新验证邮箱、确认常用设备或联系支持。对于高风险操作，可以单独要求二次验证，而不是一律关闭整个账户。

## 如何理解评分和风险等级

每个信号会返回 0 到 100 的风险分数及对应风险等级。Stripe 当前文档将最高风险等级对应到较高分数区间，将 elevated 作为中间风险带，normal 作为较低风险带。文档给出的参考区间是：highest 为 75 到 100，elevated 为 65 到 74，normal 为 0 到 64。阈值及接口细节应以当前账户使用的 API 版本和官方文档为准。

使用风险等级可以快速实现分层决策；使用原始分数则能做更细的阈值实验。但分数不应被当成某种精确概率。例如，分数 80 不表示“该用户有 80% 概率欺诈”。平台要通过自身观察来评估不同区间的真实结果，按用户群、产品类型、注册渠道和后续行为分析，而不是只看一个全局数字。

建议先建立分级响应：低风险保持正常体验；中间风险增加轻量验证或减少可被滥用的优惠；高风险进入审核或限制关键操作。具体策略要依行业、优惠成本、账号价值和客服能力调整。对新用户可以限制高成本福利而允许基础功能；对已有付费用户则考虑保护已购权益并引导安全验证。这样比一个高分就永久封号更容易处理误判。

## 将业务决策报告回 Stripe

完成评估后，平台应把实际业务决定报告回 Stripe，例如 allowed、restricted 或 blocked。allowed 表示按正常方式放行；restricted 表示允许继续使用但施加某些限制；blocked 表示完全阻止注册或登录。回传决定时引用对应的 AccountEvaluation，并使用与评估一致的 Customer 或 Account。

回传结果不仅是审计记录。官方文档说明，这些决策有助于改善后续评估。若团队只调用评估 API，却从不报告自己采取了什么行动，Dashboard 中的 outcome 统计就会不完整，也削弱模型反馈闭环。因此建议把回报调用放在真实决策事务之后：策略引擎决定允许、限制或阻止，数据库记录结果，再可靠地将 outcome 写回 Stripe。

回报过程也要考虑失败重试。如果业务决策已成功保存，但 Stripe 回报接口暂时不可用，应把结果放入队列重试，而不要回滚用户账户状态。为回报任务保留评估 ID、Customer ID、状态和尝试次数即可，避免在任务日志中复制完整注册表单或不必要的个人信息。

## 评估结果与支付数据保持连贯

如果应用在用户注册或登录阶段使用某个 Customer ID 做账户评估，后续创建付款时也应使用同一个 Customer ID。Stripe 官方资料强调，这样可以将注册、登录和支付活动关联到同一客户。若支付阶段创建了另一个 Customer，跨阶段信号会被割裂，Dashboard 调查和风险判断也可能缺少上下文。

因此，Customer ID 应存储在平台自己的用户记录中，并通过服务端映射管理。客户端不能自行指定或替换其他用户的 Customer ID。合并账户、迁移历史客户或重新绑定账户时，要有清楚的审计流程，以免把甲用户的登录活动关联到乙用户的支付历史。

多租户平台还需要把 Stripe account context 纳入记录。某些对象属于平台账户，另一些属于连接账户；事件和 API 请求应在正确账户范围内运行。上线前要确认 Customer 对象归属与后续付款对象归属一致。

## Dashboard 监控与集成健康度

开始发送评估后，可以在 Radar Dashboard 的客户账户欺诈视图中检查多账号注册和账号共享登录。官方文档说明，某些结果可能需要一定时间才出现在概览界面；最新评估可通过专门视图查看。分析时可按日期、分数、风险原因、报告结果、邮箱或 Customer ID 筛选。

同时关注 integration health 指标，例如缺少 Customer email、Radar Session 或 IP 等信号。发现缺失字段后，优先修复采集流程和请求映射，而不是立刻调整风险阈值。数据质量变差时，评分变化可能来自上下文不完整，不一定代表欺诈真的增加。

常用的运营指标包括：注册评估覆盖率、Session 创建成功率、登录评估调用延迟、风险等级分布、allowed/restricted/blocked outcome 回传率、申诉后解除限制的比例，以及不同决策组的后续滥用率。按时间和渠道分层查看，避免一个总体均值掩盖某个移动端版本或营销入口的数据问题。

## 失败场景与降级策略

**Radar Session 创建失败：** 检查脚本加载、网络拦截和客户端错误；在官方支持的场景中使用有限的客户端信息作为降级上下文，并监控弱信号请求比例。

**Customer 创建暂不可用：** 如果业务允许，可采用 entityless evaluation 方式，但应理解它无法串联之前的 Customer 活动；后续尽可能完成 Customer 绑定。

**评估请求超时：** 将它与风险高分区分开。超时不是高风险证据。根据业务选择暂时放行基础体验、要求稍后重试，或对敏感操作增加独立验证。

**评分升高但用户看起来正常：** 检查 abuse reason、评估上下文和账号历史，允许用户通过补充验证申诉。单一原因，例如共享 IP，不应自动成为封禁结论。

**决策无法回传：** 保留业务侧最终状态，并将 AccountActivity 报告加入可靠重试队列。通过 Dashboard 监控 outcome 回传率。

## 上线前的实施清单

**产品设计：** 明确注册与登录哪些步骤需要评估；定义允许、限制、阻止各自的用户体验；为误判准备验证、申诉和恢复流程；避免让风控提示暴露具体检测规则。

**工程接入：** 使用 Stripe.js 创建 Radar Session；将 Session token 安全传给后端；用稳定 Customer ID 执行评估；将登录或注册活动与请求一起提交；根据接口同步返回结果及时决策；完成后报告 outcome。

**数据与隐私：** 只采集与风险评估相关且有合法依据的数据；限制 IP、设备上下文和邮箱的内部访问；避免日志保存认证凭据或无关个人信息；设定数据保留周期并检查适用法规。

**监控与发布：** 先在沙盒使用不同测试邮箱模拟 normal、elevated 和 highest 等评分；在有限流量试运行；检查 Session 缺失和 API 错误；逐步观察申诉率、滥用率和误判情况；保留快速关闭或降级的开关。

## 常见问题

### 是否必须先创建 Stripe Customer 才能评估？

优先使用 Customer 或 Account 对象，因为它能连接之前活动并帮助后续评估。如果当前注册架构无法创建对象，可查看官方 entityless evaluation 支持的字段和限制。

### 分数高就应该封号吗？

不应该自动把分数当成最终事实。可对高风险执行额外验证、限制高成本功能或进入审核，再结合业务信号决定是否阻止。确保用户有可理解的恢复路径。

### Session 创建失败后能否继续评估？

官方文档描述了在适用请求中使用 IP、user agent 和 referrer 的降级方式，但仅有 IP 的评分可能较弱。应追踪失败原因，并持续改善设备上下文采集。

### 如何让支付阶段利用注册阶段的信息？

在后续付款中复用做评估时使用的 Customer ID，使注册、登录和支付活动指向同一客户。确保 Customer 映射由服务端维护且不会被客户端篡改。

## 总结

Account Evaluations 把 Stripe Radar 风险判断延伸到支付之前，适合平台识别疑似多账号注册和异常账号共享。高质量接入要同时完成 Radar Session 采集、稳定客户标识、风险分层、结果回传和 Dashboard 监控。分数只能作为决策信号，不能脱离业务上下文直接变成永久封禁规则。

上线前先核对实时模式的账户资格、API 版本与字段定义，在沙盒测试评分，在有限流量观察，并为误判设计恢复路径。更多实现细节请参考 [Stripe Radar 客户账户评估文档](https://docs.stripe.com/radar/customer-account-evaluations) 和 [Account Evaluations API 参考](https://docs.stripe.com/api/v2/signals/account-evaluations)。
